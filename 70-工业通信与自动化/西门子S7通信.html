西门子S7通信

AI 生成 · 待核对工业通信PLC西门子更新于 2026-10-21

⚠ 待核对：S7 协议是西门子的私有协议，没有公开的官方规范。本篇依据 Wireshark 的 S7comm 页面、python-snap7 文档，以及本机对 python-snap7 自带服务器抓到的真实字节整理；PDU 内部字段含义（ROSCTR、参数长度等）靠抓包与对照资料推断，区域代码 0x81/0x82/0x83 等未读到权威表格。实验是 python-snap7 自带的模拟服务器，不是真实 PLC；真实 S7-1200/1500 的 PUT/GET 与优化访问设置、真机行为均未在本机验证（⚠ 未在本机运行验证）。

本篇读完你应该能：说出 S7 通信的分层（TPKT / COTP / S7comm）；理解机架号、槽号、DB 块地址（如 DB1.DBW0）的含义；用 Python 读写 DB 块；知道连真实 S7-1200/1500 需要在 TIA Portal 做哪些设置。

一句话定义 ​

S7 通信（S7comm） 是西门子 S7 系列 PLC 通过以太网（TCP 端口 102）与上位机交换数据的协议，上位机可以读写 PLC 里的 DB 数据块、M 位存储区、I/Q 输入输出区等内存。

先修知识 ​

  • PLC：知道 PLC 有"程序"和"数据存储区"。
  • TCP-IP、Socket编程：端口、TCP 连接。
  • 十六进制、位运算与大小端：S7 数据是大端（高字节在前）。
  • 整数与补码、浮点数：INT 是 16 位补码，REAL 是 32 位 IEEE754。
  • 对比阅读：Modbus-TCP（开放的、简单的）、Profinet（西门子的实时现场总线，不是一回事）。

它解决什么问题 ​

西门子 PLC 在国内工厂里非常常见。上位机（MES 采集程序、SCADA、你写的 C# 服务）想拿到 PLC 里的计数、状态、温度，或者下发设定值，有几条路：

  1. 用 OPC-UA（新型号 PLC 内置服务器，标准、安全，但需要授权/配置）；
  2. 用 Modbus-TCP（要在 PLC 里额外编程实现）；
  3. 用 S7 通信：不需要在 PLC 里写通信程序，只要开放"允许外部读写"的权限，上位机就能按地址直接读写内存。

S7 通信的代价：地址要和 PLC 程序里的变量布局严格对应；对新型号需要关闭保护/优化；而且没有认证和加密，只能在隔离的工控网络里使用。

核心概念 ​

分层结构 ​

应用：S7comm（读/写变量、PLC 控制……）
传输：COTP（ISO 8073，面向连接）
封装：TPKT（RFC 1006，在 TCP 上加 4 字节头）
网络：TCP 端口 102

这也叫 ISO-on-TCP。Wireshark 页面也写明 "S7comm uses port 102"，S7comm 协议头第一个字节恒为 0x32。

机架号（Rack）和槽号（Slot） ​

S7-300/400 是模块化机架：一个机架（Rack）上有多个槽位（Slot），CPU 插在某个槽里。连接 PLC 时必须说"我要连的 CPU 在第几机架第几槽"。python-snap7 文档给出的常用值：

PLC机架槽备注
S7-30002
S7-40003多机架配置可能不同
S7-120001需在 TIA Portal 开启 PUT/GET
S7-150001同上

机架/槽在报文里表现为 COTP 连接请求里的"目的 TSAP"：Wireshark 页面说明第二个字节里槽号占低 5 位、机架占高 3 位，即 机架 × 32 + 槽。后面实验里抓到 c2 02 01 01，就是通信类型 1（PG）、机架 0 槽 1。

数据块 DB 与地址写法 ​

PLC 的数据存在不同"区域"里：DB（数据块）、M（位存储区）、I（输入）、Q（输出）、T（定时器）、C（计数器）。程序员在 TIA Portal / STEP7 里定义 DB，如 DB1，里面有若干变量，每个变量有偏移量（从块开头数第几个字节）。

地址写法：

写法含义长度
DB1.DBX6.2DB1，第 6 个字节的第 2 位1 位 BOOL
DB1.DBB4DB1，第 4 个字节1 字节 BYTE
DB1.DBW0DB1，从第 0 个字节起 2 字节16 位，INT/WORD
DB1.DBD2DB1，从第 2 个字节起 4 字节32 位，DINT/REAL

所以读 DB1.DBW0 就是"读 DB1，起始偏移 0，长度 2 字节"，再按大端解释成整数。

PUT/GET 与"优化的块访问"（S7-1200/1500） ​

S7-1200/1500 为了安全，默认禁止外部用老式 S7 协议直接读写内存。python-snap7 文档要求两步：

  1. 在 TIA Portal 的 CPU 属性里，保护设置中允许 PUT/GET 通信，编译并下载；
  2. 对要访问的每个 DB，取消"优化的块访问"，编译并下载。文档提醒：取消优化会重新初始化数据块，DB 里所有值回到默认值，所以要在调试阶段先做，或先备份数据。

文档同时警告：开启 PUT/GET 后，"网络上任何客户端都能无认证地读写 PLC 内存"，只能用于隔离的工业网络。

逐步例子：看一次读 DB 的真实字节 ​

下面是实验 2 里抓到的 python-snap7 客户端发给服务器的三个包。

包 1：COTP 连接请求（22 字节）

03 00 00 16 | 11 e0 00 00 00 01 00 | c1 02 01 00 | c2 02 01 01 | c0 01 0a
TPKT: 版本3 长度0x16=22 | COTP CR: 长度17, 类型e0 | 源TSAP 0100 | 目的TSAP 0101 | TPDU大小码0a
  • TPKT 头 4 字节：版本 03、保留 00、总长度 00 16 = 22。
  • c1 02 01 00：参数 c1（源 TSAP），长度 2，值 01 00；
  • c2 02 01 01：参数 c2（目的 TSAP），值 01 01：01 表示 PG 通信，第二字节 01 = 机架 0 × 32 + 槽 1。这就是我们 connect("127.0.0.1", 0, 1, port) 里的机架 0、槽 1。
  • c0 01 0a：TPDU 大小参数，值 0a（对应 1024 字节，推断自 COTP 规范，未读到原文）。

包 2：Setup Communication（协商参数，25 字节）

03 00 00 19 | 02 f0 80 | 32 01 0000 0001 0008 0000 | f0 00 0001 0001 01e0
TPKT 长度25 | COTP DT数据 | S7头: 协议32, 类型01(Job), 保留, PDU引用1, 参数长8, 数据长0 | 参数: 功能f0, 保留, 最大并发1/1, PDU大小0x01e0=480
  • 32 01：S7comm 头，0x32 恒定；01 是消息类型 Job（请求）。
  • 功能码 f0 = Setup communication（Wireshark 页面确认）；
  • PDU 大小 01 e0 = 480 字节：一次最多能传多少数据由它决定，所以大块数据要拆成多次读。

包 3：读变量（31 字节）

03 00 00 1f | 02 f0 80 | 32 01 0000 0002 000e 0000 | 04 01 | 12 0a 10 02 0002 0001 84 000000
  • 功能码 04 = Read Var（读变量），项目数 01；
  • 12 0a 10 是"变量说明头"，02 表示按字节（BYTE）读；
  • 00 02：读 2 个字节；
  • 00 01：DB 号 = 1；
  • 84：区域 = DB（这个值在本实验里直接看到：读 DB 时库发的就是 84）；
  • 00 00 00：起始地址，单位是位（24 位），偏移 0；若读 DB1.DBW2，偏移 2 字节，这里就会是 00 00 10（2 × 8 = 16 = 0x10）。

PLC 回的数据是 00 fa（大端 250）。

环境：Python 3.12，python-snap7 3.3.0（本机实测，纯 Python 实现，自带 Server 和 Client；老版本是对 C 库的封装，写法略有差异）。

实验 1：本机回环，用 Server 模拟 PLC，用 Client 读写 DB1 ​

只用 127.0.0.1，端口 11102（102 是特权端口，实验避开它）。

python
import time, struct
from snap7 import Server, Client
from snap7.type import SrvArea

PORT = 11102
db1 = bytearray(20)                     # DB1 共 20 字节
struct.pack_into(">h", db1, 0, 250)     # DB1.DBW0 = 250（INT）
struct.pack_into(">f", db1, 2, 3.14)    # DB1.DBD2 = 3.14（REAL）
db1[6] |= 0b00000100                    # DB1.DBX6.2 = 1（BOOL）

srv = Server()
srv.register_area(SrvArea.DB, 1, db1)
srv.start(tcp_port=PORT)
time.sleep(0.5)

c = Client()
c.connect("127.0.0.1", 0, 1, PORT)      # 机架0 槽1，回环地址
print("connected:", c.get_connected())

raw = c.db_read(1, 0, 8)
print("DB1 前 8 字节:", raw.hex(" "))
print("DBW0 INT  =", struct.unpack(">h", raw[0:2])[0])
print("DBD2 REAL =", round(struct.unpack(">f", raw[2:6])[0], 2))
print("DBX6.2    =", bool(c.db_read(1, 6, 1)[0] & 0b100))

c.db_write(1, 0, bytearray(struct.pack(">h", -7)))    # 写 DBW0 = -7
print("写后 DBW0 =", struct.unpack(">h", c.db_read(1, 0, 2))[0])
print("服务端内存里的前 2 字节:", db1[:2].hex(" "))
c.disconnect()
srv.stop(); srv.destroy()

运行：

powershell
venv\Scripts\python -I -X utf8 s7_demo.py

实际输出：

text
connected: True
DB1 前 8 字节: 00 fa 40 48 f5 c3 04 00
DBW0 INT  = 250
DBD2 REAL = 3.14
DBX6.2    = True
写后 DBW0 = -7
服务端内存里的前 2 字节: ff f9

读结果：

  • DB1 前 8 字节: 00 fa 40 48 f5 c3 04 00：
    • 00 fa = 0x00FA = 250 → DBW0（INT）；
    • 40 48 f5 c3 = IEEE754 单精度 3.14 → DBD2（REAL）；
    • 第 6 个字节 04 = 0000 0100 → 第 2 位为 1 → DBX6.2 为真；
  • 写 -7（补码 ff f9）之后，客户端读回 -7，服务端内存里的前 2 字节也变成 ff f9——说明读写真的经过了协议，而不是客户端自己的变量。
  • 因为是大端，所以 Python 里一律用 ">h"、">f" 解析。

实验 2：抓包看真实字节 ​

在客户端和服务器之间放一个回环中继，打印客户端发出的前三个包。

python
# 在 client 与 server 之间放一个回环中继，打印 client 发出的前几个报文的原始字节
import socket, threading, time, struct
from snap7 import Server, Client
from snap7.type import SrvArea

db1 = bytearray(20); struct.pack_into(">h", db1, 0, 250)
srv = Server(); srv.register_area(SrvArea.DB, 1, db1); srv.start(tcp_port=11103); time.sleep(0.5)

log = []
def relay():
    ls = socket.socket(); ls.bind(("127.0.0.1", 11104)); ls.listen(1)
    cs, _ = ls.accept(); up = socket.create_connection(("127.0.0.1", 11103))
    def pump(a, b, tag):
        while True:
            d = a.recv(4096)
            if not d: break
            if tag == "C->S": log.append(d)
            b.sendall(d)
    threading.Thread(target=pump, args=(up, cs, "S->C"), daemon=True).start()
    pump(cs, up, "C->S")
threading.Thread(target=relay, daemon=True).start(); time.sleep(0.3)

c = Client(); c.connect("127.0.0.1", 0, 1, 11104)
c.db_read(1, 0, 2); c.disconnect(); time.sleep(0.3)
for i, d in enumerate(log[:3]):
    print(i, len(d), d.hex(" "))
srv.stop(); srv.destroy()
text

1 25 03 00 00 19 02 f0 80 32 01 00 00 00 01 00 08 00 00 f0 00 00 01 00 01 01 e0
2 31 03 00 00 1f 02 f0 80 32 01 00 00 00 02 00 0e 00 00 04 01 12 0a 10 02 00 02 00 01 84 00 00 00

常见坑与排查 ​

现象最可能的原因
连接直接被拒绝/超时IP 不通；防火墙；PLC 的 PUT/GET 未开启（S7-1200/1500 默认关闭）
能连上，读 DB 报"地址超出范围"或"对象不存在"DB 号不存在；偏移+长度超过 DB 的大小；DB 开着"优化的块访问"
读出来的数是乱的字节序没处理（S7 是大端）；偏移量算错；把 BOOL 当字节读
读 REAL 出现奇怪的浮点应当用 >f，用了小端
机架槽填错S7-300 要 0/2，S7-1200/1500 要 0/1；填错会连接失败
一次读大块数据失败超过协商的 PDU 大小（实验中为 480 字节），要分块读
取消"优化访问"后 DB 数据没了取消优化会重新初始化 DB，值回到默认
担心被别人乱写S7 通信无认证；用隔离网络、限制 IP，并严格限制写操作（见 工业网络安全）

业务视角与技术视角 ​

业务视角：S7 通信常用于 设备数据采集：从产线 PLC 读取计数、状态、报警位，用于 OEE、生产看板；少数场合下发配方或设定值（写要特别谨慎，错写会直接影响设备）。是否允许写，要和设备/电气工程师确认。

技术视角：

  • C# 端有成熟的开源库可用（常见的是对 Snap7 的 .NET 封装或 S7.Net 类库），具体选型待核对，本篇没有验证；写法上和实验类似："连接（IP、机架、槽）→ 读/写 DB（DB 号、偏移、长度）→ 按大端解析"。
  • 采集程序应该把"地址表"做成配置（名称、DB 号、偏移、类型、系数），不要写死；
  • 轮询周期不要太短（100 ms–1 s 通常够用），每次尽量合并读取连续的一大段而不是逐点读；
  • 写操作必须加确认和日志。
  • 如果设备较新，优先考虑 OPC-UA，见 设备联网方案。

练习题与答案 ​

  1. DB5.DBW10 表示什么？ 答：DB5 里从第 10 个字节开始的 2 字节（16 位字）。
  2. 字节序列 ff 38 解释成大端 INT 是多少？ 答：0xFF38 的补码值 = 65336 − 65536 = -200。
  3. S7-1200 连接时机架槽一般填多少？还要做什么 TIA Portal 设置？ 答：0 和 1。允许 PUT/GET 通信，并对要访问的 DB 关闭优化的块访问，编译下载。
  4. 读 DB1.DBD2，在 S7 读请求里"起始地址"字段应当是多少？ 答：单位是位，2 字节 = 16 位 = 0x10，即 00 00 10。
  5. 为什么大块数据要分多次读？ 答：握手时协商了 PDU 大小（实验里 480 字节），单次读写的数据不能超过它。
  6. （动手）把实验 1 的 DBX6.2 改成置 0 并写入，再读回验证。 答：先读出字节 b = db_read(1, 6, 1)，再 b[0] &= 0b11111011，db_write(1, 6, b)，读回应为 0。（思路示意，未运行；在真实 PLC 上"读—改—写"整个字节可能覆盖同字节里其它位的并发改动，要小心。）

小结 ​

  • S7 通信 = TCP 102 端口上的 TPKT + COTP + S7comm，属于西门子私有协议。
  • 连接要给 IP、机架、槽；S7-300 常用 0/2，S7-1200/1500 常用 0/1。
  • 数据按 DB 号 + 偏移量 + 长度读写，大端；DBX/DBB/DBW/DBD 分别是位/字节/字/双字。
  • S7-1200/1500 需要开启 PUT/GET 并取消"优化的块访问"；协议无认证、无加密。
  • 本机用 python-snap7 自带服务器完成了读写与抓包验证，真实 PLC 未验证。
