IPC-CFX

AI 生成 · 待核对工业通信设备接口SMT更新于 2026-10-21

⚠ 待核对：IPC-2591 标准正文是收费文档，本篇没有读到。字段名、示例 JSON 取自 IPC 官方 SDK 在 GitHub 上的开源源码注释（Apache-2.0 许可）；AMQP 端口等来自 IPC 的 AMQP 指南页面。本篇的 Python 实验是"按公开文档示意"的 JSON 构造与解析，没有连接真实 AMQP 代理，也不宣称与标准完全合规。另有一处不一致待查：SDK 源码常量 CFXVERSION 为 "2.1"，而 IPC 官网目录里最新的 IPC-2591 文档为 Version 1.7（2023 年 8 月），两者版本号的对应关系请向 IPC 确认。

本篇读完你应该能：说出 CFX 是什么、它的三层结构（AMQP 传输、JSON 编码、消息定义）；看懂一条 CFX 消息的"信封 + 消息体"；知道 WorkStarted、UnitsArrived、FaultOccurred 这类消息的用途；用 Python 构造并解析一条示意消息。

一句话定义 ​

IPC-CFX（Connected Factory Exchange，互联工厂交换） 是 IPC 制定的电子组装行业设备数据交换标准，对应标准文件 IPC-2591：设备（和软件）通过 AMQP 1.0 消息中间件，互相收发 JSON 格式的标准化消息，如"开始加工""加工完成""发生故障"。

先修知识 ​

  • JSON-XML-YAML：JSON 的对象、数组、null。
  • MQTT：同样是"发布/订阅 + 消息中间件"思路，先看一眼会更容易理解（CFX 用的是 AMQP，另一种消息协议）。
  • 工业通信、SMT与电子组装流程：知道 SMT 线由印刷机、贴片机、回流焊、AOI 等设备串成。
  • SECS-GEM：了解"设备与主机"的老式模型，便于对比。

它解决什么问题 ​

一条 SMT 线上的设备来自不同厂家：印刷机、SPI、贴片机、回流焊、AOI……过去每家都有私有接口，MES 要为每台设备写对接代码，换一个品牌就重做。

CFX 的目标是：所有设备用同一套消息词汇说话。设备"做了什么、什么时候做的、有没有出错"都用标准消息广播出来，MES、追溯系统、看板谁需要谁订阅，设备不用知道有谁在听。

与相邻标准的分工：

标准管什么通信形态
IPC-Hermes（IPC-HERMES-9852）相邻两台设备之间交接板点对点 TCP + XML
IPC-CFX（IPC-2591）设备向上层系统广播事件、数据、响应请求AMQP 消息中间件 + JSON
SECS-GEM半导体风格的设备主机通信点对点 HSMS
OPC-UA通用的"读写变量 + 订阅"信息模型客户端/服务器

核心概念 ​

三层结构 ​

  1. 传输层：AMQP v1.0。IPC-2591 目录里写明"Primary Transport Layer: AMQP v1.0"。IPC 的常见问答解释：选 AMQP 是因为它省去了发送和接收 CFX 消息的大部分开发工作。AMQP 版本 0-9-1 等老版本与 CFX 不兼容。
  2. 编码层：JSON。目录里写明"Encoding: JSON"。选 JSON 是因为人容易读写、任何机器都容易解析。
  3. 消息定义层：几百种标准消息，如 CFX.Production.WorkStarted。

消息中间件（Broker） ​

设备（称为 Endpoint，端点）不直接互相连接，而是都连到一个 Broker（代理）。IPC 的 AMQP 指南推荐用 RabbitMQ：

  • 端口：5672（AMQP，无 TLS）、5671（AMQP，带 TLS）、15672（管理网页与 HTTP API）；
  • 需启用 rabbitmq_amqp1_0 插件以支持 AMQP 1.0；
  • 创建 Exchange（交换机） 时类型选 Fanout（广播）——发给它的消息会复制给所有绑定的队列；
  • Queue（队列） 像信箱，接收方从自己的队列里取消息；队列要绑定到交换机才能收到广播。

可以这样类比：Exchange 是"广播电台"，Queue 是"每个听众自己的收音机缓存"，Binding 是"收音机调到这个频道"。

Broker 可以放在线边（每条线一个）、全厂、区域或云端。厂里网络要放通 5672/5671。

CFX Handle 与端点 ​

每个端点有唯一名字 CFX Handle。SDK 文档里的示例是 SMTPlus.Model_21232.SN23123，形如"厂商.型号.序列号"。主要的"自我介绍"类消息（都在 SDK 源码根目录）：

消息用途
WhoIsThereRequest问："网络上有谁？"
AreYouThereRequest / AreYouThereResponse问某个端点"你在吗"，回复里带它的 CFX Handle
EndpointConnected端点新加入网络时广播
EndpointShuttingDown端点要关闭时广播
Heartbeat心跳。SDK 注释写明：端点至少每 5 分钟发一次；SDK 默认每 1 分钟一次
GetEndpointInformationRequest/Response查询端点信息

消息信封（Envelope） ​

所有 CFX 消息都装在同一个"信封"里，字段（来自 SDK 的 CFXEnvelope 源码注释）：

字段含义
MessageName完整消息名，如 CFX.Production.WorkStarted
Version消息所遵循的 CFX 版本号
TimeStamp事件发生的时间（不是发送时间），格式必须带时区
UniqueID这条消息的全局唯一 GUID，用来防止重复处理
Source发布者的 CFX Handle
Target请求/响应类消息里，被请求端点的 Handle
RequestID请求/响应配对用的 ID
MessageBody真正的消息内容，结构随消息名而变

EndpointConnected 的官方示例信封：

json
{
  "MessageName": "CFX.EndpointConnected",
  "Version": "1.7",
  "TimeStamp": "2018-03-26T16:52:25.3769532-04:00",
  "UniqueID": "f3b2c8ec-50b7-4c63-9cb3-2ed57c01880f",
  "Source": null,
  "Target": null,
  "RequestID": null,
  "MessageBody": {
    "CFXHandle": "SMTPlus.Model_21232.SN23123",
    "RequestNetworkUri": "amqp://host33/",
    "RequestTargetAddress": "/queue/SN23123"
  }
}

注意 RequestNetworkUri 与 RequestTargetAddress：告诉别人"想给我发请求，请发到 amqp://host33/ 这个 Broker 上的 /queue/SN23123 这个队列"。这就是 CFX 里"请求/响应"的地址。事件类消息则是广播（发布）出去，谁订阅谁收。

消息分类 ​

SDK 源码按命名空间（文件夹）分类，名称即用途：

命名空间内容举例
CFX（根）端点发现、心跳
CFX.Production生产流程：WorkStarted、WorkCompleted、UnitsArrived、配方 ActivateRecipeRequest 等，约 47 个
CFX.ResourcePerformance设备表现：FaultOccurred、FaultCleared、EnergyConsumed 等，约 26 个
CFX.Maintenance保养：ResourceMaintenanceStatusEvent 等
CFX.Structures被各消息复用的数据结构（单元、位置、故障、物料包装……约 184 个）
CFX.TransportSDK 里的 AMQP 传输实现

在 SMT 里最常用的是 Production（谁什么时候加工了哪块板）和 ResourcePerformance（设备故障、状态），这两类数据正是 设备数据采集、产品追溯、OEE 所需要的。

逐步例子：一块板过一台设备，会广播哪些消息 ​

假设板（载具）上有 1 个电路单元，板码 PCB2610000123，工单 WO-1000-1000：

  1. 板进入设备，设备广播 UnitsArrived：注明到了哪些单元（Units 列表，每个有 UnitIdentifier、PositionNumber、坐标 X/Y、旋转 Rotation、是否翻转 FlipX/FlipY）。
  2. 开始加工，广播 WorkStarted，带一个新的 TransactionID（GUID）。官方注释说明：这个 ID 用来把后续事件和数据挂到这一次加工上，直到 WorkCompleted。
  3. 过程中如果设备出故障，广播 FaultOccurred：Cause（如 MechanicalFailure）、Severity（如 Error）、FaultCode、FaultOccurrenceId 等。
  4. 加工完成，广播 WorkCompleted，带同一个 TransactionID 和 Result（官方枚举含 Completed、Failed、Aborted 等）。
  5. 订阅方（MES 追溯系统）用 TransactionID 把 1、2、3、4 串成一次完整加工记录。

这就是 CFX 的核心用法：事件广播 + 事务 ID 串联。

动手实验：用 Python 构造并解析示意消息 ​

标明：按公开文档示意。字段取自 SDK 源码注释里的示例；没有连接 AMQP 代理；校验规则只有本实验里写的几条，不是 IPC-2591 的完整校验。

环境：纯标准库，Python 3.12。

python
# 按公开文档示意：字段名取自 IPC-CFX 开源 SDK 源码里的注释示例（CFXEnvelope.cs / WorkStarted.cs / WorkCompleted.cs）
# 不是完整合规实现，没有连 AMQP 代理，只演示"外壳 + 消息体"的 JSON 结构与解析校验
import json, uuid
from datetime import datetime, timezone, timedelta

TZ = timezone(timedelta(hours=8))
HANDLE = "Acme.SMTLine1_Oven.SN0042"                   # CFX Handle：自己起的示例名

FIXED_TS = "2026-10-21T20:00:00+08:00"                  # 为了让每次输出一致，这里固定时间和 ID；真实发送时用当前时间和随机 GUID
_n = 0
def new_id():
    global _n; _n += 1
    return str(uuid.uuid5(uuid.NAMESPACE_DNS, f"demo-{_n}"))

def envelope(name, body, source=HANDLE, target=None, request_id=None):
    return {
        "MessageName": name,                            # 完整类名，如 CFX.Production.WorkStarted
        "Version": "2.1",                               # SDK 源码里 CFXVERSION 常量为 "2.1"
        "TimeStamp": FIXED_TS,      # 事件发生时间，必须带时区
        "UniqueID": new_id(),                  # 本条消息的全局唯一 ID，用于去重
        "Source": source, "Target": target, "RequestID": request_id,
        "MessageBody": body,
    }

tx = new_id()
unit = {"UnitIdentifier": "PCB2610000123", "PositionNumber": 1, "PositionName": "CIRCUIT1",
        "X": 50.45, "Y": 80.66, "Rotation": 0.0, "FlipX": False, "FlipY": False}
started = envelope("CFX.Production.WorkStarted", {
    "TransactionID": tx, "Lane": 1, "UnitCount": 1, "Units": [unit],
    "WorkOrderIdentifier": {"WorkOrderId": "WO-1000-1000", "Batch": "WO-1000-1000-B1"}})
completed = envelope("CFX.Production.WorkCompleted", {
    "TransactionID": tx, "Result": "Completed", "UnitCount": 0, "Units": []})

wire = json.dumps(started, ensure_ascii=False)          # 这就是放进 AMQP 消息正文的那段 UTF-8 JSON
print("线上字节数:", len(wire.encode("utf-8")))
print(json.dumps(started, indent=2, ensure_ascii=False))

# ---- 接收方：解析 + 基本校验（只校验本示例里用到的规则）----
def check(raw):
    m = json.loads(raw)
    for k in ("MessageName", "Version", "TimeStamp", "UniqueID", "Source", "Target", "RequestID", "MessageBody"):
        assert k in m, f"缺字段 {k}"
    uuid.UUID(m["UniqueID"])                            # 必须是 GUID
    ts = datetime.fromisoformat(m["TimeStamp"]); assert ts.tzinfo is not None, "TimeStamp 必须带时区"
    return m

m = check(wire)
print("\n解析成功:", m["MessageName"], "| 来自", m["Source"], "| 工单", m["MessageBody"]["WorkOrderIdentifier"]["WorkOrderId"])
c = check(json.dumps(completed))
print("配对检查: WorkStarted 与 WorkCompleted 的 TransactionID 相同 ->", m["MessageBody"]["TransactionID"] == c["MessageBody"]["TransactionID"], "| Result =", c["MessageBody"]["Result"])
heartbeat = envelope("CFX.Heartbeat", {"CFXHandle": HANDLE, "HeartbeatFrequency": "00:01:00"})
fault = envelope("CFX.ResourcePerformance.FaultOccurred", {"Fault": {"Cause": "MechanicalFailure", "Severity": "Error", "FaultCode": "ERROR 3943480",
        "FaultOccurrenceId": new_id(), "Lane": None, "Stage": None, "SideLocation": "Unknown", "AccessType": "Unknown", "Description": "demo", "OccurredAt": FIXED_TS}})
# 接收方按 MessageName 分发：这就是 "订阅所有消息、挑自己关心的处理" 的写法
for raw in (json.dumps(heartbeat), json.dumps(fault), wire):
    msg = check(raw); print("分发:", msg["MessageName"].ljust(42), "->", {"CFX.Heartbeat": "更新心跳时间", "CFX.ResourcePerformance.FaultOccurred": "写报警记录", "CFX.Production.WorkStarted": "写开工记录"}.get(msg["MessageName"], "忽略"))
bad = dict(started); bad["TimeStamp"] = "2026-10-21T12:00:00"          # 故意去掉时区
try: check(json.dumps(bad))
except AssertionError as e: print("坏消息被拦截:", e)

常见坑与排查 ​

现象最可能的原因
连不上 Broker端口 5672/5671 被防火墙拦；RabbitMQ 默认 guest 账号只允许本机登录
能连但收不到消息队列没绑定到 Fanout 交换机；订阅的交换机名字不对
AMQP 客户端报协议不兼容用了 AMQP 0-9-1 的客户端库；CFX 要 AMQP 1.0
同一事件处理了两遍没用 UniqueID 去重（网络重发、多订阅者重复）
时间对不上TimeStamp 是事件发生时间而不是发送时间；时区处理错误
解析 MessageBody 报字段缺失不同 CFX 版本的字段不同（例如 WorkStarted 的 2.1 版增加了 PrimaryIdentifier、HermesIdentifier 等）；解析要容忍未知/缺省字段
设备明明在线却显示掉线设备心跳间隔可调（1 秒到 5 分钟）；判断掉线的阈值要大于设备配置的心跳频率

业务视角与技术视角 ​

业务视角：

  • 谁用：MES/追溯系统要知道每块板在每台设备的开始/完成时间与结果；设备管理要故障、能耗、保养数据；看板要实时状态。见 MES、产品追溯、设备管理与设备状态、生产看板与实时报表。
  • 为什么：统一词汇，换设备品牌不必重写对接。是否值得上 CFX，取决于你们的设备是否支持（要看设备手册里是否有"IPC-CFX"认证/支持声明）；老设备往往只能走 设备数据采集 里的其他方式。

技术视角：

  • 订阅端建议做成后台服务（见 后台服务与Windows服务）：订阅 → 按 MessageName 分发 → 落库。
  • 落库时以 UniqueID 做幂等键；TransactionID 作为加工事务键；UnitIdentifier 对接 条码与板码规则。
  • C# 侧有官方 SDK，序列化用的是 Newtonsoft.Json（源码里可见 JsonProperty 属性）；自己用 System.Text.Json 解析也可以，但要注意枚举是以字符串形式出现的（如 "Result": "Completed"）。
  • 板间交接不属于 CFX 的范围，那是 IPC-Hermes；两者在 UnitsArrived/WorkStarted 里通过 HermesIdentifier 字段衔接（SDK 注释说明该字段承载 Hermes 的 BoardId）。

练习题与答案 ​

  1. CFX 用什么协议传输、什么格式编码？ 答：AMQP 1.0 传输，JSON 编码。
  2. WorkStarted 与 WorkCompleted 靠什么对应？ 答：消息体里的 TransactionID 相同。
  3. 信封里的 TimeStamp 是发送时间吗？ 答：不是，是事件发生的时间；并且必须包含时区。
  4. 为什么要给每条消息一个 UniqueID？ 答：防止同一消息被重复处理，也用于答复时指明回复的是哪条。
  5. RabbitMQ 中为什么推荐 Fanout 交换机？ 答：Fanout 把消息广播给所有绑定的队列，符合"设备广播、谁订阅谁收"的模型。
  6. （动手）在实验脚本里再构造一条 CFX.ResourcePerformance.FaultOccurred 并加一个 Severity 缺失的坏消息，让 check 拦截它。 答：在 check 里对该消息名增加对 MessageBody["Fault"]["Severity"] 的断言即可；这里的校验规则是自己加的，不是标准规定。

小结 ​

  • IPC-CFX（IPC-2591）= AMQP 1.0 + JSON + 标准消息词汇，用于电子组装设备向上层广播事件。
  • 所有消息有统一信封：MessageName、Version、TimeStamp、UniqueID、Source、Target、RequestID、MessageBody。
  • 事件广播经 Broker（如 RabbitMQ 的 Fanout 交换机）；请求/响应靠 RequestTargetAddress 指定的队列。
  • 常用：WorkStarted/WorkCompleted（以 TransactionID 串联）、UnitsArrived、FaultOccurred、Heartbeat。
  • 本篇的 Python 实验是示意，未连 Broker，未验证合规。
