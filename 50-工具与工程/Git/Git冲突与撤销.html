Git冲突与撤销

AI 生成 · 待核对工具与工程Git更新于 2026-10-21

本篇是 Git 入门路径的第 5 篇。读完你应该能：看懂冲突标记并亲手解决一次合并冲突；根据"改动在哪个区、有没有推送"选对撤销命令（restore / reset / revert / amend）；用 reflog 找回"丢掉"的提交和被误删的分支。

所有命令和输出在 Windows 11 + Git for Windows 2.54.0（Git Bash）里实际运行。文中用 sed -i 修改文件，这是 Git Bash 自带的命令；在 PowerShell 里请直接用编辑器改。哈希每次不同。

一句话定义 ​

冲突是两条分支改了同一处内容，Git 无法自动判断保留哪边，需要你人工决定；撤销是一组后悔药，按"撤销什么、撤到哪、是否已共享"选择不同的命令。

先修知识 ​

  • Git分支与合并：理解合并、HEAD、分支。
  • Git基础操作：理解三个区、status、diff。
  • Git远程仓库（撤销已推送的提交时需要）。

它解决什么问题 ​

团队协作时，两个人改同一个配置文件的同一行是迟早的事；一个人也会手滑：改错文件、提交了不该提交的、reset --hard 之后发现丢了东西。Git 的好处是几乎每一步都有退路，前提是你知道该用哪一个。

一、合并冲突 ​

冲突是怎么产生的 ​

分支 main 和 dev-a 都从同一个提交出发，都修改了 config.ini 的同一行 port=5000：main 改成 9000，dev-a 改成 8080。合并时 Git 面对"同一行，两个不同的新值"，只能求助于你。

实际制造并解决 ​

准备：config.ini 内容为：

name=MiniMES
port=5000
debug=false

在 dev-a 分支把 port 改成 8080 并提交；回到 main 把 port 改成 9000 并提交。然后合并：

$ git merge dev-a
Auto-merging config.ini
CONFLICT (content): Merge conflict in config.ini
Automatic merge failed; fix conflicts and then commit the result.

先别慌，看状态：

$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   config.ini

no changes added to commit (use "git add" and/or "git commit -a")

both modified = 双方都改了。提示里有两条路：解决后 git commit，或者 git merge --abort 放弃合并。打开文件，Git 已经把两个版本都写进去并用标记隔开：

name=MiniMES
<<<<<<< HEAD
port=9000
=======
port=8080
>>>>>>> dev-a
debug=false

怎么读：

  • <<<<<<< HEAD 到 =======：当前分支（你站着的 main）的版本。
  • ======= 到 >>>>>>> dev-a：被合并进来的分支（dev-a）的版本。
  • 没冲突的行（name=...、debug=...）已自动合并好，不带标记。

git diff 也能看到这个"组合差异"（带 ++ 两列）：

$ git diff
diff --cc config.ini
...
 name=MiniMES
++<<<<<<< HEAD
 +port=9000
++=======
+ port=8080
++>>>>>>> dev-a
 debug=false

解决步骤：

  1. 用编辑器打开文件，删掉三种标记行，只留下最终想要的内容。可以选一边、选另一边、或者两边融合。本例决定保留 8080：
name=MiniMES
port=8080
debug=false
  1. git add config.ini（告诉 Git "这个冲突我处理完了"）。
  2. git commit（合并提交，可用 -m 写说明）：
$ git add config.ini
$ git commit -m "Merge dev-a, keep port 8080"
[main cff85e7] Merge dev-a, keep port 8080
$ git log --oneline --graph
*   cff85e7 Merge dev-a, keep port 8080
|\
| * 11058b6 A: port 8080
* | 8eb1841 main: port 9000
|/
* d8afae5 add config

重要检查：提交前确认文件里没有残留 <<<<<<<、=======、>>>>>>>。残留的标记会被当成正常内容提交进去，配置文件或代码就坏了。可以 git grep -n "<<<<<<<" 搜一下。

不想解决了：abort ​

再制造一次冲突（dev-b 把 port 改成 1111，main 改成 2222），合并后发现不想处理：

$ git merge dev-b
Auto-merging config.ini
CONFLICT (content): Merge conflict in config.ini
Automatic merge failed; fix conflicts and then commit the result.
$ git merge --abort
$ git status
On branch main
nothing to commit, working tree clean

--abort 把仓库恢复到合并之前的样子，毫发无损。

避免和减少冲突 ​

  • 小步提交，经常 pull 同步，别让分支离主线太远。
  • 团队分工让不同人改不同文件；公共配置文件一次只让一个人改。
  • 代码格式化规则统一，避免"因为缩进被改全文件"造成的虚假冲突（见 代码规范与重构）。
  • 二进制文件（Excel、图片）无法行级合并，冲突时只能整体选一边：git checkout --ours 文件 或 --theirs 文件。

二、撤销：先判断"东西现在在哪" ​

你的情况用什么
工作区改乱了，想放弃修改，回到暂存区/上次提交的样子git restore 文件
已 add 但想取消暂存（改动保留在工作区）git restore --staged 文件
刚提交，提交信息写错/漏了一个文件git commit --amend
已提交但还没推送，想退回去重做git reset
已提交且已推送/已共享，想抵消它git revert
怎么都找不到自己的提交了git reflog
手上活没做完，想先切去干别的git stash

restore：撤销工作区/暂存区的改动 ​

$ echo "oops" >> u.txt
$ git status -s
 M u.txt
$ git restore u.txt
$ cat u.txt
line1

restore u.txt 把工作区的文件恢复成暂存区（没暂存则是上次提交）的样子。这一步会永久丢掉未提交的修改，Git 无法找回（没提交过，reflog 也没有）。

取消暂存：

$ echo "tmp" >> u.txt
$ git add u.txt
$ git status -s
M  u.txt
$ git restore --staged u.txt
$ git status -s
 M u.txt

改动从左列（暂存）回到右列（工作区），内容没丢。

从历史取回旧版本的某个文件：

$ git restore --source=HEAD~1 f.txt
$ cat f.txt
1
$ git status -s
 M f.txt

--source=HEAD~1 指"上一个提交里的版本"；取回后在工作区表现为一处修改，还要自己 add/commit 才算数。

另一个相关命令 git clean 删除未跟踪的文件，因为不可恢复，先用 -n（dry run，只预览）：

$ git clean -n
Would remove junk.txt
$ git clean -f
Removing junk.txt

amend：修补最近一次提交 ​

$ git commit --amend -m "add b.txt"        # 改提交说明
$ git add c.txt
$ git commit --amend --no-edit               # 把漏掉的文件补进上一次提交，说明不变
$ git show --stat --oneline HEAD
e199bf9 add b.txt
 b.txt | 1 +
 c.txt | 1 +
 2 files changed, 2 insertions(+)

amend 会产生新的提交取代旧的（哈希变），所以和 rebase 一样：已推送的提交不要 amend。

reset：移动分支指针（三种模式） ​

reset 把当前分支（和 HEAD）移到另一个提交。三种模式区别在"同时动哪些区"：

模式分支指针暂存区工作区适用
--soft移动不动（保留为已暂存）不动想把几个提交合并成一个
--mixed（默认）移动重置不动撤销提交和 add，保留改动
--hard移动重置重置彻底丢掉改动，危险

实验：连续 3 次提交（每次给 u.txt 加一行 c1/c2/c3）：

$ git log --oneline -5
6a6add8 commit c3
898d4d2 commit c2
391185d commit c1
6dc1977 add u
c0509bf main: port 2222

HEAD~1 的意思是"HEAD 的上一个"。

soft：退一步，改动还在暂存区：

$ git reset --soft HEAD~1
$ git status -s
M  u.txt
$ git commit -m "commit c3 redo"
[main f91128b] commit c3 redo

mixed：退一步，改动退回到工作区（未暂存）：

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	u.txt
$ git status -s
 M u.txt
$ cat u.txt
line1
c1
c2
c3

文件内容还是有 c3，只是不在提交里也不在暂存区了。

hard：改动彻底消失：

$ git add -A && git commit -m "commit c3 again"
$ git reset --hard HEAD~1
HEAD is now at 898d4d2 commit c2
$ cat u.txt
line1
c1
c2

c3 从历史和文件里都不见了。看起来永远丢了——但是下面的 reflog 能救。

reflog：救命的"操作日志" ​

git log 看的是分支历史；git reflog 记录的是HEAD 每一次移动（提交、切换、reset、merge ...），默认保留几十天（默认值约 90 天，可配置；此值依据常识，未在本机验证）。

$ git reflog -8
898d4d2 HEAD@{0}: reset: moving to HEAD~1
89a2f26 HEAD@{1}: commit: commit c3 again
898d4d2 HEAD@{2}: reset: moving to HEAD~1
f91128b HEAD@{3}: commit: commit c3 redo
898d4d2 HEAD@{4}: reset: moving to HEAD~1
6a6add8 HEAD@{5}: commit: commit c3
898d4d2 HEAD@{6}: commit: commit c2
391185d HEAD@{7}: commit: commit c1

HEAD@{1} 就是"HEAD 上一次所在的位置"，也就是被 --hard 丢掉前的 89a2f26。退回去：

$ git reset --hard HEAD@{1}
HEAD is now at 89a2f26 commit c3 again
$ cat u.txt
line1
c1
c2
c3

c3 回来了。只要改动曾经被 commit 过，几乎都能用 reflog 找回；没 commit 过的工作区改动（比如 restore、clean、reset --hard 抹掉的未提交修改）找不回。这就是"勤提交"的意义。

再一个典型场景，误删分支：

$ git branch -D risky
Deleted branch risky (was cb0dcb0).
$ git reflog -4
e199bf9 HEAD@{0}: checkout: moving from risky to main
cb0dcb0 HEAD@{1}: commit: risky work
e199bf9 HEAD@{2}: checkout: moving from main to risky
e199bf9 HEAD@{3}: reset: moving to HEAD
$ git branch risky-back HEAD@{1}
$ git branch -v
* main       e199bf9 add b.txt
  risky-back cb0dcb0 risky work

-D 提示里就印着被删分支的哈希（was cb0dcb0），用 git branch 新名字 哈希 立刻复活。

revert：用"反向提交"抵消已共享的提交 ​

已经 push 的提交，别人可能已经基于它工作了，不能 reset 抹掉。revert 的做法是新增一个提交，其内容恰好是那次提交的逆操作，历史只增不改：

$ git revert HEAD --no-edit
[main 6c8ee1d] Revert "commit c3 again"
 1 file changed, 1 deletion(-)
$ git log --oneline -5
6c8ee1d Revert "commit c3 again"
89a2f26 commit c3 again
898d4d2 commit c2
391185d commit c1
6dc1977 add u
$ cat u.txt
line1
c1
c2

c3 的内容没了，但 "commit c3 again" 这条历史还在，别人 pull 时只是多收到一个新提交，不会出任何冲突。

reset 与 revert 怎么选 ​

resetrevert
历史改写（提交消失）只追加
已 push 的提交不要用（除非全员知情并强推）正确做法
本地私有提交适合也行但啰嗦

stash：先把手上的活藏起来 ​

正在改东西，突然要切分支处理急事，又不想提交半成品：

$ echo "wip" >> a.txt
$ git stash
Saved working directory and index state WIP on main: e199bf9 add b.txt
$ git status -s
$ git stash list
stash@{0}: WIP on main: e199bf9 add b.txt
$ git stash pop
...
	modified:   a.txt
Dropped refs/stash@{0} (8633d9f605c27e5433e0fee2b084ee0088fe25ed)

stash 把工作区和暂存区改动存到一个栈里，让目录回到干净状态；stash pop 取回并删除那条记录。新文件（未跟踪）默认不会被 stash，需要 git stash -u。

动手实验 ​

在空文件夹 undo-lab 里 git init -b main，设置本仓库 user，然后：

实验 A：制造并解决冲突

  1. 创建 config.ini 写三行（name=X、port=5000、debug=false），提交。
  2. git switch -c dev-a，把 port 改成 8080，提交。
  3. git switch main，把 port 改成 9000，提交。
  4. git merge dev-a，确认出现 CONFLICT，git status 看到 both modified。
  5. 编辑文件删掉标记，保留 8080。git add config.ini，git commit -m "resolve"。
  6. git log --oneline --graph 应看到分叉汇合图。

实验 B：reset 三种模式与 reflog

  1. 新建 u.txt 提交，再连续提交三次追加 c1 c2 c3。
  2. 依次试 reset --soft HEAD~1（用 git status -s 观察）、再 commit；reset --mixed HEAD~1；git add -A && git commit；reset --hard HEAD~1。
  3. 用 git reflog 找到 --hard 之前的位置，git reset --hard HEAD@{1} 找回，cat u.txt 确认。

实验 C：revert：对最新提交执行 git revert HEAD --no-edit，确认内容被抵消而历史多了一条。

常见坑与排查 ​

  • 冲突后一直提示 You have unmerged paths：忘了 git add 已解决的文件。
  • commit 时被 Committing is not possible because you have unmerged files 拒绝：同上，还有文件未标记为已解决。git status 看红色的 both modified 项。
  • reset --hard 前没看清：先 git status/git stash 确认没有未提交的重要改动，因为它们找不回。
  • 对已 push 的提交 reset + 强制推送：会让同事的本地历史与远程对不上。要么用 revert，要么先和团队沟通；强制推送请用 --force-with-lease（见 Git远程仓库）。
  • rebase 时的冲突：解决后用 git add 然后 git rebase --continue（不是 commit）；想放弃用 git rebase --abort。
  • 一次改了很多无关内容：养成小步提交习惯，出了问题定位和回退都容易。
  • VS / VS Code 里的图形化冲突工具：它们本质上也是改这些标记，原理一致。

练习题与答案 ​

1. 冲突标记里 HEAD 一侧和另一侧分别是谁的？ 答：<<<<<<< HEAD 到 ======= 是你当前所在分支的版本；之后到 >>>>>>> 分支名 是被合并进来的分支的版本。

2. 我 git add 了一个不想提交的文件，怎么取消但保留修改？ 答：git restore --staged 文件。

3. 我 git restore 文件 之后发现改错了，能找回吗？ 答：不能（改动从未被提交或暂存）。这是 restore 的风险。

4. reset --soft、--mixed、--hard 的区别？ 答：都会移动分支指针；soft 保留暂存区和工作区，mixed 清空暂存区但保留工作区，hard 两者都重置。

5. 同事已经拉取了我的错误提交，我该用 reset 还是 revert？ 答：revert。reset 会改写历史，导致同事的仓库与远程不一致。

6. git reset --hard 后丢了刚提交的内容，怎么办？ 答：git reflog 找到那次提交的哈希，git reset --hard 哈希 回去。

小结 ​

  • 冲突 = 同一处被双方修改；读懂 <<<<<<< ======= >>>>>>>，编辑、add、commit 三步解决，不想解决就 merge --abort。
  • 撤销命令按"改动在哪个区、是否已共享"选：restore（工作区/暂存区）、amend（最近一次提交）、reset（私有历史）、revert（已共享历史）。
  • reflog 记录 HEAD 的每次移动，是提交过的内容的后悔药；没提交过的改动没救，所以勤提交。
