REST-API设计

AI 生成 · 待核对工具与工程APIHTTP更新于 2026-10-21

本篇的示例 API 是一个用 Python 标准库写的迷你"工单"服务，代码完整、已实际运行，下面所有 curl 输出都是真实的（服务每次从头启动，数据在内存里）。RFC 9457（错误格式）的字段名已联网核对。"最佳实践"里偏经验性的建议（如版本放哪里、分页选哪种）属于业界常见做法，没有唯一标准，基于模型知识。

读完你应该能：把业务需求设计成"资源 + HTTP 方法"的接口；为每种情况选对状态码；做分页、版本、统一的错误返回；用 curl 测试一个接口。

一句话定义 ​

REST API 是一种设计 Web 接口的风格：把系统里的东西抽象成"资源"（工单、物料），每个资源有一个网址（URL），客户端用 HTTP 自带的方法（GET/POST/PUT/DELETE……）对资源做增删改查，服务器用 HTTP 状态码和 JSON 回应。

先修知识 ​

  • HTTP：知道请求/响应、请求头、请求体、状态码的基本概念。
  • JSON-XML-YAML：接口一般用 JSON 传数据。
  • WebAPI开发：在 C# 里怎么实现这些接口（本篇讲"设计什么样"，那篇讲"用 ASP.NET Core 怎么写"，对应关系见后面的"技术视角"）。

它解决什么问题 ​

一个系统有几十上百个接口时，如果每个接口名字随心所欲，就会出现 /getOrder、/queryOrderList、/orderDelete、/removeOrderById……调用方每个都要看文档，还容易调错。

REST 的约定把这件事标准化：

  • 名字统一：URL 只写名词（资源），动作由 HTTP 方法表达；
  • 含义统一：成功还是失败，看状态码，不用每个接口自己发明 {"code":0}；
  • 行为可预期：GET 一定不改数据，DELETE 重复执行结果相同……基础设施（浏览器、缓存、网关、重试机制）才敢依赖这些保证。

在 MES、WMS 这类系统里，前端页面、设备端程序、别的系统（ERP、WMS）都要调接口，接口设计得整齐，集成成本会低很多（见 接口技术选型）。

核心概念 ​

资源与 URL ​

资源是系统里值得被单独命名的"东西"，如工单、物料、工序。设计规则：

规则好差
用名词，不用动词/orders/getOrders
集合用复数/orders、/orders/42/order/42
层级表达从属关系/orders/42/steps/getStepsOfOrder?id=42
全小写，用 - 连接/work-orders/WorkOrders、/work_orders
查询条件放 query string/orders?status=running/orders/running

URL 里 /orders 表示"工单集合"，/orders/42 表示"编号 42 的那一张工单"。

HTTP 方法 ​

方法含义对 /orders（集合）对 /orders/42（单个）安全*幂等**
GET读取列表详情是是
POST创建（或触发处理）新建一张（一般不用）否否
PUT整体替换—用请求体完整替换否是
PATCH部分修改—只改请求体里给的字段否视实现
DELETE删除—删掉否是

* 安全：不修改服务器上的数据，所以可以随便调用、被缓存、被预取。 ** 幂等：同一个请求执行 1 次和执行 N 次，对服务器最终状态的影响相同。这决定了网络出错时能不能自动重试：GET、PUT、DELETE 可以放心重试；POST 重试可能创建出两张工单。RFC 9110 定义：安全方法、PUT、DELETE 是幂等的。

PUT 与 PATCH 的区别要点：PUT 是"用我给的整个内容替换"，没给的字段会被重置（本篇示例里会看到）；PATCH 只改给出的字段。

状态码 ​

状态码是服务器给客户端的"一眼能懂的结果"，按首位数字分类：

范围含义
2xx成功
3xx重定向
4xx客户端的错（请求有问题，改了请求才可能成功）
5xx服务器的错（请求没问题，服务器出故障）

设计接口最常用的几个：

状态码名称何时用
200OK读取/修改成功，响应体里有数据
201CreatedPOST 创建成功；响应头 Location 给出新资源的地址
204No Content成功，但没有响应体（常用于 DELETE）
400Bad Request请求本身格式有误，如 JSON 解析不了、参数类型错
401Unauthorized没登录/令牌无效（尽管名字叫"未授权"，实际是"未认证"）
403Forbidden登录了，但没有权限
404Not Found资源不存在
405Method Not Allowed这个资源不支持该方法（响应头 Allow 列出支持的方法）
409Conflict与当前状态冲突，如重复创建、版本冲突
415Unsupported Media Type请求体格式不支持，如要 JSON 却发了表单
422Unprocessable Content格式没问题，但字段内容不符合业务规则（数量为负等）
429Too Many Requests请求太频繁，被限流
500Internal Server Error服务器出了未预料的错误
503Service Unavailable服务暂时不可用（维护、过载）

400 和 422 怎么选：JSON 都解析不了用 400；JSON 合法但某个字段不满足规则用 422。很多团队统一都用 400，这也行——重要的是全团队一致，并在文档里写清楚。

绝不要"不管成功失败一律返回 200，在 body 里放 {"code": 500}"：网关、监控、重试机制全都靠状态码判断，全是 200 会让它们瞎了眼。

错误响应格式 ​

所有错误用同一种 JSON 结构，调用方才能统一处理。业界有个标准：RFC 9457 "Problem Details for HTTP APIs"（取代了 RFC 7807），媒体类型 application/problem+json，标准字段：

字段含义
type标识问题类型的 URI；不提供时默认 about:blank
title对这类问题的简短、人能读懂的概括
statusHTTP 状态码（仅供参考，以真实响应状态码为准）
detail针对这一次出错的详细说明
instance标识这一次具体问题的 URI

可以在此基础上加自定义字段，如字段校验错误的 errors。ASP.NET Core 的 ProblemDetails 类就对应这套格式（见 WebAPI开发）。

分页 ​

列表接口不能一次返回几十万条。常见做法：

方式参数优点缺点
页码?page=3&page_size=20简单，可跳页翻页期间数据变化，会出现重复或漏项；页码很大时数据库慢
游标?after=<上一页最后一条的标识>&limit=20数据变化也稳，大数据量快不能跳页

后台管理页常用页码；设备日志、消息流用游标。无论哪种都要：限制 page_size 上限（防止调用方要一百万条）、返回总数或"是否还有下一页"。

版本 ​

接口一旦被调用方使用，改动就可能把对方搞坏。最常见的做法是把版本号放在 URL：/v1/orders。需要不兼容改动时发布 /v2/...，旧版本继续保留一段时间。向后兼容的改动（新增可选字段、新增接口）不用升版本；不兼容的改动（删字段、改字段类型、改含义）必须升版本。

其他约定（简述） ​

  • 过滤、排序：?status=running&sort=-createdAt。
  • 日期时间：用 ISO 8601 字符串，如 2026-10-21T08:30:00Z，明确时区。
  • 幂等键：POST 不是幂等的，重要操作（付款、报工）可让客户端带 Idempotency-Key 请求头，服务端据此去重，重试才安全。
  • 认证：令牌放在 Authorization 请求头，不要放 URL（会进日志）。见 身份认证与JWT。
  • 文档：用 OpenAPI/Swagger 描述接口，见 Swagger与OpenAPI。

逐步例子：迷你工单 API ​

下面是一个完整可运行的服务，只用 Python 标准库。接口设计如下：

方法与路径作用成功状态码
GET /v1/orders?status=&page=&page_size=工单列表（可按状态过滤、分页）200
POST /v1/orders新建工单201
GET /v1/orders/{id}工单详情200
PUT /v1/orders/{id}整体替换200
PATCH /v1/orders/{id}部分修改200
DELETE /v1/orders/{id}删除204

保存为 api.py：

python
"""迷你工单 REST API：只用 Python 标准库。运行：python api.py  （监听 127.0.0.1:8080）"""
import json
import re
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse

ORDERS = {
    1: {"id": 1, "product": "PCB-A100", "qty": 500, "status": "released"},
    2: {"id": 2, "product": "PCB-B200", "qty": 300, "status": "running"},
    3: {"id": 3, "product": "PCB-A100", "qty": 120, "status": "running"},
    4: {"id": 4, "product": "PCB-C300", "qty": 800, "status": "done"},
    5: {"id": 5, "product": "PCB-B200", "qty": 60, "status": "released"},
}
NEXT_ID = 6
STATUSES = {"released", "running", "done"}
ONE = re.compile(r"^/v1/orders/(\d+)$")


class Handler(BaseHTTPRequestHandler):
    def send_json(self, code, body=None, ctype="application/json", headers=None):
        data = b"" if body is None else json.dumps(body, ensure_ascii=False).encode("utf-8")
        self.send_response(code)
        self.send_header("Content-Type", ctype + "; charset=utf-8")
        self.send_header("Content-Length", str(len(data)))
        for k, v in (headers or {}).items():
            self.send_header(k, v)
        self.end_headers()
        self.wfile.write(data)

    def problem(self, code, title, detail, headers=None):
        # 错误格式参考 RFC 9457 (application/problem+json)
        self.send_json(code, {"type": "about:blank", "title": title, "status": code, "detail": detail},
                       ctype="application/problem+json", headers=headers)

    def read_json(self):
        if not self.headers.get("Content-Type", "").startswith("application/json"):
            self.problem(415, "Unsupported Media Type", "请求头 Content-Type 必须是 application/json")
            return None
        try:
            body = json.loads(self.rfile.read(int(self.headers.get("Content-Length", 0))) or b"")
        except ValueError:
            self.problem(400, "Bad Request", "请求体不是合法的 JSON")
            return None
        if not isinstance(body, dict):
            self.problem(400, "Bad Request", "请求体必须是 JSON 对象")
            return None
        return body

    def check(self, body, partial):
        errors = {}
        if "product" in body or not partial:
            if not isinstance(body.get("product"), str) or not body.get("product"):
                errors["product"] = "必填，非空字符串"
        if "qty" in body or not partial:
            if type(body.get("qty")) is not int or body["qty"] <= 0:
                errors["qty"] = "必填，正整数"
        if "status" in body and body["status"] not in STATUSES:
            errors["status"] = f"必须是 {sorted(STATUSES)} 之一"
        if errors:
            self.send_json(422, {"type": "about:blank", "title": "Validation Failed", "status": 422,
                                 "detail": "字段校验未通过", "errors": errors}, ctype="application/problem+json")
            return False
        return True

    def route(self):
        global NEXT_ID
        url = urlparse(self.path)
        m = ONE.match(url.path)
        if url.path == "/v1/orders":
            if self.command == "GET":
                q = parse_qs(url.query)
                items = [o for o in ORDERS.values() if "status" not in q or o["status"] == q["status"][0]]
                try:
                    page = max(1, int(q.get("page", ["1"])[0]))
                    size = min(50, max(1, int(q.get("page_size", ["2"])[0])))
                except ValueError:
                    return self.problem(400, "Bad Request", "page 和 page_size 必须是整数")
                start = (page - 1) * size
                self.send_json(200, {"items": items[start:start + size], "page": page, "page_size": size,
                                     "total": len(items), "has_next": start + size < len(items)})
            elif self.command == "POST":
                body = self.read_json()
                if body is not None and self.check(body, partial=False):
                    order = {"id": NEXT_ID, "product": body["product"], "qty": body["qty"],
                             "status": body.get("status", "released")}
                    ORDERS[NEXT_ID] = order
                    NEXT_ID += 1
                    self.send_json(201, order, headers={"Location": f"/v1/orders/{order['id']}"})
            else:
                self.problem(405, "Method Not Allowed", f"{self.command} 不适用于该资源", {"Allow": "GET, POST"})
        elif m:
            oid = int(m.group(1))
            if oid not in ORDERS:
                return self.problem(404, "Not Found", f"工单 {oid} 不存在")
            if self.command == "GET":
                self.send_json(200, ORDERS[oid])
            elif self.command in ("PUT", "PATCH"):
                body = self.read_json()
                if body is not None and self.check(body, partial=self.command == "PATCH"):
                    body.pop("id", None)  # id 由服务端决定，不允许改
                    ORDERS[oid] = {**ORDERS[oid], **body} if self.command == "PATCH" else {"id": oid, "status": "released", **body}
                    self.send_json(200, ORDERS[oid])
            elif self.command == "DELETE":
                del ORDERS[oid]
                self.send_json(204)
            else:
                self.problem(405, "Method Not Allowed", f"{self.command} 不适用于该资源",
                             {"Allow": "GET, PUT, PATCH, DELETE"})
        else:
            self.problem(404, "Not Found", f"路径 {url.path} 不存在")

    do_GET = do_POST = do_PUT = do_PATCH = do_DELETE = route

    def log_message(self, *a):  # 安静一点
        pass


if __name__ == "__main__":
    print("listening on http://127.0.0.1:8080", flush=True)
    ThreadingHTTPServer(("127.0.0.1", 8080), Handler).serve_forever()

运行 python -X utf8 api.py，另开一个终端测试。注意 curl 都带了 --noproxy '*'：本机设了 HTTP_PROXY，不加的话访问本机地址会得到 503（见 环境变量与PATH）。Windows 的 PowerShell 里要用 curl.exe（curl 是 Invoke-WebRequest 的别名），且 JSON 里的双引号要转义，下面用 Git Bash 的单引号写法演示。

1. 读取单个资源 ​

text
$ curl -i --noproxy '*' http://127.0.0.1:8080/v1/orders/1
HTTP/1.0 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 66

{"id": 1, "product": "PCB-A100", "qty": 500, "status": "released"}

（-i 显示响应头，Server、Date 两行省略。）

2. 分页 ​

共 5 张工单，每页 2 条：

text
$ curl --noproxy '*' 'http://127.0.0.1:8080/v1/orders?page=1&page_size=2'
{"items": [{"id": 1, ...}, {"id": 2, ...}], "page": 1, "page_size": 2, "total": 5, "has_next": true}

$ curl --noproxy '*' 'http://127.0.0.1:8080/v1/orders?page=3&page_size=2'
{"items": [{"id": 5, "product": "PCB-B200", "qty": 60, "status": "released"}], "page": 3, "page_size": 2, "total": 5, "has_next": false}

校验：第 3 页起始位置 = (3-1)×2 = 4，取下标 4 的一条，即 id=5；4 + 2 = 6 ≥ 5，所以 has_next 为 false。（上面第一个输出里的 ... 是我为篇幅省略的字段，实际返回完整。）

URL 要用引号包起来，否则 shell 会把 & 当成"后台运行"。

3. 过滤 ​

text
$ curl --noproxy '*' 'http://127.0.0.1:8080/v1/orders?status=running'
{"items": [{"id": 2, ...}, {"id": 3, ...}], "page": 1, "page_size": 2, "total": 2, "has_next": false}

4. 创建：201 + Location ​

text
$ curl -i --noproxy '*' -X POST http://127.0.0.1:8080/v1/orders \
    -H 'Content-Type: application/json' -d '{"product":"PCB-D400","qty":200}'
HTTP/1.0 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 66
Location: /v1/orders/6

{"id": 6, "product": "PCB-D400", "qty": 200, "status": "released"}

状态码 201 表示"创建了"，Location 告诉客户端新资源的地址，响应体返回完整的新资源（含服务器生成的 id 和默认的 status）。随后 GET /v1/orders/6 能读到同样的内容。

5. 各种错误 ​

字段校验失败 → 422，一次性把所有错误告诉调用方：

text
$ curl --noproxy '*' -X POST http://127.0.0.1:8080/v1/orders \
    -H 'Content-Type: application/json' -d '{"product":"","qty":-5,"status":"lost"}'
{"type": "about:blank", "title": "Validation Failed", "status": 422, "detail": "字段校验未通过", "errors": {"product": "必填，非空字符串", "qty": "必填，正整数", "status": "必须是 ['done', 'released', 'running'] 之一"}}

JSON 格式有误 → 400：

text
$ curl --noproxy '*' -X POST http://127.0.0.1:8080/v1/orders -H 'Content-Type: application/json' -d '{bad json'
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "请求体不是合法的 JSON"}

忘了 Content-Type → 415（curl 的 -d 默认发 application/x-www-form-urlencoded）：

text
$ curl --noproxy '*' -X POST http://127.0.0.1:8080/v1/orders -d 'product=x'
{"type": "about:blank", "title": "Unsupported Media Type", "status": 415, "detail": "请求头 Content-Type 必须是 application/json"}

资源不存在 → 404；方法不支持 → 405 加 Allow 头：

text
$ curl -i --noproxy '*' -X DELETE http://127.0.0.1:8080/v1/orders
HTTP/1.0 405 Method Not Allowed
Content-Type: application/problem+json; charset=utf-8
Allow: GET, POST

{"type": "about:blank", "title": "Method Not Allowed", "status": 405, "detail": "DELETE 不适用于该资源"}

$ curl --noproxy '*' 'http://127.0.0.1:8080/v1/orders?page=abc'
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "page 和 page_size 必须是整数"}

6. 删除与"幂等" ​

text
$ curl -i --noproxy '*' -X DELETE http://127.0.0.1:8080/v1/orders/1
HTTP/1.0 204 No Content
Content-Length: 0

$ curl -i --noproxy '*' -X DELETE http://127.0.0.1:8080/v1/orders/1
HTTP/1.0 404 Not Found
Content-Type: application/problem+json; charset=utf-8

{"type": "about:blank", "title": "Not Found", "status": 404, "detail": "工单 1 不存在"}

第一次 204，第二次 404——响应不一样，但"幂等"说的是对服务器状态的影响：两次之后，工单 1 都不存在，状态相同，所以 DELETE 仍是幂等的。

7. PATCH 与 PUT 的差异 ​

text
$ curl --noproxy '*' -X PATCH http://127.0.0.1:8080/v1/orders/2 -H 'Content-Type: application/json' -d '{"status":"done"}'
{"id": 2, "product": "PCB-B200", "qty": 300, "status": "done"}

$ curl --noproxy '*' -X PUT http://127.0.0.1:8080/v1/orders/3 -H 'Content-Type: application/json' -d '{"product":"PCB-A100","qty":999}'
{"id": 3, "status": "released", "product": "PCB-A100", "qty": 999}

PATCH 只给了 status，其余字段保持不变。PUT 没给 status，工单 3 原来是 running，被重置回了默认的 released——这就是"整体替换"的含义，也是 PUT 用错最容易丢数据的地方。

动手实验 ​

  1. 保存 api.py 并运行；用 Git Bash（或装好 curl 的任意终端）依次执行"逐步例子"的所有命令，核对状态码与输出。
  2. 用浏览器直接访问 http://127.0.0.1:8080/v1/orders/2（浏览器只能发 GET），看到 JSON。如果你的浏览器或系统设了代理，访问本机地址时同样可能被代理拦截，需在代理设置里排除。
  3. 自己扩展：给服务加一个 GET /v1/orders?sort=-qty（按数量倒序）；再加 POST /v1/orders/{id}/start（把状态改为 running；若已是 done 返回 409 Conflict）。体会"动作型"操作怎么放进 REST：把动作当作子资源用 POST。
  4. 用 Python 写客户端调用它：
python
import json, urllib.request

def make_request():
    return urllib.request.Request("http://127.0.0.1:8080/v1/orders", method="POST",
        data=json.dumps({"product": "PCB-E500", "qty": 10}).encode(), headers={"Content-Type": "application/json"})

# ProxyHandler({}) 表示不使用任何代理，绕开 HTTP_PROXY 环境变量
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
with opener.open(make_request()) as r:
    print(r.status, r.headers["Location"])

本机实测（全新启动的服务）输出 201 /v1/orders/6。如果直接用 urllib.request.urlopen(...)，在本机设了 HTTP_PROXY 的情况下得到 HTTP Error 503: Service Unavailable。注意：Request 对象一旦经过代理请求，其目标地址就被改写成代理了，不能拿同一个对象换个方式再发，所以这里每次用函数新建。

  1. 在 WebAPI开发 里用 ASP.NET Core 把同样的接口实现一遍，对照两者。

常见坑与排查 ​

现象原因与办法
本机调自己的接口返回 503不是接口的错：HTTP_PROXY 把本机请求发给了代理。curl --noproxy '*'，见 环境变量与PATH
POST 提示 415没带 Content-Type: application/json；curl -d 默认是表单格式
PowerShell 里 curl 的参数报错curl 是 Invoke-WebRequest 的别名，参数完全不同。用 curl.exe，或 Invoke-RestMethod

中文乱码响应头声明 charset=utf-8，终端也要是 UTF-8（PowerShell 5.1 默认非 UTF-8）
一律返回 200，调用方分不清成败用正确的状态码；错误用 4xx/5xx
用 GET 做修改（GET /deleteOrder?id=1）爬虫、预取、缓存可能触发它，造成误删。修改一律用 POST/PUT/PATCH/DELETE
列表接口不分页，数据多了拖垮服务从一开始就加分页和 page_size 上限

业务视角与技术视角 ​

  • 业务视角：MES 对外的接口大致分几类：给产线终端的（过站、报工、上料）、给 ERP 的（工单下达、完工回传）、给设备/EAP 的（参数下发、数据上报）。资源通常是工单、批次、条码、物料、工序。设计时先和业务方确认资源是什么、状态如何流转，再定 URL 和方法。流程动作（"过站""暂停工单"）不是简单的增删改查，常设计为子资源上的 POST，如 POST /v1/work-orders/42/pause；并且这类动作要求幂等或有去重——产线网络抖动重发一次"报工 100 件"，不能变成 200 件。
  • 技术视角：对应到 ASP.NET Core（WebAPI开发）：[HttpGet]/[HttpPost]/[HttpPut]/[HttpPatch]/[HttpDelete] 对应方法；返回 Created(...) 对应 201 + Location，NoContent() 对应 204，NotFound() 对应 404，Problem(...)/ValidationProblem(...) 对应 RFC 9457 格式；[ApiController] 会自动对模型校验失败返回 400 的 ProblemDetails。（此段为对 ASP.NET Core 的一般性描述，基于模型知识，本篇未在本机用 ASP.NET Core 验证。）

练习题与答案 ​

1. 把这些接口改成 RESTful 风格：/getOrderList、/addOrder、/deleteOrder?id=7、/updateOrderStatus?id=7&status=done。

答：GET /orders、POST /orders、DELETE /orders/7、PATCH /orders/7（请求体 {"status":"done"}）。

2. 客户端 POST 创建工单，网络超时没收到响应，直接重发安全吗？

答：不安全，POST 不幂等，可能创建出两张。应使用幂等键（Idempotency-Key）让服务端去重。

3. 工单 3 目前是 {"product":"A","qty":10,"status":"running"}。客户端 PUT {"product":"A","qty":20}，结果会怎样？如果想只改 qty 呢？

答：PUT 是整体替换，没给的 status 会丢失或重置为默认值。想只改 qty 应该用 PATCH：{"qty":20}。

4. 用户登录了，但访问别人的工单被拒绝，应该返回 401 还是 403？

答：403 Forbidden。401 表示没有登录/令牌无效，403 表示身份已确认但无权限。

5. 为什么分页必须限制 page_size 的上限？

答：防止调用方（误操作或恶意）一次请求几十万条，拖垮服务器和数据库。

6. 总共 47 条数据，每页 10 条，一共几页？第 5 页有几条？

答：5 页（⌈47/10⌉ = 5）；第 5 页起始下标 (5-1)×10 = 40，有 47 - 40 = 7 条。

小结 ​

  • REST = 资源（名词、复数）+ HTTP 方法（动词）+ 状态码（结果）；URL 里不放动词。
  • GET 安全；GET/PUT/DELETE 幂等；POST 不幂等，重要的 POST 要用幂等键防重复。PUT 是整体替换，PATCH 是局部修改。
  • 状态码要用对：201 创建、204 无内容、400/422 请求有误、401/403 认证与权限、404 不存在、405 方法不允许、409 冲突、5xx 服务器错。
  • 错误统一格式（可采用 RFC 9457 的 application/problem+json）；列表必须分页并限上限；不兼容改动升版本（/v1/）。
  • 本机调试接口遇到 503，先怀疑 HTTP_PROXY。
