数据库选型对比

AI 生成 · 待核对数据库选型更新于 2026-10-21

⚠ 待核对：授权条款、免费版资源上限、版本号这类"会随时间变化"的信息，我只做了网络检索，未逐条核对官方原文；选型决策前请到各官网确认（见"延伸阅读"）。各表中的"典型"描述属于经验性总结，不是官方定义。本篇所有 Oracle / PostgreSQL / MySQL / Redis / MongoDB 的内容均 ⚠ 未在本机运行验证（本机没有这些软件）；SQL Server 与 SQLite 的示例已在本机运行。

本篇是 数据库 入门路径的第 14 篇（也可以早点读，当地图用）。读完你应该能：说出 7 种常见数据库各自的定位；根据场景（授权、规模、事务、团队技能）排除不合适的选项；解释为什么你们公司的 MES/WMS/QMS 选 SQL Server 是合理的，以及什么时候该引入 Redis、SQLite、MongoDB。

一句话定义 ​

数据库选型就是：根据数据的形态、规模、一致性要求、预算授权和团队技能，决定用哪种（或哪几种）数据库软件。 没有"最好"的数据库，只有"最合适"的组合。

先修知识 ​

  • 数据库：知道什么是 DBMS、关系型与 NoSQL 的大致区别。
  • 关系模型、SQL基础查询：对关系型数据库有基本体感。

它解决什么问题 ​

新项目启动、老系统改造、客户指定"必须兼容 Oracle"、老板问"能不能用免费的"……这些时候需要一个清晰的比较框架，避免两种常见错误：盲目追新（为了 NoSQL 而 NoSQL）和盲目守旧（所有数据都塞进同一个库）。

关于授权的几个事实（搜索得到，需核对原文）：

  • Redis 在 2024 年 3 月从 BSD 改为 RSALv2 / SSPLv1 双授权，2025 年 5 月发布的 Redis 8 起，在这两者之外又增加了 AGPLv3 选项（来源：Redis 官方博客 Redis 8 GA）。社区因此分叉出了 Valkey（Linux 基金会）。
  • MongoDB 自 2018 年起使用 SSPL；Percona 等认为它"源码可得但不算开源"。
  • Oracle 免费版（Oracle Database Free）官网标注的上限为用户数据 12 GB、内存 2 GB、2 个 CPU 线程；同页说明了该版本不提供技术支持和补丁（以官网当前页面为准）。
  • SQL Server 2025 Express 的单库大小上限，微软发布说明里写的是 50 GB（此前版本为 10 GB；有第三方文章称 Linux 版仍是 10 GB），另有 CPU 取 1 个插槽或 4 核较小者、缓冲池约 1.4 GB 等限制。
  • 版本方面：我检索时看到 PostgreSQL 18 是最新的正式大版本，19 处于候选发布阶段（2026 年 10 月）；SQL Server 的最新版本是 2025（我本机 LocalDB 的版本号为 17.0.4025.3，已实测）。

各自的强项和弱项 ​

SQL Server

  • 强项：和 .NET / C# 的结合是所有数据库里最顺的（SqlSugar、EF Core、ADO.NET 都是一等公民）；图形化管理工具成熟；T-SQL 功能丰富；Windows 域账号集成认证；报表、ETL、分析工具一套齐全。
  • 弱项：商业授权费用较高（按核数/CAL）；Windows 平台为主（现已支持 Linux，但国内工厂仍以 Windows 居多）；高级特性依赖企业版。
  • 适合：以 Windows/.NET 为主的工厂信息化系统——也就是你们的 MES/WMS/QMS/LIMS。详见 SQL-Server。

Oracle

  • 强项：高可用、大并发、审计与安全功能全面，PL/SQL 能力强；很多大型企业的 ERP（包括 Oracle 自家 EBS）跑在它上面。
  • 弱项：价格高、运维复杂；对初学者门槛高。
  • 适合：客户指定、或大集团的 ERP / 财务核心。工厂信息化人员经常会遇到的是对接客户或集团的 Oracle 库，所以要懂它与 SQL Server 的差异：Oracle、Oracle与SQL-Server差异。

PostgreSQL

  • 强项：开源免费、功能强（JSON、数组、地理信息、全文检索、丰富的扩展），标准遵循好，社区活跃。
  • 弱项：在 Windows/.NET 工厂圈的普及度和熟练工程师数量不如 SQL Server；工具链不如微软一体化。
  • 适合：想要免费又不想牺牲功能的新项目；数据分析、地理信息、需要扩展的场景。详见 PostgreSQL、PostgreSQL特色功能。

MySQL

  • 强项：上手简单，互联网行业资料极多，云上托管服务多。
  • 弱项：历史上对标准 SQL 支持较弱（8.0 起大幅改善）；有些行为较"宽松"，容易埋隐患；复杂分析不如 PostgreSQL / SQL Server。
  • 适合：中小型 Web 系统；工厂内部系统中相对少见。

SQLite

  • 强项：零配置、零运维，一个文件搞定；几乎所有语言内置支持；可靠性极高，手机 App、浏览器、操作系统里到处都有它。
  • 弱项：只有单个写入者（同一时刻一个写事务），不适合高并发写；没有网络服务，无法让多台电脑同时访问同一个库文件；类型很宽松（见下面的实验）。
  • 适合：设备端/边缘端的本地缓存、小工具、配置库、单元测试、桌面小程序的本地存储。

Redis

  • 强项：数据在内存里，读写极快（常见量级为每秒数十万次操作）；数据结构丰富（字符串、哈希、列表、集合、有序集合）；可设置过期时间；做分布式锁、限流、排行榜、会话缓存。
  • 弱项：不适合做主存储（内存贵、持久化是辅助）；不支持复杂查询和联表。
  • 适合：给关系库"挡一层"的缓存、临时状态、消息队列轻量替代。详见 Redis。

MongoDB

  • 强项：文档结构灵活，一份数据一个 JSON，不需要提前建表；适合"每条记录字段都不完全相同"的数据；原生分片。
  • 弱项：联表能力弱；事务和一致性上比关系库更需要小心设计；要在应用里补很多约束。
  • 适合：设备上报的多变格式日志、配置、内容类数据。详见 MongoDB、NoSQL概述。

逐步例子：三个工厂场景怎么选 ​

场景 A：新建一套 MES ​

需求：工单、物料、过站、质量记录，强关联、不能丢不能错，团队是 C#，已有 SQL Server 授权，约 200 万条过站记录/年。

推理：

  1. 数据高度关联（工单—板—站—结果）并要求事务 → 关系型，排除 Redis、MongoDB 作主库。
  2. 团队技能 C# + SqlSugar → SQL Server 开发效率最高。
  3. 规模：200 万/年，几年才到千万级，单机 SQL Server 绰绰有余。
  4. 授权：公司已有，不新增成本。 → 选 SQL Server。 如要省授权费，PostgreSQL 是备选，但需要承担学习和运维转型成本。

场景 B：产线设备旁的小工具，需要断网时本地缓存测试结果 ​

需求：一台工控机，断网时本地暂存数据，网络恢复后上传；没有 DBA，不能依赖服务安装。

推理：不需要多机并发，要零运维 → SQLite。程序里就是一个 .db 文件。上传后可以清理。

场景 C：看板页面每 3 秒刷新，查询"当前各线良率"，MES 库压力过大 ​

需求：数百个看板同时拉取相同的汇总数据。

推理：数据相同、读多写少、可容忍几秒延迟 → 把算好的结果放 Redis（设 5 秒过期），看板读 Redis，MES 库只被一个后台任务查询。这样数据库只承担 1 次/5 秒的查询，而不是数百次/3 秒。注意：Redis 里只放"可重新计算出来的结果"，丢了不会出事。

决策小抄 ​

问自己若答案是…倾向
数据强关联、需要事务吗？是关系型（SQL Server / PostgreSQL / Oracle / MySQL）
团队/客户已有技术栈？.NET + 微软SQL Server
客户或集团指定？OracleOracle（先做兼容性评估）
预算为零且规模不小？是PostgreSQL（或 SQL Server Express，受上限约束）
单机、无人运维、数据量小？是SQLite
读多写少、要极快、允许丢了重算？是Redis（作缓存）
每条数据字段都不同、结构常变？是MongoDB 或"关系库 + JSON 列"
带时间戳的海量传感器数据？是时序数据库（TDengine、InfluxDB 等，本库暂不展开）

一条朴素的原则：先用关系库解决，遇到它真正解决不了的问题，再加一种专用库。系统里的数据库种类越少，运维成本越低。

动手实验 ​

实验 1：用 Python 自带的 SQLite 体验"零安装数据库" ​

Python 3 自带 sqlite3 模块，不用装任何东西。新建 sqlite_lab.py（UTF-8），运行 python -I -X utf8 sqlite_lab.py：

python
import sqlite3, os
print("sqlite 版本:", sqlite3.sqlite_version)
path = "lab.db"
if os.path.exists(path): os.remove(path)
db = sqlite3.connect(path)
db.execute("CREATE TABLE Material (MaterialCode TEXT PRIMARY KEY, MaterialName TEXT, UnitPrice REAL, Qty INTEGER)")
db.executemany("INSERT INTO Material VALUES (?,?,?,?)", [
    ("R-10K", "贴片电阻10K", 0.02, 100), ("IC-MCU01", "主控芯片MCU01", 12.8, 5), ("SOLDER-T3", "锡膏T3", 380.0, 2)])
db.commit()
print("1 取单价最高的 2 条（SQLite 用 LIMIT，不是 TOP）：")
for r in db.execute("SELECT MaterialCode, UnitPrice FROM Material ORDER BY UnitPrice DESC LIMIT 2"): print("  ", r)
print("2 往 INTEGER 列塞文字：")
db.execute("INSERT INTO Material VALUES ('X-1', '测试', 1.0, 'abc')")
for r in db.execute("SELECT MaterialCode, Qty, typeof(Qty) FROM Material WHERE MaterialCode IN ('R-10K','X-1')"): print("  ", r)
print("3 数据库就是一个文件，大小(字节)：", os.path.getsize(path))
db.close()
os.remove(path)

我的实际输出（SQLite 版本取决于你的 Python）：

sqlite 版本: 3.49.1
1 取单价最高的 2 条（SQLite 用 LIMIT，不是 TOP）：
   ('SOLDER-T3', 380.0)
   ('IC-MCU01', 12.8)
2 往 INTEGER 列塞文字：
   ('R-10K', 100, 'integer')
   ('X-1', 'abc', 'text')
3 数据库就是一个文件，大小(字节)： 12288

观察三件事：

  1. SQLite 的"取前几条"写 LIMIT，和 SQL Server 的 TOP 不同——这就是方言。
  2. SQLite 的列类型只是"建议"：往 INTEGER 列塞 'abc' 居然成功了。SQL Server 会直接报错（转换失败）。这就是"类型宽松"，用 SQLite 做业务主库要自己在程序里校验。
  3. 整个数据库只有一个 12 KB 的文件，拷走就是备份（没有写入时）。

  • sqllocaldb i：列出 LocalDB 实例；
  • 在"服务"（services.msc）里找名字含 SQL Server 的服务：MSSQLSERVER 是默认实例，MSSQL$名字 是命名实例；

常见坑与排查 ​

  • 以为 SQLite 能当多人共享库：把 .db 文件放网络共享盘让多台机器同时读写，会出现锁冲突，甚至数据损坏。SQLite 官方也不建议在网络文件系统上并发使用。
  • 把 Redis 当主数据库：Redis 重启或宕机，内存里没来得及持久化的数据会丢。只放能重新算出来的东西，或者明确配置好持久化并接受它的取舍。
  • 免费版上限踩线：SQL Server Express 的单库大小、内存、CPU 限制，Oracle Free 的 12 GB 限制，都可能在项目长大后触达，要在选型时估算数据量增长。
  • 被授权条款绊倒：Redis、MongoDB 的授权近年变化较大，如果产品要对外分发或做成服务，需要法务确认。
  • 不同方言的 SQL 直接搬：TOP / LIMIT / FETCH FIRST、+ / || / CONCAT、ISNULL / COALESCE / NVL 都会不同，迁移要逐条验证。写可移植 SQL 的原则：优先用标准写法（COALESCE、CASE、FETCH FIRST、标准 JOIN）。
  • 为"以后可能要换库"过度设计：多数系统一辈子不换库，为此牺牲当前库的特性（比如不敢用 T-SQL 功能）通常得不偿失。

业务视角与技术视角 ​

  • 业务视角：选型是一次长期承诺——系统一旦上线，数据迁移成本远高于软件本身。老板关心的是：授权费、有没有人会维护、出了问题多久能恢复、客户（尤其是大客户）是否要求审计或指定数据库。信息化人员的价值是把这些翻译成清晰的对比，而不是推荐"自己最想学的那个"。
  • 技术视角：以 SQL Server 为主库，是你们当前栈的最优解；知识扩展方向依次为：Redis（缓存/锁）→ Oracle 差异（对接客户 ERP）→ PostgreSQL（开源备选）→ 时序库（设备数据）。数据库之间的数据交换，可通过 JSON-XML-YAML 之类的文件或接口，具体对接设计见 MES与ERP及设备的接口设计。

练习题与答案 ​

1. 公司要做一个设备点检 App，运行在车间的平板上，偶尔断网，数据量很小。适合用什么数据库？

答： 平板本地用 SQLite 存点检记录（零运维、断网可用），联网后再同步到服务器的 SQL Server。

2. 为什么说"把 MES 的过站记录放 Redis"是个坏主意？

答： 过站记录是必须永久保存和追溯的核心业务数据，要求事务和持久化，数据量也会持续增长；Redis 以内存为主，成本高且丢数据的风险大，也不支持复杂的联表与统计。Redis 适合缓存，不适合作主存储。

3. 你们的客户要求把质量数据同步到他们的 Oracle 库。你需要提前了解哪些差异？至少写出三点。

答： 例如：取前 N 条的写法（TOP vs FETCH FIRST）；字符串拼接（+ vs ||）；空字符串在 Oracle 中等于 NULL；自增列的实现（IDENTITY vs 序列/GENERATED）；日期函数不同；没有 SELECT 不带 FROM（需要 DUAL）。这些都 ⚠ 未在本机运行验证，细节见 Oracle与SQL-Server差异。

4. SQLite 往 INTEGER 列插入文字 'abc' 会怎样？SQL Server 呢？

答： SQLite 会成功，并把值按文本存下（实验 1 已实测）；SQL Server 会报错（我实测 DECLARE @x int = 'abc' 得到 Msg 245 Conversion failed when converting the varchar value 'abc' to data type int.）。

5. 预算为零、需要存 5 年约 5 亿行的生产数据，应该先排除哪个数据库？

答： 先排除 SQLite（单写者、不适合大并发）；SQL Server Express 的单库上限（新版 50 GB）可能也不够，要先估算 5 亿行的占用空间；PostgreSQL 或购买授权的 SQL Server 更合适。同时要评估分区/归档策略。

小结 ​

  • 业务系统默认选关系型；你们的栈里 SQL Server 是首选；Oracle 常见于客户/集团 ERP；PostgreSQL 是最强的开源替代；MySQL 偏互联网；SQLite 是嵌入式；Redis 做缓存；MongoDB 处理灵活结构。
  • 选型看五件事：数据形态、规模、一致性要求、授权预算、团队技能。
  • 系统里数据库种类越少越好，专用库只在关系库真正解决不了时才加。
  • 授权和免费版上限会变，决策前核对官网。
