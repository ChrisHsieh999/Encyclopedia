隔离级别与锁

AI 生成 · 待核对数据库SQL事务并发更新于 2026-10-21

本篇是数据库通用系列第 11 篇。读完你应该能：用生活例子讲清脏读、不可重复读、幻读；知道 SQL Server 的四个经典隔离级别各挡住什么；用两个 sqlcmd 会话亲眼看到阻塞（等待）、死锁（错误 1205）、丢失更新；会开启 READ_COMMITTED_SNAPSHOT 让读不再被写阻塞；懂得为什么"条件 UPDATE"是 MES 防并发的首选。所有输出都是在 SQL Server（LocalDB）里实际跑出来的。

一句话定义 ​

隔离级别规定：当多个事务同时操作同一批数据时，一个事务能"看到"别的事务做到一半的哪些结果；锁是数据库实现隔离的主要手段——谁先动了某行，就给它"上锁"，别人要么等待、要么看旧版本。

先修知识 ​

  • 事务与ACID：本篇讲的是 ACID 里的 I（隔离性）。
  • 并发与锁：操作系统层面"多个线程抢同一资源要加锁"的基本概念；数据库的锁是同一思想。
  • 死锁：两方互相等待对方释放资源。
  • SQL子查询与CTE 里的 Lab_Adv 库（用 WorkOrder 表）。

它解决什么问题 ​

工厂里多个终端、多个服务同时在读写同一批工单。如果完全不隔离：

  • A 正在改工单数量还没提交，B 就读到了这个"半成品"的数字（脏读）；
  • A 一个报表里连读两次同一行，两次结果不同（不可重复读）；
  • A 统计"待下发工单数"，过程中 B 又新建了一张，A 再统计就多了一张（幻读）；
  • A、B 同时"读数量→算新值→写回"，一个人的修改被另一个人覆盖（丢失更新）。

如果隔离得太狠（所有人排队），系统又慢。隔离级别就是在正确性和并发性能之间选一个平衡点。

核心概念 ​

三种读异常 ​

异常含义类比
脏读（Dirty Read）读到别人尚未提交、之后可能回滚的数据看到同事草稿上的数字，结果他撕了重写
不可重复读（Non-repeatable Read）同一事务里读同一行两次，值变了（被别人改后提交）你核对库存，核到一半同事改了数
幻读（Phantom Read）同一事务里按同一条件查两次，行数变了（别人插入/删除了符合条件的行）你数一遍待办单，同事又加了一张

SQL Server 的隔离级别 ​

级别脏读不可重复读幻读说明
READ UNCOMMITTED会会会读不加锁（等同 NOLOCK 提示）；最快、最不可靠
READ COMMITTED（默认）不会会会读时加短暂共享锁，读完即放；被别人未提交的修改挡住时会等待
REPEATABLE READ不会不会会读到的行锁到事务结束
SERIALIZABLE不会不会不会连"范围"一起锁，别人不能往这个范围插入
SNAPSHOT不会不会不会基于行版本：事务看到的是开始那一刻的快照，读不加锁

另外有一个数据库选项 READ_COMMITTED_SNAPSHOT（RCSI）：打开后，默认的 READ COMMITTED 级别改用行版本读，读不再被写阻塞，也不阻塞写。

锁的几个基本概念 ​

  • 共享锁（S）：读用的。多个事务可同时持有 S。
  • 排它锁（X）：写用的。X 与任何其他锁都不兼容。
  • 更新锁（U）：先读后写时用，避免两个人同时拿 S 再同时要 X 造成死锁。
  • 意向锁（IS/IX）：加在表上，表示"我下面有行被锁了"，方便快速判断冲突。
  • 粒度：行（KEY/RID）、页、表（OBJECT）。锁太多时会升级为表锁（锁升级）。

兼容规则一句话：读读不冲突，读写、写写冲突。

阻塞与死锁 ​

  • 阻塞（blocking）：A 持有 X 锁，B 想读/写同一行，B 就排队等 A 提交或回滚。这是正常现象，只要 A 的事务短，等一下就过去。
  • 死锁（deadlock）：A 等 B 持有的资源，B 又等 A 持有的，互相等死。数据库有个后台检测，发现后挑一个事务当牺牲品回滚，并向它报错误 1205，另一个事务继续。

实验准备 ​

沿用 Lab_Adv（见 SQL子查询与CTE）。先给 WorkOrder 加一条约束，使 DoneQty 不能超计划：

sql
ALTER TABLE WorkOrder ADD CONSTRAINT CK_WO_Done CHECK (DoneQty >= 0 AND DoneQty <= PlanQty);

重置脚本 reset.sql（每次实验前运行）：

sql
SET NOCOUNT ON;
UPDATE WorkOrder SET DoneQty = 120 WHERE WoNo = N'WO-002';
UPDATE WorkOrder SET DoneQty = 0   WHERE WoNo = N'WO-003';
DELETE WorkOrder WHERE WoNo LIKE N'WO-9%';

如何用两个会话做实验：每个实验有会话 A 的脚本和会话 B 的脚本。同时开两个命令行窗口，在第一个窗口运行 A，紧接着（几秒内）在第二个窗口运行 B：

sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -f 65001 -d Lab_Adv -i A1.sql
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -f 65001 -d Lab_Adv -i B1.sql

脚本里用 WAITFOR DELAY '00:00:0N'（等 N 秒）来安排先后顺序，所以只要两个窗口启动间隔很短就行。下面的"等待秒数"在你机器上可能差 1 秒。

逐步例子 ​

实验 1：脏读与阻塞 ​

A1.sql：改数量但不提交，持有 6 秒后回滚。

sql
SET NOCOUNT ON;
BEGIN TRAN;
UPDATE WorkOrder SET DoneQty = 250 WHERE WoNo = N'WO-002';
PRINT 'A: set DoneQty=250, not committed';
WAITFOR DELAY '00:00:06';
ROLLBACK;
PRINT 'A: ROLLBACK done';

B1.sql：2 秒后先用 READ UNCOMMITTED 读，再用默认的 READ COMMITTED 读，并记录等了几秒。

sql
SET NOCOUNT ON;
WAITFOR DELAY '00:00:02';
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT DoneQty AS ReadUncommitted FROM WorkOrder WHERE WoNo = N'WO-002';
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
DECLARE @t DATETIME2 = SYSDATETIME();
SELECT DoneQty AS ReadCommitted FROM WorkOrder WHERE WoNo = N'WO-002';
SELECT DATEDIFF(MILLISECOND, @t, SYSDATETIME()) / 1000 AS WaitedSeconds;

B 的实际输出：

ReadUncommitted
250
ReadCommitted
120
WaitedSeconds
4

解读：

  • READ UNCOMMITTED 立刻读到 250——一个后来被回滚、从未真正存在过的数字。这就是脏读。
  • READ COMMITTED 被 A 的 X 锁挡住，等了约 4 秒（从第 2 秒到 A 在第 6 秒回滚），读到的是回滚后真实的 120。

看到谁挡了谁：再开第三个会话 C，在 A 持有锁期间查系统视图：

sql
SET NOCOUNT ON;
WAITFOR DELAY '00:00:04';
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_resource
FROM sys.dm_exec_requests r WHERE r.blocking_session_id <> 0;
SELECT l.request_session_id AS spid, l.resource_type, l.request_mode, l.request_status
FROM sys.dm_tran_locks l
WHERE l.resource_database_id = DB_ID() AND l.resource_type IN ('KEY','RID','OBJECT')
ORDER BY l.request_session_id, l.resource_type;

实测输出（会话号每次不同）：

session_id blocking_session_id wait_type wait_resource
52 51 LCK_M_S KEY: 8:72057594047299584 (e51ea83a91c3)
spid resource_type request_mode request_status
51 KEY X GRANT
51 OBJECT IX GRANT
52 KEY S WAIT
52 OBJECT IS GRANT

读法：会话 52（B）被会话 51（A）阻塞；等待类型 LCK_M_S = 等一个共享锁；51 在那一行（KEY）上持有 X 锁（已授予 GRANT）；52 想要 S 锁，状态 WAIT。表上是意向锁（IX / IS）。线上排查"系统卡住"，第一件事就是查 blocking_session_id。

实验 2：不可重复读 ​

A2.sql（隔离级别可改）：同一事务读两次，中间间隔 5 秒。

sql
SET NOCOUNT ON;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- 之后改成 REPEATABLE READ 再测
BEGIN TRAN;
SELECT DoneQty AS FirstRead FROM WorkOrder WHERE WoNo = N'WO-002';
WAITFOR DELAY '00:00:05';
SELECT DoneQty AS SecondRead FROM WorkOrder WHERE WoNo = N'WO-002';
COMMIT;

B2.sql：2 秒后加 10 并提交，记录自己等了几秒。

sql
SET NOCOUNT ON;
WAITFOR DELAY '00:00:02';
DECLARE @t DATETIME2 = SYSDATETIME();
UPDATE WorkOrder SET DoneQty = DoneQty + 10 WHERE WoNo = N'WO-002';
SELECT DATEDIFF(MILLISECOND, @t, SYSDATETIME()) / 1000 AS UpdateWaitedSeconds;
A 的隔离级别A 第一次读A 第二次读B 的 UPDATE 等待
READ COMMITTED1201300 秒（直接成功）
REPEATABLE READ1201202 秒（被 A 挡住，等 A 提交）

READ COMMITTED 下 A 读完就放锁，B 随便改，A 的第二次读到 130——不可重复读。REPEATABLE READ 下 A 把读过的行一直锁到事务结束，B 的修改只能排队，A 两次读都是 120。代价是 B 被迫等待——隔离性越强，并发越差。

实验 3：幻读 ​

A3.sql：数"状态为 Created 的工单"两次。

sql
SET NOCOUNT ON;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- 之后改成 SERIALIZABLE 再测
BEGIN TRAN;
SELECT COUNT(*) AS FirstCount FROM WorkOrder WHERE Status = N'Created';
WAITFOR DELAY '00:00:05';
SELECT COUNT(*) AS SecondCount FROM WorkOrder WHERE Status = N'Created';
COMMIT;

B3.sql：2 秒后插入一张新的 Created 工单。

sql
SET NOCOUNT ON;
WAITFOR DELAY '00:00:02';
DECLARE @t DATETIME2 = SYSDATETIME();
INSERT WorkOrder (WoNo, ProductCode, PlanQty, DoneQty, Status, CreatedAt)
VALUES (N'WO-901', N'A100', 50, 0, N'Created', SYSDATETIME());
SELECT DATEDIFF(MILLISECOND, @t, SYSDATETIME()) / 1000 AS InsertWaitedSeconds;
A 的隔离级别第一次数第二次数B 的 INSERT 等待
REPEATABLE READ12（幻读）0 秒
SERIALIZABLE113 秒（被挡住，等 A 结束）

REPEATABLE READ 只锁"读到的那一行"，挡不住别人新插入符合条件的行；SERIALIZABLE 会锁住整个查询范围（键范围锁），把插入也挡在外面。

实验 4：丢失更新——"先读后写"的陷阱 ​

这是 MES 里最实用的一个实验。两个终端同时报工：A 报 10 件，B 报 20 件，起点 120，正确结果应为 150。

A4.sql（先读到变量，再算新值写回）：

sql
SET NOCOUNT ON;
DECLARE @q INT;
BEGIN TRAN;
SELECT @q = DoneQty FROM WorkOrder WHERE WoNo = N'WO-002';
PRINT 'A read ' + CAST(@q AS VARCHAR(10));
WAITFOR DELAY '00:00:04';                 -- 模拟程序处理时间
UPDATE WorkOrder SET DoneQty = @q + 10 WHERE WoNo = N'WO-002';
COMMIT;
SELECT DoneQty AS FinalA FROM WorkOrder WHERE WoNo = N'WO-002';

B4.sql：1 秒后做同样的事，加 20，不用等待。

sql
SET NOCOUNT ON;
WAITFOR DELAY '00:00:01';
DECLARE @q INT;
BEGIN TRAN;
SELECT @q = DoneQty FROM WorkOrder WHERE WoNo = N'WO-002';
PRINT 'B read ' + CAST(@q AS VARCHAR(10));
UPDATE WorkOrder SET DoneQty = @q + 20 WHERE WoNo = N'WO-002';
COMMIT;
SELECT DoneQty AS FinalB FROM WorkOrder WHERE WoNo = N'WO-002';

实际输出：

A: A read 120      FinalA = 130
B: B read 120      FinalB = 140

时序：A 读 120，B 读 120；B 先写 140 并提交；A 随后写 120+10=130，覆盖了 B 的结果。最终 DoneQty = 130（A 的 FinalA）——B 的 20 件丢了，正确应为 150。这就是丢失更新。

修法一：加 UPDLOCK，在读的时候就拿更新锁，别人读之前要等：把两个脚本里的 FROM WorkOrder 改成 FROM WorkOrder WITH (UPDLOCK)。实际输出：

A: A read 120      FinalA = 130
B: B read 130      FinalB = 150

B 的 SELECT 被 A 的更新锁挡住，等 A 提交后才读到 130，再加 20，得到正确的 150。

修法二（首选）：把计算放进 UPDATE 里，一条语句完成，这正是 工单管理 里的条件 UPDATE：

sql
UPDATE WorkOrder SET DoneQty = DoneQty + 10 WHERE WoNo = N'WO-002' AND DoneQty + 10 <= PlanQty;

实测（A 先开事务做 +10 并持有 4 秒，B 在 1 秒后做 +20）：B 等待 A 提交后执行，最终 150。单条 UPDATE 在读取、判断、修改的整个过程中一直持有行的 X 锁，中间插不进别人，不需要特别的隔离级别，也不需要先读到程序里。这就是 MES 里"把条件写进 WHERE"能防并发超报的根本原因。

实验 5：死锁与错误 1205 ​

死锁的经典造法：A 先锁 WO-002 再要 WO-003；B 先锁 WO-003 再要 WO-002。

A6.sql：

sql
SET NOCOUNT ON;
BEGIN TRAN;
UPDATE WorkOrder SET DoneQty = DoneQty + 1 WHERE WoNo = N'WO-002';
PRINT 'A locked WO-002';
WAITFOR DELAY '00:00:03';
UPDATE WorkOrder SET DoneQty = DoneQty + 1 WHERE WoNo = N'WO-003';
PRINT 'A got WO-003';
COMMIT;
PRINT 'A committed';

B6.sql（DEADLOCK_PRIORITY LOW 让它优先当牺牲品，结果可预期）：

sql
SET NOCOUNT ON;
SET DEADLOCK_PRIORITY LOW;
BEGIN TRAN;
UPDATE WorkOrder SET DoneQty = DoneQty + 1 WHERE WoNo = N'WO-003';
PRINT 'B locked WO-003';
WAITFOR DELAY '00:00:03';
UPDATE WorkOrder SET DoneQty = DoneQty + 1 WHERE WoNo = N'WO-002';
PRINT 'B got WO-002';
COMMIT;
PRINT 'B committed';

实际输出：

A: A locked WO-002 / A got WO-003 / A committed
B: B locked WO-003
   Msg 1205, Level 13, State 51, ...
   Transaction (Process ID 52) was deadlocked on lock resources with another process and has been chosen as the deadlock victim. Rerun the transaction.

3 秒后双方各自去要对方的锁，成了环：数据库检测到后让 B 当牺牲品，B 的事务被整个回滚（所以 WO-003 没被改），A 顺利完成。事后检查：WO-002 的 DoneQty = 121（A 的 +1），WO-003 = 1（A 的 +1，B 的没有）。

**解决死锁最有效的办法：所有事务按相同顺序访问资源。**把 B 改成也先锁 WO-002、再锁 WO-003（B7.sql），重跑，输出：

A: A locked WO-002 / A got WO-003 / A committed
B: B locked WO-002 first / B committed

B 在第一步就被 A 挡住，排队等 A 提交，再接着执行——没有环，也就没有死锁。

程序里怎么处理 1205：它是"可重试"的错误。在 C# 里捕获 SqlException，Number == 1205 时短暂等待后重新执行整个事务，一般重试 2–3 次。

实验 6：READ COMMITTED SNAPSHOT——读不再被写阻塞 ​

打开数据库选项（需要独占，ROLLBACK IMMEDIATE 会踢掉别的连接，只在练习库上做）：

sql
ALTER DATABASE Lab_Adv SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE Lab_Adv SET ALLOW_SNAPSHOT_ISOLATION ON;

再跑一遍实验 1（A1 + B1）。B 的输出：

ReadUncommitted
250
ReadCommitted
120
WaitedSeconds
0

默认的 READ COMMITTED 不再等待（0 秒），立刻读到 A 修改前、已提交的 120——它读的是"行的旧版本"。同时仍然没有脏读。（READ UNCOMMITTED 照旧读到 250，那是它自己的选择。）

代价：旧版本存放在 tempdb 里，写入多的库要关注 tempdb 空间。写与写之间仍然互相阻塞，RCSI 只解决"读被写挡住"。很多读多写多的业务库会开启 RCSI。

SNAPSHOT 隔离需要在会话里显式使用，它保证事务内读到的始终是事务开始时的快照；如果你要修改的行在你开始之后被别人改过，会报错误 3960（更新冲突），事务被中止，应用要重试。实测：

sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRAN;
SELECT DoneQty FROM WorkOrder WHERE WoNo = N'WO-002';    -- 120
WAITFOR DELAY '00:00:04';                                -- 此时另一会话把它改成 140 并提交
SELECT DoneQty FROM WorkOrder WHERE WoNo = N'WO-002';    -- 仍是 120（快照）
UPDATE WorkOrder SET DoneQty = DoneQty + 10 WHERE WoNo = N'WO-002';   -- 报 3960

实际输出两次读都是 120，UPDATE 报 Msg 3960 ... Snapshot isolation transaction aborted due to update conflict ...，最终库里是另一会话写的 140。实验结束后用 ALTER DATABASE Lab_Adv SET ALLOW_SNAPSHOT_ISOLATION OFF; ALTER DATABASE Lab_Adv SET READ_COMMITTED_SNAPSHOT OFF WITH ROLLBACK IMMEDIATE; 恢复。

动手实验 ​

  1. 建好 Lab_Adv 和约束，保存 reset.sql。
  2. 逐个完成实验 1 到 6，每个实验前运行 reset.sql。每次都写下你看到的数字，与本篇对照。
  3. 用实验 1 的 A 脚本，另开一个窗口手动运行 SELECT * FROM sys.dm_tran_locks WHERE resource_database_id = DB_ID('Lab_Adv');，观察锁的种类。
  4. 挑战：把实验 4 的 WAITFOR 去掉（模拟"程序处理很快"），丢失更新还会发生吗？（会变得很少见但理论上仍可能——并发 bug 的可怕之处就在于"测试时不出、上线偶发"。）

常见坑与排查 ​

现象原因 / 办法
系统突然卡住，很多请求在等有一个事务没结束并持有锁。查 sys.dm_exec_requests.blocking_session_id 找到源头；DBCC OPENTRAN 看最老的未结事务
滥用 WITH (NOLOCK) 提速等于 READ UNCOMMITTED：会读到脏数据，甚至漏读/重复读行。报表可以接受少量误差时才用；更好的办法是开 RCSI
偶发错误 1205死锁。统一访问资源的顺序、缩短事务、给常用查询加合适索引（减少锁住的行数，见 数据库索引）、应用层捕获 1205 重试
"先查后改"在多终端下偶发数据错丢失更新。改成条件 UPDATE，或 UPDLOCK，或乐观并发（版本号列）
开了 SERIALIZABLE，系统很慢、死锁多锁范围太大。只在必要的短事务里使用
开 RCSI 后 tempdb 变大行版本存放在 tempdb。避免长事务，监控 tempdb
事务里调了外部接口，一直占着锁事务内别做耗时/不可控操作，见 事务与ACID

业务视角与技术视角 ​

  • 业务视角：工厂里多个报工终端、扫码枪、看板、ERP 接口同时在读写工单、库存、条码状态。要杜绝的业务事故：超报（完成数量大于计划）、同一物料被两个工单重复领用、同一条码被重复过站。
  • 技术视角：首选"条件 UPDATE + 受影响行数"（原子、短、不依赖隔离级别）；其次是短事务 + 统一加锁顺序避免死锁；报表和看板用 RCSI 或快照，不要靠 NOLOCK；程序里对 1205 做有限次重试。READ COMMITTED 是 SQL Server 默认，已满足大多数业务。

练习题与答案 ​

  1. 实验 2 中，为什么 REPEATABLE READ 能挡住不可重复读，却挡不住幻读？
  2. 打开 RCSI 后，还会不会有"写阻塞写"？
  3. 两个事务分别按 (WO-002, WO-003) 与 (WO-003, WO-002) 顺序更新，会发生什么？怎么避免？
  4. 为什么 UPDATE ... SET DoneQty = DoneQty + 10 比"先 SELECT 到程序、再 UPDATE ... SET DoneQty = @q + 10"安全？

答案

  1. REPEATABLE READ 锁住的是已经读到的行，别人不能改或删它们（所以不可重复读被挡住）；但别人仍可插入新行满足你的查询条件，这些新行你的锁没覆盖到，所以幻读还在。SERIALIZABLE 才会锁范围。
  2. 会。RCSI 只让读走行版本；两个事务改同一行仍要排队（X 锁互斥）。
  3. 有死锁风险（实验 5 已复现，其中一个收到 1205 并被回滚）。避免：所有事务按同样顺序（如工单号升序）加锁。
  4. 前者读取、计算、写入在同一条语句里、持续持有行的 X 锁，别的会话插不进来；后者读和写之间有时间窗口，别人可能已经改过值，写回时就覆盖了别人的结果（实验 4：最终 130 而不是 150）。

小结 ​

  • 三种异常：脏读、不可重复读、幻读；SQL Server 默认 READ COMMITTED 只挡脏读。
  • 读读不冲突，读写、写写冲突；冲突的结果是阻塞，互相等待则是死锁（1205，要重试）。
  • 解决方案：条件 UPDATE、短事务、统一加锁顺序、合适的索引、RCSI/快照隔离。
  • 丢失更新是"先读后写"的典型 bug，MES 报工要用条件 UPDATE 避免。
