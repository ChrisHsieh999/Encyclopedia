执行计划与SQL优化

AI 生成 · 待核对数据库SQL-Server性能更新于 2026-10-21

本篇是 数据库 通用部分的第 14 篇。示例用 SQL Server（T-SQL），所有数字都来自本机 SQL Server 2025 LocalDB 上 50 万行数据的实测；"看执行计划、SARGable、常见慢查询模式"的思路对 Oracle、PostgreSQL 同样适用，但命令不同。读完你应该能：解释"执行计划"是什么；用 SET STATISTICS IO 和 SHOWPLAN 看出一条查询慢在哪里；区分 Index Seek、Index Scan、Key Lookup；写出 SARGable（能用上索引）的条件；认出八种常见慢查询写法并改好它。

⚠ 待核对：隐式转换那一节里"Windows 排序规则下有时仍能 seek"、以及 SqlSugar/Dapper 默认把 C# string 传成 nvarchar 参数这两点，是我的已有知识，没有在本机实测；其余结论和数字都是本机实际跑出来的。

一句话定义 ​

执行计划（Execution Plan） 是数据库在运行一条 SQL 之前，由查询优化器（Query Optimizer） 决定的"怎么拿数据"的具体步骤：先走哪个索引、表怎么连接、要不要排序。SQL 只说"要什么"，执行计划决定"怎么拿"；SQL 优化就是让优化器有机会选到又快又省的那条路。

先修知识 ​

  • SQL基础查询、SQL连接JOIN：会写 WHERE、JOIN。
  • 数据库索引：知道索引是什么、聚集索引和非聚集索引的区别。最简版：聚集索引就是表本身按主键排好序存放；非聚集索引是另一棵小的"目录树"，里面记着"索引列的值 → 对应行在哪"。
  • 用 sqlcmd 或 SSMS 连上 LocalDB（见 SQL-Server）。

它解决什么问题 ​

同一份数据、同一句话意思的 SQL，可以差几百倍速度。比如工厂的"工位过站记录表"几个月下来有几十万、几百万行，白天看板每隔几秒查一次"某条产线今天的过站数"：

  • 查询写得好、有合适索引：几毫秒；
  • 写得不好：每次翻遍整张表，几秒甚至更久，看板一刷新服务器就卡，其他程序也跟着慢。

没有办法靠"凭感觉"调优：必须能看见数据库实际是怎么执行的、读了多少数据。执行计划就是这面镜子。

核心概念 ​

优化器怎么决定 ​

  1. 你提交 SQL。
  2. 优化器根据统计信息（Statistics） 估算"满足条件的大概有多少行"（详见 SQL-Server索引与统计信息）。
  3. 对候选方案算一个"成本"，选最低的，生成执行计划。
  4. 执行，并把计划缓存起来供下次复用。

所以优化器是"估算 + 选最便宜"，不是"永远选索引"。估得不准（统计信息过期）、写法让它没法用索引，都会选出差的计划。

怎么看执行计划 ​

方法说明
SSMS：Ctrl+L显示预估计划（不执行查询）
SSMS：Ctrl+M 后执行显示实际计划（执行后，带真实行数）
SET SHOWPLAN_TEXT ON命令行里看预估计划的文字树，不执行查询；必须独占一个批（前后加 GO）
SET STATISTICS IO ON执行并报告每张表读了多少页（logical reads，逻辑读）
SET STATISTICS TIME ON报告 CPU 时间和耗时

怎么读逻辑读：SQL Server 把数据存成 8 KB 的页（Page），一次"逻辑读"就是读了内存里的一页。耗时会受缓存、机器负载影响而抖动，逻辑读几乎不变，所以做前后对比时优先比逻辑读。

计划里最常见的几个操作 ​

操作含义好坏
Clustered Index Scan / Table Scan把整张表（或整个聚集索引）从头读到尾表大而只要几行时很差
Index Scan把一个非聚集索引从头读到尾同上，只是索引比表窄
Index Seek沿着索引树直接定位到起点，只读需要的那段通常最好
Key Lookup（键查找）非聚集索引里找到了行，但缺少需要的列，要回聚集索引再取一次行数多时很贵
Nested Loops对一边的每一行去另一边查找适合一边很小
Hash Match / Merge Join另两种连接方式，适合大批量看数据量
Sort排序数据多时要消耗内存，可能溢出到磁盘

Seek 与 Scan 的类比：Seek 像先翻字典目录定位到"S"开头，再顺着往下读；Scan 像把整本字典从第一页读到最后一页找词。

SARGable：能用上索引的写法 ​

SARGable（Search ARGument-able）：指 WHERE 里的条件写成优化器能拿去直接在索引上定位的形式。核心规则只有一条：

索引列要原样放在比较符号的一边；计算、函数、转换都放到另一边。

不 SARGableSARGable原因
WHERE YEAR(CreatedAt) = 2026 AND MONTH(CreatedAt) = 10WHERE CreatedAt >= '2026-10-01' AND CreatedAt < '2026-11-01'函数包住了列，索引是按 CreatedAt 原值排的，不是按"年"排的
WHERE Amount * 2 = 100WHERE Amount = 50列参与了运算
WHERE OrderNo LIKE '%2500'WHERE OrderNo LIKE 'SO02500%'前面有通配符，没法从某个位置开始找
WHERE ISNULL(Status, 0) = 1WHERE Status = 1（并处理 NULL）函数包住了列
列是 varchar，参数是 nvarchar参数类型和列类型一致隐式转换作用在列上

逐步例子 ​

准备一张 50 万行的订单表 SalesOrder（Id 主键聚集索引，另有 OrderNo varchar(20)、CustomerId、Amount、CreatedAt、Status 等列）。聚集索引共约 3958 页。其中 CustomerId = 77 的有 100 行。

目标：查 CustomerId = 77 的订单号和金额。

  • 没有索引：只能全表扫描，读 3958 页（几乎整张表）。
  • 在 CustomerId 上建非聚集索引：用 Index Seek 找到 100 个主键，再逐个回聚集索引取 OrderNo、Amount（Key Lookup）。读 318 页，约是之前的 8%。可见每次 Key Lookup 要多读 2～3 页。
  • 建覆盖索引（把 OrderNo、Amount 也放进索引的 INCLUDE 里）：索引本身就含查询所需全部列，不用回表，读 3 页。

覆盖索引（Covering Index） 的意思是：一个索引已经"覆盖"了某条查询要用的所有列，所以只读索引就够了。

动手实验 ​

前提：LocalDB + sqlcmd。实验建临时库 Lab_Ops（含 50 万行，约几十 MB），结束时删除，不碰其它库。把下面各步依次存入一个文件 ops2.sql（UTF-8），运行：

sqlcmd -S "(localdb)\MSSQLLocalDB" -E -I -f 65001 -y 200 -i ops2.sql -o ops2.out

输出很长（A、B、C 每次会打印 100 行结果）。用 PowerShell 只抽出关键行：

Select-String -Path .\ops2.out -Pattern '===|logical reads' | ForEach-Object { $_.Line -replace ', physical reads.*','' }

-y 200 限制可变宽度列的显示宽度（与 -W 不能同时用）。逻辑读数字在你的机器上应与下面完全一致或非常接近（表是确定性生成的）；页数可能因版本略有差别。

第 3 步（B）：建索引，再看。

sql
PRINT N'=== B. 建索引后 ===';
GO
SET STATISTICS IO OFF;
CREATE INDEX IX_SalesOrder_CustomerId ON dbo.SalesOrder(CustomerId);
SET STATISTICS IO ON;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WHERE CustomerId = 77;
GO
SET SHOWPLAN_TEXT ON;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WHERE CustomerId = 77;
GO
SET SHOWPLAN_TEXT OFF;
GO

关键输出：

Table 'SalesOrder'. Scan count 1, logical reads 318
       |--Index Seek(OBJECT:([...].[IX_SalesOrder_CustomerId]), SEEK:([...].[CustomerId]=(77)) ORDERED FORWARD)
       |--Clustered Index Seek(OBJECT:([...].[PK__SalesOrd__...]), SEEK:([...].[Id]=[...].[Id]) LOOKUP ORDERED FORWARD)

两个 Seek：第一个在新索引里找 CustomerId=77，第二个带 LOOKUP 字样，就是 Key Lookup，回表取 OrderNo、Amount。读 318 页（3958 → 318）。

第 4 步（C）：覆盖索引。

sql
PRINT N'=== C. 覆盖索引（INCLUDE）===';
GO
SET STATISTICS IO OFF;
CREATE INDEX IX_SalesOrder_CustomerId_Cover ON dbo.SalesOrder(CustomerId) INCLUDE (OrderNo, Amount);
SET STATISTICS IO ON;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WHERE CustomerId = 77;
GO
SET SHOWPLAN_TEXT ON;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WHERE CustomerId = 77;
GO
SET SHOWPLAN_TEXT OFF;
GO
DROP INDEX IX_SalesOrder_CustomerId ON dbo.SalesOrder;
GO

关键输出：

Table 'SalesOrder'. Scan count 1, logical reads 3
  |--Index Seek(OBJECT:([...].[IX_SalesOrder_CustomerId_Cover]), SEEK:([...].[CustomerId]=CONVERT_IMPLICIT(int,[@1],0)) ORDERED FORWARD)

只剩一个 Index Seek，没有 Lookup，3 页。3958 → 318 → 3，这就是索引设计的威力。代价是索引占更多空间、每次写数据要多维护一份。（最后那句 DROP INDEX 去掉旧索引，避免干扰后面的对比；优化器会选更便宜的覆盖索引，旧的没必要留。）

YEAR(CreatedAt)=2026 AND MONTH(CreatedAt)=10Index Scan ... WHERE:(datepart(year,...)=(2026) AND datepart(month,...)=(10))994
CreatedAt >= '2026-10-01' AND CreatedAt < '2026-11-01'Index Seek ... SEEK:(CreatedAt > ... AND CreatedAt < ...)61

同样的结果，读的页差了 16 倍。第一种写法对每一行先算 YEAR() 再比较（Scan），第二种直接在索引里定位到 10 月 1 日那个位置读到 11 月 1 日为止（Seek）。**范围写成"大于等于起点、小于终点"（左闭右开）**是处理日期区间最稳的习惯，也避免了 BETWEEN ... 23:59:59 漏掉最后一秒内数据的问题。

第 6 步（E）：隐式转换。

sql
PRINT N'=== E. 隐式转换：varchar 列 vs nvarchar 参数 ===';
GO
SET STATISTICS IO OFF;
CREATE UNIQUE INDEX IX_SalesOrder_OrderNo ON dbo.SalesOrder(OrderNo);
SET STATISTICS IO ON;
GO
DECLARE @a varchar(20) = 'SO0250000';
SELECT Id, Amount FROM dbo.SalesOrder WHERE OrderNo = @a;
GO
DECLARE @b nvarchar(20) = N'SO0250000';
SELECT Id, Amount FROM dbo.SalesOrder WHERE OrderNo = @b;
GO

两个都返回 Id=250000 这一行，但：

-- @a varchar：    Scan count 0, logical reads 6
-- @b nvarchar：   Scan count 1, logical reads 1430

再看 @b 版本的预估计划（单独运行 SET SHOWPLAN_TEXT ON 后执行）：

|--Nested Loops(Inner Join, ...)
     |--Index Scan(OBJECT:([...].[IX_SalesOrder_OrderNo]), WHERE:(CONVERT_IMPLICIT(nvarchar(20),[...].[OrderNo],0)=[@b]))
     |--Clustered Index Seek(... LOOKUP ...)

CONVERT_IMPLICIT(nvarchar(20), [OrderNo], 0)：数据库悄悄把列转成了 nvarchar 再比较。SQL Server 有一条"数据类型优先级"规则：两边类型不同时，低优先级的转成高优先级的，nvarchar 比 varchar 优先级高，所以被转的是列，于是索引用不上，退化成 Index Scan（本机的数据库用的是 SQL 排序规则 SQL_Latin1_General_CP1_CI_AS；换成 Windows 排序规则时，优化器有时仍能 seek，这一点我没有实测）。

这和你写 C# 的关系很大：C# 的 string 默认会被很多库当作 nvarchar 参数传给数据库。如果表里的编码列是 varchar（例如条码、工单号这类纯英文数字），就会踩到这个坑。我没有在本机实测 SqlSugar/Dapper 的默认参数类型，若怀疑，可以用 SQL Server Profiler 或 Extended Events（见 SQL-Server常用运维）抓到真实发出的语句，看参数类型是 nvarchar 还是 varchar。

第 7 步（F、G）：前导通配符和深翻页。

sql
PRINT N'=== F. LIKE 前导通配符 ===';
GO
SELECT COUNT(*) AS Cnt FROM dbo.SalesOrder WHERE OrderNo LIKE 'SO02500%';
GO
SELECT COUNT(*) AS Cnt FROM dbo.SalesOrder WHERE OrderNo LIKE '%2500';
GO
PRINT N'=== G. 分页：深翻页 ===';
GO
SELECT Id, OrderNo FROM dbo.SalesOrder ORDER BY Id OFFSET 400000 ROWS FETCH NEXT 20 ROWS ONLY;
GO
SELECT Id, OrderNo FROM dbo.SalesOrder WHERE Id > 400000 ORDER BY Id OFFSET 0 ROWS FETCH NEXT 20 ROWS ONLY;
GO
查询结果逻辑读
LIKE 'SO02500%'（后面通配）100 行3
LIKE '%2500'（前面通配）50 行1427
OFFSET 400000 ROWS FETCH NEXT 20（跳过 40 万行）取到 Id 400001～4000203164
WHERE Id > 400000 ... FETCH NEXT 20（记住上一页最后的 Id，"键集分页"）同样 Id 400001～4000203

深翻页用 OFFSET 慢，是因为数据库必须先数过前 40 万行再丢掉；"键集分页（Keyset Pagination）"记住上一页最后一行的主键，下一页直接从那里往后取，翻到第几页成本都一样。

第 8 步（H）：索引不是越多越好。

sql
PRINT N'=== H. 选择性差的索引，优化器不用 ===';
GO
SET STATISTICS IO OFF;
CREATE INDEX IX_SalesOrder_Status ON dbo.SalesOrder(Status);
SET STATISTICS IO ON;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WHERE Status = 1;
GO
SELECT Id, OrderNo, Amount FROM dbo.SalesOrder WITH (INDEX(IX_SalesOrder_Status)) WHERE Status = 1;
GO

Status 只有 0～3 四种值，每种占 25%（12.5 万行）。结果：

-- 优化器自己选：   logical reads 3958  （Clustered Index Scan，无视了新索引）
-- 用 WITH (INDEX(...)) 强制走索引：  logical reads 382995

强制走索引读了 38 万页，是全表扫描的约 97 倍。原因：走索引要对 12.5 万行各做一次 Key Lookup（每次 2～3 页），远比顺序扫一遍表贵。优化器根据统计信息知道"这个值占 25%"，所以聪明地选了扫描。区分度（选择性）很低的列单独建索引通常没用，只会拖慢写入。

第 9 步（I）：找出最耗资源的语句，然后清理。

sql
SET STATISTICS IO OFF;
PRINT N'=== I. 找最耗资源的语句 ===';
GO
SELECT TOP (4)
       qs.execution_count AS Runs,
       qs.total_logical_reads AS Reads,
       REPLACE(REPLACE(LEFT(st.text, 70), CHAR(13), ' '), CHAR(10), ' ') AS SqlText
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
WHERE st.text LIKE N'%SalesOrder%' AND st.text NOT LIKE N'%dm_exec_query_stats%'
ORDER BY qs.total_logical_reads DESC;
GO
USE master;
GO

GO

常见坑与排查 ​

下面八种写法在真实项目里最常见，按"现象 → 原因 → 改法"：

#写法原因改法
1WHERE YEAR(列)=...、WHERE CONVERT(varchar, 列, 23)='2026-10-01'函数包住列改成范围条件（左闭右开）
2列 varchar，参数 nvarchar（或相反）隐式转换作用在列上参数类型对齐列类型；C# 里显式指定 DbType.AnsiString
3LIKE '%关键字%'前导通配符，没法用索引定位业务允许时改前缀匹配；确实要全文搜索用全文索引
4SELECT *多取了不需要的列，覆盖索引失效，要大量 Key Lookup只写需要的列
5OFFSET 大数字 深翻页要数过再丢弃键集分页
6对低区分度列（状态、性别）单独建索引优化器不会用，只拖慢写入和高区分度列组合成复合索引，或用筛选索引
7统计信息过期优化器估错行数，选错计划（详见 SQL-Server索引与统计信息）更新统计信息
8应用里循环调用：先查 100 张工单，再对每张工单各查一次明细（"N+1"）101 次往返数据库，每次都有网络和解析开销一次 JOIN 或 WHERE Id IN (...) 取回

此外：

  • 参数嗅探（Parameter Sniffing）：存储过程第一次执行时，优化器按当时传入的参数值生成计划并缓存；之后不同参数值复用这个计划。数据分布不均时（例如 99% 订单是客户 A、1% 是客户 B），同一个计划对一部分参数很慢。常见缓解办法：OPTION (RECOMPILE)（每次重新编译）、OPTION (OPTIMIZE FOR UNKNOWN)；SQL Server 2022 起的"参数敏感计划优化"在所有版本里默认提供一定自动缓解（据微软 2025 版功能对比表，该功能在 Enterprise、Standard、Express 均为 Yes，详细行为请查文档）。
  • 别只信一次测试：第一次运行包含"编译计划"和"把数据读进内存"的开销，第二次才是稳态。比较逻辑读最可靠。
  • LocalDB/Express 的限制：和 Standard、Enterprise 相比，Express 用的内存和 CPU 核数有限（Express 版缓冲池约 1410 MB、1 个 socket 或 4 核，数据库最大 50 GB，据微软 2025 版文档），小数据看不出差别，大数据量的结论请在接近生产的环境验证。

业务视角与技术视角 ​

业务视角：MES 的实时看板、追溯查询（"这块板的所有过站记录"）是典型的"高频 + 大表"场景，也是最容易在工厂数据量增长几个月后突然变慢的地方。把"用户在页面上点查询"翻译成"数据库读了多少页"，是 IT 排查"为什么系统越用越慢"的基本功。

技术视角：

  • 排查顺序：先抓到慢语句（sys.dm_exec_query_stats / Query Store / 应用日志，见 日志） → 看执行计划找到 Scan 或大量 Lookup → 判断是缺索引、写法问题还是统计信息问题 → 改 → 用逻辑读复测。
  • C# + SqlSugar：SqlSugar 能输出它生成的 SQL（Aop.OnLogExecuting），把那条 SQL 拿到 SSMS 看计划，是最实用的组合。参数类型问题见上面第 6 步。
  • 索引不是万能：每个索引都要占空间并拖慢 INSERT/UPDATE/DELETE；先找"最慢最频繁的那几条"针对性地建，不要给每一列都建。

练习题与答案 ​

1. 为什么说"优化器不是永远选索引"？

答：优化器按统计信息估算成本。如果条件命中的行占比很高（如第 8 步的 25%），走索引需要大量 Key Lookup，反而比顺序扫描贵，所以它会选扫描。

2. 把 WHERE CAST(CreatedAt AS date) = '2026-10-20' 改成 SARGable 的写法。

答：WHERE CreatedAt >= '2026-10-20' AND CreatedAt < '2026-10-21'。（注：SQL Server 对 CAST(列 AS date) 有特殊处理，有时仍能用索引，但这种优化不可依赖，范围写法在任何数据库里都稳。）

3. 第 3 步里为什么 Key Lookup 让读页数是 318 而不是 100 × 1？

答：每个 Key Lookup 要沿着聚集索引树从根走到叶，通常读 2～3 页（具体层数取决于表大小）；加上在非聚集索引里读 100 个主键本身的页，合计 318。

4. 一个页面按"客户 + 日期范围"查订单，应该建 (CustomerId, CreatedAt) 还是 (CreatedAt, CustomerId)？

答：(CustomerId, CreatedAt)。复合索引先按第一列排序，第一列内再按第二列排序。条件是"客户 = 具体值 + 日期是范围"时，先用等值列定位到一小段，再在这一小段内顺着日期范围读；反过来，先按日期范围会扫出一大片，再逐条过滤客户。规则：等值条件的列放前面，范围条件的列放后面。

5. 上线后看板变慢，你手上只有这条 SQL，怎么确认是不是隐式转换导致？

答：在 SSMS 里显示它的实际执行计划，看 Index Scan 或 Seek 谓词里有没有 CONVERT_IMPLICIT，并且 SSMS 常会在运算符上给出黄色警告图标；命令行里用 SET SHOWPLAN_TEXT ON 搜 CONVERT_IMPLICIT。

小结 ​

  • 执行计划是优化器选出的"怎么拿数据"的步骤；用 SET STATISTICS IO 比逻辑读，用 SHOWPLAN 看 Seek/Scan/Lookup。
  • Seek 是定位，Scan 是通读，Key Lookup 是回表；覆盖索引可以消灭 Lookup。
  • SARGable：索引列原样放一边，别包函数、别运算、别隐式转换、别前导通配符。
  • 区分度低的列单独建索引无益；深翻页用键集分页；应用里避免 N+1。
  • 本机实测：3958 → 318 → 3 页（索引与覆盖）、994 → 61 页（SARGable）、1430 → 6 页（类型对齐）。
