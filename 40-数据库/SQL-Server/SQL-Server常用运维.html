SQL-Server常用运维

AI 生成 · 待核对数据库SQL-Server运维更新于 2026-10-21

⚠ 待核对：Profiler（SQL Server Profiler）在 Express 版本不可用，只能由 Standard/Enterprise 的 Profiler 去跟踪 Express（据微软 2025 版功能对比表），所以我没有在本机运行 Profiler，只讲了概念；Extended Events 和 Query Store 则在本机运行过。"Profiler/SQL Trace 已被 Extended Events 取代、不建议新用"是我的已有知识，请以微软文档为准。权限一节里的角色名（db_datareader 等）和登录类型是通用知识，没有逐项实测，只实测了 CREATE LOGIN/GRANT/EXECUTE AS 的效果。

本篇是 SQL-Server 目录的第 4 篇。读完你应该能：在系统慢或"卡住"时找出是谁堵了谁，并知道怎么处理；查看库和日志的大小，明白为什么日志会涨爆、怎么收；理解排序规则和"varchar 里的中文变成问号"的原因；知道用 Extended Events 和 Query Store 追踪问题；会建登录名、用户并授予最小权限。

一句话定义 ​

这是 DBA（数据库管理员）和后端开发在日常中最常碰到的"系统体检与急救"操作合集：看连接与阻塞、看空间、处理日志、理解字符集规则、做性能追踪、管权限。

先修知识 ​

  • 事务与ACID、隔离级别与锁：知道事务会持有锁、别的会话要改同一行就得等待。简化理解：A 在改一行时，这一行被"上了锁"，B 要改同一行就排队。
  • 备份与恢复：知道事务日志与恢复模式（FULL/SIMPLE）。
  • 字符编码：知道 ASCII、GBK、Unicode(UTF-8/UTF-16)的区别。
  • SQL-Server：会用 sqlcmd 连接 LocalDB。

它解决什么问题 ​

典型"救火"场景：

  • 车间扫码报工一直转圈，查不出原因——其实是一个会话开了事务没提交，堵住了所有要改同一工单的人（阻塞）。
  • 服务器磁盘红了，一查是 SQL Server 的日志文件涨到了几十 GB（日志膨胀）。
  • 往表里存"焊接"，读出来是"??"（排序规则/varchar 问题）。
  • 开发抱怨"这条 SQL 偶尔很慢，但复现不了"（需要追踪）。
  • 新同事需要查数据但不该有修改权限（权限）。

核心概念 ​

连接、请求与阻塞 ​

  • 会话（Session）：一个客户端的一次连接，有一个 session_id（用户会话一般 > 50）。
  • 请求（Request）：会话当前正在执行的一条语句。
  • 阻塞（Blocking）：会话 A 持有锁，会话 B 想要冲突的锁就得等待，B 被 A "阻塞"。blocking_session_id 列告诉你 B 在等谁。链条最前面、自己不被任何人堵的那个叫头号阻塞者（Head Blocker），处理它就能放开一串。
  • 死锁（Deadlock）：A 等 B、B 又等 A，互相等死。SQL Server 会自动选一个"牺牲者"回滚（错误号 1205）。与阻塞不同：阻塞只要等对方结束就会解除，死锁无法自行解除。详见 死锁。

三个常用视图：

视图看什么
sys.dm_exec_sessions所有会话：谁登录的、从哪台机器、状态、开着几个事务
sys.dm_exec_requests正在执行的请求：执行了多久、等什么（wait_type）、被谁堵（blocking_session_id）
sys.dm_tran_locks谁持有、谁在等哪些锁
sys.dm_exec_sql_text(sql_handle)把请求关联到 SQL 文本

常见的 wait_type：LCK_M_X（等排他锁，典型阻塞）、LCK_M_S（等共享锁）、PAGEIOLATCH_*（等磁盘读）、WAITFOR（主动等待，不是问题）。

数据库与日志大小 ​

一个库至少有两种文件：数据文件（.mdf/.ndf，存表和索引）和日志文件（.ldf，事务日志）。工具：

  • EXEC sp_spaceused：当前库的总大小、已分配、未分配、数据/索引占用；
  • sys.database_files：当前库每个文件的大小（单位是 8 KB 页）和增长设置；
  • sys.master_files：整个实例所有库的文件（需要看全局时用）；
  • DBCC SQLPERF(LOGSPACE)：每个库的日志大小和已用百分比。

日志文件膨胀 ​

事务日志是"流水账"。只有当日志中的一段不再被需要时，这段空间才能被重复使用（称为"截断"，不是缩小文件）。什么情况下日志不被需要：

  • SIMPLE 模式：事务提交后遇到检查点就可以重用；
  • FULL 模式：必须做过日志备份才能重用；
  • 另外有长事务没提交、复制/可用性组还没消费等原因也会拖住日志。

sys.databases.log_reuse_wait_desc 会告诉你"日志现在为什么不能重用"：NOTHING（没有障碍）、LOG_BACKUP（等日志备份）、ACTIVE_TRANSACTION（有未提交的长事务）等。看到日志大，先看这一列。

处理顺序：先弄清原因 → 解决根因（做日志备份、结束长事务、改模式）→ 最后才考虑 DBCC SHRINKFILE 缩小文件（缩小文件只是一次性手术，不解决根因；经常缩小再涨会产生碎片和性能抖动）。

排序规则（Collation）与 varchar 中文 ​

排序规则决定两件事：字符串怎么比较、排序（区分大小写吗？区分重音吗？），以及 varchar 列用哪个代码页存储字符。

名字拆开看，如 SQL_Latin1_General_CP1_CI_AS：

片段含义
SQL_老式 SQL 排序规则（相对于 Windows 排序规则，如 Chinese_PRC_CI_AS）
Latin1_General西欧语言字母顺序
CP1代码页 1252（西欧字符集）
CICase Insensitive，不区分大小写（CS 区分）
ASAccent Sensitive，区分重音（AI 不区分）
_UTF8 后缀该排序规则让 varchar 用 UTF-8 编码存储（SQL Server 2019 起）

关键事实：

  • varchar(n)：按排序规则的代码页存，每字符 1 或 2 字节。西欧代码页 1252 里没有汉字，所以存汉字时被替换成 ?。
  • nvarchar(n)：始终用 UTF-16 存，每字符 2 字节（极少数字符 4 字节），能存所有 Unicode 字符，包括汉字，字面量要写 N'焊接'（N 前缀）。
  • 因此：含中文的列用 nvarchar，字面量加 N。这也是本知识库 MES 系列的约定。
  • 比较两个排序规则不同的字符串（如跨库、临时表对库）会报"无法解决排序规则冲突"；解决：在比较时显式 COLLATE 某规则。
  • LocalDB 的实例排序规则固定为 SQL_Latin1_General_CP1_CI_AS，不能改（据微软文档），但库、列、表达式级别可以另指定。

追踪工具：Query Store、Extended Events、Profiler ​

工具说明
Query Store内置在每个库里的"黑匣子"：持续记录每条查询的执行计划和运行统计，重启不丢，可对比"变慢前后"。SQL Server 2022 起新建库默认开启（本机 2025 实测 is_query_store_on = 1）
Extended Events（扩展事件，XE）轻量的事件追踪框架：你选要监听的事件（如"语句执行完成""发生死锁""等待超时"）、加过滤条件、选存放目标（内存环形缓冲、文件）。取代了旧的 Profiler
SQL Server Profiler旧的图形化追踪工具，基于 SQL Trace，开销较大，微软已不推荐新用；在 Express 版不可用，需要用 Standard/Enterprise 的 Profiler 去连 Express（据微软功能对比表）
sys.dm_exec_query_stats缓存中语句的累计耗时/读页统计，见 执行计划与SQL优化

登录、用户与权限 ​

SQL Server 的权限分两层：

  1. 登录名（Login）：实例级的"身份证"，决定能不能连上这个实例。可以是 Windows 账户，也可以是 SQL Server 登录名（用户名+密码）。
  2. 数据库用户（User）：库级，把一个登录名"映射"进某个库，决定在该库里能做什么。

然后给用户授权：GRANT（给）、DENY（明确拒绝，优先级最高）、REVOKE（撤销之前的给予或拒绝）。权限可以细到某个表的某个操作（SELECT、INSERT、UPDATE、DELETE、EXECUTE），也可以通过角色（Role） 批量授权：

角色作用
sysadmin（服务器角色）实例里的"上帝"，什么都能做。不要给应用程序
db_owner库内的"上帝"
db_datareader / db_datawriter读/写库内所有用户表
自定义角色按岗位自行定义，如"报表只读""MES 应用"

最小权限原则（Least Privilege）：应用账号只给它需要的权限。例如 MES 的服务账号只需要操作自己库里的表和存储过程，不应该是 sysadmin。一个常见的好做法：只授权存储过程和视图的访问，不直接授权基表。

逐步例子 ​

例：一次阻塞的时间线。

时刻会话 A会话 B会话 C（你）
t0BEGIN TRAN; UPDATE T SET V=V+1 WHERE Id=1;（对 Id=1 加排他锁，不提交）
t0+3sUPDATE T SET V=V+10 WHERE Id=1; → 要对同一行加排他锁，被 A 堵住
t0+6s仍在等查 dm_exec_requests：B 的 blocking_session_id = A，wait_type = LCK_M_X
t0+6sKILL A → A 的事务回滚，锁释放
之后连接被断开B 立即执行完成，V 变为 10（A 的 +1 已被回滚，所以是 0+10，不是 11）

动手实验 ​

前提：LocalDB + sqlcmd。实验建临时库 Lab_Ops；另创建一个登录名 lab_reader 和一个扩展事件会话 lab_xe（它们是实例级对象，不随删库消失，所以脚本最后会手动删除）。不碰任何其它库。

实验 A：制造并排查阻塞（需要三个终端窗口） ​

准备：窗口 C（观察者）先建库表。把下面存成 g_setup.sql，运行 sqlcmd -S "(localdb)\MSSQLLocalDB" -E -I -f 65001 -W -i g_setup.sql：

sql
SET NOCOUNT ON;
IF DB_ID(N'Lab_Ops') IS NOT NULL
BEGIN
    ALTER DATABASE Lab_Ops SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
    DROP DATABASE Lab_Ops;
END
GO
CREATE DATABASE Lab_Ops;
GO
USE Lab_Ops;
CREATE TABLE dbo.T (Id int PRIMARY KEY, V int);
INSERT dbo.T VALUES (1, 0), (2, 0);
GO

窗口 A：存成 g_a.sql，运行 sqlcmd ... -i g_a.sql（开事务改一行，睡 20 秒，不提交）：

sql
USE Lab_Ops;
BEGIN TRAN;
UPDATE dbo.T SET V = V + 1 WHERE Id = 1;
WAITFOR DELAY '00:00:20';
ROLLBACK;

窗口 B（A 启动后约 3 秒内启动）：存成 g_b.sql，运行：

sql
USE Lab_Ops;
UPDATE dbo.T SET V = V + 10 WHERE Id = 1;
SELECT N'B 终于执行完了' AS Msg;

此时窗口 B 会卡住不动，这就是被阻塞。

窗口 C（A 启动后 6 秒内）：存成 g_obs.sql，运行：

sql
SET NOCOUNT ON;
USE Lab_Ops;
SELECT r.session_id AS Spid, r.blocking_session_id AS BlockedBy, r.status, r.command, r.wait_type, r.wait_time AS WaitMs,
       LEFT(REPLACE(t.text, CHAR(13)+CHAR(10), ' '), 50) AS SqlText
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE r.session_id > 50 AND r.session_id <> @@SPID;
SELECT request_session_id AS Spid, resource_type, request_mode, request_status
FROM sys.dm_tran_locks
WHERE resource_database_id = DB_ID() AND resource_type IN ('KEY','OBJECT') AND request_session_id <> @@SPID
ORDER BY request_session_id, resource_type;
DECLARE @head int = (SELECT TOP (1) blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id > 0);
SELECT @head AS HeadBlocker;
DECLARE @k nvarchar(30) = N'KILL ' + CAST(@head AS nvarchar(10));
EXEC (@k);
WAITFOR DELAY '00:00:01';
SELECT COUNT(*) AS StillBlocked FROM sys.dm_exec_requests WHERE blocking_session_id > 0;
SELECT Id, V FROM dbo.T ORDER BY Id;

HeadBlocker
75
StillBlocked
0
Id V
1  10
2  0

怎么读：

  • 第一个结果：会话 81（窗口 B）的 BlockedBy 是 75，wait_type 是 LCK_M_X——在等排他锁；会话 75（窗口 A）自己没被堵（BlockedBy 为 0），它的状态是 WAITFOR（我们故意睡着）。75 就是头号阻塞者。
  • 第二个结果：75 在 KEY（索引键，也就是那一行）上持有 X（排他锁，GRANT）；81 想要同一个 KEY 的 X，状态是 WAIT（在等）。两者在表（OBJECT）上都持有 IX（意向排他锁，只是"我要在下面加行锁"的声明，互不冲突）。
  • KILL 75 之后，A 的事务回滚，B 马上继续；V 最终是 10（0 + 10），A 的 +1 没有生效。窗口 A 的输出会报 Cannot continue the execution because the session is in the kill state.。

提示：KILL 会回滚该会话的未提交事务，大事务回滚可能很慢；在线上一定先看清这个会话是谁、在做什么，确认后再杀，并且最好先联系业务方。

第 2 步：排序规则与 varchar 中文。 同一份数据存进四种列：

sql
PRINT N'=== 2. 排序规则与 varchar 中文 ===';
CREATE TABLE dbo.C (
    Id int IDENTITY PRIMARY KEY,
    V_latin   varchar(20)  COLLATE SQL_Latin1_General_CP1_CI_AS,
    V_prc     varchar(20)  COLLATE Chinese_PRC_CI_AS,
    V_utf8    varchar(40)  COLLATE Latin1_General_100_CI_AS_SC_UTF8,
    V_nvarchar nvarchar(20)
);
INSERT dbo.C (V_latin, V_prc, V_utf8, V_nvarchar) VALUES (N'焊接', N'焊接', N'焊接', N'焊接');
INSERT dbo.C (V_latin, V_prc, V_utf8, V_nvarchar) VALUES (N'𠀀', N'𠀀', N'𠀀', N'𠀀');
SELECT V_latin, V_prc, V_utf8, V_nvarchar FROM dbo.C ORDER BY Id;
SELECT Id, DATALENGTH(V_latin) AS Bytes_latin, DATALENGTH(V_prc) AS Bytes_prc,
       DATALENGTH(V_utf8) AS Bytes_utf8, DATALENGTH(V_nvarchar) AS Bytes_nvarchar FROM dbo.C ORDER BY Id;
GO

输出：

V_latin V_prc V_utf8 V_nvarchar
?? 焊接 焊接 焊接
?? ?? 𠀀 𠀀
Id Bytes_latin Bytes_prc Bytes_utf8 Bytes_nvarchar
1  2           4         6          4
2  2           2         4          4

逐列解读：

  • V_latin（西欧代码页）：汉字全被替换成 ?，每个汉字只剩 1 字节（? 本身），数据已经永久丢失，无法找回。
  • V_prc（Chinese_PRC，对应 GBK 代码页）：常用汉字"焊接"正常，每字 2 字节共 4 字节；但生僻字 𠀀（Unicode 扩展区的字，GBK 里没有）仍变成 ?。
  • V_utf8（UTF-8 排序规则）：都正常；汉字每个 3 字节（"焊接"共 6 字节），生僻字 4 字节。
  • V_nvarchar：都正常，每个字符 2 字节（UTF-16），生僻字占 4 字节（两个 UTF-16 码元）。

结论：varchar + 中文不可靠，要么 nvarchar，要么明确用 UTF-8 排序规则（SQL Server 2019 起）。在 SqlSugar 里把含中文的列声明为 nvarchar(N)。

sql
PRINT N'--- 大小写敏感与排序规则冲突 ---';
SELECT CASE WHEN N'abc' = N'ABC' COLLATE Latin1_General_CS_AS THEN N'相等' ELSE N'不相等' END AS CS_AS,
       CASE WHEN N'abc' = N'ABC' COLLATE Latin1_General_CI_AS THEN N'相等' ELSE N'不相等' END AS CI_AS;
GO
SELECT 1 WHERE N'a' COLLATE Latin1_General_CS_AS = N'a' COLLATE Chinese_PRC_CI_AS;
GO
SELECT name, collation_name FROM sys.columns WHERE object_id = OBJECT_ID('dbo.C') AND collation_name IS NOT NULL ORDER BY column_id;
GO

输出：

CS_AS  CI_AS
不相等  相等
Msg 468, Level 16, State 9, Server ..., Line 1
Cannot resolve the collation conflict between "Chinese_PRC_CI_AS" and "Latin1_General_CS_AS" in the equal to operation.

V_latin     SQL_Latin1_General_CP1_CI_AS

CS 区分大小写所以 abc ≠ ABC，CI 不区分所以相等；两个不同排序规则的表达式直接比较会报 468，要把其中一侧改成同一个规则。最后一个查询显示：V_nvarchar 没指定排序规则，继承了库的默认值——nvarchar 也有排序规则，只影响比较和排序，不影响能不能存汉字。

第 4 步：日志膨胀、查原因、收回。

sql
PRINT N'=== 4. 日志膨胀 ===';
ALTER DATABASE Lab_Ops SET RECOVERY FULL;
BACKUP DATABASE Lab_Ops TO DISK = N'NUL';
GO
CREATE TABLE dbo.Big (Id int IDENTITY PRIMARY KEY, Pad char(500) NOT NULL DEFAULT 'x');
INSERT dbo.Big (Pad) SELECT TOP (50000) 'x' FROM sys.all_objects a CROSS JOIN sys.all_objects b;
UPDATE dbo.Big SET Pad = 'y';
GO
SELECT name, recovery_model_desc, log_reuse_wait_desc FROM sys.databases WHERE name = N'Lab_Ops';
SELECT name, size * 8 / 1024 AS SizeMB FROM sys.database_files WHERE type_desc = 'LOG';
DBCC SQLPERF(LOGSPACE);
GO

BACKUP ... TO DISK = N'NUL' 把备份"扔进黑洞"，只用于这个实验（让 FULL 模式生效而不产生文件）。它会让真正的备份链断掉，生产库绝不要这样做。

输出（节选）：

name    recovery_model_desc log_reuse_wait_desc
Lab_Ops FULL                LOG_BACKUP
name        SizeMB
Lab_Ops_log 72
Database Name Log Size (MB) Log Space Used (%) Status
Lab_Ops       71.992188     54.861637           0

只往表里插了 5 万行（每行 500 字节）再整表更新一次，日志文件就从 8 MB 涨到了 72 MB，因为每次修改都要先记入日志，而 FULL 模式下没做日志备份，这些日志就不能重用，只能让文件继续增长；log_reuse_wait_desc = LOG_BACKUP 直接说明了原因。真实生产库，一次大批量更新或没有日志备份计划，日志涨到几十上百 GB 并不稀奇。

收回的办法：先做日志备份（让日志可重用），再缩小文件。

sql
BACKUP LOG Lab_Ops TO DISK = N'NUL';
CHECKPOINT;
BACKUP LOG Lab_Ops TO DISK = N'NUL';
SELECT name, log_reuse_wait_desc FROM sys.databases WHERE name = N'Lab_Ops';
GO
DECLARE @i int = 0;
WHILE @i < 6 AND (SELECT size FROM sys.database_files WHERE type_desc = 'LOG') > 1024
BEGIN
    INSERT dbo.Big (Pad) VALUES ('t');
    BACKUP LOG Lab_Ops TO DISK = N'NUL';
    DBCC SHRINKFILE (N'Lab_Ops_log', 8) WITH NO_INFOMSGS;
    SET @i += 1;
END
SELECT name, size * 8 / 1024 AS SizeMB, @i AS Rounds FROM sys.database_files WHERE type_desc = 'LOG';
GO

输出：

name    log_reuse_wait_desc
Lab_Ops NOTHING
name        SizeMB Rounds
Lab_Ops_log 8      2

日志备份后 log_reuse_wait_desc 变成 NOTHING（没有障碍）。但直接 DBCC SHRINKFILE 我在本机第一次试时报错 Cannot shrink log file ... because the logical log file located at the end of the file is in use（日志文件末尾的那段仍在使用，缩不了）。解法是制造一点日志写入、再备份日志，让"活动日志"移走后重试，我这里循环了 2 轮就缩回了 8 MB。注意：缩小文件是一次性手术，根因（缺日志备份计划）不处理，日志还会涨回来。

常见坑与排查 ​

现象原因办法
程序偶发超时、某操作一直转圈阻塞：某个会话开事务忘了提交/回滚查 dm_exec_requests 的 blocking_session_id，找头号阻塞者；修代码保证 finally 里回滚；用 SET LOCK_TIMEOUT 或命令超时避免无限等待
杀掉会话后系统还是慢被杀的是大事务，回滚本身也要很久耐心等；KILL n WITH STATUSONLY 可以看回滚进度
日志越来越大FULL 模式没有日志备份；或有长事务看 log_reuse_wait_desc；做日志备份计划；结束长事务
DBCC SHRINKFILE 反复缩小又涨回来根因没解决，频繁收缩带来文件碎片别定期收缩；预留合理的固定大小
中文变 ?varchar 列（西欧代码页）存中文列改 nvarchar，字面量加 N；已丢失的数据要从源头重新导入
Cannot resolve the collation conflict比较的两边排序规则不同（典型：临时表与库的排序规则不同）比较时显式 COLLATE DATABASE_DEFAULT，或统一建表时的排序规则
恢复库到另一台机器后某用户登录不了"孤立用户"：库里的用户在新实例上没有对应登录名在新实例建同名登录名后用 ALTER USER 用户 WITH LOGIN = 登录名 修复
应用账号权限过大为图省事给了 sysadmin 或 db_owner按最小权限重新分配；只授权所需存储过程/视图
忘了删实例级对象（登录名、XE 会话、作业）它们不在库里，删库不会带走脚本收尾时手动删除，并核对

业务视角与技术视角 ​

业务视角：MES 是"产线停不得"的系统。一次未提交的事务、一块写满的磁盘，都可能让产线停摆。运维的价值在于：在事故发生前就能发现苗头（日志在涨、磁盘剩余少、慢查询变多），并有标准化的处理手册。哪些账号可以做什么，也是质量体系（数据完整性、可追溯，见 数据完整性）要求的一部分。请对照你们公司的权限管理制度和变更流程核实。

技术视角：

  • 应用程序应使用专用账号，权限最小；开发/测试/生产三套环境账号分开。C# 连接字符串里避免使用 sa 或 sysadmin。
  • 查慢先看阻塞和等待（本篇），再看单条语句的执行计划（执行计划与SQL优化），最后看索引和统计信息（SQL-Server索引与统计信息）。
  • 日志管理 = 恢复模式 + 日志备份计划（备份与恢复）；LocalDB/Express 没有 SQL Server Agent，定时任务要靠 Windows 任务计划程序（⚠ 未在本机运行验证）。
  • 对象命名、批量脚本里的临时对象要成对"创建-清理"。

练习题与答案 ​

1. 阻塞和死锁有什么区别？

答：阻塞是 B 等 A 释放锁，A 一旦提交或回滚，B 就继续，无需外部干预；死锁是 A 等 B 同时 B 等 A，互相等待永远不会解除，SQL Server 会检测到并强制回滚其中一方（错误 1205）。

2. 看到日志文件很大，第一步做什么？

答：先查 sys.databases.log_reuse_wait_desc，确定是缺日志备份（LOG_BACKUP）还是长事务（ACTIVE_TRANSACTION）等。别上来就缩小文件。

3. 为什么 nvarchar(30) 能存 30 个汉字，而 varchar(30) 在 GBK 排序规则下只能存 15 个汉字？

答：nvarchar 每字符 2 字节（UTF-16），30 个字符 60 字节，汉字都在基本平面，每个汉字 1 个字符；varchar(30) 的 30 是字节数，GBK 代码页的汉字每个 2 字节，所以只能放 15 个汉字（英文数字每个 1 字节）。

4. 创建登录名后，这个人就能查所有库了吗？

答：不能。登录名只让他能连上实例。要访问某个库，还要在该库里创建对应的用户，并授予权限；public 角色默认带的权限很少。

5. 为什么实验里用 EXECUTE AS USER 就可以测权限，却没用这个登录名真的连一次？

答：EXECUTE AS USER 在当前会话里切换身份，足以检验库内权限。LocalDB 默认只让所有者访问，用 SQL 登录名真正登录要看实例的认证模式，我没有在本机实测（只验证了库内权限的效果）。

小结 ​

  • 阻塞排查三步：dm_exec_requests 看 blocking_session_id → 找头号阻塞者 → 确认后 KILL，同时修复应用里不提交的事务。
  • 空间：sp_spaceused、sys.database_files、DBCC SQLPERF(LOGSPACE)；日志涨大先看 log_reuse_wait_desc。
  • 排序规则：varchar 受代码页限制，含中文必须 nvarchar（或 UTF-8 排序规则）；跨规则比较要 COLLATE。
  • 追踪：Query Store（长期历史）、Extended Events（灵活事件）、Profiler（旧，Express 不可用）。
  • 权限：登录名（实例）→ 用户（库）→ GRANT；最小权限原则。
  • 实例级对象（登录名、XE 会话）不随删库消失，用完要手动清理。
