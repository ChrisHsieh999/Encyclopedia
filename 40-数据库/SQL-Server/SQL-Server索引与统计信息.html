SQL-Server索引与统计信息

AI 生成 · 待核对数据库SQL-Server性能更新于 2026-10-21

⚠ 待核对：关于"缺失索引 DMV 的局限（只是建议、不考虑已有索引的重叠、实例重启后清空）"以及"页拆分的细节"，我依据的是已有知识，没有逐条对照微软文档；碎片阈值、统计信息自动更新的公式和"重建索引会用 FULLSCAN 更新统计信息"这几点，已对照微软文档。所有代码和数字都在本机 SQL Server 2025 LocalDB 上实际运行过（GUID 是随机生成的，碎片百分比每次运行会有 ±1 左右的差别）。

本篇是 SQL-Server 目录的第 3 篇。读完你应该能：说清索引碎片和页密度是什么、怎么测量；知道 REORGANIZE 和 REBUILD 的区别以及填充因子的取舍；明白统计信息为什么让查询计划变好或变坏、怎么更新；会用缺失索引 DMV 找候选索引，又知道不能照单全收。

一句话定义 ​

  • 索引碎片（Fragmentation）：索引的页在磁盘上的物理顺序和逻辑顺序对不上，或页里空着很多位置；
  • 填充因子（Fill Factor）：建索引时每页最多填多满（比如 70 表示填到 70%，留 30% 空位给将来插入）；
  • 统计信息（Statistics）：数据库对某一列"值是怎么分布的"的小结（直方图），优化器靠它估算"这个条件会命中多少行"，进而选择执行计划。

先修知识 ​

  • 数据库索引：知道索引是一棵有序的树（B+ 树），叶子层按索引列有序存放。
  • 执行计划与SQL优化：知道 Seek、Scan、Key Lookup，会用 SET STATISTICS IO。
  • 可选：SQL-Server 里"页（8 KB）"和系统库的介绍。

它解决什么问题 ​

建好索引不是一劳永逸。数据库用久了会遇到两类退化：

  1. 索引变"松散"了：不断插入、删除、更新后，索引的页变得半空、排序错乱，同样的数据要读更多页。比如主键用随机 GUID 的表，每次插入都落在树中间的随机位置，满了的页要拆成两个半满的页。
  2. 优化器的"地图"过期了：统计信息记录的是上次更新时的数据分布。如果表里数据已经大变样（比如一个状态列从全是 0 变成一半是 1），优化器仍按旧分布估算，会选出灾难性的计划（比如该扫描却去走索引）。

这篇讲怎么发现并处理这两类问题，以及怎么避免"瞎维护"（微软的态度是：不要机械地按固定阈值定期重建所有索引，要先测量）。

核心概念 ​

页、页拆分与碎片 ​

SQL Server 以 8 KB 的页（Page） 为单位存数据。索引的叶子层是一串页，每页存若干行，按索引列有序，页与页之间用指针串成链。

页拆分（Page Split）：往一个已经装满的页中间插入一行，没地方放，数据库就新分配一页，把原页大约一半的行搬过去，再插入新行。结果：原来 1 个满页变成 2 个半满页，而且新页在磁盘上的位置不一定紧挨着旧页。

由此产生两种"松散"，要分开看：

指标含义在 DMV 里对应的列
逻辑碎片页链的逻辑顺序和物理顺序不一致的比例avg_fragmentation_in_percent
页密度（Page density）页平均填了多满avg_page_space_used_in_percent

比喻：一个按字母排好的相册，插入新照片时发现本页塞满了，只好拿一本新相册册页夹进去，旧页只剩一半；翻起来就要跳着翻（碎片），而且同样多的照片占了更多册页（页密度低）。

微软文档的看法：在很多负载下，提高页密度的收益比降低逻辑碎片更大；并且不要只根据固定的碎片百分比阈值来决定维护，要结合负载实测。网上广为流传的"碎片 5%～30% 做 REORGANIZE，超过 30% 做 REBUILD"只是历史上的经验起点，不是规定。

REORGANIZE 与 REBUILD ​

ALTER INDEX ... REORGANIZEALTER INDEX ... REBUILD
做什么只整理叶子层：把页按逻辑顺序重排、压实到填充因子删掉重建整个索引
在线？始终在线（不阻塞读写），可以中途停止，进度保留默认离线，持有表级锁；ONLINE = ON 可在线
资源消耗较轻较重，需要额外空间放新旧两份索引
统计信息不更新用 FULLSCAN 更新该索引的统计信息
版本限制各版本都能用在线重建（ONLINE = ON）只有 Enterprise 版有；Express、Standard 不支持（据微软 2025 版文档）

微软文档提醒了一个常被忽略的事实：很多人重建索引后觉得变快了，其实主要是重建时顺便更新了统计信息；多数时候，单独更新统计信息就能得到类似的效果，而且便宜得多。

填充因子 ​

FILLFACTOR = 70 表示重建时每页只填 70%，留 30% 空位给后来插入的数据，以减少页拆分。代价：同样的数据要多占约 40% 的页（1/0.7 ≈ 1.43 倍），读起来更慢。

微软的建议是：一般不要改（保持默认 100 或 0）；只有对确实频繁发生页拆分的索引（典型就是用随机 GUID 做主键或前导列）才考虑设一个小于 100 的值，并且要实测。后面实验会看到它的效果和代价。

提示：主键尽量用递增的值（IDENTITY 自增列，或 SQL Server 的 NEWSEQUENTIALID()），避免随机 GUID 造成大量页拆分。

统计信息 ​

给一列（或几列）建索引时，数据库会同时创建一份统计信息。里面最主要的是一个直方图（Histogram），把值分成最多 200 个"桶"，记下每个桶的范围和行数。优化器用它估算"WHERE Status = 1 大概命中多少行"。

  • 估得准 → 选对计划（少量行用索引 Seek + Lookup，大量行用扫描）。
  • 估得不准 → 选错计划。

自动更新：库的 AUTO_UPDATE_STATISTICS 默认开。当表上累计的修改行数超过阈值，下一次用到这份统计信息的查询会先触发更新。按微软文档，阈值（兼容级别 130 及以上）是 MIN(500 + 0.20 × 行数, SQRT(1000 × 行数))：行数 n 越大，阈值占比越小。例如 200 万行：MIN(400,500, 44,721) = 每 44,721 次修改更新一次。我们下面的实验有 10 万行，阈值是 SQRT(1000 × 100,000) = 10,000 次修改。

即便自动更新了，也有两类问题：一是自动更新默认采样（只扫一部分行），数据分布很偏时可能不准，需要 FULLSCAN；二是自动更新发生在查询等着的时候（同步），可以开 AUTO_UPDATE_STATISTICS_ASYNC 改成后台更新（默认关）。

缺失索引 DMV ​

DMV（Dynamic Management View，动态管理视图） 是以 sys.dm_ 开头的系统视图，反映数据库引擎运行时的状态。优化器在编译查询时，如果觉得"有某个索引会让这条查询明显更快"，就会把这个建议记在缺失索引 DMV 里：

  • sys.dm_db_missing_index_details：缺在哪张表、哪些等值列/不等值列/要包含的列；
  • sys.dm_db_missing_index_groups、sys.dm_db_missing_index_group_stats：被多少次查询需要、预计改善百分比。

局限（已有知识，见顶部说明）：它只是建议，不会考虑你已有的相似索引（容易建出重叠的）；列的顺序不一定最优；实例重启后清空；过于简单的"琐碎计划"的查询不会产生建议（本机实验里，最简单的 COUNT(*) 查询就没有出建议，换成带 GROUP BY 的才出来）。所以：把它当线索，不要当命令；建之前人工检查已有索引，评估对写入的影响。

逐步例子 ​

例 1：随机 GUID 主键的碎片。 两张表各 5 万行，每行 200 字节左右，分 50 批、每批 1000 行插入。一张用自增 int 主键，一张用随机 uniqueidentifier 主键。

  • 自增：每次都插在最后，页被依次填满。5 万行 ≈ 1316 页，页密度 100%，碎片约 4%。
  • 随机 GUID：每次插在树的随机位置，页不停拆分。同样数据 ≈ 2086 页，页密度只有 66.6%，碎片 98.8%。多了 58% 的页。

例 2：统计信息过期的灾难。 表有 10 万行，Status 全部是 0，统计信息只知道有 10 万个 0。然后把其中 5 万行改成 1（关闭了自动更新）。此时查 WHERE Status = 1，优化器依据旧统计信息估计"几乎没有 1"（估 1 行），于是选 Index Seek 加 Key Lookup；实际有 5 万行，要做 5 万次 Lookup，读了 15 万页。更新统计信息后，优化器知道有 5 万行，改选扫描，只读 1415 页。

动手实验 ​

前提：LocalDB + sqlcmd。实验建临时库 Lab_Ops，用完删除。把下面各步依次存入 ops6.sql（UTF-8），运行：

sqlcmd -S "(localdb)\MSSQLLocalDB" -E -I -f 65001 -W -i ops6.sql -o ops6.out

用 -o 把输出写进文件再看（STATISTICS PROFILE 的输出非常宽）。

第 1 步：建库；造出碎片。

sql
SET NOCOUNT ON;
IF DB_ID(N'Lab_Ops') IS NOT NULL
BEGIN
    ALTER DATABASE Lab_Ops SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
    DROP DATABASE Lab_Ops;
END
GO
CREATE DATABASE Lab_Ops;
GO
USE Lab_Ops;
GO
PRINT N'=== 1. 碎片：随机主键 vs 递增主键 ===';
CREATE TABLE dbo.T_Guid (Id uniqueidentifier NOT NULL DEFAULT NEWID() PRIMARY KEY, Pad char(200) NOT NULL DEFAULT 'x');
CREATE TABLE dbo.T_Seq  (Id int IDENTITY(1,1) PRIMARY KEY, Pad char(200) NOT NULL DEFAULT 'x');
GO
DECLARE @i int = 0;
WHILE @i < 50
BEGIN  -- 分 50 批、每批 1000 行：模拟业务系统一批批地写入
    INSERT dbo.T_Guid (Pad) SELECT TOP (1000) 'x' FROM sys.all_objects;
    INSERT dbo.T_Seq  (Pad) SELECT TOP (1000) 'x' FROM sys.all_objects;
    SET @i += 1;
END
GO
SELECT OBJECT_NAME(object_id) AS Tbl, index_level AS Lvl, page_count AS Pages,
       CAST(avg_fragmentation_in_percent AS decimal(5,1)) AS FragPct,
       CAST(avg_page_space_used_in_percent AS decimal(5,1)) AS PageFullPct
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'DETAILED')
WHERE index_level = 0 AND object_id IN (OBJECT_ID('dbo.T_Guid'), OBJECT_ID('dbo.T_Seq'))
ORDER BY Tbl;
GO

为什么要分批插入？如果用一条 INSERT ... SELECT 一次性插 5 万行，SQL Server 会先把这批行按键值排好序再写入，几乎不拆页——我第一次就是这样做的，结果碎片只有 0.1%。真实系统里是一个个请求、一批批零散地写入，才会产生碎片。

我的输出：

Tbl Lvl Pages FragPct PageFullPct
T_Guid 0 2086 98.8 66.6
T_Seq 0 1316 4.0 100.0

sys.dm_db_index_physical_stats 的 'DETAILED' 模式扫描所有页，最准确但最慢；index_level = 0 只看叶子层。你的数字会略有不同（GUID 随机）。

第 2 步：整理索引。

sql
PRINT N'=== 2. 重建 vs 重新组织 ===';
ALTER INDEX ALL ON dbo.T_Guid REORGANIZE;
SELECT N'REORGANIZE后' AS Step, page_count AS Pages, CAST(avg_fragmentation_in_percent AS decimal(5,1)) AS FragPct,
       CAST(avg_page_space_used_in_percent AS decimal(5,1)) AS PageFullPct
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('dbo.T_Guid'), NULL, NULL, 'DETAILED') WHERE index_level = 0;
GO
ALTER INDEX ALL ON dbo.T_Guid REBUILD;
SELECT N'REBUILD后' AS Step, page_count AS Pages, CAST(avg_fragmentation_in_percent AS decimal(5,1)) AS FragPct,
       CAST(avg_page_space_used_in_percent AS decimal(5,1)) AS PageFullPct
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('dbo.T_Guid'), NULL, NULL, 'DETAILED') WHERE index_level = 0;
GO

我的输出：

Step Pages FragPct PageFullPct
REORGANIZE后 1434 .6 96.9
REBUILD后 1429 .0 97.2

两种方法都把 2086 页压回了 1430 左右，页密度回到 97%，碎片降到接近 0。REORGANIZE 更轻、在线；REBUILD 更彻底（0.0%）。（页密度是 97% 而不是 100%，因为随机 GUID 的键值排序后，每页会留一点零头。）

第 3 步：填充因子的效果和代价。

sql
PRINT N'=== 3. 填充因子 ===';
ALTER INDEX ALL ON dbo.T_Guid REBUILD WITH (FILLFACTOR = 70);
SELECT N'FILLFACTOR=70' AS Step, page_count AS Pages, CAST(avg_fragmentation_in_percent AS decimal(5,1)) AS FragPct,
       CAST(avg_page_space_used_in_percent AS decimal(5,1)) AS PageFullPct
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('dbo.T_Guid'), NULL, NULL, 'DETAILED') WHERE index_level = 0;
DECLARE @i int = 0;
WHILE @i < 10
BEGIN
    INSERT dbo.T_Guid (Pad) SELECT TOP (1000) 'x' FROM sys.all_objects;
    SET @i += 1;
END
SELECT N'再随机插入1万行后' AS Step, page_count AS Pages, CAST(avg_fragmentation_in_percent AS decimal(5,1)) AS FragPct,
       CAST(avg_page_space_used_in_percent AS decimal(5,1)) AS PageFullPct
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('dbo.T_Guid'), NULL, NULL, 'DETAILED') WHERE index_level = 0;
SELECT name, fill_factor FROM sys.indexes WHERE object_id = OBJECT_ID('dbo.T_Guid');
GO

我的输出：

Step Pages FragPct PageFullPct
FILLFACTOR=70 1924 .0 72.2
再随机插入1万行后 2032 10.5 82.1
name fill_factor
PK__T_Guid__3214EC07F6ABB3A1 70

用 FILLFACTOR = 70 重建后，同样 5 万行占 1924 页（比刚才多 35%），页密度 72%；之后再随机插入 1 万行（增加 20% 数据），页数只从 1924 涨到 2032（涨 5.6%），碎片 10.5%。对比第 1 步没有预留空位时，插入同样规模数据会严重拆页。预留空位确实减少了拆页，但代价是平时就多占 35% 的页（读更多、缓存更多）。sys.indexes.fill_factor 记录了这个设置。

第 5 步：制造过期统计信息，对比计划。

sql
PRINT N'--- 关掉自动更新，制造过期统计 ---';
ALTER DATABASE Lab_Ops SET AUTO_UPDATE_STATISTICS OFF;
UPDATE TOP (50000) dbo.Ord SET Status = 1;
GO
SET STATISTICS IO ON; SET STATISTICS PROFILE ON;
GO
SELECT MAX(Pad) AS MaxPad FROM dbo.Ord WHERE Status = 1 OPTION (RECOMPILE);
GO
SET STATISTICS PROFILE OFF; SET STATISTICS IO OFF;
GO
SELECT s.name, sp.rows, sp.modification_counter, sp.last_updated
FROM sys.stats s CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) sp
WHERE s.object_id = OBJECT_ID('dbo.Ord') AND s.name = N'IX_Ord_Status';
GO
UPDATE STATISTICS dbo.Ord IX_Ord_Status WITH FULLSCAN;
GO
SET STATISTICS IO ON; SET STATISTICS PROFILE ON;
GO

GO

GO

GO

OPTION (RECOMPILE) 要求每次都重新编译，避免用到缓存的旧计划，方便对比。STATISTICS PROFILE 在结果后面追加执行计划，每个运算符有 Rows（实际行数） 和 EstimateRows（估计行数） 两列，这正是对比"估得准不准"的地方。我从输出里摘出的关键信息：

阶段运算符实际行数 Rows估计行数 EstimateRows逻辑读
统计信息过期Index Seek（IX_Ord_Status）500001150071
统计信息过期Clustered Index Seek（Key Lookup）50000（执行 50000 次）1
更新统计信息之后Clustered Index Scan50000500001415

dm_db_stats_properties 的输出里能看到 rows = 100000、modification_counter = 50000：统计信息还记着 10 万行，累计了 5 万次修改没更新。更新后估计行数与实际吻合，优化器改选了扫描，逻辑读从 150071 降到 1415，相差 100 多倍。实验末尾把自动更新重新打开。

第 6 步：缺失索引 DMV。

sql
PRINT N'=== 5. 缺失索引 DMV ===';
CREATE TABLE dbo.SO (Id int IDENTITY PRIMARY KEY, CustomerId int NOT NULL, Status tinyint NOT NULL, Amount decimal(10,2) NOT NULL);
INSERT dbo.SO (CustomerId, Status, Amount)
SELECT TOP (200000) ABS(CHECKSUM(NEWID())) % 5000, ABS(CHECKSUM(NEWID())) % 4, 10
FROM sys.all_objects a CROSS JOIN sys.all_objects b;
GO
SELECT CustomerId, SUM(Amount) AS Total FROM dbo.SO WHERE CustomerId = 77 AND Status = 1 GROUP BY CustomerId;
SELECT CustomerId, SUM(Amount) AS Total FROM dbo.SO WHERE CustomerId = 88 AND Status = 2 GROUP BY CustomerId;
GO
SELECT d.equality_columns, d.inequality_columns, d.included_columns,
       s.user_seeks, CAST(s.avg_user_impact AS decimal(5,1)) AS AvgImpactPct
FROM sys.dm_db_missing_index_details d
JOIN sys.dm_db_missing_index_groups g ON g.index_handle = d.index_handle
JOIN sys.dm_db_missing_index_group_stats s ON s.group_handle = g.index_group_handle
WHERE d.database_id = DB_ID() AND d.object_id = OBJECT_ID('dbo.SO');
GO

数据是随机生成的，两条查询返回的 Total 每次不同，不用在意；DMV 的输出：

equality_columns       inequality_columns included_columns user_seeks AvgImpactPct
[CustomerId], [Status] NULL               NULL             2          99.6

意思是：优化器认为在 (CustomerId, Status) 上建索引（两列都是等值条件）能改善约 99.6%，已经有 2 次查询需要它。这两条查询结构相同，只是常量不同，被合并成了一个建议。

按建议建一个索引（并把 Amount 放进 INCLUDE，让查询完全被索引覆盖），然后看索引使用情况：

sql
CREATE INDEX IX_SO_Cust_Status ON dbo.SO(CustomerId, Status) INCLUDE (Amount);
SELECT CustomerId, SUM(Amount) AS Total FROM dbo.SO WHERE CustomerId = 77 AND Status = 1 GROUP BY CustomerId;
GO
SELECT i.name, s.user_seeks, s.user_scans, s.user_updates
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats s ON s.object_id = i.object_id AND s.index_id = i.index_id AND s.database_id = DB_ID()
WHERE i.object_id = OBJECT_ID('dbo.SO');
GO

输出：

name                       user_seeks user_scans user_updates
PK__SO__...                0          2          1
IX_SO_Cust_Status          1          0          0

sys.dm_db_index_usage_stats 统计每个索引被查找（seeks）、扫描（scans）、因写入而被维护（updates）的次数。清理索引时，长期 seeks 和 scans 都是 0 而 updates 很高的索引，只在拖慢写入，是删除的候选（但要观察足够长的时间，包括月末报表等低频场景；该视图在实例重启后清零）。

常见坑与排查 ​

现象原因办法
每晚重建所有索引，维护窗口越来越长机械式维护，不管需不需要只维护页数较多且碎片/密度确实有问题的索引；很多时候只更新统计信息就够了
重建后又很快碎片化主键是随机 GUID，或频繁更新变长列改自增主键 / NEWSEQUENTIALID()；或为该索引设合适的填充因子
整个库都设了很低的填充因子把"预防"当成"默认"填充因子默认保持 100，仅对确认页拆分严重的索引调整
查询忽快忽慢，同一条 SQL 换个参数就慢统计信息过期，或参数嗅探UPDATE STATISTICS（必要时 FULLSCAN）；见 执行计划与SQL优化
REORGANIZE 后查询计划没变化REORGANIZE 不更新统计信息另外执行 UPDATE STATISTICS
照缺失索引 DMV 建了一堆索引，写入变慢DMV 不考虑重叠和写入成本先合并相似建议，检查已有索引能否扩展；上线后观察使用情况，没用就删
小表碎片很高但重建没效果小索引只有几页，本来就不连续忽略（页数很少的索引不必维护）
对大表 REBUILD 把日志撑爆、堵住别的会话离线重建持表锁，且产生大量日志低峰期做；Enterprise 用 ONLINE = ON；用 REORGANIZE；监控日志，见 SQL-Server常用运维

业务视角与技术视角 ​

业务视角：过站表、追溯表这类只增不删的"流水"表，每天写入量大、行数一直涨；用随机主键或不当索引，几个月后看板就会变慢，却很难让业务方理解为什么。把"页密度低、统计信息过期"这类问题定期检查，相当于给数据库做体检。

技术视角：

  • 流水表主键用自增或有序值；业务上需要全局唯一编号时（如条码）单独建唯一索引，不要拿它做聚集索引键。
  • 建议的例行做法：监控；对确实退化的索引做 REORGANIZE/REBUILD；定期（例如每天夜间）更新统计信息；不要给所有索引统一设填充因子。
  • 若数据库由 SQL Server Agent 调度这些任务，Express/LocalDB 没有 Agent，要用 Windows 任务计划程序跑 sqlcmd（⚠ 未在本机运行验证）。
  • C# + SqlSugar 自动建表会按实体生成聚集索引和主键，大表上线前要检查生成的索引是否满足查询；可结合 执行计划与SQL优化 分析。

练习题与答案 ​

1. REORGANIZE 与 REBUILD 哪个会更新统计信息？

答：REBUILD 会（对该索引的统计信息等价于 FULLSCAN）；REORGANIZE 不会。

2. 为什么自增主键的表（T_Seq）页密度是 100%，随机 GUID 的却只有 66.6%？

答：自增值总是追加到索引末尾，页依次填满不拆分。随机 GUID 插到随机位置，页满了就拆成两个半满页，所以平均密度趋向 50%～70%。

3. 一张表 500 万行，自动更新统计信息的阈值大约是多少次修改？

答：按 MIN(500 + 0.20 × n, SQRT(1000 × n))：500 + 0.2 × 5,000,000 = 1,000,500；SQRT(1000 × 5,000,000) = SQRT(5,000,000,000) ≈ 70,711。取较小者约 70,711 次（兼容级别 130 及以上）。

4. 你看到 dm_db_index_usage_stats 里某个索引 user_seeks = 0, user_scans = 0, user_updates = 80000。可以立刻删吗？

答：不能立刻删。该视图在实例重启后清零，且低频场景（月结、季度报表）可能还没跑过。要观察足够长的时间，确认没用再删，最好先在测试环境验证或先"禁用"（ALTER INDEX ... DISABLE）观察一段时间。

5. 为什么一条一次性 INSERT ... SELECT 50000 个随机 GUID 几乎不产生碎片？

答：SQL Server 会先把这批行按索引键排序，再按顺序写入，不会反复往已满的页中间插入，因此几乎没有页拆分。分批零散插入则会（本实验第 1 步）。

小结 ​

  • 碎片有两面：逻辑碎片和页密度；页拆分是主因，随机 GUID 主键最典型。
  • REORGANIZE 轻量在线；REBUILD 彻底但重，并顺便更新统计信息；不要机械地定期全部重建。
  • 填充因子：默认 100；仅对确认页拆分严重的索引调低，要权衡多占空间。
  • 统计信息是优化器的地图：过期会导致估行数错误、选错计划；UPDATE STATISTICS ... FULLSCAN 往往比重建索引划算。
  • 缺失索引 DMV 是线索不是命令；用 dm_db_index_usage_stats 评估索引是否有用。
  • 在线索引重建只有 Enterprise 版有。
