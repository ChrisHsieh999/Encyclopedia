Prompt工程

AI 生成 · 待核对AI大语言模型更新于 2026-10-21

本篇是 AI 入门路径的第 3 步。读完你应该能：把一个模糊需求写成一份"模型不会误解"的提示词；会用角色、示例、结构化输出、思维链这几招；为工厂场景写出"不良描述 → 缺陷代码"的提示词模板，并写出程序去校验模型的回答；知道哪些写法是反例。

⚠ 提示词效果未在本机运行验证：本机没有调用大模型，所以本篇的提示词模板只验证了"能正确拼出来"和"校验程序能挡住坏输出"（这两部分有实际运行），模型看到这份提示词后到底答得多准，没有测过，上线前请用自己的真实样本评测。

一句话定义 ​

提示词（Prompt）是你发给大语言模型的那段输入；Prompt 工程就是把这段输入写得足够清楚、足够具体、可以检验的一门手艺，目标是让模型稳定地给出你要的结果。

先修知识 ​

  • 大语言模型：知道模型是在"接龙"，知道上下文窗口是什么。
  • JSON-XML-YAML：结构化输出要用 JSON。
  • Python字符串：实验用到字符串拼接和正则。

它解决什么问题 ​

模型很聪明，但它读不到你的心。同样一句"帮我整理一下这个不良描述"：

  • 你心里想的是"输出一个缺陷代码，用于入库"；
  • 模型可能给你一段两百字的分析，里面还夹着"建议检查炉温"。

程序拿到的是一大段自由文本，无法入库。Prompt 工程要解决的就是：把你心里的要求写成白纸黑字，包括任务是什么、材料是什么、输出什么格式、遇到拿不准的怎么办。

类比：你给新来的实习生派活。说"整理一下"，他不知道往哪整理；说"对照这张表，把每条不良描述填成表里的代码，拿不准的填 D99 并标红"，他就能干。模型就是那个很聪明、没有任何背景、从不主动提问的实习生。

核心概念 ​

1. 好提示词的五个部分 ​

部分作用例子
角色 / 背景告诉它站在什么立场、什么场景"你是 PCB 贴片厂的质检数据整理员"
任务一句话说清楚要做什么"把不良描述归一化成缺陷代码"
材料它需要依据的数据或规则（代码表、SOP 片段）缺陷代码表
规则与边界禁止什么、拿不准怎么办"只能从表里选；无法判断用 D99，不要猜"
输出格式规定长什么样，程序才能读"只输出 JSON：{...}"

缺了哪块，模型就按"常见情况"自己脑补，脑补的结果最不可控。

2. 角色 ​

"你是……"有用，但别指望一句"你是世界顶级专家"就变聪明。有用的角色是在划定场景和口径："质检数据整理员"会倾向于用规范术语，"客服"会倾向于客气。把角色写成具体岗位 + 工作范围，比写形容词有用。

3. 示例（Few-shot） ​

直接给 2～5 个"输入 → 输出"样例，比写一大段文字描述更管用。模型会模仿样例的格式和判断尺度。

  • 0 个示例叫 zero-shot，1 个叫 one-shot，几个叫 few-shot。
  • 示例要覆盖边界：至少包含一个"拿不准"的样例（输出 D99），否则模型会倾向于总是硬猜一个。
  • 示例的格式要和你要求的输出格式完全一致，否则模型会听示例的、不听规则的。

4. 结构化输出 ​

要让程序读，就别让模型写散文。做法：

  1. 指定 JSON 格式并给出字段样例；
  2. 说明"只输出 JSON，不要解释"；
  3. 把可取值写死（枚举）：confidence 只能是 high|medium|low；
  4. 程序侧一定要校验：模型输出再规矩，也必须当作"不可信输入"检查——能不能解析、字段是否齐全、值是否在合法范围。许多模型平台还提供"约束输出格式"的功能，用不用都要保留校验。

5. 思维链（Chain of Thought） ​

对需要多步推理的问题，要求模型"先一步步写出推理过程，再给结论"，常常比直接要答案更准。

  • 适合：多条件判断、计算、排错分析。
  • 代价：输出变长、变贵、变慢。
  • 要给程序读时，把"推理"和"结论"分开：让模型输出 {"reasoning": "...", "answer": "..."}，程序只取 answer，推理部分留给人复核。
  • 提醒：模型写出的"推理过程"是一段生成的文字，不等于它内部真实的计算过程，也可能一本正经地写错。所以结论仍要校验。

6. 常见模式速查 ​

模式句式用在哪
约束范围"只根据下面资料回答，没有就说不知道"RAG 问答，减少编造
要求引用"每个结论后标出资料编号"便于人工核对出处
分步"先列出关键事实，再给结论"复杂分析
自检"输出前对照规则检查一遍"格式容易出错时
拒答出口"无法判断时输出 D99 并说明原因"减少瞎猜
分隔符用 ``` 或 XML 风格标签把"指令"和"数据"隔开降低AI的局限与幻觉中说的提示注入风险

7. 反例（为什么这样写不好） ​

反例问题改进
"帮我看看这个不良"没有任务、格式、边界写明任务、代码表、输出 JSON
"尽量详细，但是要简洁"自相矛盾定量："不超过 100 字"
"不要输出解释" 却在示例里带了解释示例和规则冲突，模型听示例示例与规则保持一致
把整本 SOP 全塞进去占窗口、干扰注意力、费钱只放相关片段，或用 RAG
"你一定要保证 100% 正确"模型无法保证，反而诱导它硬编给出"拿不准就标 low"的出口
把密码、客户机密直接写进提示词数据泄露（见 AI的局限与幻觉）脱敏，或使用公司批准的私有部署
一次性提需求，一次就上线没评测就信用 20～50 条真实样本评测、迭代

8. 把提示词当代码管理 ​

提示词是系统的一部分：放进版本管理（Git）、记录每次修改的原因、保留一套固定的评测样本，每次改提示词都跑一遍看变好还是变坏。凭感觉改，改好了这个又坏了那个，是最常见的情况。

逐步例子：不良描述归一化 ​

场景：SMT 线操作员在终端里随手写不良描述，如 C5 一端翘起来了，另一端焊住了。质量系统需要缺陷代码（参见 缺陷代码与不良分类），以便做统计和 SPC 分析。

下面的代码表是演示用的示例编码，不是任何公司的真实编码；你们公司的缺陷代码请以 QMS 里的主数据为准。

代码含义
D01少锡
D02连锡(桥接)
D03虚焊
D04立碑
D05偏移
D06缺件
D07错件
D08极性反
D99其他(无法归类)

设计思路：

  1. 角色 + 任务：一句话。
  2. 规则：只能选表里的；多缺陷都列；拿不准用 D99。
  3. 输出：JSON，带 evidence（原文依据）和 confidence（把握）。evidence 的目的是让程序能检查"你引用的话是不是真在原文里"。
  4. 3 个示例，其中一个是拿不准的。

然后程序侧做两件事：拼提示词、校验回答。下面的代码都实际运行过。

动手实验：拼提示词 + 校验模型输出 ​

环境：Python 3.12，标准库。保存为 defect_prompt.py，运行 python -I -X utf8 defect_prompt.py。

python
import json, re

# 示例缺陷代码表（演示用，不是任何公司的真实编码）
DEFECTS = {
    "D01": "少锡", "D02": "连锡(桥接)", "D03": "虚焊", "D04": "立碑",
    "D05": "偏移", "D06": "缺件", "D07": "错件", "D08": "极性反", "D99": "其他(无法归类)",
}

def build_prompt(raw_text):
    table = "\n".join(f"{k}: {v}" for k, v in DEFECTS.items())
    return f"""你是 PCB 贴片厂的质检数据整理员。任务：把操作员写的不良描述归一化成缺陷代码。

规则：
1. 只能从下面的缺陷代码表里选，禁止自造代码。
2. 描述里有多个缺陷时都列出；无法判断就用 D99，不要猜。
3. 只输出 JSON，不要任何解释，格式：
{{"codes": ["D01"], "evidence": "原文中支持判断的片段", "confidence": "high|medium|low"}}

缺陷代码表：
{table}

示例1
描述：R12 两端锡不够，焊盘露铜
输出：{{"codes": ["D01"], "evidence": "锡不够，焊盘露铜", "confidence": "high"}}
示例2
描述：U3 脚之间连在一起了
输出：{{"codes": ["D02"], "evidence": "脚之间连在一起", "confidence": "high"}}
示例3
描述：板子看着有点怪
输出：{{"codes": ["D99"], "evidence": "板子看着有点怪", "confidence": "low"}}

现在处理：
描述：{raw_text}
输出："""

def validate(model_output, raw_text):
    """校验模型输出；返回 (ok, 结果或失败原因)。永远不要直接信任模型输出。"""
    m = re.search(r"\{.*\}", model_output, re.S)           # 容忍模型包了 ```json 围栏
    if not m: return False, "找不到 JSON"
    try: obj = json.loads(m.group(0))
    except json.JSONDecodeError as e: return False, f"JSON 解析失败: {e.msg}"
    codes = obj.get("codes")
    if not isinstance(codes, list) or not codes: return False, "codes 缺失或为空"
    bad = [c for c in codes if c not in DEFECTS]
    if bad: return False, f"出现表外代码 {bad}"
    if obj.get("confidence") not in ("high", "medium", "low"): return False, "confidence 非法"
    ev = obj.get("evidence", "")
    if codes != ["D99"] and ev not in raw_text: return False, "evidence 不是原文片段（可能编造）"
    needs_review = obj["confidence"] != "high" or codes == ["D99"]
    return True, {"codes": codes, "needs_review": needs_review}

if __name__ == "__main__":
    raw = "C5 一端翘起来了，另一端焊住了"
    print(build_prompt(raw))
    print("=" * 40)
    samples = {   # 手工编写的"假想模型输出"，用来测校验器，不是真模型产出
        "合格输出": '{"codes": ["D04"], "evidence": "一端翘起来了，另一端焊住了", "confidence": "high"}',
        "带围栏": '```json\n{"codes": ["D04"], "evidence": "一端翘起来了", "confidence": "medium"}\n```',
        "自造代码": '{"codes": ["D44"], "evidence": "一端翘起来了", "confidence": "high"}',
        "编造证据": '{"codes": ["D04"], "evidence": "元件立起", "confidence": "high"}',
        "不是JSON": "这是立碑缺陷，建议调整炉温。",
        "无法归类": '{"codes": ["D99"], "evidence": "", "confidence": "low"}',
    }
    for name, out in samples.items():
        print(name, "->", validate(out, raw))

实际运行输出的后半部分（前半部分是拼好的提示词，内容就是函数里的模板，最后两行是 现在处理： 加上你的描述）：

现在处理：
描述：C5 一端翘起来了，另一端焊住了
输出：
========================================
合格输出 -> (True, {'codes': ['D04'], 'needs_review': False})
带围栏 -> (True, {'codes': ['D04'], 'needs_review': True})
自造代码 -> (False, "出现表外代码 ['D44']")
编造证据 -> (False, 'evidence 不是原文片段（可能编造）')
不是JSON -> (False, '找不到 JSON')
无法归类 -> (True, {'codes': ['D99'], 'needs_review': True})

怎么读这个结果：

  • 校验器挡住了 3 种典型坏输出：自造代码、编造证据、根本不是 JSON。这些在真实模型上都发生过。
  • needs_review：不是 high 把握、或归类为 D99 的，自动标"需人工复核"，而不是直接入库。AI 给建议、人来拍板，详见 AI的局限与幻觉。
  • 校验失败的怎么办：重试 1～2 次（可以把失败原因附在提示词里再问一遍）；仍失败就进入人工队列，不要静默丢弃，也不要凑合入库。

接上真实模型（⚠ 提示词效果未在本机运行验证） ​

不同厂商接口不一样，这里只示意调用的位置，具体写法请看你所用平台的官方文档：

python
# 伪代码：⚠ 未在本机运行验证
prompt = build_prompt(raw)
reply = call_model(prompt, temperature=0)   # call_model 由你所用平台的 SDK 实现；分类任务建议低温度
ok, result = validate(reply, raw)
if ok and not result["needs_review"]:
    save_to_db(result["codes"])             # 仍建议先写入"待确认"状态，见 [[AI的局限与幻觉]]
else:
    send_to_human_queue(raw, reply)

分类类任务建议温度调低（参见 大语言模型 里的温度），但要记住"温度 0 也不保证每次逐字一致"。

常见坑与排查 ​

现象可能原因排查与对策
输出里夹着解释文字，JSON 解析失败规则里没写"只输出 JSON"，或示例带了解释规则写明；示例只放 JSON；解析时用正则取第一个 {...}
总是硬猜，不肯说"不知道"没给出口加"无法判断用 D99"并在示例里放一个
同类描述有时答 D03 有时答 D04代码含义没说清；温度高在代码表里给每个代码一句判别标准；降温度；加示例
换了模型/改了一句话，效果变差没有评测样本固定一套 20～50 条真实样本 + 期望答案，改一次跑一次
提示词越写越长，越来越乱补丁式修改按"角色/任务/材料/规则/格式"重新整理；删掉冲突的句子
用户输入里夹了"忽略前面的指令"提示注入用分隔符隔开数据；输出走校验；模型没有直接写库的权限（见 AI的局限与幻觉）
费用高提示词太长、示例太多精简；示例只留最有代表性的；视平台是否支持缓存重复前缀

业务视角与技术视角 ​

  • 业务视角：操作员输入不规范，导致缺陷统计失真；用 AI 归一化能减少人工整理量，但缺陷代码是质量数据，错一个会影响整改和客户报告，所以必须设计"高把握自动通过、低把握人工确认"的流程，并抽检。
  • 技术视角：提示词模板进代码库；validate 放在服务端；用 C# 实现同样的校验也很直接（System.Text.Json 解析 + 枚举字典，参见 System.Text.Json）；入库用"待确认"状态字段，确认后再生效，并记录 AI 建议、人工最终结论，便于以后评估准确率。公司实际缺陷代码表与 QMS 的接口请对照你们系统核实。

练习题与答案 ​

1. 下面的提示词有什么问题？"请帮我分析不良原因，要详细，不要太长。"

答案：没有材料（哪一条不良？依据什么？）、没有输出格式、"详细"与"不要太长"矛盾。改成："根据下面的不良描述和代码表，输出缺陷代码 JSON；不超过 100 字。"

2. 为什么示例里要放一个"拿不准 → D99"的样例？

答案：没有"拿不准"的出口，模型会倾向于对一切输入都硬选一个代码，把错的数据混进来；示例教它承认"不知道"。

3. 校验器里为什么要检查 evidence in raw_text？

答案：防止模型编造依据。模型的"引用"必须在原文里出现，这是一条廉价可靠的编造检测。

4.（动手） 在 validate 里增加一条规则：codes 里不能有重复代码，重复则返回失败。写出修改后的那一行并测试 {"codes": ["D04","D04"], ...}。

参考：在 bad = ... 之前加 if len(set(codes)) != len(codes): return False, "codes 有重复"。已实际运行，返回 (False, 'codes 有重复')。

5. 提示词里写"如果你不确定就输出 low"，模型输出 high 时就一定可靠吗？

答案：不一定。模型自评的"把握"并不是校准过的概率。要想知道可靠度，必须拿真实样本统计：看它自称 high 的那批里有多少真的对了。

小结 ​

  • 好提示词 = 角色/任务/材料/规则/输出格式五块齐全。
  • 示例比文字描述更管用，要包含"拿不准"的样例。
  • 结构化输出必须在程序侧校验：解析、枚举、依据是否在原文里。
  • 思维链提高复杂推理的准确率，但代价是更长更贵，且推理文字也可能是错的。
  • 不要靠感觉调提示词，要有固定评测样本。
  • AI 给建议，低把握的进人工队列。
