8D与CAPA

AI 生成 · 待核对制造业务QMS更新于 2026-10-21

⚠ 待核对：8D 各步骤的名称、历史（Ford 1987 年的 TOPS 手册，后来加入 D0 成为 Global 8D）已对照维基百科；ISO 9001 第 10.2 条的要点来自二手资料，未核对官方原文；VDA 也发布有 8D 指南（文末链接），但该 PDF 在本机无法读出文字，VDA 版本的具体步骤和时限我没有核对；钢网"面积比 0.66、宽厚比 1.5"是 IPC-7525 的常见引用值，来自二手资料，未核对 IPC 原文。SMT 虚焊案例是教学用的假设数据：数字自洽，并用 Python 和 SQL 复算过，但不是真实工厂数据。各客户对 8D 的格式和时限要求不同，以客户 SQE（供应商质量工程师）的要求为准。

本篇是 QMS 系列的一篇。读完你应该能：区分"现象、直接原因、根本原因"；用 5Why 和鱼骨图找根因；按 D0–D8 写完一份 8D；理解 CAPA（纠正和预防措施）的闭环和效果验证；用 SQL 做 CAPA 跟踪和逾期提醒。

一句话定义 ​

8D 是一套"用 8 个（加准备共 9 个）步骤解决重复发生的质量问题"的团队方法，从围堵、找根因到防止再发；CAPA（Corrective and Preventive Action，纠正和预防措施）是把这些措施登记成单子、指定责任人和期限、验证有效后才关闭的管理闭环。

先修知识 ​

  • 不合格品控制NCR：8D 和 CAPA 大多是由 NCR（或客诉）触发的，NCR 解决"眼前这批东西怎么办"，CAPA 解决"以后别再发生"。
  • 质量管理基础、缺陷代码与不良分类：用不良代码做柏拉图，才能知道先解决哪个问题。
  • 会写基本的 SQL 日期运算和 GROUP BY。

它解决什么问题 ​

一个工厂里最常见的怪圈：

每个月总有一两次虚焊爆发。产线把不良板返修了，品质向客户道歉并发了回复，大家松口气。一个月后同样的虚焊再来一次。没有人问过一句：为什么总是它？

这是"救火式"管理：处理了结果，没动原因。8D 与 CAPA 要做到：

  1. 先围堵，保证问题别再流到客户手里（止血）；
  2. 再找根因，找到"为什么发生"和"为什么没被发现"两件事；
  3. 然后永久纠正，改的是产生问题的系统，而不是再多检一遍；
  4. 最后验证措施有效，并预防同类问题在别的产品、别的线再发生；
  5. 全程有责任人、期限和记录，到期没做的会被催。

核心概念 ​

现象、直接原因、根本原因 ​

这三个层次分不清，是 8D 做砸的头号原因。

层次回答的问题SMT 虚焊例子对策的性质
现象看到了什么板子 FCT 间歇不工作，X-ray 看到 U3 焊点空洞 / 未润湿返修、挑选（纠正 Correction）
直接原因立刻导致它的是什么印刷在 U3 焊盘上的锡膏量不足，焊点没形成补印、加严检查
根本原因为什么会这样，改掉它问题就不再发生擦网频率沿用旧产品（每 50 块），0.5mm 间距孔壁积膏越印越少纠正措施（Corrective Action）：改擦网频率
逃逸点为什么在工厂内没被拦住SPI 体积下限设为标称的 50%，过宽，基本不报警纠正措施：收紧检测阈值
系统原因为什么这种错会发生在别的产品新产品导入（NPI）评审没有检查擦网频率和 SPI 阈值预防措施（Preventive Action）：补进评审清单

记住三个词的区别（ISO 9001 第 10.2 条的口径）：

  • 纠正（Correction）：处理已经发生的不合格本身（返修、报废），见 不合格品控制NCR。
  • 纠正措施（Corrective Action）：消除不合格的原因，防止它再次发生。
  • 预防措施（Preventive Action）：消除潜在不合格的原因，防止它在别处发生。ISO 9001:2015 把"预防措施"的思想并入"风险和机遇"的管理，但制造业现场的 CAPA 单仍普遍同时登记纠正和预防两类。

ISO 9001 第 10.2.1 条对发生不合格时的要求大致是：①对它做出反应，控制并纠正，处理后果；②评审和分析不合格，确定原因，并检查是否存在或可能发生类似的不合格；③实施所需的措施；④评审所采取纠正措施的有效性；⑤必要时更新策划时确定的风险和机遇；⑥必要时变更质量管理体系。第 10.2.2 条要求保留成文信息作为证据：不合格的性质和后续措施，以及纠正措施的结果。（来源：二手资料，见文首提示。）

8D 的步骤 ​

8D 起源于福特：1986 年福特动力总成部门被要求开发一种让设计、制造工程、生产团队共同解决顽固问题的方法，1987 年出版了《Team Oriented Problem Solving》（TOPS）手册；90 年代末福特修订为 Global 8D（G8D），加入了 D0 和逃逸点的概念。以下是维基百科对各步骤的概括：

步骤名称做什么SMT 虚焊例子里的产出
D0准备与应急响应记下触发症状，决定要不要开 8D，必要时先做应急动作记录 FQC 报警；当班先停 U3 相关机种出货
D1组建团队有产品和工艺知识的跨部门小组，指定组长品质（组长）、SMT 工艺、设备、产线班长
D2描述问题用 5W2H 把问题量化，写清"是什么、不是什么"3 天 3,600 块里 23 块 U3 虚焊，0.639%
D3临时围堵保证问题不流向客户的临时措施，要有效、要验证出货前对 U3 100% X-ray；库存板复检
D4根因与逃逸点找出并验证根本原因，以及为什么没被发现5Why + 鱼骨图 + 数据验证
D5验证永久纠正措施试生产验证拟采用的措施能解决问题小批量试产
D6实施永久纠正措施正式落地并用证据证明有效，撤销临时围堵改擦网频率、收紧 SPI 阈值，3 天数据
D7预防再发修改制度、流程、文件，把同类问题堵在系统层面NPI 评审清单、相似机种横向展开
D8认可团队正式关闭，感谢团队，沉淀经验8D 报告归档

不同公司和客户的 8D 在 D5/D6 的划分上略有差别（有的把"选择并验证措施"放 D5、"实施"放 D6，有的把"实施并验证"放 D6），汽车行业的 VDA 也有自己的格式。照客户要求的格式写。

5W2H：把问题描述清楚（D2） ​

问回答
What 什么问题A100 板 U3（QFN32）焊点虚焊，FCT 间歇不上电
Where 在哪发现、在板上哪里FQC 工位发现；只在 U3，不在其它元件
When 什么时候开始10 月 12 日开始，之前三周没有
Who 哪条线 / 哪个班 / 哪个人2 号线，三个班都有
Why 初步原因（D4 才回答，D2 不下结论）
How 怎么发现FQC 抽检、FCT 不良

一个有用的小练习是写"是什么、不是什么"：是 U3、不是别的 IC；是 2 号线、1 号线没有……这些对比直接把原因范围缩小。

5Why：连续问"为什么" ​

一次问一层，直到问到"改掉它问题就不再出现"为止。不是死板的 5 次，可能 3 次也可能 7 次。

层问答（需要用数据或现场确认，不要拍脑袋）
Why 1为什么 U3 会虚焊？X-ray 显示焊点空洞和未润湿，焊料量不足
Why 2为什么焊料不足？SPI 数据显示 U3 焊盘锡膏体积在连续印刷后期低至标称的 58%
Why 3为什么印刷后期锡膏量下降？钢网 0.5mm 间距的小开孔，孔壁积膏，越印越堵
Why 4为什么孔壁积膏没被清掉？自动擦网设置为每 50 块一次，对细间距太稀
Why 5为什么设成每 50 块？新机种 A100 导入时沿用了旧机种（0.65mm 间距）的参数，NPI 评审没有检查这一项
逃逸点为什么没拦住？SPI 体积下限设为标称的 50%，最低的 58% 没触发报警

根因是 Why 4 / Why 5（参数沿用 + 评审漏项），逃逸点是 SPI 阈值。注意验证：要用数据证明这个原因真的在起作用——比如把擦网频率改为每 10 块，看虚焊是否消失；"改了没效果"就说明根因找错了。

鱼骨图（石川图）：系统地列原因 ​

鱼骨图把可能原因按类别排开，避免只盯着一个方向。电子制造常用"人、机、料、法、环、测"（4M1E 加测量）。图中红字是确认的根因或逃逸点，其余是排查后排除的：

柏拉图：先打最大的 ​

D2 常用柏拉图（见 缺陷代码与不良分类）。本篇实验里，虚焊发生的 3 天 FQC 一共发现 34 个不良：U3 虚焊 23 个（67.6%），连锡 4 个（11.8%），偏移和缺件各 3 个（各 8.8%），极性反 1 个（2.9%）。前两项累计 79.4%，先解决 U3 虚焊，投入产出比最高。

CAPA 的闭环 ​

CAPA 把"改进"变成可管理的单子，闭环如下：

  1. 创建：由 NCR、客诉、内审、审核发现、趋势异常触发，关联来源单号；
  2. 分析并分派：写根因，拆成措施，指定责任人和到期日；
  3. 实施：责任人执行，必要时写进变更（变更管理ECN-ECR）；
  4. 效果验证：不是"做完了"，而是"有效"——看数据。要定好验证标准（例如不良率 ≤ 0.1%）和足够的观察样本与时间；
  5. 关闭：验证有效才能关闭；无效就退回重新分析。

CAPA 的状态在实验里设计为 Open → InProgress → Verified → Closed，逐级前进、不能跳步；进入 Verified 必须填全根因、纠正措施、预防措施。到期未完成的要被催办，这是 CAPA 系统最核心的"牙齿"。

业务视角 ​

什么时候必须开 8D ​

通用的触发条件（具体阈值各公司不同，⚠ 请对照你们的程序文件）：

  • 客户投诉（尤其是严重度高的）；
  • 同一不良代码在一段时间内重复超过阈值；
  • 来料批退严重、同一供应商重复批退（对供应商发 SCAR，见 供应商质量管理）；
  • 内审或外审的不符合项；
  • 严重的内部失败（影响安全、法规、批量报废）。

角色 ​

角色职责
品质工程师 / SQE组长或推动者，把控流程和质量，验证有效性
工艺 / 设备 / 生产提供专业知识，实施措施
责任人（Owner）每条措施一个，对期限负责
管理层看逾期清单，协调资源，审批关闭

常见时限（行业习惯，非通用标准） ​

很多客户要求：D3 围堵措施 24 小时内给出，8D 初步报告几天内提交，完整报告 15–30 天内关闭。这些数字因客户而异，写进你们的程序文件时以客户的 SQE 手册为准。

KPI ​

指标含义
CAPA 按时关闭率在到期日前或当天关闭的比例（实验里按责任人统计）
CAPA 平均关闭天数开单到关闭
逾期未关闭数及账龄管理层最该盯的数字
重复发生率同一根因再次出现的比例，直接反映措施有没有治本
措施有效率验证为有效的比例

技术视角 ​

表设计：Capa ​

字段含义
CapaNoCAPA 编号，唯一
NcrNo来源 NCR 编号（客诉来源可另加 ComplaintNo，或把 NCR 类型扩展为 Customer）
RootCause根本原因（文字）
CorrectiveAction纠正措施
PreventiveAction预防措施
Owner责任人
DueDate到期日
StatusOpen / InProgress / Verified / Closed
OpenedDate、VerifiedAt、ClosedAt开单、验证、关闭日期（扩展，用于账龄和按时率）
sql
CREATE TABLE dbo.Capa (
    Id               INT IDENTITY PRIMARY KEY,
    CapaNo           NVARCHAR(30)  NOT NULL,
    NcrNo            NVARCHAR(30)  NOT NULL,
    RootCause        NVARCHAR(500) NULL,
    CorrectiveAction NVARCHAR(500) NULL,
    PreventiveAction NVARCHAR(500) NULL,
    Owner            NVARCHAR(30)  NOT NULL,
    DueDate          DATE          NOT NULL,
    Status           NVARCHAR(15)  NOT NULL DEFAULT 'Open' CHECK (Status IN ('Open','InProgress','Verified','Closed')),
    OpenedDate       DATE          NOT NULL,
    VerifiedAt       DATE          NULL,
    ClosedAt         DATE          NULL,
    CONSTRAINT UQ_Capa_CapaNo UNIQUE (CapaNo));
CREATE INDEX IX_Capa_Status_Due ON dbo.Capa (Status, DueDate);

要点：

  • (Status, DueDate) 索引服务于最高频的查询："未结的、到期日早于今天的"。
  • 文字列用 NVARCHAR，中文才不会变成问号；SqlSugar 实体里写 ColumnDataType = "nvarchar(500)"。
  • 实际系统里 NcrNo 建议加外键指向 Ncr；实验里为了能单独运行没有加。
  • 一个 NCR 可能对应多个 CAPA（一个根因对应多条措施）。如果要精细到措施级跟踪（每条措施单独责任人、期限、状态），可以另建措施子表；实验为了聚焦只用一张主表。
  • 8D 报告本身（D0–D8 的文字）通常存成附件或者结构化的步骤表；CAPA 单则是跟踪措施的"账本"。

状态机 ​

Open → InProgress → Verified → Closed，和 工单管理、不合格品控制NCR 的套路一样：流转表 + WHERE 条件。进入 Verified 的条件写在 WHERE 里："根因、纠正措施、预防措施都不为空"；关闭只允许从 Verified 来。

逾期定义与提醒 ​

问题建议
什么叫逾期状态是 Open 或 InProgress，且 DueDate < 今天
Verified 但没关闭的算逾期吗措施已经做完，只是没行政关闭，单独列"待关闭清单"，不混进逾期
什么时候提醒每天定时任务（SQL Agent 作业、Windows 服务或后台任务）扫描：到期前 7 天提醒责任人，逾期后提醒责任人和其主管，逾期超过 30 天升级给质量负责人
"今天"怎么取查询里用参数传入日期，不要写死 GETDATE()——这样才方便测试和回放

逐步例子：SMT 虚焊 8D（教学案例） ​

以下数据为教学案例的假设数据，自洽并经复算。

D1：张伟（品质，组长）、SMT 工艺、设备、2 号线班长，共 4 人。

D2：5W2H 见上文。柏拉图：U3 虚焊占 67.6%。"不是什么"：只有 2 号线，1 号线的 B200（QFN 间距 0.65mm）没有。

D3（10 月 14 日起）：临时围堵——所有 A100 出货前对 U3 做 100% X-ray；成品仓库存板全部复检；产线 SPI 报警人工确认。围堵有效的证据：出货批 X-ray 复检后，客户端 0 投诉。围堵是临时的，要花额外人力，所以必须尽快有永久措施。

D4：

  • 数据验证 1：钢网开孔 0.25 × 0.80 mm，厚 0.12 mm：面积比 (0.80×0.25) / (2×(0.80+0.25)×0.12) = 0.794，大于经验下限 0.66；宽厚比 0.25/0.12 = 2.08，大于 1.5。钢网设计没问题，排除。

  • 逃逸点：SPI 下限是 50%，最低点 58% 没有触发报警。
  • 5Why 与鱼骨图见上文。

D5：在 2 号线小批量试产 200 块：擦网频率改为每 10 块，SPI 下限改为 70%。每 10 块一个周期里，平均体积 95.5%，最低 93%，没有一块低于 70%；试产 200 块虚焊 0 块。

    NcrNo            NVARCHAR(30)  NOT NULL,        -- 来源 NCR（实际系统建议加外键；本实验为方便单独运行未加）
    RootCause        NVARCHAR(500) NULL,

    PreventiveAction NVARCHAR(500) NULL,

    Status           NVARCHAR(15)  NOT NULL DEFAULT 'Open' CHECK (Status IN ('Open','InProgress','Verified','Closed')),
    OpenedDate       DATE          NOT NULL,
    VerifiedAt       DATE          NULL,
    ClosedAt         DATE          NULL,
    CONSTRAINT UQ_Capa_CapaNo UNIQUE (CapaNo));
CREATE INDEX IX_Capa_Status_Due ON dbo.Capa (Status, DueDate);   -- 逾期查询就靠它
CREATE TABLE dbo.FqcDaily (Day DATE PRIMARY KEY, Phase NVARCHAR(10) NOT NULL, Inspected INT NOT NULL, OpenJoint INT NOT NULL);
CREATE TABLE dbo.FqcDefect (Day DATE NOT NULL, DefectName NVARCHAR(30) NOT NULL, Cnt INT NOT NULL);
GO
-- 状态流转：Open -> InProgress -> Verified -> Closed，逐级，不能跳；进入 Verified 必须填全三项
CREATE PROC dbo.usp_CapaMove @CapaNo NVARCHAR(30), @To NVARCHAR(15), @On DATE, @Msg NVARCHAR(100) OUTPUT
AS BEGIN
    SET NOCOUNT ON;
    UPDATE c SET Status = @To,
           VerifiedAt = CASE WHEN @To = 'Verified' THEN @On ELSE c.VerifiedAt END,
           ClosedAt   = CASE WHEN @To = 'Closed'   THEN @On ELSE c.ClosedAt END
    FROM dbo.Capa c
    JOIN (VALUES ('Open','InProgress'), ('InProgress','Verified'), ('Verified','Closed')) t(f, t2)
      ON t.f = c.Status AND t.t2 = @To
    WHERE c.CapaNo = @CapaNo
      AND (@To <> 'Verified' OR (NULLIF(c.RootCause, N'') IS NOT NULL
                             AND NULLIF(c.CorrectiveAction, N'') IS NOT NULL
                             AND NULLIF(c.PreventiveAction, N'') IS NOT NULL));
    SET @Msg = CASE WHEN @@ROWCOUNT = 1 THEN N'成功' ELSE N'拒绝：流转不合法，或根因/纠正/预防措施没填全' END;
END;
GO

-- ========== 3. 逾期与提醒查询 ==========
DECLARE @Today DATE = '2026-10-21';
PRINT N'--- 1. 逾期清单（未到 Verified 且已过期），最严重的在前 ---';
SELECT CapaNo, Owner, DueDate, Status, DATEDIFF(DAY, DueDate, @Today) AS OverdueDays
FROM dbo.Capa
WHERE Status IN ('Open','InProgress') AND DueDate < @Today
ORDER BY OverdueDays DESC, CapaNo;
PRINT N'--- 2. 7 天内到期（含今天），提前提醒 ---';
SELECT CapaNo, Owner, DueDate, Status, DATEDIFF(DAY, @Today, DueDate) AS DaysLeft
FROM dbo.Capa
WHERE Status IN ('Open','InProgress') AND DueDate BETWEEN @Today AND DATEADD(DAY, 7, @Today)
ORDER BY DueDate, CapaNo;
PRINT N'--- 3. 逾期账龄分桶 ---';
SELECT CASE WHEN d <= 7 THEN N'1-7 天' WHEN d <= 30 THEN N'8-30 天' ELSE N'30 天以上' END AS Bucket, COUNT(*) AS Cnt
FROM (SELECT DATEDIFF(DAY, DueDate, @Today) AS d FROM dbo.Capa WHERE Status IN ('Open','InProgress') AND DueDate < @Today) x
GROUP BY CASE WHEN d <= 7 THEN N'1-7 天' WHEN d <= 30 THEN N'8-30 天' ELSE N'30 天以上' END
ORDER BY MIN(d);
PRINT N'--- 4. 按责任人：未结数、逾期数、已关闭数、按时关闭率 ---';
SELECT Owner,
       SUM(CASE WHEN Status <> 'Closed' THEN 1 ELSE 0 END) AS NotClosed,
       SUM(CASE WHEN Status IN ('Open','InProgress') AND DueDate < @Today THEN 1 ELSE 0 END) AS Overdue,
       SUM(CASE WHEN Status = 'Closed' THEN 1 ELSE 0 END) AS ClosedCnt,
       CASE WHEN SUM(CASE WHEN Status = 'Closed' THEN 1 ELSE 0 END) = 0 THEN NULL
            ELSE CAST(100.0 * SUM(CASE WHEN Status = 'Closed' AND ClosedAt <= DueDate THEN 1 ELSE 0 END)
                      / SUM(CASE WHEN Status = 'Closed' THEN 1 ELSE 0 END) AS DECIMAL(5,1)) END AS OnTimeRatePct
FROM dbo.Capa GROUP BY Owner ORDER BY Owner;
PRINT N'--- 5. 已验证但还没关闭（别让它们躺着）---';
SELECT CapaNo, Owner, VerifiedAt FROM dbo.Capa WHERE Status = 'Verified';

SELECT Phase, SUM(Inspected) AS Inspected, SUM(OpenJoint) AS OpenJoint,
       CAST(100.0 * SUM(OpenJoint) / SUM(Inspected) AS DECIMAL(6,3)) AS DefectRatePct,
       CAST(1000000.0 * SUM(OpenJoint) / SUM(Inspected) AS INT) AS Ppm
FROM dbo.FqcDaily GROUP BY Phase ORDER BY Phase DESC;

             AND 1.0 * SUM(CASE WHEN Phase='After' THEN OpenJoint END) / SUM(CASE WHEN Phase='After' THEN Inspected END) <= 0.001

# 8D 案例的数字复算（案例数据是教学用的假设数据，但算术要自洽）
# 1) 钢网开孔：U3(QFN32, 0.5mm 间距) 焊盘开孔 0.25 x 0.80 mm，钢网厚 0.12 mm
L, W, T = 0.80, 0.25, 0.12
print(f"面积比 = {(L * W) / (2 * (L + W) * T):.3f}（经验下限 0.66），宽厚比 = {W / T:.2f}（经验下限 1.5）")
# 2) 擦网后连续印刷第 n 块时，U3 焊盘锡膏体积占标称的百分比（SPI 实测点，其余按线性插值）
pts = {1: 98, 10: 93, 20: 85, 30: 76, 40: 66, 50: 58}
xs = sorted(pts)
def vol(n):
    for a, b in zip(xs, xs[1:]):
        if a <= n <= b:
            return pts[a] + (pts[b] - pts[a]) * (n - a) / (b - a)
for cycle in (50, 10):
    v = [vol(n) for n in range(1, cycle + 1)]
    low = sum(1 for x in v if x < 70)
    print(f"每 {cycle} 块擦一次：平均 {sum(v) / len(v):.1f}%，最低 {min(v):.1f}%，低于 70% 的块数 {low}/{cycle}（{100 * low / cycle:.0f}%）")
for lo in (50, 70):
    print(f"SPI 下限 {lo}%：每 50 块一个周期里被拦下的块数 = {sum(1 for n in range(1, 51) if vol(n) < lo)}")
# 3) 措施前后的虚焊率（与 capa.sql 的结果核对）
before = [(1200, 8), (1100, 7), (1300, 8)]
after = [(1250, 1), (1150, 0), (1300, 1)]
for name, rows in (("措施前", before), ("措施后", after)):
    n, d = sum(r[0] for r in rows), sum(r[1] for r in rows)
    print(f"{name}：检验 {n}，虚焊 {d}，不良率 {100 * d / n:.3f}%，约 {int(1e6 * d / n)} PPM（截断取整，和 SQL 的 CAST AS INT 一致）")
print(f"下降幅度 {100 * (1 - (2 / 3700) / (23 / 3600)):.1f}%")
# 4) 柏拉图
p = {"U3 虚焊": 23, "连锡": 4, "偏移": 3, "缺件": 3, "极性反": 1}
tot, cum = sum(p.values()), 0
for k, v in sorted(p.items(), key=lambda kv: -kv[1]):
    cum += v
    print(f"{k}：{v}（{100 * v / tot:.1f}%），累计 {100 * cum / tot:.1f}%")

实验 2：C# + SqlSugar ​

前提：已运行 capa.sql；项目同 不合格品控制NCR 实验 2 的 QmsLab（有 Db.cs）。新建 LabCapa.cs：

csharp
using SqlSugar;

namespace QmsLab;

// 映射到 T-SQL 实验里建好的 dbo.Capa 表
[SugarTable("Capa")]
public class Capa
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public int Id { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(30)")] public string CapaNo { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(30)")] public string NcrNo { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(500)", IsNullable = true)] public string RootCause { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(500)", IsNullable = true)] public string CorrectiveAction { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(500)", IsNullable = true)] public string PreventiveAction { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(30)")] public string Owner { get; set; }
    public DateTime DueDate { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(15)")] public string Status { get; set; }
    public DateTime OpenedDate { get; set; }
    [SugarColumn(IsNullable = true)] public DateTime? VerifiedAt { get; set; }
    [SugarColumn(IsNullable = true)] public DateTime? ClosedAt { get; set; }
}

public static class LabCapa
{
    public static void Run(SqlSugarClient db)
    {
        var today = new DateTime(2026, 10, 21);       // 固定“今天”，保证每次输出一致；真实系统用 DateTime.Today
        var overdue = db.Queryable<Capa>()
            .Where(c => (c.Status == "Open" || c.Status == "InProgress") && c.DueDate < today)
            .OrderBy(c => c.DueDate)
            .ToList();
        Console.WriteLine($"逾期 CAPA 共 {overdue.Count} 张：");
        foreach (var c in overdue)
            Console.WriteLine($"{c.CapaNo} {c.Owner} 到期 {c.DueDate:yyyy-MM-dd} 已逾期 {(today - c.DueDate).Days} 天");
        var soon = db.Queryable<Capa>()
            .Where(c => (c.Status == "Open" || c.Status == "InProgress") && c.DueDate >= today && c.DueDate <= today.AddDays(7))
            .OrderBy(c => c.DueDate).ToList();
        Console.WriteLine($"7 天内到期 {soon.Count} 张：{string.Join("、", soon.Select(c => c.CapaNo))}");
    }
}

常见坑与排查 ​

坑现象 / 事实办法
把现象当根因"原因：操作员疏忽"，措施是"加强培训"人为失误是现象，继续问：为什么容易出错？是否缺防错（poka-yoke）？
5Why 靠拍脑袋每个"因为"都没有证据每层都要有数据或现场确认；根因要能复现和消除
只有围堵没有永久措施D3 的 100% 检查一直做下去，成本越来越高围堵是临时的，设撤销条件和日期
忘了逃逸点只改了产生问题的环节，检测漏洞依旧D4 同时问"为什么没被发现"
效果验证样本太少观察了 1 天、300 块就宣布有效事先定验证标准和最小样本量、观察周期
只改这一条线同类问题在别的机种复发D7 做横向展开
CAPA 没有期限和责任人成了"愿望清单"必填；逾期自动提醒并升级
到期日被反复延期逾期永远是零，但问题没解决延期要审批并留日志，统计延期次数
关闭条件形同虚设没验证有效就关了状态机强制：只有 Verified 才能 Closed；Verified 要求内容填全
重复发生却开新单同一根因每次开新 CAPA创建时检索历史，关联并升级，统计重复率

练习题与答案 ​

  1. 请说出纠正、纠正措施、预防措施的区别，并各举一个 SMT 的例子。 答：纠正是处理已发生的不合格（返修虚焊板）；纠正措施消除原因防止再发（把擦网频率从每 50 块改为每 10 块）；预防措施防止同类问题在别处发生（把检查项加进 NPI 清单，并检查其他机种）。
  2. 为什么 8D 要同时找"根因"和"逃逸点"？ 答：根因回答"为什么发生"，逃逸点回答"为什么没被发现"。只改前者，下次类似问题仍可能流出；只改后者，问题仍然不断发生。
  3. 实验里 CAPA-26-005 的到期日是 10 月 28 日，"今天"是 10 月 21 日，为什么它出现在 7 天内到期的清单里？ 答：DATEDIFF(DAY, 今天, 到期日) = 7，BETWEEN @Today AND DATEADD(DAY, 7, @Today) 含两端，所以刚好在内。
  4. 为什么按时关闭率的分母是"已关闭数"，没有已关闭时要显示 NULL 而不是 0%？ 答：没有已关闭的单子，"按时率"无意义；显示 0% 会误导成"全部不按时"。
  5. 措施前虚焊率 0.639%，措施后 0.054%，下降了多少？是否一定能说措施有效？ 答：下降了 (0.639 - 0.054) / 0.639 = 91.5%。不一定只凭两个数字下结论：需要样本量足够（实验中 3,700 ≥ 3,000）、观察周期覆盖多个班次和批次，并排除其它同时变化的因素（如换了锡膏批次）。
  6. CAPA 单从 Open 想直接改成 Verified 会怎样？为什么？ 答：被拒绝。流转表中没有这条路径；这保证每条措施至少经过"实施中"，不会没做就被标成"已验证"。
  7. （思考）如果一个 CAPA 到期时措施没做完，应该怎么处理才不会失控？ 答：申请延期，写清原因和新到期日，经主管批准，延期记录进日志，统计延期次数；延期超过一定次数或天数，自动升级。

小结 ​

  • 区分现象、直接原因、根本原因和逃逸点；用 5Why 配合数据，用鱼骨图保证不漏方向。
  • 8D：D0 准备与应急、D1 团队、D2 描述问题、D3 围堵、D4 根因与逃逸点、D5 验证措施、D6 实施措施、D7 预防再发、D8 认可团队。
  • CAPA 是闭环：创建、分派、实施、效果验证、关闭；逾期要被催、被升级。
  • 技术上 CAPA 就是一张带状态机的表 + (Status, DueDate) 索引 + 参数化"今天"的逾期查询。
  • 效果验证需要事先定标准和样本量；措施落地要走变更（变更管理ECN-ECR）。
