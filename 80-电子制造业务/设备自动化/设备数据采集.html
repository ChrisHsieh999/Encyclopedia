设备数据采集

AI 生成 · 待核对制造业务设备自动化数据采集更新于 2026-10-21

⚠ 待核对：本篇讲的是通用的采集思路。IPC-CFX（需要 AMQP 1.0 消息代理）、SEMI GEM/SECS-II/HSMS 的描述已对照 IPC 官网和公开介绍，但 SEMI 标准原文是收费文件，我没有读到原文。例子里的"温度×10""32767 表示传感器断线"是为讲解而设的假想设备约定，真实设备的寄存器地址、比例、特殊值一律以设备手册为准。你们公司自研 EAP/MES 的采集方式请对照核实。实验代码和输出是我在本机（Python 3.12、.NET 10、SQL Server LocalDB）实际运行得到的，只连本机回环地址，不连接任何真实设备。

本篇是 EAP 系列第 2 篇。读完你应该能：说出该采哪几类数据、用哪些方式采；设计采集频率、死区和存储；处理断线重连、时钟不准、单位和比例换算、数据质量问题；用 C# 搭出采集服务的骨架；并亲手跑通一个"读 Modbus 温度寄存器 → 压缩 → 落库"的采集器。

一句话定义 ​

设备数据采集是用程序按一定规则从设备读取数据，换算成有意义的工程值，打上时间和质量标记，可靠地存进数据库的过程。关键在"可靠"二字：设备会断线，网络会抖动，数据库会短暂不可用，采集器要保证数据不丢、不重、不乱。

先修知识 ​

  • EAP：知道采集是 EAP 五项职责之一。
  • Modbus、Modbus-TCP、Modbus数据模型与地址：本篇的实验就读 Modbus 寄存器。
  • 后台服务与Windows服务：C# 里长期运行的服务怎么写。
  • 基础 SQL 和 Python：会看 INSERT、SELECT 即可。

它解决什么问题 ​

一个常见的故事：回流焊炉的炉温每秒都在变，工艺工程师想在出质量问题时回头看"那一小时炉温有没有异常"。如果采集做得糙，会出现这些问题：

  • 网线松了 10 秒，那 10 秒的数据永远没了，也没人知道缺了；
  • 采集程序每秒写一次数据库，一天 8.64 万行/位号，位号一多数据库被拖慢；
  • 设备寄存器里是 2531，程序当成 2531 ℃ 存了进去（实际是 253.1 ℃）；
  • 传感器断线时寄存器返回 32767，程序把它当成真实温度，报警系统响了一夜；
  • 采集服务器的时钟比设备慢 3 分钟，事件顺序对不上。

本篇就是把这些坑逐个填上。

核心概念 ​

采什么：五类数据 ​

类别例子特点典型采集方式
状态运行/待机/报警/停机离散值，变化时才重要变化上报或高频轮询后检测变化
产量累计贴装点数、过板数单调递增的计数器，注意溢出和清零周期读取后算差值
报警报警码、报警开始/结束时间事件型，不能漏优先用设备主动上报；轮询要足够快
参数设定值、Recipe 名称、程序版本变化少，但出错代价大变化时读取，定期核对
过程数据炉温、气压、刮刀压力、贴装偏移连续量，数据量大周期采样 + 死区压缩

"采什么"取决于要回答什么问题：想算稼动率（OEE）就要状态和产量；想追溯质量要参数和过程数据；想报警要事件。先写下问题，再决定采什么，别"能采的都采"。

怎么采：六种常见通道 ​

通道原理优点局限
PLC 寄存器通过 Modbus、西门子S7通信、三菱MC协议、欧姆龙FINS 等协议轮询读取 PLC 的存储区通用，老设备常有只有地址没有含义，要对着地址表；轮询而非主动上报
OPC UA标准化的工业通信，数据带名字、类型、单位，支持订阅（变化时推送）自描述，跨厂商，安全机制完善设备要支持；配置比 Modbus 复杂，见 OPC-UA
SECS/GEM半导体行业的设备通信标准：SEMI E5（SECS-II 消息内容）、E37（HSMS，走以太网的传输）、E30（GEM，通用设备模型）。据公开介绍，GEM 涵盖远程控制、数据输出、报警与事件、程序管理、状态模型事件、报警、Recipe 管理的模型成熟主要在半导体设备上；SMT 设备少见，见 SECS-GEM
设备日志/文件设备把生产记录写成 CSV/XML/文本，采集程序监听文件夹解析很多设备只有这条路；不侵入设备是事后的、非实时；格式各厂不同；要处理文件正在写入、轮转、编码问题
数据库设备软件把数据存进本地数据库（Access、SQLite、SQL Server），采集程序读库结构化，易查询要征得厂商同意（有的会影响保修）；表结构各异；别在它库上长时间加锁
IPC-CFX / HermesCFX（IPC-2591）是 IPC 的组装行业数据交换标准：设备把事件消息发布到消息代理，据 IPC 的指南，代理必须是 AMQP 1.0，推荐 RabbitMQ。Hermes（IPC-HERMES-9852）管设备之间的板子交接，基于 TCP/IP 和 XML，可携带板码，是 SMEMA 的继任者行业标准，消息语义统一要设备支持，各厂商实现的消息子集不同，见 IPC-CFX、IPC-Hermes

选择的经验：能用标准协议（CFX、OPC UA）就别用私有接口；没有接口再用 PLC 寄存器；实在没有再用文件/数据库；连这些都没有，就加传感器（见 设备联网方案）。

位号表：采集的"地址簿" ​

不管用哪种通道，采集器都需要一张位号表（Tag List），一个位号对应设备上的一个数据点：

位号设备地址数据类型比例单位死区说明
TempREFLOW-01保持寄存器 0uint160.1℃0.5第 3 温区温度
CountREFLOW-01保持寄存器 1uint161块0累计过板数
StatusREFLOW-01保持寄存器 2uint161无00 待机/1 运行/2 报警

位号表放在数据库或配置文件里，不要写死在代码里：新增一台设备、改一个比例，只改数据，不重新发布程序。

采集频率：不是越快越好 ​

数据建议思路
炉温等缓变量1 到 5 秒采一次，配合死区压缩
状态1 秒左右，或设备支持订阅/事件时用事件
产量计数器5 到 60 秒，算差值，不需要太快
报警尽量事件上报；轮询的话，间隔不能比最短报警持续时间长

采样定理的朴素版本：你想看到持续 T 秒的现象，采样间隔至少要小于 T，最好小于 T 的一半。每 10 秒采一次，一个 3 秒的报警有七成概率被漏掉。（这里的"七成"只是个直觉的比方：3 秒的事件落在两次采样之间的概率约 7/10。）

存储：先算一笔账 ​

20 个位号，每秒存一条：20 × 86400 = 1,728,000 行/天，一年约 6.3 亿行。如果用"死区压缩"后只保留 10% 的数据，也要 6300 万行。所以要同时做：

  1. 死区压缩（Deadband）：与"上次已记录的值"相比，变化小于死区就不记。注意比的是上次记录的值，不是上次读到的值，否则缓慢漂移（每次涨 0.1，永远小于 0.5）会一直不被记录。
  2. 心跳：值一直没变也每隔固定时间记一条，让人知道采集器还活着，而不是"死了"。
  3. 分层存储：原始数据保留较短时间（如 3 个月），长期保留小时/班次汇总；超期数据归档。
  4. 索引与分区：按（设备，位号，时间）建索引；表很大时按月分区（见 数据库索引）。
  5. 批量写入：攒一批再一次写，比一条条写快得多。

断线重连与续传 ​

网络和设备都不可靠，采集器要做到：

  • 超时：连接超时、读超时都要设，不要无限等。
  • 重连带退避：失败后等 0.1 秒、0.2 秒、0.4 秒…重试，上限比如 30 秒，避免对重启中的设备狂轰滥炸。
  • 断线要有记录：断线期间的数据是"缺失"而不是"没变化"，要能区分（数据质量标记，见下）。
  • 续传（Store and Forward）：采集到的数据先进本地队列，数据库不可用时留在队列（或本地文件）里，恢复后补写。
  • 幂等写入：补写时可能重复写同一条，所以写库要保证"同一条写两次也只有一行"。常用做法是给（设备，位号，时间）建唯一约束，写入用 WHERE NOT EXISTS 或 MERGE。

时间同步 ​

设备有自己的时钟，采集服务器有自己的时钟，数据库服务器还有一个。时间对不上，事件顺序就错了：

  • 采集器、数据库服务器都与同一个 NTP 时间源同步。
  • 设备自己带时间戳的（日志、CFX 事件），存两个时间：DeviceTime（设备说的）和 ReceiveTime（采集器收到的）。两者差值大，说明设备时钟漂移或网络延迟大。
  • 内部统一用 UTC 存储，界面再转本地时间（见 工艺参数与炉温曲线管理 里同样的建议）。
  • 设备不带时间戳的轮询数据，用采集时刻作为时间，并知道它有最大一个轮询周期的误差。

单位换算与标度 ​

设备寄存器里是整数，真实值要换算。常见情形：

情形例子处理
整数 + 比例寄存器 2531，比例 0.1253.1
有符号数uint16 的 65526 其实是 int16 的 -10按 int16 解释
32 位数据占两个寄存器浮点数、大计数器先问清字序（见下）
量程映射模拟量原始值 0~10000 对应 0~300 ℃工程值 = 原始值 / 10000 × 300，原始值 5000 对应 150.0 ℃
特殊值32767 = 传感器断线先判断特殊值，再换算

32 位数据的字序：一个 32 位浮点数占两个 16 位寄存器，两个寄存器谁在前各厂家不同。用 Python 验证：寄存器值 0x4348 和 0x0000，按"高字在前"读成浮点数是 200.0；按"低字在前"读成 2.4e-41（显然是乱码）。同样，32 位整数 [0x0001, 0x86A0] 按高字在前读是 100000。（以上结果我在本机运行验证过。）所以：读出来的值明显离谱，先怀疑字序。

数据质量 ​

每条数据带一个质量标记，让使用者知道能不能信：

质量含义例子
好（Good）正常读到253.1 ℃
坏（Bad）读不到或明显错误传感器断线（32767）、设备断线
不确定（Uncertain）能读到但不可靠值被冻结多个周期没变、超出量程

常用检查：范围检查（温度不可能是 -500 ℃）、突变检查（1 秒涨 100 ℃ 不合理）、冻结检查（模拟量连续一小时一位小数都没变，多半是传感器或采集挂了）、计数器倒退检查（累计数变小，可能清零了）。坏数据要保留并标记，不要悄悄丢掉也不要悄悄当好数据。

技术视角：C# 采集服务架构 ​

用 C# 做采集服务，推荐拆成三块，用接口和队列解耦：

  • 驱动层：定义一个 IDeviceDriver 接口，每种协议实现一个（Modbus、S7、OPC UA、文件监听）。上层只知道"读一次拿到位号值"。换协议只换实现。NModbus 是 .NET 里常用的 Modbus 库。
  • 队列：用 System.Threading.Channels 的 Channel<T>。有界队列满了会让生产者等待，保护内存。
  • 入库：消费者取一批、一次写入，失败就保留重试。
  • 宿主：用 BackgroundService，既能当控制台程序调试，又能装成 Windows 服务长期运行，见 后台服务与Windows服务。
  • 多设备：每台设备一个独立的轮询任务，一台掉线不影响其他台。

动手实验：读 Modbus 模拟从站的温度寄存器并落库 ​

目标：写一个采集器：轮询 Modbus 从站的温度，死区压缩，断线自动重连，数据库暂时不可用时不丢数据，重复写入不产生重复行。全程只连本机回环地址。

temp_server.py：

python
"""模拟温控仪（Modbus TCP 从站）：温度按固定剧本变化，第一条连接在服务 6 个请求后"掉线"。"""
import socket
import struct
import time

HOST, PORT = "127.0.0.1", 5021
DROP_AFTER = 6          # 第一条连接服务 6 个请求后，第 7 个请求不回应并断开
OFFLINE_SECONDS = 0.8   # 掉线后这段时间内拒绝连接，模拟设备重启

# 每次"读 3 个寄存器"推进一步：(温度×10, 累计产量, 状态 1=运行 2=报警)；温度 32767 表示传感器断线
SCRIPT = [
    (2500, 100, 1), (2503, 101, 1), (2498, 102, 1), (2512, 103, 1), (2560, 104, 1), (2561, 105, 1),
    (2560, 106, 1), (2625, 107, 1), (2625, 108, 1), (2626, 109, 1), (2624, 110, 1), (2700, 111, 2),
    (2701, 112, 2), (32767, 113, 2), (2702, 114, 1), (2701, 115, 1), (2700, 116, 1),
]
step = 0  # 剧本进度，跨连接保留（掉线丢失的那个请求不推进）


def recv_exact(conn, n):
    buf = b""
    while len(buf) < n:
        chunk = conn.recv(n - len(buf))
        if not chunk:
            raise ConnectionError
        buf += chunk
    return buf


def serve(conn, drop_after, srv):
    global step
    served = 0
    while True:
        tid, _pid, length, unit = struct.unpack(">HHHB", recv_exact(conn, 7))
        pdu = recv_exact(conn, length - 1)
        if drop_after is not None and served == drop_after:
            print(f"[从站] 第 {served + 1} 个请求到达，模拟掉线：直接断开", flush=True)
            srv.close()                 # 先关监听口，再断开连接：之后一段时间内新连接会被拒绝
            return
        fc, addr, qty = struct.unpack(">BHH", pdu[:5])
        if fc != 3 or addr != 0 or qty != 3:
            body = bytes([fc | 0x80, 2])
        else:
            vals = SCRIPT[min(step, len(SCRIPT) - 1)]
            step += 1
            body = bytes([3, 6]) + struct.pack(">3H", *vals)
        conn.sendall(struct.pack(">HHHB", tid, 0, len(body) + 1, unit) + body)
        served += 1


def main():
    first = True
    srv = socket.create_server((HOST, PORT))
    print(f"[从站] 已启动 {HOST}:{PORT}", flush=True)
    while True:
        conn, _ = srv.accept()
        with conn:
            try:
                serve(conn, DROP_AFTER if first else None, srv)
            except ConnectionError:
                pass
        if first:
            first = False
            time.sleep(OFFLINE_SECONDS)
            srv = socket.create_server((HOST, PORT))
            print("[从站] 恢复服务", flush=True)


if __name__ == "__main__":
    main()

collector.py：

python
"""最小采集器：轮询 Modbus 从站 -> 换算 -> 死区压缩 -> 内存队列 -> 批量幂等写库；断线自动重连。"""
import socket
import struct
import time
from datetime import datetime, timedelta

import pyodbc

HOST, PORT, UNIT = "127.0.0.1", 5021, 1
CONN_STR = (r"DRIVER={ODBC Driver 17 for SQL Server};SERVER=(localdb)\MSSQLLocalDB;"
            r"DATABASE=Lab_eap;Trusted_Connection=yes;")
DEVICE = "REFLOW-01"
POLL_SECONDS = 0.05      # 真实采集常用 0.5~5 秒；实验里调快
T0 = datetime(2026, 10, 21, 8, 0, 0)   # 实验用"虚拟时钟"，让输出每次一样；真实系统用 datetime.now()
TOTAL_POLLS = 17
BATCH = 4                # 队列攒够几条就写库
HEARTBEAT = 4            # 值没变化也每 4 次轮询记一条，证明采集器还活着
FAIL_FLUSH = {2}         # 让第 2 次写库失败，演示"断库续传"

# 位号表：名称 -> (寄存器偏移, 比例, 死区)。死区 0 表示只要变化就记
TAGS = {"Temp": (0, 0.1, 0.5), "Status": (2, 1, 0)}
BAD_RAW = 32767          # 假设手册规定：温度寄存器 32767 = 传感器断线


class ModbusDriver:
    """驱动层：只负责"连上、读 3 个寄存器、出错抛异常"，上层不关心协议细节。"""

    def __init__(self):
        self.sock, self.tid = None, 0

    def connect(self):
        self.sock = socket.create_connection((HOST, PORT), timeout=0.3)   # 连接超时要短，别卡住轮询
        self.sock.settimeout(1)                                           # 读写超时
        self.tid = 0

    def close(self):
        if self.sock:
            self.sock.close()
        self.sock = None

    def _recv(self, n):
        buf = b""
        while len(buf) < n:
            chunk = self.sock.recv(n - len(buf))
            if not chunk:
                raise ConnectionError("连接被对方关闭")
            buf += chunk
        return buf

    def read3(self):
        self.tid += 1
        pdu = struct.pack(">BHH", 3, 0, 3)
        self.sock.sendall(struct.pack(">HHHB", self.tid, 0, len(pdu) + 1, UNIT) + pdu)
        _t, _p, length, _u = struct.unpack(">HHHB", self._recv(7))
        body = self._recv(length - 1)
        if body[0] & 0x80:
            raise RuntimeError(f"异常响应 {body[1]}")
        return struct.unpack(">3H", body[2:8])


def reconnect(drv):
    drv.close()
    delay, attempt = 0.1, 0
    while True:
        attempt += 1
        try:
            drv.connect()
            print(f"  重连成功（第 {attempt} 次尝试）")
            return
        except OSError:
            print(f"  第 {attempt} 次重连失败，{delay:.1f}s 后再试")
            time.sleep(delay)
            delay = min(delay * 2, 2.0)   # 退避：0.1 -> 0.2 -> 0.4 ... 上限 2 秒


def init_db(db):
    db.execute("""IF OBJECT_ID('DeviceSample') IS NULL CREATE TABLE DeviceSample(
        Id BIGINT IDENTITY PRIMARY KEY,
        DeviceCode NVARCHAR(30) NOT NULL, TagCode NVARCHAR(30) NOT NULL,
        SampleTime DATETIME2(3) NOT NULL, ValueNum DECIMAL(18,4) NULL, Quality TINYINT NOT NULL,
        CONSTRAINT UQ_DeviceSample UNIQUE (DeviceCode, TagCode, SampleTime))""")
    db.execute("DELETE FROM DeviceSample")   # 仅实验：每次从空表开始
    db.commit()


def flush(db, queue, n_flush):
    """批量写库。用 NOT EXISTS 保证同一条重复写入也不会产生重复行（幂等）。"""
    if n_flush in FAIL_FLUSH:
        raise RuntimeError("模拟数据库暂时不可用")
    inserted = 0
    cur = db.cursor()
    for s in queue:
        cur.execute("""INSERT INTO DeviceSample(DeviceCode,TagCode,SampleTime,ValueNum,Quality)
            SELECT ?,?,?,?,? WHERE NOT EXISTS (SELECT 1 FROM DeviceSample
            WHERE DeviceCode=? AND TagCode=? AND SampleTime=?)""",
                    s[0], s[1], s[2], s[3], s[4], s[0], s[1], s[2])
        inserted += cur.rowcount
    db.commit()
    return inserted


def should_record(prev, val, q, band):
    """死区压缩：第一次、质量变了、变化量达到死区，才算"变化"。"""
    if prev is None:
        return True
    pval, pq = prev
    if pq != q:
        return True
    if val is None or pval is None:
        return False
    return abs(val - pval) >= band if band > 0 else val != pval


def main():
    db = pyodbc.connect(CONN_STR)
    init_db(db)
    drv = ModbusDriver()
    reconnect(drv)
    queue, last, last_k, raw_cnt, n_flush = [], {}, {}, 0, 0
    k = 0                                    # 已成功完成的轮询次数
    while k < TOTAL_POLLS:
        try:
            raw = drv.read3()
        except (ConnectionError, OSError) as e:
            print(f"轮询 {k + 1} 失败：{e}，进入重连")
            reconnect(drv)
            continue                         # 同一次轮询重试，不跳过
        k += 1
        now = T0 + timedelta(seconds=k)
        raw_cnt += 1
        for tag, (off, scale, band) in TAGS.items():
            r = raw[off]
            bad = tag == "Temp" and r == BAD_RAW
            val = None if bad else round(r * scale, 4)
            q = 0 if bad else 1
            changed = should_record(last.get(tag), val, q, band)
            beat = k - last_k.get(tag, 0) >= HEARTBEAT
            if changed or beat:
                queue.append((DEVICE, tag, now, val, q))
                last[tag], last_k[tag] = (val, q), k
                print(f"轮询 {k:2d} {now:%H:%M:%S} {tag:6s} = {val}  质量 {q}  入队（{'变化' if changed else '心跳'}）")
        if len(queue) >= BATCH:
            n_flush += 1
            try:
                n = flush(db, queue, n_flush)
                print(f"  第 {n_flush} 次写库：写入 {n} 条，队列清空")
                queue.clear()
            except RuntimeError as e:
                print(f"  第 {n_flush} 次写库失败（{e}），队列保留 {len(queue)} 条，下次一起写")
        time.sleep(POLL_SECONDS)
    n_flush += 1
    print(f"  收尾写库：写入 {flush(db, queue, n_flush)} 条")
    print(f"原始轮询 {raw_cnt} 次 x {len(TAGS)} 个位号 = {raw_cnt * len(TAGS)} 个读数")
    # 去重演示：把已入库的第一条再写一遍，应该新增 0 条
    again = flush(db, [(DEVICE, "Temp", T0 + timedelta(seconds=1), 250.0, 1)], 99)
    print(f"重复写入同一条记录：新增 {again} 条（幂等）")
    total = db.execute("SELECT COUNT(*) FROM DeviceSample").fetchone()[0]
    print(f"库里共 {total} 行")


if __name__ == "__main__":
    main()

每次运行前都要重新启动 temp_server.py：它的剧本进度保存在内存里，不重启的话第二次运行会读到剧本的末尾。重连"第 3 次尝试成功"取决于时间（掉线 0.8 秒、连接超时 0.3 秒），机器很慢时可能是第 2 或第 4 次，这不影响其余输出。

看懂输出：

  • 第 1~6 次轮询正常，第 7 次轮询时从站掉线：采集器发现"连接被对方关闭"，进入重连，前两次失败（退避 0.1 秒、0.2 秒），第三次成功。同一次轮询重试，不跳过，所以没有漏掉第 7、8 次的数据。
  • 温度的入队时刻是第 1、4、5、8、12、14、15 次：这就是死区压缩。第 14 次温度寄存器是 32767（传感器断线），质量标记为 0，值为 NULL；第 15 次恢复。
  • Status 位号在第 5、9 次出现"心跳"：值没变，但距离上次记录已满 4 次轮询，所以还是记一条。
  • 第 2 次写库失败（实验故意让它失败）：队列保留 4 条，没有清空；下一次写库时连同新数据一起写，没有丢。
  • 最后用同一条记录再写一次：新增 0 条，这就是幂等。
  • 17 次轮询 × 2 个位号 = 34 个读数，最后只有 12 行入库。

﻿using System.Threading.Channels;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using SqlSugar;

// 采集服务骨架：驱动抽象 + 队列 + 入库，三者通过接口和 Channel 解耦
var builder = Host.CreateApplicationBuilder(args);
builder.Services.AddSingleton(Channel.CreateBounded<Sample>(1000));   // 有界队列：满了会让生产者等待，而不是无限吃内存
builder.Services.AddSingleton<IDeviceDriver, ScriptedDriver>();       // 换成 ModbusDriver / S7Driver 只改这一行
builder.Services.AddHostedService<PollWorker>();
builder.Services.AddHostedService<SinkWorker>();
await builder.Build().RunAsync();

// 与 T-SQL 建的 DeviceSample 表对应（表已由 Python 实验建好，这里不让 SqlSugar 建表）
[SugarTable("DeviceSample")]
public class DeviceSample
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public long Id { get; set; }
    public string DeviceCode { get; set; } = "";
    public string TagCode { get; set; } = "";
    public DateTime SampleTime { get; set; }
    public decimal? ValueNum { get; set; }
    public byte Quality { get; set; }
}

public record Sample(string Device, string Tag, DateTime Time, double? Value, byte Quality);

// 驱动接口：上层只知道"读一次，拿到若干位号的值"，不知道底层是 Modbus 还是别的
public interface IDeviceDriver
{
    Task<IReadOnlyDictionary<string, double?>> ReadAsync(CancellationToken ct);
}

// 演示用驱动：按剧本返回温度（真实项目里这里是 Modbus/S7/OPC UA 的读取）
public class ScriptedDriver : IDeviceDriver
{
    static readonly double[] Seq = { 250.0, 250.3, 249.8, 251.2, 256.0, 256.1, 256.0, 262.5 };
    int _i;
    public Task<IReadOnlyDictionary<string, double?>> ReadAsync(CancellationToken ct) =>
        Task.FromResult<IReadOnlyDictionary<string, double?>>(new Dictionary<string, double?> { ["Temp"] = Seq[_i++] });
}

// 生产者：定时轮询 -> 死区压缩 -> 放进队列。它不碰数据库，数据库慢不会拖慢采集
public class PollWorker(IDeviceDriver drv, Channel<Sample> queue) : BackgroundService
{
    static readonly DateTime T0 = new(2026, 10, 21, 8, 0, 0);   // 演示用虚拟时钟，真实系统用 DateTime.UtcNow
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        double? last = null;
        for (int k = 1; k <= 8 && !ct.IsCancellationRequested; k++)
        {
            var v = (await drv.ReadAsync(ct))["Temp"];
            if (last is null || Math.Abs(v!.Value - last.Value) >= 0.5)    // 死区 0.5 ℃
            {
                await queue.Writer.WriteAsync(new Sample("REFLOW-CS", "Temp", T0.AddSeconds(k), v, 1), ct);
                last = v;
            }
            await Task.Delay(50, ct);
        }
        queue.Writer.Complete();   // 告诉消费者：没有更多数据了
    }
}

// 消费者：从队列取出，攒成一批，用 SqlSugar 批量写库
public class SinkWorker(Channel<Sample> queue, IHostApplicationLifetime life) : BackgroundService
{
    const string ConnStr = @"Server=(localdb)\MSSQLLocalDB;Database=Lab_eap;Trusted_Connection=True;TrustServerCertificate=True;";
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var db = new SqlSugarClient(new ConnectionConfig { ConnectionString = ConnStr, DbType = DbType.SqlServer, IsAutoCloseConnection = true });
        db.Deleteable<DeviceSample>().Where(s => s.DeviceCode == "REFLOW-CS").ExecuteCommand();   // 仅实验：重复运行结果一致
        var batch = new List<DeviceSample>();
        await foreach (var s in queue.Reader.ReadAllAsync(ct))
        {
            Console.WriteLine($"入队 {s.Device} {s.Tag} {s.Time:HH:mm:ss} {s.Value:F1} Q={s.Quality}");
            batch.Add(new DeviceSample { DeviceCode = s.Device, TagCode = s.Tag, SampleTime = s.Time, ValueNum = (decimal?)s.Value, Quality = s.Quality });
        }
        db.Insertable(batch).ExecuteCommand();   // 真实服务按"满 N 条或满 T 秒"就写一批，失败则保留重试
        Console.WriteLine($"批量写库 {batch.Count} 条；库里 REFLOW-CS 共 {db.Queryable<DeviceSample>().Count(s => s.DeviceCode == "REFLOW-CS")} 行");
        life.StopApplication();
    }
}

常见坑与排查 ​

现象最可能的原因
数据偶尔缺一段断线期间没有续传；或队列满了丢弃；检查有无"缺失"标记
重启采集器后数据重复没有唯一约束和幂等写入
值差 10 倍/100 倍比例没配或配错，对照设备手册的"倍率"
浮点数读出来是 2.4e-41 这类怪数32 位数据字序反了
温度值是 32767 或 -32768设备约定的"传感器故障"特殊值，要先判断再换算
计数器突然变小设备清零或溢出（16 位计数器到 65535 回 0），算差值时要处理回绕
时间对不上，事件顺序颠倒设备/服务器时钟不同步，没有存两个时间
日志文件解析到一半崩溃文件正在被设备写入；要等写完（文件大小稳定）或只读已完成的行
数据库越来越慢没压缩、没批量、没分区、没归档
一台设备断线拖慢所有设备所有设备共用一个线程串行轮询；改为每设备独立任务并设超时
文本日志中文变成乱码编码不对（UTF-8/GBK），读文件时要明确指定编码

练习题与答案 ​

  1. 读数序列 2500, 2503, 2498, 2512, 2560, 2561（比例 0.1，死区 0.5 ℃，第一条总是记录），哪几条会被记录？ 答：250.0（第一条）、251.2、256.0，共 3 条；最后的 256.1 与上次记录的 256.0 只差 0.1，不记。
  2. 为什么死区比较的对象必须是"上次记录的值"而不是"上次读到的值"？ 答：如果每次只涨 0.1 而比较上次读到的值，差值永远小于 0.5，缓慢漂移永远不会被记录。比较上次记录的值，累计漂移到 0.5 就会记下来。
  3. 20 个位号每秒采一次、每条存一行，一天多少行？一年呢？ 答：20 × 86400 = 1,728,000 行/天；× 365 = 630,720,000 行/年。
  4. 寄存器值 65526 是 uint16，设备手册说它是有符号 16 位的温度（比例 1），实际是多少？ 答：-10。65526 − 65536 = −10。
  5. 为什么写库要做成"幂等"的？ 答：续传和重试可能把同一条数据写两次，幂等写入保证重复写入不会产生重复行，数据才是准确的。
  6. 采集器每 10 秒轮询一次状态，设备出现了一次 4 秒的报警，一定会被发现吗？ 答：不一定。如果两次轮询都落在报警之外就漏掉了。想不漏要么缩短轮询间隔，要么让设备主动上报事件，或者读取设备自己记录的报警历史。
  7. 为什么要把"轮询"和"入库"拆成两个 Worker 中间放队列？ 答：数据库偶尔变慢时，轮询不会被拖住；队列还起到缓冲作用。反过来，设备慢也不会让入库线程空转卡死。

小结 ​

  • 先想清要回答的问题，再决定采什么；五类数据：状态、产量、报警、参数、过程数据。
  • 六条通道：PLC 寄存器、OPC UA、SECS/GEM、文件、数据库、CFX/Hermes；优先用标准协议。
  • 用位号表描述每个点；频率、死区、心跳、批量、归档一起考虑存储。
  • 断线要重连（带退避）、要续传、要幂等；设备和服务器要时间同步；单位、比例、字序要核对。
  • 每条数据带质量标记，坏数据要保留并标记。
  • C# 架构：驱动接口 + Channel 队列 + 批量入库，用 BackgroundService 托管。
