设备保养与TPM

AI 生成 · 待核对制造业务设备自动化设备管理更新于 2026-10-21

⚠ 待核对：TPM 的"八大支柱"在不同资料里名称和排列不完全一致（我对照维基百科的版本，JIPM 官方版本的措辞略有不同，例如"早期设备管理""行政与办公室 TPM"），写论文或对外资料时请对照 JIPM 的原始资料。TPM 的起源年代各资料说法也不同（维基百科：1950 到 1970 年间发展，1971 年开始应用）。网上常见的"OEE 85% 为世界级水平"出处有争议，我没有找到一手来源，本篇不采用。保养周期、点检项、限值都是示例，实际以设备手册和公司设备管理制度为准；你们自研系统怎么管保养，请对照核实。表设计是通用做法。SQL 与 C# 代码、输出是我在本机 SQL Server LocalDB 上实际运行得到的。

本篇是 EAP 系列第 5 篇。读完你应该能：说清 TPM 是什么、八大支柱各自的意思；分清日常点检、定期保养、预防性维护、预测性维护、事后维修；设计保养计划、点检表和到期提醒；计算 MTBF、MTTR 和可用率；用 SQL 查出哪些保养到期了，并记录一次点检。

一句话定义 ​

TPM（Total Productive Maintenance，全员生产维护）是一种设备管理方法：不只由维修部门"坏了再修"，而是让操作员、维修、工艺、管理一起，通过日常点检、定期保养和持续改进，把设备故障、停机和不良消灭在发生之前。

先修知识 ​

  • 设备管理与设备状态：知道设备台账和运行/待机/故障/保养等状态。
  • OEE：知道设备综合效率由可用率、性能、质量三部分组成。
  • 设备数据采集：知道设备状态和产量怎么采上来（保养计划里的"使用量"来自这里）。
  • T-SQL编程：能看懂 SELECT、JOIN、事务。

它解决什么问题 ​

一条 SMT 线早上开线，贴片机突然报"吸嘴吸不起料"，停了 40 分钟：原来吸嘴上的灰尘一个月没清了。排查时发现，保养记录本上这个月的"月度保养"栏是空的，大家都以为别人做了。更糟的是，上周回流炉的排风压力其实已经偏低，点检表上也没人记数值，只打了个勾，到了这周出现虚焊才暴露。

没有制度化保养的常见后果：

问题后果
保养靠记忆漏保养，故障频发
点检只打勾不记数值看不出趋势，渐变的劣化发现不了
备件没人管坏了才发现没备件，等待几天
不统计故障时间不知道哪台设备最麻烦、修一次要多久
保养和生产排程互相不知道保养时间和生产冲突，被迫推迟

把保养管起来，就是用计划、记录、提醒、统计四件事，把"凭感觉"变成"有据可查"。

核心概念 ​

TPM 的来源和八大支柱 ​

据维基百科，TPM 的"父亲"是日本的 Seiichi Nakajima（中岛清一）；TPM 在 1950 到 1970 年间发展起来，1971 年开始应用，丰田的零部件供应商 Nippondenso（日本电装）是最早受益并获得首届 PM 奖的企业之一。后来 JIPM（日本工厂维修协会，Japan Institute of Plant Maintenance）把原来的五项原则扩展为"全公司 TPM"的八项活动。

八大支柱（据维基百科，JIPM 的措辞略有不同，见文首提示），结合 SMT 例子：

支柱意思SMT 车间的例子
1. 自主保全（Autonomous maintenance）操作员用自己的感官发现问题、做清扫点检润滑贴片机操作员每班清理飞达、擦拭相机镜头
2. 个别改善（Focused improvement）用科学方法逐项消灭损失分析最近一个月抛料最多的物料，改善吸嘴和料带
3. 计划保全（Planned maintenance）由专业维修人员按计划保养回流炉链条每月润滑，季度更换风扇滤网
4. 品质保全（Quality maintenance）用统计方法找出造成不良的设备因素把虚焊的板与炉温、链速的记录做关联分析
5. 初期管理 / 设备开发管理（Early / Development management）新设备引进时就考虑易保养、少故障采购新贴片机时评估易损件更换难易度、联网能力
6. 教育训练（Education and training）持续提升操作和维修技能新员工上岗培训、维修工认证
7. 事务部门 TPM（Administrative and office TPM）把 TPM 的思想用到计划、物料、信息流等事务工作备件采购流程、保养排程与生产计划的协同
8. 安全、健康、环境（Safety, health and environment）保证保养作业安全炉子高温作业防烫、断电挂牌、静电防护

对做信息化的人来说，系统最直接支撑的是：自主保全（点检表）、计划保全（保养计划与提醒）、个别改善与品质保全（数据统计分析）。

五种"保养/维修"方式 ​

方式做什么触发例子
事后维修（Breakdown Maintenance, BM）坏了再修故障发生灯泡烧了换灯泡。便宜的非关键件可以这样
日常点检每班/每天按点检表检查关键项，记录数值或打勾时间（每班）回流炉排风压力、气压、异响
定期保养按固定周期做清洁、润滑、更换时间（周/月/季）或使用量印刷机周保养、吸嘴按贴装点数清洗
预防性维护（Preventive Maintenance, PM）在故障发生之前，按计划（时间或使用量）更换/修理易损件时间或使用量轴承用满 5000 小时更换。日常点检和定期保养都属于广义的 PM
预测性维护（Predictive Maintenance）根据设备的实际状态数据（振动、温度、电流趋势）预测何时会坏，在最合适的时机维护状态数据风扇电流逐渐变大，预测两周内会失效

预防性维护是"定好周期到点就做"，可能做早了（零件还能用）或做晚了；预测性维护是"看状态决定"，更省，但依赖数据和模型。预测性维护需要持续采集的设备数据，这正是 设备数据采集 的价值；用 AI 做预测的思路见 AI在制造业的应用。起步阶段先把计划保养和点检做好，比一上来就搞预测更重要。

保养计划：按时间还是按使用量 ​

类型触发规则适合系统需要
时间型每 N 天，下次到期 = 上次完成时间 + N 天与运行时长关系不大的项目（清洁、润滑日期）计划表里记 CycleDays、LastDoneAt、NextDueAt
使用量型每 N 次/点/小时，到期 = 上次保养时的累计量 + N磨损与使用强度相关（吸嘴、刮刀、轴承）设备累计使用量（来自采集），计划里记 CycleUsage、LastDoneUsage

到期提醒规则（常见）：

  • 提前量：到期前 N 天开始提醒（如 3 天），到期当天高亮，超期标红并升级通知（通知主管）。
  • 使用量型：用到 80% 时预警，100% 到期。
  • 完成后重置：完成一次保养，下次到期从实际完成时间重新算（或从计划时间算，要事先约定；前者更真实，后者防止越拖越晚）。
  • 允许的宽限：有的制度允许周期的 ±10% 窗口内完成都算按时。

点检表 ​

点检表是自主保全的核心：列出要检查的项目、标准、方法，操作员逐项记录。设计要点：

要点说明
项目要少而准一张表十几项以内，抓影响质量和安全的关键点，否则大家只会随便打勾
有判定标准"排风压力 10 到 30 Pa"比"压力正常"好；能记数值的就记数值（才能看趋势）
数值型有上下限系统自动判 OK/NG，超限立即提示、可触发报修
要有方法和图示怎么查、在哪里查，新人也看得懂
记录不可篡改只追加，补录要留痕
异常要有闭环NG 后自动生成报修/待办，处理完成才关闭

备件管理 ​

保养和维修都要用备件（吸嘴、皮带、滤网、传感器）。管理要点：

  • 备件与设备关联：每台设备有"易损件清单"，保养计划关联用到的备件。
  • 库存上下限：最小库存（低于它就提醒采购）、最大库存。关键件（缺了就停线、采购周期长）要多备。
  • 领用与消耗记录：保养/维修时扣减备件，才能算出每台设备的维护成本。
  • 采购周期：库存的最小值要覆盖"采购周期内的消耗"。例如一种备件每月用 2 个，采购周期 1.5 个月，最小库存至少应覆盖 3 个再加安全余量。（这里是简化算法，真实还要考虑波动。）
  • 与 WMS 或 ERP 的备件库存如何衔接，由公司系统决定，请对照核实。

MTBF、MTTR 与可用率 ​

据公开资料：

  • MTBF（Mean Time Between Failures，平均故障间隔时间）：可修复设备平均能连续工作多久才坏一次。常用算法：总运行时间 ÷ 故障次数。
  • MTTR（Mean Time To Repair，平均修复时间）：平均修一次要多久。算法：总修复时间 ÷ 故障次数。
  • MTTF 用于不可修复的东西（用坏就换），不要和 MTBF 混淆。
  • 固有可用率 = MTBF ÷ (MTBF + MTTR)，只计算实际修理的时间；实际的"运行可用率"还要算上等待备件、等人等行政和物流延误。
  • MTBF 取决于你怎么定义"故障"：停机 1 分钟算不算？要事先规定（常见做法是设一个最短时间，如超过几分钟才算故障，或者短停另算）。

这三个指标怎么用：MTBF 低说明设备爱坏，要从预防保养和零件质量找原因；MTTR 高说明修得慢，要从备件、维修技能、故障诊断上改善。两者都和 OEE 的"可用率"相关：维基百科列出的"六大损失"里，第一项就是故障停机。

业务视角 ​

角色在什么环节做什么
操作员每班按点检表检查设备并记录，发现异常报修
设备工程师/维修工制定保养计划，执行定期保养，处理报修，分析故障原因
设备主管看到期提醒与逾期清单，安排保养窗口，审核备件采购
生产主管/计划配合安排保养时间，避免与交期冲突
管理层看 MTBF、MTTR、保养完成率、故障次数等 KPI

流程：制定计划 → 到期提醒 → 保养/点检执行并记录 → 异常报修 → 维修与备件消耗 → 记录归档 → 统计分析 → 优化计划。

涉及单据：保养计划、点检表（模板）、点检/保养记录、报修单、维修记录、备件领用单。

KPI：保养完成率（按时完成数 ÷ 计划数）、逾期数、点检完成率、MTBF、MTTR、故障停机时间、备件缺货次数。（见 工厂常见KPI）

PmPlan保养/点检计划（头）设备、计划名、类型（日/周/月/季/使用量）、周期（天或使用量）、上次完成时间/使用量、下次到期时间、是否启用
PmPlanItem计划里的点检项（明细）项目名、标准、数值上下限
PmRecord每次执行的记录，一次执行的每个点检项一行计划、执行单号、点检项、完成时间、执行人、实测值、结果 OK/NG
RepairRecord故障与维修记录（算 MTBF/MTTR 的原料）设备、故障时间、恢复时间、原因

设计取舍：

  • 记录只追加：PmRecord 不改不删，补录用新记录。
  • 完成一次保养 = 写记录 + 更新计划，必须放在同一个事务里（见 事务与ACID），否则可能出现"记录写了但计划没更新，系统一直提示到期"。
  • NextDueAt 可以冗余存起来（查询快，可建索引，见 数据库索引）；也可以每次计算。冗余的代价是要保证每次完成都更新。
  • 使用量型计划的"当前累计量"来自采集（例如贴片机累计贴装点数）。
  • 提醒本身用定时任务（后台服务与Windows服务）扫描 PmPlan 发送通知，并记下已通知过谁、什么时间，避免重复轰炸。
  • 点检项与设备型号关联、点检模板版本化，是更完整的设计，本篇的迷你表没有做。

逐步例子：算一次 MTBF 和 MTTR ​

贴片机 MOUNTER-01 过去 30 天（2026-09-21 到 2026-10-21，按每天 24 小时运行共 720 小时）发生了 3 次故障：

故障开始恢复修复时长
吸嘴堵塞9-25 10:009-25 11:3090 分钟
飞达卡料10-5 14:0010-5 14:3030 分钟
相机故障10-14 09:0010-14 11:00120 分钟
  • 总停机 = 90 + 30 + 120 = 240 分钟 = 4 小时
  • MTTR = 4 ÷ 3 = 1.33 小时（80 分钟）
  • 总运行时间 = 720 − 4 = 716 小时
  • MTBF = 716 ÷ 3 = 238.67 小时
  • 可用率 = MTBF ÷ (MTBF + MTTR) = 238.67 ÷ (238.67 + 1.33) = 716 ÷ 720 = 99.44%

我用 Python 复算验证：MTTR 1.3333、MTBF 238.6667、可用率 99.4444%。

sql
SET NOCOUNT ON;
DECLARE @Now DATETIME2(0) = '2026-10-21 08:00';   -- 实验固定"现在"，结果才可复现；真实查询用 SYSDATETIME()

PRINT N'--- 1. 到期提醒（时间型）：逾期 / 3 天内到期 / 正常';
SELECT p.PlanName, e.EquipmentName, p.NextDueAt,
       DATEDIFF(HOUR, @Now, p.NextDueAt) AS HoursLeft,
       CASE WHEN p.NextDueAt <= @Now THEN N'到期/逾期'
            WHEN p.NextDueAt <= DATEADD(DAY, 3, @Now) THEN N'即将到期' ELSE N'正常' END AS Status
FROM PmPlan p JOIN Equipment e ON e.EquipmentCode = p.EquipmentCode
WHERE p.Enabled = 1 AND p.CycleDays IS NOT NULL
ORDER BY p.NextDueAt;

PRINT N'--- 2. 到期提醒（使用量型）';
SELECT p.PlanName, e.UsageCount - p.LastDoneUsage AS UsedSince, p.CycleUsage,
       CAST(100.0 * (e.UsageCount - p.LastDoneUsage) / p.CycleUsage AS DECIMAL(5,1)) AS UsedPct,
       p.CycleUsage - (e.UsageCount - p.LastDoneUsage) AS Remaining
FROM PmPlan p JOIN Equipment e ON e.EquipmentCode = p.EquipmentCode
WHERE p.Enabled = 1 AND p.CycleUsage IS NOT NULL;

PRINT N'--- 3. 完成一次点检：写记录 + 更新计划，放在一个事务里';
BEGIN TRAN;
    INSERT INTO PmRecord (PlanId, ExecNo, ItemId, DoneAt, DoneBy, MeasuredValue, Result, Remark)
    SELECT 1, 'PM-20261021-01', i.ItemId, '2026-10-21 08:10', N'张工', v.Val,
           CASE WHEN v.Val IS NULL THEN 'OK'
                WHEN v.Val BETWEEN i.LowerLimit AND i.UpperLimit THEN 'OK' ELSE 'NG' END, NULL
    FROM PmPlanItem i
    JOIN (VALUES (1, CAST(3.2 AS DECIMAL(9,2))), (2, NULL), (3, CAST(8.5 AS DECIMAL(9,2))), (4, NULL)) v(ItemId, Val)
         ON v.ItemId = i.ItemId;
    UPDATE PmPlan SET LastDoneAt = '2026-10-21 08:10', NextDueAt = DATEADD(DAY, CycleDays, '2026-10-21 08:10') WHERE PlanId = 1;
COMMIT;

SELECT i.ItemName, r.MeasuredValue, i.LowerLimit, i.UpperLimit, r.Result
FROM PmRecord r JOIN PmPlanItem i ON i.ItemId = r.ItemId WHERE r.ExecNo = 'PM-20261021-01' ORDER BY i.ItemId;

SELECT PlanName, LastDoneAt, NextDueAt FROM PmPlan WHERE PlanId = 1;

PRINT N'--- 4. MTBF / MTTR / 可用率（MOUNTER-01，观察窗口 30 天 = 720 小时，按 24 小时/天计）';
DECLARE @WindowH DECIMAL(9,2) = 720;
SELECT COUNT(*) AS Failures,
       SUM(DATEDIFF(MINUTE, FailedAt, RestoredAt)) AS DownMin,
       CAST(SUM(DATEDIFF(MINUTE, FailedAt, RestoredAt)) / 60.0 / COUNT(*) AS DECIMAL(9,2)) AS MTTR_h,
       CAST((@WindowH - SUM(DATEDIFF(MINUTE, FailedAt, RestoredAt)) / 60.0) / COUNT(*) AS DECIMAL(9,2)) AS MTBF_h,
       CAST(100.0 * (@WindowH - SUM(DATEDIFF(MINUTE, FailedAt, RestoredAt)) / 60.0) / @WindowH AS DECIMAL(9,2)) AS AvailPct
FROM RepairRecord WHERE EquipmentCode = N'MOUNTER-01' AND FailedAt >= '2026-09-21' AND FailedAt < '2026-10-21';

常见坑与排查 ​

现象最可能的原因
保养"做了"但系统一直提示到期只写了记录没更新计划（没放进同一事务）；或没刷新 NextDueAt
点检全是 OK，出了故障才发现早就有异常点检只打勾不记数值；改成能记数值的项记数值，看趋势
保养到期提醒太多，大家不看计划太多、提前量太大；分级提醒，只推送给相关责任人
MTBF 数字一直很漂亮故障没有如实登记（短停不算故障、隐瞒）；定义"故障"并从设备状态数据自动识别
MTTR 很大但维修明明很快把等备件、等人的时间也算进去了（那是平均停机时间 MDT，不是 MTTR）
用时间型计划去管磨损型零件磨损和使用量有关，应使用使用量型计划
补录记录时间乱填要求记录实际时间，补录必须标注并留痕
设备累计使用量归零（设备换了控制器）采集的计数器被重置；计划里按差值计算，处理回绕和清零
保养时间和生产冲突被一再推迟保养要进入排程（见 APS）；不做的后果要让管理层看到
想用 AI 预测性维护，却没有数据先把状态、报警、点检、故障记录持续采集和规范起来，积累一年数据再谈预测

练习题与答案 ​

  1. 日常点检、定期保养、预防性维护有什么区别和联系？ 答：日常点检是每班/每天检查关键项；定期保养是按周期做清洁、润滑、更换；它们都按计划在故障前进行，属于广义的预防性维护。预测性维护则是根据设备状态数据决定时机。
  2. 为什么点检表里能记数值的项要尽量记数值，而不是只打勾？ 答：数值才能自动判上下限、看变化趋势，能发现"慢慢变坏"的劣化；只打勾只能判断有没有，发现不了渐变。
  3. 贴片机一个月（720 小时）发生 2 次故障，共停机 3 小时，求 MTBF、MTTR 和可用率。 答：MTTR = 3 ÷ 2 = 1.5 小时；运行时间 = 720 − 3 = 717 小时；MTBF = 717 ÷ 2 = 358.5 小时；可用率 = 717 ÷ 720 = 99.58%。
  4. 吸嘴保养周期是 500000 点，上次保养时累计 3,200,000 点，现在累计 3,640,000，预警线 80%，是否该预警？剩余多少？ 答：已用 440,000，占 88%，超过 80%，应预警；剩余 60,000 点。
  5. 为什么"写点检记录"和"更新计划的下次到期时间"要放在同一个事务里？ 答：如果只成功了一半，会出现记录有了但计划没更新（系统一直提示到期），或计划更新了但记录丢了（无据可查）。事务保证两件事要么都成功要么都不做。
  6. MTBF 和 MTTF 有什么区别？ 答：MTBF 用于可修复的设备，是两次故障之间的平均运行时间；MTTF 用于不可修复的东西，是用到坏的平均寿命。
  7. 八大支柱里，哪几个最直接依赖信息系统的支持？ 答：自主保全（点检表记录与提醒）、计划保全（保养计划与到期提醒）、个别改善与品质保全（对设备数据做统计分析）。

小结 ​

  • TPM 是全员参与、把故障消灭在发生之前的设备管理方法，有八大支柱（各资料措辞略有差异）。
  • 方式分五种：事后维修、日常点检、定期保养、预防性维护、预测性维护；起步先做好计划保养和点检。
  • 保养计划分时间型和使用量型；要有到期提醒和完成后重置规则；点检表要少而准、有标准、能记数值。
  • 备件要和设备关联，有库存上下限和消耗记录。
  • MTBF = 运行时间 ÷ 故障次数；MTTR = 修复时间 ÷ 故障次数；可用率 = MTBF ÷ (MTBF + MTTR)。
  • 表设计：PmPlan、PmPlanItem、PmRecord、RepairRecord；完成一次保养要在同一事务里写记录并更新计划。
