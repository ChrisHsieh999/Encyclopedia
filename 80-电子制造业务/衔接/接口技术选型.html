接口技术选型

AI 生成 · 待核对制造业务衔接接口技术选型C#更新于 2026-10-21

⚠ 待核对：几种接口方式的对比表（REST、SOAP、gRPC、消息队列、中间表、文件、数据库链接、ETL、ESB）是通用经验总结，只有 MQTT 的 QoS 含义、RabbitMQ 的确认与重复投递、gRPC 用 Protocol Buffers、Polly 重试选项默认值、Microsoft.Extensions.Http.Resilience 的默认策略、Idempotency-Key 草案的状态这几项，我联网核对过官方文档。Kafka 的投递语义、SOAP / WS-* 的细节、ESB 与 ETL 产品功能没有逐条核实，以官方文档为准。你们的 ERP 能提供什么接口（API、WebService、中间表）、公司有没有消息队列、厂区网络怎么隔离，请对照核实。 C# 代码和输出是我在本机（.NET 10 SDK、SQL Server LocalDB 临时库 Lab_join）实际运行得到的。

本篇是"衔接"系列第 5 篇。前三篇回答"传什么、怎么对账"，这一篇回答"用什么技术传，怎么传得可靠"。读完你应该能：对比九种集成方式并为一个具体接口选型；区分同步与异步；说清"至少一次 + 幂等"为什么等于"效果上恰好一次"；设计带退避的重试和死信；讲清并实现 Outbox（发件箱）模式；知道接口监控、日志、安全该做什么；用 C#（HttpClient、Polly、BackgroundService、SqlSugar）跑出一个"发件箱 + 后台发送 + 失败重试到上限"的最小示例。

一句话定义 ​

接口技术选型，就是在"实时性、可靠性、耦合度、对方能提供什么、团队能维护什么"之间，为每一条数据流（见 系统集成总览 的全景表）挑一种合适而不是最先进的交接方式，并给它配上重试、幂等、监控和安全。

先修知识 ​

  • 系统集成总览：全景表里的 15 条数据流；五条原则。本篇是"幂等、补偿、解耦"三条的技术落地。
  • HTTP、REST-API设计：请求 / 响应、状态码、幂等方法（GET、PUT、DELETE 天然幂等，POST 不是）。
  • HttpClient：C# 里调用 HTTP 接口。
  • MQTT：轻量级的发布 / 订阅协议，工业现场常用。
  • 后台服务与Windows服务：BackgroundService 怎么在后台跑循环。
  • 事务与ACID：本地事务能保证"多条 SQL 同成同败"。
  • 身份认证与JWT：接口认证。

它解决什么问题 ​

  • 厂里 ERP 是买来的，只给了"写中间表"和一个老式 WebService，MES 团队想用消息队列，结果协调了三个月才发现对方根本不支持；
  • MES 同步调用 ERP 接口报工，ERP 慢了 30 秒，车间所有终端卡住；
  • 重试写成了 while(true)，ERP 恢复的一瞬间，积压的上万条请求同时压过去，又把它打挂；
  • 网络超时后重试，对方其实已经处理了第一次，账记了两遍；
  • 接口用明文 HTTP、固定密码，同一内网任何人都能伪造一条"完工入库"；
  • 接口三个月前悄悄失败，没有告警，月底才发现。

核心概念 ​

九种集成方式对比 ​

方式通俗解释同步 / 异步优点缺点电子厂里的典型位置
REST / JSON（HTTP API）一方提供网址，另一方发 HTTP 请求，传 JSON默认同步简单、通用、易调试、C# 支持好对方宕机你就失败；要自己做重试和幂等自研系统之间（MES 与 WMS 与 QMS）；现代 ERP 的开放 API
WebService（SOAP）用 XML 描述的老式接口，有 WSDL 契约文件默认同步契约严格，老 ERP / 银行常见XML 冗长，调试麻烦，现代工具少对接老 ERP
gRPC基于 Protocol Buffers 定义接口，生成客户端代码（据 grpc.io，服务和消息用 .proto 定义）同步（也支持流）性能好，强类型，契约清晰浏览器直连不便，调试门槛高，要双方都支持内部高频服务间调用；多数电子厂用不到
消息队列（RabbitMQ / Kafka）发送方把消息放进队列，接收方有空时取走异步解耦、缓冲、可重试、可广播要部署和运维中间件；要处理重复和顺序事件量大、多个系统订阅同一事件（报工事件）
MQTT轻量发布 / 订阅，设备端常用异步轻、省带宽、断线续传业务可靠性要自己补；一般不做业务账务设备与 EAP / MES 之间的状态与参数，见 MQTT
中间表（接口表）一方写表，另一方定时轮询读异步（轮询）最容易起步，双方各自只写自己的表，易排查不实时；轮询有负载；表结构变更要协调ERP 与自研系统之间（最常见）
文件交换定时生成文件（CSV / XML）放共享目录或 FTP异步（批）对方不需要开发接口不实时；半个文件被读；编码与格式易错与外部客户 / 供应商、与 APS 的批量数据
数据库链接一个库直接读写另一个库（SQL Server 的 Linked Server、Oracle 的 DB Link）同步写起来最快耦合最高；对方改表就坏；安全与性能风险；跨库事务麻烦临时过渡、报表，不建议做业务接口
ETL抽取（Extract）、转换（Transform）、加载（Load）：定时把数据批量搬到另一处异步（批）适合大批量、清洗、汇总实时性差；不适合事务性指令报表数仓、主数据批量同步
ESB（企业服务总线）中间一层"总线"，各系统都连总线，由总线路由和转换同步或异步集中管理接口、协议转换重；自身成为单点和瓶颈；成本高大型企业集团；中小电子厂通常没有

表里的"优缺点"是通用的权衡，不同产品差别很大；能用中间表就不要上总线，能用 HTTP API 就不要上 gRPC，除非真有需要。

同步 vs 异步 ​

比较同步（我问你答）异步（我放下就走）
调用方体验立刻知道结果只知道"已受理"，结果稍后
对方宕机时调用方也失败或卡住调用方不受影响，消息积压
实现复杂度低高（要处理重复、顺序、状态查询）
适合需要立即结果的校验和查询（如上料时查 MSD 剩余寿命、查询追溯）通知类、结果类（报工、完工回传、不良事件）

经验法则：向下的校验用同步，向上的结果用异步。 同步调用必须配超时和降级（对方慢了怎么办），异步必须配幂等和对账。

投递语义：最多一次、至少一次、恰好一次 ​

语义含义举例
最多一次（at most once）发一次，可能丢，不会重复MQTT QoS 0（据 MQTT 3.1.1 规范：尽力而为，消息可能丢）
至少一次（at least once）保证送到，但可能重复MQTT QoS 1；RabbitMQ 手动确认（官方文档说明未确认的投递会重新入队，消费者必须准备好处理重复投递）
恰好一次（exactly once）不丢不重MQTT QoS 2 声称做到，但代价高；跨系统业务上很难真正"恰好一次"

业务系统的现实做法：至少一次 + 接收方幂等 = 效果上的恰好一次。 发送方宁可多发，接收方负责去重。所以前三篇每个接收方都有 MsgId 门卫。

幂等与重试设计 ​

什么错误值得重试：

错误是否重试原因
网络超时、连接被重置重试暂时性，且可能对方已处理，所以更要幂等
HTTP 5xx（对方内部错误）、503重试通常暂时性
HTTP 429（请求太多）退避后重试对方限流
HTTP 408（超时）重试暂时性
HTTP 4xx（400 参数错、401 未认证、404 找不到）不重试请求本身有问题，重试一万次结果一样
业务拒绝（物料未建档、余额不足）不重试，转人工数据问题，重试没用（见 MES与WMS衔接 的 E06）

怎么重试：

  1. 限次：设上限（本篇实验为 4 次），达到上限转死信，告警等人，不要无限重试；
  2. 退避：每次等待时间变长（常用指数退避：100ms、200ms、400ms……真实系统用秒到分钟），给对方恢复时间；Polly 的 DelayBackoffType.Exponential 即是这样（官方文档：默认 MaxRetryAttempts 为 3，Delay 为 2 秒，BackoffType 默认 Constant，UseJitter 默认 False）；
  3. 抖动（Jitter）：在等待时间上加随机量，避免成百上千个调用者在同一时刻一起重试（"重试风暴"）；
  4. 总超时 + 单次超时：整条重试链不能超过业务容忍的时间；
  5. 幂等键：重试必须是安全的。HTTP 接口可以带 Idempotency-Key 请求头（IETF 有名为 The Idempotency-Key HTTP Header Field 的草案，我查到的状态是已过期的 Internet-Draft，不是正式标准，但做法已被广泛参考）；消息则带 MsgId；
  6. POST 默认不幂等：Microsoft.Extensions.Http.Resilience 的标准处理器默认对所有 HTTP 方法重试，官方文档特别提醒 POST 重试可能造成数据重复，可以用 DisableForUnsafeHttpMethods() 关闭，或确保接收方幂等后再放开。

Outbox（发件箱）模式 ​

问题：业务要"改自己的库"并"通知别人"。两件事是两个系统，没有分布式事务。先改库再发消息：发送前崩溃，消息丢；先发消息再改库：库改失败，消息已发出，对方收到一个不存在的事。

解法（据 microservices.io 的 Transactional Outbox 模式）：把"要发的消息"作为一行写进同一个数据库的 Outbox 表，和业务数据在同一个本地事务里提交；另有一个独立的"消息中继"（后台发送器）扫描这张表，把消息发出去。发出成功才标记已发送。

要点：

  1. 业务表和发件箱同事务：要么都写入，要么都不写（实验步骤 2 演示：重复报工整个回滚，发件箱没有孤儿消息）；
  2. 发送方至少一次：发送前崩溃、发送后确认丢了，都会重发，所以接收方必须幂等；
  3. 认领：多个发送器同时跑，用条件 UPDATE（WHERE Id = @id AND Status = 'Pending'，受影响行数为 1 才算抢到），和 工单管理 的防超报同一个套路；
  4. 卡在 Sending 的消息：进程崩溃时有消息停在 Sending。启动时把 Sending 放回 Pending（接收方幂等，所以重发安全）；
  5. 顺序：同一个业务对象（同一张工单）的多条消息，需要按序发送；简单做法是一个发送器按 Id 顺序，或者按业务键分区。要求严格顺序时，不要为了并发而打乱；
  6. 清理：已发送的消息保留一段时间（用于对账与审计）再归档；
  7. 也有用数据库变更捕获（CDC）去读事务日志代替轮询发件箱的做法，更复杂，这里不展开。

接口监控与日志 ​

要监控的指标告警条件示例
积压发件箱 Pending 条数、最老一条的年龄最老 Pending 超过 10 分钟
失败失败率、死信数量死信新增、失败率持续升高
延迟业务发生到对方入账的耗时超过业务容忍（如 5 分钟）
活着每个接口最后一次成功时间（LastSuccessAt）超过 1 天无成功
对账对账差异条数非零且持续

日志每条至少记录：消息号、接口名、方向、业务键（工单号 / 标签）、结果（成功、重复忽略、过期忽略、失败）、失败原因、耗时、重试次数。日志里不要明文记录密码、令牌、客户敏感信息。

安全 ​

层面做法
认证谁在调用我：JWT / API Key / 双向 TLS。见 身份认证与JWT
授权调用方只能调自己该调的接口（最小权限）：WMS 不能调"关闭工单"
传输加密内网也尽量用 HTTPS；至少跨网段必须加密
签名与防重放消息带时间戳 + 随机数 + HMAC 签名；接收方校验签名，拒绝过期或见过的随机数，防止篡改和重放
内网隔离办公网、MES / ERP 所在网络、设备网络（OT）分段；跨段只开必要端口，经过网关 / 防火墙。见 工业网络安全
凭据管理密钥不写进代码和仓库；用配置或密钥管理；定期轮换
输入校验所有外来数据当作不可信：长度、范围、枚举、单位

C# 实现要点 ​

  1. HttpClient：不要每次请求都 new HttpClient()（连接耗尽），使用 IHttpClientFactory 或复用单例，见 HttpClient；设置 Timeout；
  2. 重试 / 超时 / 熔断用 Polly：Polly 的核心包是 Polly.Core（ResiliencePipelineBuilder）；ASP.NET Core / 通用主机里可用 Microsoft.Extensions.Http.Resilience 的 AddStandardResilienceHandler()（官方文档：默认依次是限流、总超时 30 秒、重试最多 3 次且指数退避并带抖动、熔断、单次尝试超时 10 秒）；只对幂等请求或带幂等键的请求重试；
  3. 后台服务：BackgroundService 的 ExecuteAsync 里循环扫描发件箱；每轮新建数据库连接（SqlSugar 的 SqlSugarClient 不是线程安全的，见 SqlSugar）；用 CancellationToken 响应停止；循环里 try/catch，一次异常不要让整个循环退出；
  4. 数据库操作：认领和标记状态用条件 UPDATE，业务写入和发件箱写入放同一个事务（db.Ado.UseTran）；
  5. 幂等接收：接收方的 MsgId 用主键 / 唯一索引兜底，不要只靠"先查再插"（并发时有空档）；
  6. 时间：用 UTC 或统一服务器时间存储和比较，不要混用各机器的本地时钟。

业务视角 ​

选型不是纯技术决定，常见参与方和考虑：

角色关心什么
IT / 接口负责人团队会不会维护；出问题谁排查；有没有监控
ERP 厂商 / 外部供应商他们愿意提供什么接口、改一次要多少钱和多久
车间 / 业务部门延迟能不能接受；接口挂了生产会不会停
网络 / 安全能不能跨网段；端口、证书、审计
品质 / 财务数据是否可追溯、可对账、可审计

选型的 5 个问题：对方能提供什么？延迟要求多高？量有多大（每分钟几条还是几万条）？对方宕机时自己要不要继续工作？谁来运维？ 大多数电子厂的答案是：买来的 ERP 用中间表或它提供的 API，自研系统之间用 HTTP API + 发件箱，设备用 OPC UA / MQTT / IPC-CFX，报表用 ETL。只有事件量大、多个系统要订阅同一事件时，才值得引入消息队列。

逐步例子：一条报工消息的一生 ​

用实验的数据，R-002（报工 400 块）：

  1. 业务事务：LabReport 写入 R-002，LabOutbox 写入 CMP-R-002（Pending，尝试 0 次），同一事务提交。
  2. 第 1 次发送（t≈0）：ERP 返回 503，尝试 1 次，失败，100 ms 后重试。
  3. 第 2 次发送（t≈100 ms）：仍 503，尝试 2 次，200 ms 后重试。
  4. 第 3 次发送（t≈300 ms）：成功，尝试 3 次，状态 Sent。LastError 还保留着最后一次的错误信息 503 Service Unavailable（用于事后排查）。

同一批里 R-003 的 ERP 一直报 物料 A100 未在 ERP 建档：尝试 4 次，状态 Dead；人工在 ERP 建好档后，把死信放回 Pending，第 5 次（算新一轮的第 1 次）成功。R-004 的 ERP 其实收到了，但确认丢了：发送方以为失败，重发，ERP 靠 MsgId 识别重复，不再重复入账。

动手实验 ​

实验 1：Outbox + 后台发送 + 失败重试到上限（C# + SqlSugar） ​

目标：一个最小的发件箱实现：业务写入和发件箱写入同事务；BackgroundService 后台扫描、认领、发送；失败退避重试，达到 4 次转死信；修好后放回再发；对方靠 MsgId 幂等。

csharp
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;
using SqlSugar;

namespace JoinLab;

// 业务表：MES 的报工记录
[SugarTable("LabReport")]
public class LabReport
{
    [SugarColumn(IsPrimaryKey = true, ColumnDataType = "nvarchar(30)")] public string ReportNo { get; set; }
    public int Qty { get; set; }
}

// 发件箱：和业务表在同一个数据库、同一个事务里写入
[SugarTable("LabOutbox")]
[SugarIndex("UQ_LabOutbox_MsgId", nameof(MsgId), OrderByType.Asc, true)]
public class LabOutbox
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public int Id { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(40)")] public string MsgId { get; set; }          // 幂等键，接收方靠它去重
    [SugarColumn(ColumnDataType = "nvarchar(200)")] public string Payload { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(10)")] public string Status { get; set; }         // Pending / Sending / Sent / Dead
    public int Attempts { get; set; }
    public DateTime NextRetryAt { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(200)", IsNullable = true)] public string LastError { get; set; }
}

// 对方（ERP）的收件记录：MsgId 是主键，重复消息进不来
[SugarTable("LabErpInbox")]
public class LabErpInbox
{
    [SugarColumn(IsPrimaryKey = true, ColumnDataType = "nvarchar(40)")] public string MsgId { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(200)")] public string Payload { get; set; }
}

public static class Db
{
    // 临时库 Lab_join（LocalDB）。每次创建一个新连接：SqlSugarClient 不是线程安全的
    public static SqlSugarClient Create() => new SqlSugarClient(new ConnectionConfig
    {
        ConnectionString = @"Server=(localdb)\MSSQLLocalDB;Database=Lab_join;Integrated Security=true;TrustServerCertificate=true",
        DbType = DbType.SqlServer,
        IsAutoCloseConnection = true,
    });

    public static void EnsureDatabase()
    {
        var master = new SqlSugarClient(new ConnectionConfig
        {
            ConnectionString = @"Server=(localdb)\MSSQLLocalDB;Database=master;Integrated Security=true;TrustServerCertificate=true",
            DbType = DbType.SqlServer,
            IsAutoCloseConnection = true,
        });
        master.Ado.ExecuteCommand("IF DB_ID('Lab_join') IS NULL CREATE DATABASE Lab_join");
    }
}

// 模拟 ERP 的收货接口：按 MsgId 做脚本化的故障
public static class FakeErp
{
    public static int Calls;                 // 总调用次数
    public static int DuplicatesIgnored;     // 被去重丢掉的重复消息数
    public static bool R003Fixed;            // R-003 的根因修好了没有
    static readonly Dictionary<string, int> tries = new();

    public static void Reset() { Calls = 0; DuplicatesIgnored = 0; R003Fixed = false; tries.Clear(); }

    public static void Receive(string msgId, string payload)
    {
        Calls++;
        var n = tries[msgId] = tries.GetValueOrDefault(msgId) + 1;
        if (msgId == "CMP-R-002" && n <= 2) throw new HttpRequestException("503 Service Unavailable");      // 前两次 ERP 不可用
        if (msgId == "CMP-R-003" && !R003Fixed) throw new InvalidOperationException("500 物料 A100 未在 ERP 建档"); // 一直失败，直到有人修好
        var erp = Db.Create();
        if (erp.Queryable<LabErpInbox>().Any(x => x.MsgId == msgId)) DuplicatesIgnored++;                  // 幂等：已收过，直接当成功
        else erp.Insertable(new LabErpInbox { MsgId = msgId, Payload = payload }).ExecuteCommand();
        if (msgId == "CMP-R-004" && n == 1) throw new TimeoutException("等确认超时（其实 ERP 已经收下了）");   // 收到了，但确认丢了
    }
}

// 后台发送器：不停扫描发件箱，认领、发送、成功标记 / 失败退避重试 / 超过上限标死信
public class OutboxSender : BackgroundService
{
    public const int MaxAttempts = 4;
    const int BaseDelayMs = 100;             // 退避：100ms、200ms、400ms……（真实系统用秒或分钟）

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        // 上次进程崩溃时卡在 Sending 的消息，重新放回 Pending（接收方幂等，重发是安全的）
        Db.Create().Updateable<LabOutbox>().SetColumns(o => new LabOutbox { Status = "Pending" }).Where(o => o.Status == "Sending").ExecuteCommand();
        while (!ct.IsCancellationRequested)
        {
            var db = Db.Create();
            var due = db.Queryable<LabOutbox>().Where(o => o.Status == "Pending" && o.NextRetryAt <= DateTime.Now).OrderBy(o => o.Id).Take(10).ToList();
            foreach (var o in due)
            {
                // 认领：把条件写进 WHERE，多个发送器同时跑时只有一个抢到（和工单报工同一个套路）
                var claimed = db.Updateable<LabOutbox>().SetColumns(x => new LabOutbox { Status = "Sending" })
                    .Where(x => x.Id == o.Id && x.Status == "Pending").ExecuteCommand();
                if (claimed != 1) continue;
                var attempts = o.Attempts + 1;
                try
                {
                    FakeErp.Receive(o.MsgId, o.Payload);
                    db.Updateable<LabOutbox>().SetColumns(x => new LabOutbox { Status = "Sent", Attempts = attempts }).Where(x => x.Id == o.Id).ExecuteCommand();
                }
                catch (Exception ex)
                {
                    var dead = attempts >= MaxAttempts;
                    var next = DateTime.Now.AddMilliseconds(BaseDelayMs * Math.Pow(2, attempts - 1));
                    var msg = ex.Message;
                    db.Updateable<LabOutbox>().SetColumns(x => new LabOutbox { Status = dead ? "Dead" : "Pending", Attempts = attempts, NextRetryAt = next, LastError = msg })
                        .Where(x => x.Id == o.Id).ExecuteCommand();
                }
            }
            try { await Task.Delay(50, ct); } catch (OperationCanceledException) { }
        }
    }
}

public static class LabOutboxRun
{
    // 业务操作：报工记录 + 发件箱消息，同一个事务，要么都写入要么都不写
    static bool Report(SqlSugarClient db, string reportNo, int qty)
    {
        var r = db.Ado.UseTran(() =>
        {
            db.Insertable(new LabReport { ReportNo = reportNo, Qty = qty }).ExecuteCommand();
            db.Insertable(new LabOutbox
            {
                MsgId = "CMP-" + reportNo,
                Payload = $"{{\"reportNo\":\"{reportNo}\",\"qty\":{qty}}}",
                Status = "Pending",
                NextRetryAt = DateTime.Now,
            }).ExecuteCommand();
        });
        return r.IsSuccess;
    }

    static async Task WaitIdle(SqlSugarClient db)
    {
        while (db.Queryable<LabOutbox>().Any(o => o.Status == "Pending" || o.Status == "Sending")) await Task.Delay(100);
    }

    static void Print(SqlSugarClient db)
    {
        foreach (var o in db.Queryable<LabOutbox>().OrderBy(o => o.Id).ToList())
            Console.WriteLine($"   {o.MsgId,-10} {o.Status,-5} 尝试 {o.Attempts} 次  最后错误：{o.LastError ?? "无"}");
    }

    public static async Task Run()
    {
        Db.EnsureDatabase();
        var db = Db.Create();
        db.CodeFirst.InitTables<LabReport, LabOutbox, LabErpInbox>();
        db.Deleteable<LabReport>().ExecuteCommand();
        db.Deleteable<LabOutbox>().ExecuteCommand();
        db.Deleteable<LabErpInbox>().ExecuteCommand();
        FakeErp.Reset();

        Console.WriteLine("1. 报工 4 次，每次同时写发件箱");
        foreach (var (no, qty) in new[] { ("R-001", 300), ("R-002", 400), ("R-003", 200), ("R-004", 300) }) Report(db, no, qty);
        Console.WriteLine($"   报工 {db.Queryable<LabReport>().Count()} 行，发件箱 {db.Queryable<LabOutbox>().Count()} 行");
        Console.WriteLine($"2. 重复报工 R-001 -> {(Report(db, "R-001", 300) ? "成功" : "被拒绝（报工单号重复，整个事务回滚）")}");
        Console.WriteLine($"   报工 {db.Queryable<LabReport>().Count()} 行，发件箱 {db.Queryable<LabOutbox>().Count()} 行（发件箱没有多出孤儿消息）");

        using var host = Host.CreateDefaultBuilder().ConfigureLogging(l => l.ClearProviders())
            .ConfigureServices(s => s.AddHostedService<OutboxSender>()).Build();
        await host.StartAsync();
        await WaitIdle(db);
        Console.WriteLine($"3. 后台发送器跑完（上限 {OutboxSender.MaxAttempts} 次）：");
        Print(db);
        Console.WriteLine($"   ERP 实际收到 {db.Queryable<LabErpInbox>().Count()} 条不同的消息，调用了 {FakeErp.Calls} 次，其中 {FakeErp.DuplicatesIgnored} 次是重复消息被忽略");

        Console.WriteLine("4. 修好 ERP 里的物料档案，把死信 R-003 重新放回队列");
        FakeErp.R003Fixed = true;
        db.Updateable<LabOutbox>().SetColumns(o => new LabOutbox { Status = "Pending", Attempts = 0, NextRetryAt = DateTime.Now })
            .Where(o => o.Status == "Dead").ExecuteCommand();
        await WaitIdle(db);
        Print(db);
        Console.WriteLine($"   ERP 现在收到 {db.Queryable<LabErpInbox>().Count()} 条不同的消息，发件箱里 Sent {db.Queryable<LabOutbox>().Count(o => o.Status == "Sent")} 条、Dead {db.Queryable<LabOutbox>().Count(o => o.Status == "Dead")} 条");
        await host.StopAsync();
    }
}

读懂输出：

  • 步骤 1、2：4 次报工各写一行发件箱；重复的 R-001 触发主键冲突，UseTran 回滚，报工表和发件箱都没有多出行——业务和消息同成同败。
  • 步骤 3：R-001 一次成功；R-002 失败两次后成功（尝试 3 次）；R-003 失败 4 次转 Dead；R-004 尝试 2 次——第一次 ERP 收下但确认超时，第二次 ERP 发现是重复消息，直接成功。
  • 统计：ERP 实际只有 3 条不同的消息（R-001、R-002、R-004），调用 10 次（1 + 3 + 4 + 2），其中 1 次是重复被忽略。"至少一次 + 幂等"的效果：4 次业务调用里 R-004 被调用了两次，但账只记了一次。
  • 步骤 4：把死信放回 Pending 后，R-003 第 1 次成功（Attempts 被重置，LastError 保留了上一轮的错误作为痕迹）；最终 4 条都是 Sent，Dead 为 0。

动手改：

  1. 把 MaxAttempts 改成 2（我实际运行过）：R-002 需要 3 次才成功，于是也变成 Dead（尝试 2 次），ERP 只收到 2 条不同的消息，调用 7 次（1 + 2 + 2 + 2）。上限应怎么定？取决于对方典型的故障恢复时间和业务容忍度；
  2. 把 BaseDelayMs 改成 1000，总耗时会明显变长（没有测）；想想如果有 1 万条积压消息，同时退避会发生什么（重试风暴，需要加抖动）；
  3. 思路演示（我没有运行）：在 OutboxSender.ExecuteAsync 的 try 里、FakeErp.Receive 之后手工 Environment.Exit(1) 模拟崩溃，再重新运行：重启时 Sending 会被放回 Pending，消息被重发，ERP 靠 MsgId 去重（注意：实验的清空逻辑在 Run() 里，需要自己把清空去掉再测）；
  4. 思路演示（我没有运行）：同时开两个终端各跑一个发送器（把 Run 拆开），预期能看到"认领"的条件 UPDATE 保证同一条消息只被一个发送器处理。

实验 2：HttpClient + Polly 的小重试（同步调用） ​

目标：看 Polly 的重试策略怎么只重试 5xx、不重试 4xx，并且重试时用同一个幂等键。服务端用 HttpListener 在本机模拟：/api/flaky 前两次返回 503，第三次返回 200；/api/bad 一律返回 400。

新建 PollyLab.cs：

csharp
using System.Net;
using System.Text;
using Polly;
using Polly.Retry;

namespace JoinLab;

// 同步调用的“小重试”：HttpClient + Polly。对方是本机 HttpListener 模拟的 ERP 接口
public static class PollyLab
{
    public static async Task Run()
    {
        const string prefix = "http://localhost:5199/";
        using var listener = new HttpListener();
        listener.Prefixes.Add(prefix);
        listener.Start();
        int flakyHits = 0, badHits = 0;
        var keys = new HashSet<string>();
        _ = Task.Run(async () =>
        {
            while (listener.IsListening)
            {
                HttpListenerContext ctx;
                try { ctx = await listener.GetContextAsync(); } catch { break; }
                if (ctx.Request.Url!.AbsolutePath == "/api/flaky")
                {
                    flakyHits++;
                    lock (keys) keys.Add(ctx.Request.Headers["Idempotency-Key"] ?? "");
                    ctx.Response.StatusCode = flakyHits <= 2 ? 503 : 200;      // 前两次 503，第三次正常
                }
                else { badHits++; ctx.Response.StatusCode = 400; }              // 请求本身有问题：重试没用
                ctx.Response.Close();
            }
        });

        var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
            .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
            {
                MaxRetryAttempts = 3,
                Delay = TimeSpan.FromMilliseconds(100),
                BackoffType = DelayBackoffType.Exponential,   // 100、200、400 ms
                UseJitter = false,                            // 真实系统建议打开抖动，避免大家同一刻重试
                ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
                    .Handle<HttpRequestException>()
                    .HandleResult(r => (int)r.StatusCode >= 500),     // 只重试网络错误和 5xx，不重试 4xx
                OnRetry = args =>
                {
                    var why = args.Outcome.Result?.StatusCode.ToString() ?? args.Outcome.Exception?.Message;
                    Console.WriteLine($"   第 {args.AttemptNumber + 1} 次失败（{why}），{args.RetryDelay.TotalMilliseconds} ms 后重试");
                    return default;
                },
            })
            .AddTimeout(TimeSpan.FromSeconds(2))               // 整条流水线的总超时
            .Build();

        using var http = new HttpClient(new HttpClientHandler { UseProxy = false });   // 本机测试：别走系统代理
        var key = "CMP-R-001";                                 // 幂等键：在重试之前生成，重试用同一个
        async ValueTask<HttpResponseMessage> Post(string path, CancellationToken ct)
        {
            var req = new HttpRequestMessage(HttpMethod.Post, prefix + path) { Content = new StringContent("{\"qty\":300}", Encoding.UTF8, "application/json") };
            req.Headers.Add("Idempotency-Key", key);
            return await http.SendAsync(req, ct);
        }

        Console.WriteLine("1. 调用 /api/flaky（前两次返回 503）");
        var r1 = await pipeline.ExecuteAsync(ct => Post("api/flaky", ct), CancellationToken.None);
        Console.WriteLine($"   最终结果 {(int)r1.StatusCode}，服务器共收到 {flakyHits} 次请求，幂等键种类 {keys.Count} 个");
        Console.WriteLine("2. 调用 /api/bad（返回 400，不该重试）");
        var r2 = await pipeline.ExecuteAsync(ct => Post("api/bad", ct), CancellationToken.None);
        Console.WriteLine($"   最终结果 {(int)r2.StatusCode}，服务器共收到 {badHits} 次请求");
        listener.Stop();
    }
}

运行 dotnet run -- polly，输出：

1. 调用 /api/flaky（前两次返回 503）
   第 1 次失败（ServiceUnavailable），100 ms 后重试
   第 2 次失败（ServiceUnavailable），200 ms 后重试
   最终结果 200，服务器共收到 3 次请求，幂等键种类 1 个
2. 调用 /api/bad（返回 400，不该重试）
   最终结果 400，服务器共收到 1 次请求

读懂输出：

  • 第 1 个调用：前两次 503，Polly 分别等 100 ms、200 ms 重试，第三次 200；服务器共收到 3 次请求，但幂等键只有 1 种——重试用的是同一个键，接收方可以据此去重；
  • 第 2 个调用：400 不在 ShouldHandle 里，不重试，服务器只收到 1 次。

一个本机踩到的坑：我的环境里设置了 HTTP_PROXY 环境变量，HttpClient 默认会走系统代理，连本机的 localhost 测试服务也被代理接管，返回了代理的 503，服务器一次请求都没收到。代码里 new HttpClientHandler { UseProxy = false } 就是为此加的。生产环境的代理配置按公司网络规定来，不要照抄。

清理：sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -Q "DROP DATABASE Lab_join"。

现象 / 坑原因与办法
先改库后发消息，进程崩了消息丢了没有发件箱。把消息和业务数据同事务写入，再由后台发送
同一条消息被处理两次接收方没有幂等。MsgId 主键 / 唯一索引兜底，不要先查再插

练习题与答案 ​

  1. 为什么说"至少一次 + 幂等 = 效果上恰好一次"？ 答：发送方保证送到（宁可多发），接收方对重复的消息只处理一次，所以每条业务消息最终只产生一次效果。真正"恰好一次"的传输很难，且代价高，业务系统通常用这种组合。
  2. 发件箱解决了什么问题？它没有解决什么？ 答：解决了"业务数据已提交但消息丢了 / 消息发了但业务回滚"的不一致，因为消息和业务数据同事务。没有解决：消息仍可能重复（所以接收方要幂等）、对方宕机时消息仍积压（要监控和告警）、业务性错误（重试没用，要转死信人工处理）。
  3. 什么错误不应该重试？为什么？ 答：4xx（参数错误、未认证、找不到）和业务拒绝（物料未建档、余额不足）。请求本身有问题，重试结果一样，还会堵住后面的消息；应转死信、告警、人工处理。
  4. 实验 1 里 ERP 调用 10 次，却只有 3 条不同的消息，差在哪？ 答：R-002 的 2 次 503 失败、R-003 的 4 次失败，都没进收件表；R-004 调用了 2 次但第二次是重复被忽略。10 = 1 + 3 + 4 + 2，其中真正入库的只有 R-001、R-002、R-004 各一次。
  5. 为什么重试要加抖动（Jitter）？ 答：很多调用者在同一时间失败，会在同一时间按相同的退避重试，对方一恢复就被同时压垮；抖动给等待时间加随机量，把重试错开。
  6. 同步调用和异步消息各适合什么场景？ 答：需要立刻结果的校验、查询（上料时查 MSD、查追溯）用同步，配超时和降级；通知和结果类（报工、完工回传、不良事件）用异步，配幂等和对账。
  7. 为什么发送器的"认领"要用条件 UPDATE？ 答：多个发送器或多个线程可能同时看到同一条 Pending，条件 UPDATE 把检查和修改放在一条语句里，只有一个能把行数改成 1 抢到，其余得到 0，避免同一条消息被并发发送。
  8. 什么情况下值得引入 RabbitMQ / Kafka 这样的消息中间件？ 答：事件量大、多个系统订阅同一事件、需要缓冲削峰，且团队能运维。如果只是两个系统一对一、量不大，中间表或 HTTP API 加发件箱更简单。

小结 ​

  • 九种集成方式没有最优，只有合适：自研系统之间 HTTP API 加发件箱，对接买来的 ERP 常用中间表，设备用 OPC UA / MQTT / IPC-CFX，报表用 ETL；少用数据库链接做核心接口。
  • 向下的校验用同步，向上的结果用异步；异步必须有幂等和对账。
  • 投递以"至少一次 + 接收方幂等"为主；重试要限次、退避、抖动、只重试暂时性错误，达到上限转死信。
  • Outbox 模式：消息与业务数据同事务，后台发送器扫描、认领、发送；崩溃后 Sending 放回 Pending。
  • 监控看积压、最老消息年龄、死信、最后成功时间、对账差异；安全看认证、授权、签名防重放、内网隔离。
  • C# 里：IHttpClientFactory 或单例 HttpClient、Polly 重试、BackgroundService 做发送器、SqlSugar 事务与条件 UPDATE。
