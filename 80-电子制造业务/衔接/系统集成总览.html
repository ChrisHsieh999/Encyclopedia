系统集成总览

AI 生成 · 待核对制造业务衔接集成入门路径更新于 2026-10-21

⚠ 待核对：本篇的数据流全景表、"主数据谁是源头"和五条集成原则是行业通用做法，与本库 电子制造信息系统全景图、主数据与物料编码、WMS与MES交互 保持一致，不是某家公司的实际接口清单。你们的自研 MES/WMS/QMS/LIMS 与 ERP 之间到底有哪些接口、用什么方式、谁认领，请对照你们的系统核实，把差异告诉我，我来改。 文中的 SQL 和数字都是我在本机 SQL Server LocalDB 上实际运行得到的，数据是虚构的。

本篇是"衔接"系列的总览。读完你应该能：说清为什么系统之间的"衔接"是最容易出事的地方；看懂 ERP、PLM、APS、MES、WMS、QMS、LIMS、SPC、EAP/设备 之间的数据流全景表；知道每类主数据谁是源头；记住集成的五条通用原则（幂等、对账、补偿、解耦、版本）；按"入门路径"把本目录另外 4 篇读完；并动手建一张"接口台账"，把你们公司的接口盘点一遍。

一句话定义 ​

系统集成（也叫"衔接"）就是让几个各自独立的系统，对同一件事（一张工单、一盘料、一块不良板）说同样的话、记同样的账；它不是"把接口通了"，而是"通了以后每天都对得上"。

先修知识 ​

  • 电子制造信息系统全景图：知道有哪些系统、各管什么。本篇是它的"深入版"：只讲系统之间。
  • ISA-95：Level 4（ERP 这一层）和 Level 3（MES 这一层）之间怎么分工。
  • MES、WMS、QMS、ERP：至少读过各自的入口篇，知道它们的核心单据。

它解决什么问题 ​

单个系统出问题，通常只影响一个部门；系统之间的衔接出问题，会让两个部门同时说"我的数是对的"。现场故事：

  • ERP 里工单 WO-E001 改成了 300 拼板，车间 MES 还在按 250 拼板做，多做或少做了才有人发现；
  • MES 报工接口超时，操作员重试了一次，ERP 里入库 记了两遍；
  • 仓库的账说线边还有 980 个电阻，MES 说只剩 569 个，谁也说服不了谁；
  • 品质在 QMS 里新增了缺陷代码 PR-009，MES 的下拉框里没有，操作员只好选"其他"，柏拉图失真；
  • 一个接口三个月前悄悄停了，没有告警，直到月底关账才发现 少了 200 块的入库。

这些问题的共同点：每个系统自己都"没有错"，错在两个系统之间——没有人对这条缝负责。本系列就是把这条缝讲清楚：谁传什么给谁、什么时候传、传错了怎么办、怎么证明两边一致。

核心概念 ​

术语通俗解释
接口（Interface）两个系统约定好的"交接窗口"：传什么字段、什么格式、什么时候传、对方怎么回复
主数据（Master Data）多个系统共用、相对稳定的基础数据：物料、BOM、客户、供应商、设备、缺陷代码。见 主数据与物料编码
事务数据每天不断产生的业务记录：工单、报工、发料、检验结果。接口里流动最多的是它
同步 / 异步同步：我问你答，答完我才继续；异步：我把消息放下就走，你有空再处理。见 接口技术选型
幂等（Idempotent）同一条消息处理一次和处理十次，结果相同。重试、重发的前提
对账（Reconciliation）定期把两边的数拿出来逐条比，找出不一致
补偿（Compensation）发现不一致或失败后，用额外的动作把账补平（重发、冲销、人工调整）
死信（Dead Letter）重试多次仍失败的消息，单独放着等人工处理，不能悄悄丢掉
发件箱（Outbox）把"要发的消息"和业务数据放在同一个事务里存起来，再由后台慢慢发。见 接口技术选型

注意几个规律：

  1. MES 参与 9 条，所以后面三篇都围绕它展开：ERP与MES衔接（F02、F04、F05）、MES与WMS衔接（F06、F07）、MES与QMS衔接（F11、F12、F13）。
  2. 向下（计划到执行）的是"指令"（工单、配方、锁定），向上（执行到计划）的是"结果"（报工、检验、不良）。指令要能撤回和变更，结果要不丢不重。
  3. 同一个方向常有多条接口（ERP 到 MES 有 F02 和 F04，MES 到 WMS 有 F06 和 F07），它们的频率、失败处理都不同，不要混成一条。
  4. 设备层（F14）实时性最高，但不需要对账到单据级；业务层（F05、F07）实时性不用那么高，但必须对账。

主数据：谁是源头 ​

接口里最先要问的不是"怎么传"，而是"这份数据归谁改"。下表和 主数据与物料编码 一致（通用做法，你们公司可能不同）：

四条规则：

  1. 一个字段只有一个写入方，其他系统只读或同步，不要"两边都能改"；
  2. 所有系统用同一套编码，确实有多套（如客户料号），要有映射表；
  3. 同步要有方向、频率、版本号、失败处理四件事；
  4. 主数据变更要有生效日期，不要立刻覆盖正在生产的数据（见 ERP与MES衔接 的"BOM 版本生效"）。

集成的五条通用原则 ​

这五条贯穿本目录所有实验，先记住名字，每一条在后面的篇章里都会跑出数字来。

1. 幂等：同一条消息，处理一次和十次一样 ​

重试、网络抖动、人工重发，都会让同一条消息到达多次（RabbitMQ 官方文档明确说"消费者必须准备好处理重复投递"，MQTT 的 QoS 1 也是"至少一次、可能重复"）。所以接收方必须去重。常见做法：每条消息带一个唯一号（MsgId），接收方把已处理的唯一号记在一张表里，主键冲突就忽略。HTTP 接口也可以用 Idempotency-Key 请求头（IETF 有相关草案，状态是已过期的 Internet-Draft，不是正式标准，但做法已被广泛使用）。实验见 ERP与MES衔接。

2. 对账：不要相信"接口返回了成功" ​

接口成功只说明"这一次送到了"，不说明"两边总数一致"。要定期把两边的数拿出来逐条比：MES 报过的工，ERP 都有收货记录吗？WMS 的线边余额加上机台余额加上已消耗，等于发料吗？对账的粒度越细，定位越快：先按工单汇总找出差异工单，再按消息逐条找出缺的那一条。

3. 补偿：失败不是终点，要有"补"的路 ​

失败后有三种补法：自动重试（暂时性故障，如网络抖动）、重新投递（对账发现缺失，把缺的重发）、人工处理（数据本身有问题，如物料未建档，重试一万次也没用）。要给消息一个"死信"状态，重试到上限就停下来、告警、等人，而不是无限重试或悄悄丢掉。

4. 解耦：别让一个系统的宕机拖垮另一个 ​

MES 不能因为 ERP 维护两小时就停产。做法是先在本地落库，再异步发送（发件箱），ERP 恢复后自动补发。反过来，ERP 的表结构一改，MES 不该跟着坏，所以中间要有一层"接口表"或"消息格式"，两边只认这层约定，不直接读对方的业务表。

5. 版本：数据会变，要说清"哪一版" ​

BOM 有版本，工单有变更序号，缺陷代码有版本，接口报文本身也有版本。带版本号的消息，才能判断"这条是不是已经过期"（乱序到达时，版本小的丢掉）；工单下发时绑定 BOM 版本，之后改版不影响在制工单（见 工单管理）。

原则一句话在哪篇实验里跑
幂等唯一号 + 主键去重ERP与MES衔接、MES与WMS衔接、MES与QMS衔接
对账按工单、按消息两级比对ERP与MES衔接、MES与WMS衔接
补偿重发、死信、人工MES与WMS衔接、接口技术选型
解耦发件箱 + 后台发送接口技术选型
版本变更序号、代码版本ERP与MES衔接、MES与QMS衔接

业务视角 ​

谁在管这些接口 ​

角色做什么
接口负责人（通常是 IT）维护接口台账；新增或修改接口前评审；接口告警时第一响应
主数据管理员创建和变更物料、BOM、缺陷代码；对"两边不一致"的主数据做裁决
计划员看 ERP 与 MES 工单是否一致；处理"下发失败"的工单
仓库 / 品质 / 财务各自对账：WMS 账与实物，QMS 与 MES 的不良，ERP 与 MES 的完工

新增一个接口前，先回答这 8 个问题 ​

  1. 这份数据谁是源头？谁只读？
  2. 传什么字段？单位是否一致（PCS、PNL、千个）？
  3. 什么时候触发？多久一次？
  4. 失败了怎么办？谁收告警？
  5. 重复发会怎样？接收方怎么去重？
  6. 乱序到达会怎样？有没有版本号？
  7. 怎么对账？对账 SQL 谁来跑、多久跑？
  8. 一边停机时，另一边能否继续工作、恢复后怎么补？

KPI ​

指标含义
接口成功率成功消息数 ÷ 总消息数（按接口分别统计）
积压量 / 最老未处理消息年龄比成功率更早发现问题
死信数量与平均处理时长死信放了几天没人管，等于丢了
对账差异条数每日对账找出的不一致数，趋势比绝对值重要
主数据不一致数如"只在一边的缺陷代码"数量

技术视角 ​

接口台账（不可省的一张表） ​

接口台账是把全景表搬进数据库：每条数据流一行，写清谁、传什么、怎么传、频率、有没有对账、有没有重试、出事找谁。一开始做在 Excel 里也行，但放在数据库里就能用 SQL 查"哪些接口没人认领"。表结构见下面的实验。

一条消息至少要有什么 ​

不管用什么方式传（中间表、API、消息队列），一条业务消息至少带这些字段：

字段作用
MsgId全局唯一号，幂等的钥匙
MsgType / Version消息类型和版本；业务对象的变更序号
Source谁发的
OccurredAt业务发生的时间（不是处理时间）
业务键工单号、料盘标签、序列号等，便于对账与追查
业务数据数量、单位、状态等

接口日志与监控 ​

每条消息至少记录：接收时间、消息号、处理结果（成功、重复忽略、过期忽略、失败）、失败原因、处理耗时。监控看三件事：失败率、积压量、最老消息的年龄。详见 接口技术选型。

逐步例子：一张 ERP 工单穿过哪些接口 ​

以 ERP与MES衔接 的实验数据为例（工单 WO-E001，产品 A100，1 拼板 = 4 块）：

  1. F04：ERP 下发 250 拼板（= 1000 块）。计划员随后把数量改成 300 拼板（= 1200 块）；变更序号 v3 先到、v2 后到，MES 丢掉过期的 v2；
  2. MES 把 1200 块拆给两条线：700 + 500（一对多拆分）；
  3. F06：MES 向 WMS 提备料请求，WMS 回齐套结果（见 MES与WMS衔接）；
  4. F07：1 线上料、消耗、抛料、下线、退料，每一步都有唯一号，WMS 靠它去重；
  5. F11：AOI 判一块板桥连，MES 锁板并产生不良事件，QMS 自动开 NCR，评审结果回写，板从 Hold 变成 Repair（见 MES与QMS衔接）；
  6. F05：四次报工 300 + 400 + 200 + 300 = 1200 块，每次报工产生一条完工回传；其中一条丢了，ERP 只收到 1000 块；
  7. 日终对账发现 差 200 块，逐条找出缺失的那一条，重新投递，差异归零。

这个例子里"丢一条消息"不是意外，而是必然会发生的事——设计的目标是丢了能发现、能补。

常见坑与排查 ​

现象 / 坑原因与办法
"接口通了就完事"通了只是开始。没有幂等、对账、重试，运行三个月必出账不平
两边都能改同一个字段主数据没有唯一源头。指定源头，其他系统只读
直接读写对方的业务表对方一改表结构你就坏。读写"接口表"，由对方负责把业务表和接口表对接
失败消息悄悄丢掉必须有"失败"和"死信"状态，并告警
无限重试数据本身错误的消息重试一万次也没用，还会堵住后面的消息。设上限，到上限转死信
对账只看总数总数一致可能是一边多一边少抵消了。要按工单、按料盘、按消息逐级对
时间用各系统自己的本地时钟事件时间差几分钟，对账对不上。统一用服务器时间或带时区的时间
单位不一致（PCS、PNL、千个）在接口层显式换算，并保存换算系数；换算后不是整数要报错而不是四舍五入
接口只有人知道在哪做接口台账，写清负责人与对账方法
测试环境能通，正式环境不通网络隔离、权限、证书；上线前做一次真实网络环境联调

入门路径 ​

"衔接"目录共 5 篇，推荐这样读：

  1. 先读本篇（系统集成总览）：建立全景，记住五条原则。
  2. 再读 ERP与MES衔接：最主干的一条线，计划层和执行层之间。这里把"幂等、版本、对账"三件事用 T-SQL 完整跑一遍。
  3. 接着读 MES与WMS衔接：物料在仓库和产线之间流动，重点是"接口契约与对账"，业务背景先看 WMS与MES交互。
  4. 然后读 MES与QMS衔接：不良、锁定、NCR 的联动，以及缺陷代码主数据同步。业务背景先看 不良品拦截与锁定 和 不合格品控制NCR。
  5. 最后读 接口技术选型：前面三篇说"传什么、怎么对"，这一篇说"用什么技术传"，并用 C# 做出一个发件箱 + 后台发送 + 失败重试的最小实现。

学完后，再回头读几个完整场景会更有感觉：工单从下达到入库的全过程、物料从收货到上线的全过程、不良品从发现到关闭的全过程。MES 侧的设备接口见 MES与ERP及设备的接口设计。

练习题与答案 ​

  1. 为什么说"每个系统自己都没有错，错在两个系统之间"？ 答：每个系统只对自己的数据负责，都能自洽；但同一件事（工单数量、完工数量、库存）在两边各有一份，同步出问题时两边都"没错"，却对不上。没有人对"两边一致"负责，这条缝最容易出事。
  2. 全景表里 F05（MES 到 ERP 的报工）为什么必须对账，而 F14（设备过站参数）一般不需要？ 答：F05 是业务数据，直接影响入库和成本，少一条就少一笔账；F14 是实时过程数据，丢一条参数只影响曲线的一个点，且设备有缓存和补传，不追求单条对齐。
  3. 一个字段"只有一个写入方"，那么 BOM 的拥有者应是谁？ 答：有 PLM 的工厂，工程 BOM 的源头是 PLM，制造 BOM 常由 ERP 持有；MES 和 WMS 只读。没有 PLM 的小厂常以 ERP 为源头。具体以你们公司为准。
  4. 幂等和对账有什么分工？ 答：幂等保证"重复到达不出错"，是接收方每条消息的防线；对账保证"总数一致"，是事后整体的防线。两者缺一不可：只有幂等，丢了的消息发现不了；只有对账，重复的消息会先把账弄错。
  5. 实验里查询 3 找出 F03、F12、F14，你认为哪个最该优先整改，为什么？ 答：F12（缺陷代码同步）和 F03（排程数据）。它们是业务数据，既无对账也无重试，又没人认领；F14 是设备实时数据，设计上不追求单条对齐。
  6. 新增接口前的 8 个问题里，哪两个最容易被忽略？ 答：通常是"乱序到达会怎样"（没有版本号）和"一边停机时怎么补"（没有发件箱）。这两种情况平时不出现，一出现就是大事故。

小结 ​

  • 系统之间的衔接比系统本身更容易出事，因为没有人天然对"两边一致"负责。
  • 全景表把 15 条常见数据流列清楚：谁到谁、传什么、何时、多频、怎么传、失败怎么办。
  • 主数据要有唯一源头；一个字段只有一个写入方；编码统一；同步带版本。
  • 五条原则：幂等、对账、补偿、解耦、版本。
  • 做一张接口台账，是集成治理的第一步。
  • 按入门路径读完本目录另外 4 篇，每条原则都会跑出数字。
