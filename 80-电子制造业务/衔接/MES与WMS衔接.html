MES与WMS衔接

AI 生成 · 待核对制造业务衔接MESWMS接口更新于 2026-10-21

⚠ 待核对：本篇讲 MES 与 WMS 之间物料事件的接口契约与对账，是通用设计，不是你们系统的实际做法。你们的自研 WMS / MES 里线边仓归谁管、上料后在 WMS 里是什么位置、消耗用扫码还是反冲、MSD 寿命谁记，请对照核实。 实验里的位置模型（WH / LINE / MACH / USED / LOSS）和事件名是教学用的虚构设计；SQL 和输出是我在本机 SQL Server LocalDB 的临时库 Lab_join 上实际运行得到的。

本篇是"衔接"系列第 3 篇。业务背景（备料、齐套、发料、线边仓、反冲 vs 扫码）已经在 WMS与MES交互 里讲过，本篇不重复，侧重"两个系统之间的接口契约怎么定、怎么证明账是平的"。读完你应该能：列出 MES 与 WMS 之间的事件清单并为每个事件设计唯一号与失败处理；比较三种扣账时机的利弊并用数字算出它们的差；说清谁管线边库存、MSD 状态怎么共享；用 T-SQL 跑通发料 → 上料 → 消耗 → 抛料 → 下线 → 退料的数量守恒对账。

一句话定义 ​

MES 与 WMS 的衔接，就是物料每换一个"位置"（原料库、线边、机台、已消耗、损耗），就在两个系统之间留下一条带唯一号的事件，并且任何时候都能证明"发出去的 = 用掉的 + 损耗的 + 剩下的"。

先修知识 ​

  • WMS与MES交互：物料流六步、齐套、线边仓三种归属模式、反冲与扫码消耗。先读它。
  • 系统集成总览：全景表 F06、F07；五条原则。
  • SMT上料防错与站位表：上料时"扫料盘码对站位"，是 MES 的关键动作。
  • 库存管理与批次序列号、库存账与账实一致：库存按"物料 + 批次 + 库位"记，账由流水累加。
  • ERP与MES衔接：本篇用同样的幂等和对账手法。

它解决什么问题 ​

WMS与MES交互 讲了"怎么分工"，这里要解决"分工之后，接口怎么不出事"：

  • MES 把一天的消耗回写给 WMS，网络抖了一下丢了一条 2210 个的消耗，线边在 WMS 里一直显示还有 2210 个，实际早就用完了，仓库以为不缺料，下一张工单没料可用；
  • 超时重试，同一条消耗被 WMS 扣了两遍，线边余额变成负数或把别的料盘的库存扣光；
  • 操作员误扫，MES 上报"消耗 9999 个"，WMS 该不该收？收了账就乱，不收这条消息要不要消失？
  • 工单做完，线边还剩 365 个，谁也不知道它在线边仓还是在机台上，盘点时对不上；
  • 发料即扣、上料即扣、过站反冲，三种口径各有人用，月底三份数字谁也对不上谁。

核心概念 ​

先把"位置"定义清楚 ​

对账的前提是两个系统用同一套位置。本篇用 5 个位置（教学模型；你们的系统叫法可能不同）：

位置含义谁记变化事件
WH原料库（含收货上架后的库位）WMS收货、退料回仓
LINE线边仓：发到产线旁、还没上机台的料WMS（线边仓是 WMS 的一个仓库，见 WMS与MES交互）发料（WH 到 LINE）、下线（MACH 回 LINE）、退料（LINE 回 WH）
MACH机台：已经装上飞达（Feeder）的料盘MES 产生事件，WMS 记账上料（LINE 到 MACH）
USED已消耗：贴到板子上的MES 产生事件，WMS 记账消耗（MACH 到 USED）
LOSS损耗：抛料、料带头尾、飞达损耗MES 产生事件，WMS 记账抛料（MACH 到 LOSS）

每个料盘标签（LabelNo）在每个位置上有一个余额；每个事件是一次"从某位置扣、往某位置加"。守恒定律：对同一个标签，所有位置的余额之和永远等于最初的数量（这是双向记账的天然性质）。对账要抓的是更细的东西：MES 说发生的事，WMS 流水里是否都有；工单结束时线边和机台是否清零。

接口契约：事件清单 ​

事件方向触发时机唯一键（幂等键）建议WMS 的动作失败 / 异常时
备料请求MES → WMS工单下发工单号 + 版本生成备料单、算齐套超时未回告警
齐套结果WMS → MES备料后工单号 + 版本—MES 保留旧结果直到新结果到达
发料完成WMS → MES拣货出库发料单号 + 标签WH 到 LINEWMS 单边事务，MES 只接收
上料确认MES → WMS扫码对站位通过工单 + 站位 + 标签 + 时间序号LINE 到 MACH余额不足拒绝并告警（可能漏发料）
消耗回写MES → WMS周期（每班或每小时）或报工工单 + 标签 + 周期序号MACH 到 USED余额不足拒绝，进差异清单
抛料回写MES → WMS同上（设备计数得到）同上MACH 到 LOSS同上
下线（尾料）MES → WMS换料、换线、工单结束工单 + 标签 + 下线序号MACH 回 LINE余额不足拒绝

契约里要写死的几件事：

  1. 唯一键怎么拼：必须由发送方生成，同一个业务动作重发时保持不变。实验里用 E01 到 E06；真实系统可用"工单号-标签号-类型-序号"，不要用"当前时间"（重发时时间会变，唯一键就失效了）；
  2. 数量的单位：料盘数量用料的基本单位（个）；不要出现"盘"和"个"混用；
  3. 事件的先后依赖：下线必须发生在上料之后，消耗在上料之后。如果因为网络，消耗比上料先到，WMS 会因"来源余额不足"拒绝它——这是对的，发送方应该稍后重发，而不是强行记账；
  4. 拒绝不是丢失：被拒绝的消息仍然留在 MES 的事件表里，对账时作为差异出现，直到人工处理；
  5. 时间字段用事件发生时间（不是处理时间），便于事后核对。

扣账时机：发料即扣 vs 上料即扣 vs 过站反冲 ​

"什么时候在账上算这批料已经用掉"，三种常见口径：

口径账面上的"消耗"在何时记优点缺点
A. 发料即扣发料到线边就算消耗最简单，WMS 压力最小线边剩多少账上看不到；余料和尾料没人管；退料要做"负消耗"
B. 上料即扣料盘上机台时按整盘扣比 A 更靠近现场；扫码纪律好时可行机台上剩下的部分账外；尾料下线时要冲回
C. 过站反冲完工报工时按 良品数 × 单耗 倒推不用逐步记账，对 WMS 友好只扣理论值：抛料、报废板的料、飞达损耗全不在账里
D. 扫码实际（本篇实验）按周期把设备计数 / 扫码得到的实际消耗回写与现场最接近；能分出消耗、损耗、余料依赖扫码纪律和设备数据，接口事件最多

用本篇实验的数字对比。标签 LB001（电阻 R-10K-0402）一盘 5000 个，每块板 10 个（虚构），工单做完时：良品 450 块，另有 5 块板贴完后报废（板上料已消耗），贴片机抛料 85 个，尾料下线 365 个。

  • 实际：消耗 = (450 + 5) × 10 = 4550，损耗 85，余 365。检验：4550 + 85 + 365 = 5000 ✓。
  • A 发料即扣：账面消耗 5000，线边余 0。现场其实还有 365，账少了 365。
  • B 上料即扣：整盘上料账面消耗 5000，机台上 365 账外，直到下线才能冲回。
  • C 过站反冲：账面消耗 450 × 10 = 4500，账面线边应有 5000 − 4500 = 500；现场只有 365。这 500 − 365 = 135 个"消失"的料，由 5 块报废板的 50 个加 85 个抛料组成（50 + 85 = 135 ✓）。账面显示线边有 500，其实只有 365，和 WMS与MES交互 里"账面余量偏大、实际缺货"是同一件事。
  • D 实际：消耗 4550、损耗 85、余 365，和现场一致。

务实的做法（和 WMS与MES交互 一致）是 D 为主、C 当对照：实际消耗回写，工单完工时用反冲值核对，差异超过阈值就查原因。同一个料号、同一张工单，只能选一个口径作为"记账口径"，另一个只做对照，否则会重复扣（见 ERP与MES衔接）。

谁管线边库存 ​

结论和 WMS与MES交互 一致：线边库存在 WMS。MES 只持有两样东西：

  1. 上料关系：某个标签现在装在哪台设备的哪个站位（防错用）；
  2. 事件：上料、消耗、抛料、下线。

这意味着 MES 在做"这盘料还够不够"的实时判断时，不能只看自己的事件，还要有 WMS 余额作参照；反过来 WMS 看到的 MACH 余额，是 MES 事件送达后的结果，有延迟。所以对账一定要在"事件都已送达"的时点做，例如班末或工单结束时，而不是随时。

MSD 状态共享 ​

湿敏元件（MSD / MSL，见 MSD湿敏元件管理）拆袋后有"车间寿命"，超期必须烘烤。涉及两个系统：

数据谁是源头另一方怎么用
拆封时间、已用车间寿命、剩余时间WMS（标签与库存的主人）MES 上料前查询；或 WMS 超期时主动通知
上料后"暴露在车间环境"的时间MES 产生（料盘在机台上的时间）回写给 WMS，计入车间寿命
烘烤后寿命重置WMS通知 MES 刷新
超期冻结WMS库存状态变化事件 → MES 拒绝上料

关键点：车间寿命的"累计"只能有一个地方做，不然两边各算各的会越差越多。常见做法是 MES 回写"上机台 / 下线"时间戳，WMS 统一累计；MES 上料时调用 WMS 的校验接口（同步），失败就不让上。这一环如果用异步，必须有"最后一次校验的时间"，过期要重新校验。

线边仓盘点 ​

盘点（盘点与调拨）是对账之外的最后防线：

  1. 先让 MES 把已经产生的事件全部送达（班末同步），再冻结该线的事件处理；
  2. 仓管扫码盘点线边实物 + 机台上的料盘；
  3. 差异用"调整流水"（ADJ）补，写原因；不要直接改余额；
  4. 调整结果同步给 MES（机台上的料盘数量被修正）。

角色在衔接里关心什么
仓管 / 物料员发出的料是否到线边；线边余料何时退回
上料员扫码上料是否被接受；被拒绝时提示什么
线长缺料预警；班末线边清点
仓库账务 / 成本消耗、损耗、退料是否都进账
IT每日对账结果，死信与"被拒绝"的事件

KPI：对账差异条数（每日）、被拒绝事件数（根因分类：漏发料 / 误扫 / 重复）、消耗回写延迟（事件发生到 WMS 入账）、线边残留率（工单结束时线边剩余 ÷ 发料）、理论与实际消耗差异率（见 WMS与MES交互）。

技术视角 ​

三个原则 ​

  1. 记账口径单一：WMS 的每一次位置移动都是一条流水（WmsLedger），余额（WmsBalance）由流水驱动；流水只增不改。
  2. 每次移动是"检查 + 修改"一条语句：从来源位置扣减时写成条件 UPDATE（Qty >= @Qty），余额不足影响 0 行，整笔回滚；不允许负库存（CHECK (Qty >= 0) 兜底）。这和 工单管理 的防超报是同一个技巧。
  3. 幂等键就是唯一约束：WmsLedger.MsgId 唯一，重复消息要么先查到已处理，要么主键冲突被忽略。

对账分三层 ​

层问题做法
逐条MES 说发生过的事，WMS 流水里都有吗？按 MsgId 全外连接：缺失、数量不一致
余额工单结束，线边和机台是否清零？各位置余额合理吗？按标签汇总各位置余额
守恒发料 = 消耗 + 损耗 + 线边残留 + 机台残留？汇总核对，不等就是有人动了账外的料

逐条对账能精确指出"哪一条"；余额对账能发现"MES 没报但数对不上"（例如有人手工搬料）；守恒对账能给出整体结论。三层缺一不可。

补偿的写法 ​

补偿不是"再发一遍"那么简单：

  • 幂等重发：把所有 WMS 流水里没有的 MES 事件重发。已处理的靠 MsgId 自动忽略，所以重发可以是粗暴的"全部重发"，不需要精确知道丢了哪几条（实验步骤 7）；
  • 被拒绝的怎么办：重发依旧会被拒绝（如 E06 的 9999），这是业务问题不是传输问题，重发一万次也没用，要进人工处理，并写原因；
  • 重发的顺序：按事件序号（实验里按 MsgId 排序），保证上料先于消耗。

逐步例子 ​

场景（对应实验）：工单 WO-1001，标签 LB001，电阻 5000 个。

  1. WMS 发料：WH 5000 到 LINE 5000。
  2. 上料：LINE 5000 到 MACH 5000。
  3. 一天里 MES 记了 6 条事件：E01 上料 5000；E02 消耗 2340；E03 消耗 2210；E04 抛料 85；E05 下线 365；E06 消耗 9999（误扫）。
  4. 发送给 WMS，E03 没送到：WMS 流水里没有它。E06 被拒绝，因为机台上只有 2210，没有 9999。
  5. E02 又被重发一次（超时重试）→ 重复消息，忽略。
  6. 逐条对账：E03、E06 缺失；余额对账：MACH 还有 2210（本该消耗掉），USED 才 2340。
  7. 补偿：全部重发。E03 成功，其余已处理的忽略，E06 仍被拒绝（要人工）。
  8. 再对账：只剩 E06。余额：USED 4550，LOSS 85，LINE 365，MACH 0。守恒：4550 + 85 + 365 + 0 = 5000 ✓。
  9. 退料：LINE 365 回 WH，LINE 清零。

DROP TABLE IF EXISTS dbo.WmsLedger, dbo.WmsBalance, dbo.MesMatEvent;
GO
-- WMS 一侧：每个料盘标签在每个"位置"上有一个余额；每次移动写一条流水
--   WH 原料库 / LINE 线边仓 / MACH 机台（已上料） / USED 已消耗 / LOSS 抛料损耗
CREATE TABLE dbo.WmsBalance (
    LabelNo varchar(20) NOT NULL,
    Loc     varchar(5)  NOT NULL CHECK (Loc IN ('WH','LINE','MACH','USED','LOSS')),
    Qty     int         NOT NULL CHECK (Qty >= 0),          -- 不允许负库存
    PRIMARY KEY (LabelNo, Loc)
);
CREATE TABLE dbo.WmsLedger (
    LedgerId int IDENTITY PRIMARY KEY,
    MsgId    varchar(30) NOT NULL UNIQUE,                   -- 幂等键：同一条消息只记一次
    LabelNo  varchar(20) NOT NULL,
    TxnType  varchar(8)  NOT NULL,                          -- ISSUE / LOAD / CONSUME / SCRAP / UNLOAD / RETURN
    FromLoc  varchar(5)  NOT NULL,
    ToLoc    varchar(5)  NOT NULL,
    Qty      int         NOT NULL CHECK (Qty > 0),
    WoNo     varchar(20) NULL
);
-- MES 一侧：MES 自己记的物料事件（上料、消耗、抛料、下线），发给 WMS 之前先落库
CREATE TABLE dbo.MesMatEvent (
    MsgId   varchar(30) PRIMARY KEY,
    LabelNo varchar(20) NOT NULL,
    EvtType varchar(8)  NOT NULL,                           -- LOAD / CONSUME / SCRAP / UNLOAD
    Qty     int         NOT NULL,
    WoNo    varchar(20) NOT NULL
);
GO
-- WMS 的统一入口：按 MsgId 幂等；扣减写成"条件 UPDATE"，余额不够就整笔拒绝
CREATE OR ALTER PROCEDURE dbo.usp_WmsMove
    @MsgId varchar(30), @LabelNo varchar(20), @TxnType varchar(8), @From varchar(5), @To varchar(5), @Qty int, @WoNo varchar(20) = NULL
AS
BEGIN
    SET NOCOUNT ON;
    IF EXISTS (SELECT 1 FROM dbo.WmsLedger WHERE MsgId = @MsgId) BEGIN PRINT @MsgId + N' -> 重复消息，忽略'; RETURN; END
    BEGIN TRY
        BEGIN TRAN;
        UPDATE dbo.WmsBalance SET Qty = Qty - @Qty WHERE LabelNo = @LabelNo AND Loc = @From AND Qty >= @Qty;
        IF @@ROWCOUNT = 0 THROW 50020, N'来源位置余额不足', 1;
        MERGE dbo.WmsBalance AS t USING (SELECT @LabelNo AS LabelNo, @To AS Loc) AS s ON t.LabelNo = s.LabelNo AND t.Loc = s.Loc
        WHEN MATCHED THEN UPDATE SET Qty = t.Qty + @Qty
        WHEN NOT MATCHED THEN INSERT (LabelNo, Loc, Qty) VALUES (@LabelNo, @To, @Qty);
        INSERT dbo.WmsLedger (MsgId, LabelNo, TxnType, FromLoc, ToLoc, Qty, WoNo) VALUES (@MsgId, @LabelNo, @TxnType, @From, @To, @Qty, @WoNo);
        COMMIT;
        PRINT @MsgId + N' ' + @TxnType + N' ' + CAST(@Qty AS nvarchar(10)) + N' -> 成功';
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;
        PRINT @MsgId + N' ' + @TxnType + N' ' + CAST(@Qty AS nvarchar(10)) + N' -> 被拒绝：' + ERROR_MESSAGE();
    END CATCH
END
GO
-- MES 把自己的事件按事件类型翻译成 WMS 的移动，再发出去。@Skip 模拟"这一条没送到"
CREATE OR ALTER PROCEDURE dbo.usp_SendMesEvents @Skip varchar(30) = NULL AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @m varchar(30), @l varchar(20), @t varchar(8), @q int, @w varchar(20);
    DECLARE c CURSOR LOCAL FAST_FORWARD FOR SELECT MsgId, LabelNo, EvtType, Qty, WoNo FROM dbo.MesMatEvent WHERE MsgId <> ISNULL(@Skip, '') ORDER BY MsgId;
    OPEN c; FETCH c INTO @m, @l, @t, @q, @w;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        IF @t = 'LOAD'    EXEC dbo.usp_WmsMove @m, @l, 'LOAD',    'LINE', 'MACH', @q, @w;
        IF @t = 'CONSUME' EXEC dbo.usp_WmsMove @m, @l, 'CONSUME', 'MACH', 'USED', @q, @w;
        IF @t = 'SCRAP'   EXEC dbo.usp_WmsMove @m, @l, 'SCRAP',   'MACH', 'LOSS', @q, @w;
        IF @t = 'UNLOAD'  EXEC dbo.usp_WmsMove @m, @l, 'UNLOAD',  'MACH', 'LINE', @q, @w;
        FETCH c INTO @m, @l, @t, @q, @w;
    END
    CLOSE c; DEALLOCATE c;
END
GO
-- 对账：把"MES 说发生了什么"和"WMS 流水里记了什么"逐条比对（按 MsgId 对）
CREATE OR ALTER PROCEDURE dbo.usp_ReconMesWms AS
BEGIN
    SET NOCOUNT ON;
    SELECT COALESCE(e.MsgId, l.MsgId) AS MsgId, e.EvtType AS MesType, e.Qty AS MesQty, l.TxnType AS WmsType, l.Qty AS WmsQty,
           CASE WHEN l.MsgId IS NULL THEN N'WMS 缺失' WHEN e.MsgId IS NULL AND l.TxnType IN ('LOAD','CONSUME','SCRAP','UNLOAD') THEN N'MES 缺失'
                WHEN e.Qty <> l.Qty THEN N'数量不一致' ELSE N'一致' END AS Result
    FROM dbo.MesMatEvent e FULL JOIN dbo.WmsLedger l ON l.MsgId = e.MsgId
    WHERE l.MsgId IS NULL OR (e.MsgId IS NULL AND l.TxnType IN ('LOAD','CONSUME','SCRAP','UNLOAD')) OR e.Qty <> l.Qty
    ORDER BY 1;
END
GO

动手改：

  1. 把 E06 的数量从 9999 改成 100，重新运行（我实际运行过）：E06 在步骤 3 会被接受（此时 MACH 余额 2210 ≥ 100），MACH 变成 2110；到了步骤 7，补发 E03（消耗 2210）反而因为 MACH 只剩 2110 而被拒绝，最后 MACH 残留 2110、USED 只有 2440，守恒检查里 OnMach 不是 0。这说明两点：条件扣减只能防"越界"，防不住"误扫的小数"；而且一条错误数据被接受后，会让后面正确的数据反过来被拒绝，所以误扫要靠班末盘点和人工核对发现。
  2. 把 @Skip = 'E03' 改成 'E01'（上料这条丢了），重新运行（我实际运行过）：步骤 3 里 E02 到 E06 全部被拒绝（MACH 上没有料），逐条对账 6 条全部缺失；步骤 7 按顺序重发，E01 先成功，E02 到 E05 随后全部成功，只有 E06 仍被拒绝。这就是"事件先后依赖"，也是补偿要按序重发的原因。

常见坑与排查 ​

现象 / 坑原因与办法
线边显示有料，实际没有消耗回写丢了。逐条对账 + 余额对账；回写失败进发件箱重发
同一条消耗扣了两次幂等键没有（或每次重发都生成新键）。唯一键由发送方生成，重发保持不变
余额变成负数扣减没有写成条件 UPDATE，或没有 CHECK (Qty >= 0)
上料丢了，后面一串消耗全被拒绝事件依赖。补偿要按序重发；上料丢失要优先处理
总数守恒但位置不对守恒只是必要条件，必须配合逐条与余额对账
MES 与 WMS 各自累计 MSD 寿命寿命累计只能有一个地方；MES 回写时间戳，WMS 统一累计
盘点调整直接改余额要写调整流水并说明原因，余额由流水驱动
退料没扫码退料必须单据化 + 扫码，否则线边残留永远对不上
同一盘料被两个工单占用上料时检查料盘状态与归属，已被占用就拒绝
记账口径换了没人通知记账口径写进接口文档；变更要有版本与生效日期

练习题与答案 ​

  1. 为什么线边库存放在 WMS，而不是 MES？ 答：库存要有单一数据源和完整的流水，WMS 本就管库位、批次和先进先出；MES 只记上料关系和事件，各司其职，避免两边都有库存形成"双账"。
  2. 实验步骤 6 里 TotalAcrossLocs 是 5000，为什么还说账有问题？ 答：总和守恒是双向记账的天然性质，哪怕少了一条消耗，也只是物料停留在 MACH 而不是 USED。要发现问题，必须看每个位置是否合理（工单结束时机台应清零）和 MES 与 WMS 的逐条对账。
  3. 过站反冲的账面线边余量是多少？和实际差多少，差异由哪几部分组成？ 答：5000 − 450 × 10 = 500；实际 365，差 135，其中 5 块报废板的料 50 加抛料 85。
  4. E06 补偿重发仍被拒绝，下一步怎么办？ 答：它是业务问题而非传输问题，要人工核查（是否误扫、是否该冲正），写明原因后在 MES 里作废该事件，或补相应的上料 / 调整流水；不能靠重发解决，也不能放宽 WMS 的余额检查。
  5. 为什么唯一键不能用"当前时间"？ 答：重发时时间变了，唯一键就变了，WMS 无法识别它是重复；应该由业务动作决定（工单、标签、类型、序号），同一动作重发保持不变。
  6. 对账为什么要在"事件都已送达"的时点做？ 答：事件在途时，两边本来就有时间差，此时对账会产生大量假差异；班末或工单结束、事件补偿完成后再对，差异才是真问题。
  7. MSD 剩余车间寿命，谁是源头？为什么不让 MES 和 WMS 各算各的？ 答：WMS 作为标签和库存的主人是源头，MES 回写上线 / 下线时间戳；两边各算会因取舍和延迟越差越多，且超期冻结的判断会不一致。

小结 ​

  • MES 与 WMS 之间的接口是位置移动事件：发料、上料、消耗、抛料、下线、退料，每条事件有唯一键、有失败处理。
  • 线边库存归 WMS；MES 只管上料关系和事件；MSD 寿命的累计只能在一处。
  • 扣账口径不能混用：发料即扣、上料即扣、过站反冲、扫码实际，各有利弊；务实做法是实际为主、反冲对照。
  • 条件 UPDATE 防负库存，唯一键防重复；被拒绝的事件要留在差异清单里等人，不能悄悄消失。
  • 对账三层：逐条、余额、守恒；守恒不能单独证明账是对的。
  • 补偿可以"全部幂等重发"，但业务问题只能人工处理。
