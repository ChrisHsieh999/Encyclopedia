物料标签与条码

AI 生成 · 待核对制造业务WMS条码追溯更新于 2026-10-21

⚠ 待核对：数据标识符（Q、1T、1P、P、10D 等）的含义已对照 MHI 官网的 ANSI MH10.8.2 数据标识符页面；ECIA 的 2D 标签规范 EIGP 114 我只看到了摘要，没有读到正文，具体字段与版面请以供应商标签和该规范原文为准。本篇的内部标签格式、标签状态、拆分合并规则是通用设计，你们的自研 WMS 一定有自己的格式和规则，请对照核实。SQL 与 C# 代码及输出都是我在本机 SQL Server LocalDB 上实际运行得到的。

本篇是 WMS 系列的一篇。读完你应该能：看懂一张电子料盘标签上每个字段是什么；说清"一物一码、一批一码、一盘一码"的区别和各自适用的场景；设计一张内部物料标签的字段和编号；理解拆分、合并、补打标签时为什么要"作废旧的、印新的、记血缘"；并用 C# + SqlSugar 做出保持数量守恒的拆分合并。

一句话定义 ​

物料标签是贴在料盘、料袋或料箱上的一张身份证：用文字和条码/二维码写明"这是什么料、哪个批次、多少数量、什么日期码、放在哪"。仓库里的每一次扫码，认的就是它。

先修知识 ​

  • 条码与二维码：知道一维码、二维码是什么，扫码枪读出来的是一串文本。
  • 条码与板码规则：知道 PCB 板码（SN）的编码思路，本篇讲的是"物料"而不是"板"。
  • 库存管理与批次序列号：知道库存按"物料 + 批次 + 库位"记录，批次和序列号的区别。
  • 收货与上架：知道来料是怎么收进仓库的（标签通常是收货时打印）。

它解决什么问题 ​

现场故事：

  • 仓库里有两盘 R-10K-0402（10 kΩ 贴片电阻）。一盘来自批次 L2610A，另一盘来自 L2609Z，外观完全一样。上料员凭印象拿了一盘，贴到板上。后来质量说 L2609Z 这批电阻阻值偏移，要找出用了这批的所有板子——没有批次标签，根本查不出来。
  • 一盘 5000 个的料用了 2000 个，剩下的尾料没有新标签，原标签还写着 5000。下一个人扫码，系统说"还有 5000"，实际只有 3000，账实不符，工单因缺料停线。
  • 供应商标签五花八门：每家的字段位置、条码类型、批次写法都不同，没法统一扫码。
  • 标签丢了或者脏了，仓库管理员凭记忆手写一个补上，从此这盘料的来历断了。

所以要有统一的、可扫的、唯一的标签，并且数量一旦改变，标签必须跟着变，而且改变的来龙去脉要留下记录。

核心概念 ​

供应商标签 vs 内部标签 ​

电子元件的包装上，供应商已经贴了标签，上面有条码或二维码。但仓库还是要再贴一张自己的内部标签，原因：

供应商标签内部标签
格式由供应商决定，各家不同格式统一，扫码枪和系统只认一种
写的是供应商料号写的是本公司物料编码（见 主数据与物料编码）
不保证每盘唯一（同批次多盘可能同号）每盘一个唯一标签号
无库位、无收货信息有库位、收货日期、状态
无法记录拆分合并可以靠标签号建立血缘关系

内部标签通常在收货时打印并贴上，同时把供应商标签里的关键信息（供应商料号、批次、日期码、数量）扫进系统，作为内部标签的内容。

读懂供应商标签：数据标识符（Data Identifier） ​

电子行业的物料标签大多遵循 ANSI MH10.8.2 的数据标识符（DI）约定：每个字段前有一个短前缀，告诉扫码系统后面是什么。据 MHI 官网的 DI 列表，常见几个：

DI含义（官方英文说明的意译）
P客户（采购方）料号，Item Identification Code assigned by Customer
1P供应商料号，Item Identification Code assigned by Supplier
Q数量（只含数字，单位双方约定）
1T供应商的批次/追溯号，Traceability Number assigned by the Supplier（lot、batch 等）
T客户的批次/追溯号
10D日期，格式 YYWW（年 + 周）
1D日期，格式 DDMMYY
9D日期，格式由双方约定（资料提示 2021 版不推荐使用，因为 0 容易和字母 O 混淆）
4L原产国，两位 ISO 3166 国家码
V客户分配给供应商的供应商代码
S序列号，Serial Number

供应商二维码标签里的内容由这些"DI + 值"拼接而成，中间用分隔符隔开。你的扫码枪读出来的是一整串文本，系统要按 DI 把它拆开。具体的分隔符和信封格式（如 ISO/IEC 15434）以供应商标签和规范原文为准，这里不展开。

ECIA（电子元件行业协会）发布了专门的 2D 条码标签规范 EIGP 114，建议了条码类型、尺寸、打印质量、标准数据集和 DI 等。EIA/CEA-556 则管的是外箱标签，料盘/料管/托盘的标记另归产品包装标签规范。

日期码 ​

日期码（Date Code）说明元件的生产时间，最常见格式是 YYWW：两位年 + 两位周。例如 2543 表示 2025 年第 43 周。仓库用它判断元件新旧，先进先出的依据之一（见 先进先出与先到先用），也是有保质期的物料的计算依据。日期码和批次是两个东西：批次说"同一次生产"，日期码说"什么时候生产的"。

一物一码、一批一码、一盘一码 ​

标签的"粒度"是设计标签最重要的决定。

粒度含义适合的物料例子
一物一码每一个实体一个唯一码有序列号管理的产品、昂贵或关键元件PCB 板的 SN；整机 SN；某些 FPGA 的 chip ID
一盘（箱/卷）一码每个物理包装一个码电子贴片元件的主流做法一卷 5000 个的 0402 电阻（Reel）
一批一码同批次整批共用一个码价值低、不逐件追溯的物料螺丝、标签纸、包装袋

为什么元件通常是"一盘一码"：元件一盘里成千上万个，没法每个都有码；但每盘独立管理才能记录"这盘装在哪个站位、用了多少、剩多少"。再往下想一步：上了线以后，追溯就是"这块板用了哪些盘"（见 物料追溯与批次关联、SMT上料防错与站位表）。

内部标签应该有哪些字段 ​

字段说明例子
标签号唯一，不重复；做成流水号，系统生成LB26102000001
物料编码公司内部料号IC-MCU-32
批次供应商批次，追溯用L2610A
数量本盘此刻的数量2000
日期码供应商日期码2543
库位 / 状态库位在系统里，打印在标签上可选RAW-A-01
供应商、收货日期追溯和账龄—
MSL 等级湿敏元件的醒目标识，见 MSD湿敏元件管理MSL 3

标签号的设计原则：

  • 唯一第一，不重复一次都不允许；
  • 短，方便人工核对和输入（11–15 位足够）；
  • 可以带前缀和日期（示例中的 LB + 年月日 + 5 位流水），但不要把物料号塞进去——因为物料号以后可能改，而标签号不能变；
  • 由数据库序列（SEQUENCE）或类似机制生成，不要由多台电脑各自在本地生成。

条码里放什么：最稳妥的做法是条码里只放标签号，其余信息全在数据库里查；这样标签就算数量变了也不会"条码内容和数据库不一致"。另一种做法是条码里放全部字段（离线也能读），但数量一旦变化就必须作废重印。本篇实验用的是后者，格式借用 DI 的写法：

LB26102000001|P=IC-MCU-32|1T=L2610A|Q=2000|10D=2543

标签的状态 ​

状态含义
Active有效。盘上的数量就是标签上写的数量
Consumed已用完（整盘消耗）
Void作废。被拆分、合并或补打所取代，纸还在物理世界里，但系统不再认它

铁律：标签上印的数量，一经打印就不能改 ​

这是本篇最重要的一条。想象你手里的料盘，标签上印着 Q=5000。如果系统里把这个标签的数量改成了 3000，那么：

  • 之后任何人拿着这个旧标签去扫码，看到的是 5000，系统里是 3000，谁对？
  • 如果有离线查看的二维码内容（里面写着 5000），就和数据库冲突了。

所以规则是：数量变了，就作废旧标签，印新标签，并记录"新标签是从哪个旧标签来的"。三种场景：

操作旧标签新标签数量关系
拆分（把一盘分成两盘）作废两张：剩余 + 拆出新两张之和 = 旧标签数量
合并（把几盘并成一盘）全部作废一张：总和新标签数量 = 各旧标签之和；只能合并物料、批次、日期码、库位都相同的
补打（标签丢了、脏了）作废一张：数量相同数量不变

每次操作在 LabelLink 里记一条"谁来自谁"，沿着这条链就能追到原始来料。

守恒不变式 ​

同一物料同一批次同一库位下，所有有效（Active）标签的数量之和 = 库存数量。 拆分、合并、补打都不会改变库存总量；只有收货、发料、报废这种真正的库存动作才会。这条等式可以用来日常自检，也是账实不符时的排查起点（见 库存账与账实一致）。

业务视角 ​

标签在仓库流程中的位置 ​

环节标签相关动作说明
收货扫供应商标签，系统生成并打印内部标签，贴在每盘上一盘一张。数量以实物清点为准
上架扫内部标签 + 扫库位码建立"这盘在哪"。见 收货与上架
发料按工单扫标签，系统记发料；整盘发或拆盘发拆盘发料要拆标签。见 拣货与发料
线边/上料扫标签上料，对站位见 SMT上料防错与站位表
尾料下线扫标签 + 称/数实际剩余，换新标签拆分的一种：用掉的作废，剩余出新签
退料剩余物料回仓，补标签见 退料与呆滞料

谁来补打？ ​

补打是风险点：随便补打可以"洗"出新标签，让真假难辨。通用做法：

  • 补打需要权限（仓库管理员以上）并填原因；
  • 补打自动作废旧标签，建立 Reprint 血缘；
  • 统计补打次数，补打频繁的物料/操作员要查原因（标签质量差？流程不顺？）。

KPI ​

  • 标签覆盖率：在库物料盘中，有有效内部标签的比例；
  • 扫码一次通过率：首次扫描即成功的比例，低则要查标签打印质量；
  • 补打次数/比例；
  • 拆分/合并次数：反映尾料处理的频繁程度。

表设计 ​

标签表和血缘表（也是本篇实验里的表）：

表作用
MatLabel一张标签一行；打印后 Qty 不再修改，只改 Status

三个关键技术点 ​

1. 标签号用 SQL Server 的 SEQUENCE，原子递增，多台电脑同时申请也不会重复：

sql
CREATE SEQUENCE dbo.SeqLabel AS int START WITH 1 INCREMENT BY 1;
-- 取下一个：SELECT NEXT VALUE FOR dbo.SeqLabel

2. "抢占"旧标签：把状态条件写进 UPDATE 的 WHERE（和 工单管理 里防超报是同一招）：

sql
UPDATE MatLabel SET Status = 'Void' WHERE LabelNo = @no AND Status = 'Active';
-- 受影响行数 = 1 表示"抢到了"，= 0 表示别人已经处理过，直接拒绝

如果两个人同时拆同一张标签，只有一个能抢到。先抢占，抢到才去创建新标签，所以新标签的编号只会被成功的一方消耗。

3. 一个事务包住所有动作：作废旧标签、插入新标签、写血缘、（消耗时）扣库存和写 InvTxn，要么全成要么全不成。

守恒校验 SQL ​

sql
SELECT i.MaterialCode, i.LotNo, i.Qty AS InvQty,
       ISNULL((SELECT SUM(l.Qty) FROM MatLabel l
               WHERE l.Status = 'Active' AND l.MaterialCode = i.MaterialCode
                 AND l.LotNo = i.LotNo AND l.LocationCode = i.LocationCode), 0) AS LabelQty
FROM Inventory i WHERE i.Status = 'Available';

任何一行 InvQty <> LabelQty 都要追查。

追溯：沿血缘往上找 ​

用递归 CTE 沿 LabelLink 一路往上，就能回答"这盘料最初是哪个来料标签"。实验里有演示。

逐步例子 ​

0初始2000 + 4002400
1把 2000 的拆出 500（比如工单要 500）旧 0001 作废；新 1500、新 5001500 + 500 + 400 = 2400
2把 1500 和 400 合并（同批次同库位）1500、400 作废；新 19001900 + 500 = 2400
3500 的标签被油污弄脏，补打旧 500 作废；新 5001900 + 500 = 2400
4500 的标签拆出 100旧 500 作废；新 400、新 1001900 + 400 + 100 = 2400
5消耗掉 400 那张该标签 Consumed，库存减 4001900 + 100 = 2000

每一步合计都是 2400，直到第 5 步真正消耗才变。这也是下面实验在验证的。

核心逻辑 LabLabel.cs：

csharp
using SqlSugar;

namespace Wms2Lab;

// 标签实验：拆分 / 合并 / 补打 / 消耗，全程保持"有效标签数量合计 = 库存数量"
public static class LabLabel
{
    static readonly DateTime Now = new(2026, 10, 26, 10, 0, 0);

    static string NewNo(SqlSugarClient db) => $"LB261026{db.Ado.GetInt("SELECT NEXT VALUE FOR dbo.SeqLabel"):D5}";

    // 二维码内容：借用 MH10.8.2 风格的数据标识符（P 物料号、1T 批次、Q 数量、10D 日期码 YYWW）
    public static string Encode(MatLabel l) => $"{l.LabelNo}|P={l.MaterialCode}|1T={l.LotNo}|Q={l.Qty:0.###}|10D={l.DateCode}";

    public static MatLabel Decode(string s)
    {
        var p = s.Split('|');
        string F(string k) => p.Skip(1).First(x => x.StartsWith(k + "=")).Substring(k.Length + 1);
        return new MatLabel { LabelNo = p[0], MaterialCode = F("P"), LotNo = F("1T"), Qty = decimal.Parse(F("Q")), DateCode = F("10D") };
    }

    static MatLabel Child(MatLabel from, decimal qty, string no) => new()
    {
        LabelNo = no, MaterialCode = from.MaterialCode, LotNo = from.LotNo, DateCode = from.DateCode,
        Qty = qty, LocationCode = from.LocationCode, Status = "Active", CreatedAt = Now
    };

    // 作废旧标签。条件写进 WHERE：只有仍是 Active 的才能被处理，返回 1 才算抢到
    static bool Claim(SqlSugarClient db, string no, string to) =>
        db.Updateable<MatLabel>().SetColumns(x => new MatLabel { Status = to })
          .Where(x => x.LabelNo == no && x.Status == "Active").ExecuteCommand() == 1;

    public static string Split(SqlSugarClient db, string no, decimal n)
    {
        var l = db.Queryable<MatLabel>().InSingle(no);
        if (l == null || l.Status != "Active") return "拒绝：标签不存在或已失效";
        if (n <= 0 || n >= l.Qty) return "拒绝：拆出数量必须大于 0 且小于标签数量";
        db.Ado.BeginTran();
        try
        {
            if (!Claim(db, no, "Void")) { db.Ado.RollbackTran(); return "拒绝：标签刚被别人处理过"; }
            var a = Child(l, l.Qty - n, NewNo(db));
            var b = Child(l, n, NewNo(db));
            db.Insertable(new List<MatLabel> { a, b }).ExecuteCommand();
            db.Insertable(new List<LabelLink> {
                new() { Kind = "Split", FromLabel = no, ToLabel = a.LabelNo, Qty = a.Qty, At = Now },
                new() { Kind = "Split", FromLabel = no, ToLabel = b.LabelNo, Qty = b.Qty, At = Now } }).ExecuteCommand();
            db.Ado.CommitTran();
            return $"成功：{no}({l.Qty:0.###}) -> {a.LabelNo}({a.Qty:0.###}) + {b.LabelNo}({b.Qty:0.###})";
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    public static string Merge(SqlSugarClient db, params string[] nos)
    {
        var ls = db.Queryable<MatLabel>().In(nos).ToList();
        if (ls.Count != nos.Length || ls.Any(x => x.Status != "Active")) return "拒绝：有标签不存在或已失效";
        if (ls.Select(x => (x.MaterialCode, x.LotNo, x.DateCode, x.LocationCode)).Distinct().Count() != 1)
            return "拒绝：物料、批次、日期码、库位必须完全相同才能合并";
        db.Ado.BeginTran();
        try
        {
            foreach (var x in ls)
                if (!Claim(db, x.LabelNo, "Void")) { db.Ado.RollbackTran(); return "拒绝：标签刚被别人处理过"; }
            var c = Child(ls[0], ls.Sum(x => x.Qty), NewNo(db));
            db.Insertable(c).ExecuteCommand();
            db.Insertable(ls.Select(x => new LabelLink { Kind = "Merge", FromLabel = x.LabelNo, ToLabel = c.LabelNo, Qty = x.Qty, At = Now }).ToList()).ExecuteCommand();
            db.Ado.CommitTran();
            return $"成功：{string.Join(" + ", ls.Select(x => $"{x.LabelNo}({x.Qty:0.###})"))} -> {c.LabelNo}({c.Qty:0.###})";
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    public static string Reprint(SqlSugarClient db, string no)
    {
        var l = db.Queryable<MatLabel>().InSingle(no);
        if (l == null || l.Status != "Active") return "拒绝：标签不存在或已失效";
        db.Ado.BeginTran();
        try
        {
            if (!Claim(db, no, "Void")) { db.Ado.RollbackTran(); return "拒绝：标签刚被别人处理过"; }
            var c = Child(l, l.Qty, NewNo(db));
            db.Insertable(c).ExecuteCommand();
            db.Insertable(new LabelLink { Kind = "Reprint", FromLabel = no, ToLabel = c.LabelNo, Qty = c.Qty, At = Now }).ExecuteCommand();
            db.Ado.CommitTran();
            return $"成功：{no} 作废，补打 {c.LabelNo}({c.Qty:0.###})";
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    // 整盘消耗：标签 Active -> Consumed，同时库存减少并记一条 Issue 流水，三件事在一个事务里
    public static string Consume(SqlSugarClient db, string no, string woNo)
    {
        var l = db.Queryable<MatLabel>().InSingle(no);
        if (l == null || l.Status != "Active") return "拒绝：标签不存在或已失效";
        db.Ado.BeginTran();
        try
        {
            if (!Claim(db, no, "Consumed")) { db.Ado.RollbackTran(); return "拒绝：标签刚被别人处理过"; }
            var ok = db.Updateable<Inventory>().SetColumns(i => i.Qty == i.Qty - l.Qty)
                .Where(i => i.MaterialCode == l.MaterialCode && i.LotNo == l.LotNo && i.LocationCode == l.LocationCode
                         && i.Status == "Available" && i.Qty >= l.Qty).ExecuteCommand();
            if (ok != 1) { db.Ado.RollbackTran(); return "拒绝：库存不足"; }
            db.Insertable(new InvTxn { TxnType = "Issue", MaterialCode = l.MaterialCode, LotNo = l.LotNo, FromLoc = l.LocationCode,
                Qty = l.Qty, DocNo = woNo, CreatedAt = Now }).ExecuteCommand();
            db.Ado.CommitTran();
            return $"成功：{no}({l.Qty:0.###}) 消耗给 {woNo}";
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    class Row { public string MaterialCode { get; set; } public string LotNo { get; set; } public decimal InvQty { get; set; } public decimal LabelQty { get; set; } }

    public static void Check(SqlSugarClient db, string title)
    {
        Console.WriteLine($"[{title}] 库存 vs 有效标签合计：");
        var rows = db.Ado.SqlQuery<Row>(@"
SELECT i.MaterialCode, i.LotNo, i.Qty AS InvQty,
       ISNULL((SELECT SUM(l.Qty) FROM MatLabel l WHERE l.Status = 'Active' AND l.MaterialCode = i.MaterialCode
                AND l.LotNo = i.LotNo AND l.LocationCode = i.LocationCode), 0) AS LabelQty
FROM Inventory i WHERE i.Status = 'Available' ORDER BY i.LotNo");
        foreach (var r in rows)
            Console.WriteLine($"  {r.MaterialCode} {r.LotNo}: 库存 {r.InvQty:0.###}，标签 {r.LabelQty:0.###} -> {(r.InvQty == r.LabelQty ? "一致" : "不一致!")}");
    }

    class Anc { public string FromLabel { get; set; } public string ToLabel { get; set; } public string Kind { get; set; } public decimal Qty { get; set; } public int Lvl { get; set; } }

    // 沿血缘往上追到源头（递归 CTE）
    public static void Lineage(SqlSugarClient db, string no)
    {
        Console.WriteLine($"{no} 的来源：");
        var rows = db.Ado.SqlQuery<Anc>(@"
WITH up AS (
    SELECT FromLabel, ToLabel, Kind, Qty, 1 AS Lvl FROM LabelLink WHERE ToLabel = @no
    UNION ALL
    SELECT k.FromLabel, k.ToLabel, k.Kind, k.Qty, up.Lvl + 1 FROM LabelLink k JOIN up ON k.ToLabel = up.FromLabel)
SELECT * FROM up ORDER BY Lvl, FromLabel", new { no });
        foreach (var r in rows) Console.WriteLine($"  {new string(' ', (r.Lvl - 1) * 2)}{r.Kind}: {r.FromLabel} -> {r.ToLabel} ({r.Qty:0.###})");
    }

    public static void Run(SqlSugarClient db)
    {
        var first = db.Queryable<MatLabel>().InSingle("LB26102000001");
        Console.WriteLine("二维码内容：" + Encode(first));
        var back = Decode(Encode(first));
        Console.WriteLine($"解析回来：物料 {back.MaterialCode}，批次 {back.LotNo}，数量 {back.Qty:0.###}，日期码 {back.DateCode}");
        Check(db, "初始");

        Console.WriteLine("1. 拆分 LB26102000001 拆出 500 -> " + Split(db, "LB26102000001", 500));
        Console.WriteLine("2. 合并 LB26102600001 + LB26102000002 -> " + Merge(db, "LB26102600001", "LB26102000002"));
        Check(db, "拆分合并后");
        Console.WriteLine("3. 跨批次合并 -> " + Merge(db, "LB26102600003", "LB26102000003"));
        Console.WriteLine("4. 拆出 600（标签只有 500）-> " + Split(db, "LB26102600002", 600));
        Console.WriteLine("5. 再拆已作废的 LB26102000001 -> " + Split(db, "LB26102000001", 100));
        Console.WriteLine("6. 补打 LB26102600002 -> " + Reprint(db, "LB26102600002"));

        var res = new string[2];
        Parallel.For(0, 2, i => res[i] = Split(Db.Create(), "LB26102600004", 100));
        Console.WriteLine($"7. 两人同时拆分 LB26102600004 -> 成功 {res.Count(r => r.StartsWith("成功"))} 个，拒绝 {res.Count(r => r.StartsWith("拒绝"))} 个");

        Console.WriteLine("8. 消耗拆分后剩下的 400 标签 -> " + Consume(db, "LB26102600005", "WO-DEMO-01"));
        Console.WriteLine("9. 再消耗一次 -> " + Consume(db, "LB26102600005", "WO-DEMO-01"));
        Check(db, "消耗后");
        Lineage(db, "LB26102600005");
    }
}

第 3 步，读懂输出 ​

  • 开头：先把标签编码成二维码内容，再解析回来，字段完全对得上；
  • 第 1、2 步：拆分和合并后，两个批次的库存与有效标签合计始终一致；
  • 第 3 步：L2610A 和 L2610B 是不同批次，合并被拒绝；
  • 第 4 步：标签只有 500，想拆 600，被拒绝；

  • 第 7 步：两个独立的数据库连接同时拆分同一张标签，总是只有一个成功，因为"抢占"这一步的 UPDATE 只会让一个返回 1；

  • 血缘：LB26102600005 这张 400 的标签往上追：拆分自 ...004，...004 是补打自 ...002，...002 又是拆分自最初的来料标签 LB26102000001。三层链条一目了然。

第 4 步，动手改 ​

  • 把 Merge 里"必须完全相同"的那个 if（Distinct().Count() != 1）改成 if (false)，重新执行 label.sql 再运行：跨批次合并会"成功"，最后的守恒检查变成 L2610A: 库存 1900，标签 0 -> 不一致! 和 L2610B: 库存 300，标签 2200 -> 不一致!（我实际运行的结果），因为合并后的标签只能写一个批次，另一个批次的追溯就断了；
  • 把 Claim 里 WHERE 的 x.Status == "Active" 去掉：单线程下第 5、9 步仍会被前面 Status != "Active" 的读检查挡住，所以现象不变；但那只是"先查后改"，并发时检查和修改之间有空档，就没人守门了。我没能稳定复现出两个都成功，只作思考：为什么必须把条件写进 UPDATE？
  • 想一想：如果要允许"同一物料、不同批次的零散尾料合并成一包"（比如螺丝），标签上批次怎么办？（答案见练习题。）

常见坑与排查 ​

现象 / 坑原因与办法
修改标签数量而不换标签违反铁律。数量变化必须作废重印并记血缘
补打后旧标签没作废，同一盘出现两张"有效"标签补打必须在同一事务里作废旧的；数量守恒检查会发现多出的数量
标签号用本地时间 + 随机数会重复。用数据库序列
条码里放了物料号，物料号改了标签作废条码尽量只放标签号，其余内容查库
合并时批次/日期码不同禁止，否则追溯断链
热敏纸标签褪色、扫不出选合适的标签材质和碳带；仓库久存的标签用热转印
供应商标签和内部标签贴在同一位置互相遮盖约定固定贴位，供应商标签不要被盖住（追溯时还要看）
二维码打印太小、密度太高按扫码枪能力选择尺寸；打印后抽扫验证
数量有小数数量列用 decimal，不要用 float；单位在物料主数据里统一
手工改库存表而没有标签动作守恒校验会发现。所有库存变化必须经过标签动作或库存事务

练习题与答案 ​

  1. 为什么电子元件一般"一盘一码"，而不是"一物一码"？ 答：一盘有成千上万个元件，逐个编码没有意义也做不到；以盘为单位就足够支持"装在哪个站位、用了多少、剩多少"的管理和批次追溯。
  2. 一张 500 的标签要拆出 120。拆完后有效标签是哪几张，数量各是多少？ 答：旧 500 作废；新标签两张：剩余 380 和拆出 120。合计仍为 500。
  3. 为什么不能直接把 500 的标签数量改成 380，再新建一张 120？ 答：纸上印的是 500，改系统不会改变纸；之后任何离线读取或人工核对都会冲突。数量变化必须作废旧标签、印新标签。
  4. 两个操作员同时拆分同一张标签，怎样保证只有一个成功？ 答：把"状态必须是 Active"写进 UPDATE 的 WHERE，用受影响行数判断是否"抢到"，只有返回 1 的才继续创建新标签。
  5. 同一物料不同批次的零散尾料能合并成一包吗？ 答：对要求批次追溯的元件不能。若业务上允许（如螺丝），合并后要新建一个"混批"的批次号，并通过 LabelLink 保留它来自哪些原批次，且需要业务和质量认可。
  6. 守恒不变式是什么？不一致说明什么？ 答：同一物料、批次、库位下，有效标签数量之和等于库存数量。不一致说明有库存变化没经过标签动作、或标签动作没写完整，要从流水和标签血缘两头查。

小结 ​

  • 内部标签是仓库的"身份证"，要唯一、可扫、字段统一；供应商标签格式不一，仍要换成内部标签。
  • 数据标识符（Q、1T、1P、10D 等）是电子行业标签的通用写法。
  • 电子元件常用"一盘一码"，产品 SN 用"一物一码"，低值件用"一批一码"。
  • 标签数量不能原地修改：拆分、合并、补打都是"作废旧的、印新的、记血缘"。
  • 守恒不变式（有效标签合计 = 库存）是日常自检的好工具；用 UPDATE 的 WHERE 抢占保证并发安全。
