MES与ERP及设备的接口设计

AI 生成 · 待核对制造业务MES接口集成幂等自研专题更新于 2026-10-21

⚠ 待核对：接口清单、谁是主数据源、各接口方式的取舍，是通用做法加我的设计建议，你们公司的 ERP 是什么产品、MES 与 ERP/WMS/QMS 现在怎么对接（中间表？Web 服务？文件？）、设备通过什么协议联网、InterfaceLog 类似的表有没有、有什么字段，请对照你们的系统，不一致的地方告诉我。HTTP 方法的幂等性、MQTT 的 QoS、SECS/GEM 的基本情况已对照 RFC 9110 和维基百科；OPC UA、WebService/SOAP、消息队列产品（如 RabbitMQ）我没有在本机运行，只讲概念，不给代码；出站队列用一个"假 ERP"代替（不连任何真实 ERP 或设备）。其余代码和输出是我在本机 SQL Server LocalDB 上实际运行得到的。

本篇是 MES 系列第 20 篇（最后一篇），定义一个新实体：InterfaceLog（接口收发日志）。读完你应该能：列出 MES 与 ERP、设备、WMS/QMS/LIMS 之间各有哪些接口；在 REST、WebService、消息队列、中间表、文件、OPC UA、MQTT、SECS/GEM 之间做出选择；解释幂等、重试、补偿、对账、失败队列、消息顺序、版本兼容这些词；说清"谁是主数据源"；设计"ERP 挂了产线也不能停"的降级方案；并用代码做出入站幂等去重和出站队列（重试、到上限转人工）。

一句话定义 ​

MES 的接口是 MES 与别的系统（ERP、设备、WMS、QMS、LIMS……）交换数据的约定和实现；接口设计的核心不是"怎么把数据传过去"，而是"传丢了、传重了、传晚了、对方挂了，怎么办"。

先修知识 ​

  • MES 和 电子制造信息系统全景图：知道 MES 在系统群里的位置，周围有哪些系统。
  • ISA-95：MES 在 Level 3，ERP 在 Level 4，设备在 Level 0–2；接口主要发生在层与层之间。
  • 工单管理：工单的状态机；本篇的入站接口会在 MES 里建工单。
  • 过站与工序流转、设备管理与设备状态：设备自动过站、状态上报最终落到这两篇的表里。
  • 会基本的 JSON 和 HTTP 的概念。

它解决什么问题 ​

一个没有认真设计接口的车间，会这样出事：

  • 工单重复：ERP 网络抖了一下，把同一张工单下发了两遍，MES 建了两张一样的工单，同一批料被领了两次，产量统计翻倍。
  • 报工丢了：MES 向 ERP 回传完工数，那一刻 ERP 在维护，请求失败了，没人知道，月底财务发现 ERP 里少了几千块板的入库，对不上账。
  • ERP 一挂，产线停了：MES 每次过站都实时去问 ERP "这张工单还能做吗"，ERP 慢了，扫码一直转圈，工人干等。
  • 谁说了算：物料描述在 ERP 里改了，MES 里还是旧的；有人在 MES 里也改了一份，两边对不上，没人知道哪个是对的。
  • 设备重复上报：贴片机断网重连后，把最近 100 条产量记录又发了一遍，MES 里产量多了 100。
  • 接口出问题，没人能查：对方说"我发了"，我方说"没收到"，没有日志，只能扯皮。

接口设计要解决的就是这些：不丢、不重、不乱、可对账、可补救、对方挂了自己不倒。

接口方式怎么选 ​

选型的详细对比见 接口技术选型，这里给出面向 MES 的速查表：

方式一句话优点缺点MES 里的典型用途
REST/HTTP（JSON）对方提供 URL，用 HTTP 请求读写通用、易调试、跨语言同步调用，对方挂了你就卡；要自己做重试和幂等与 ERP、WMS、QMS 的新接口首选；见 REST-API设计、WebAPI开发
WebService（SOAP/XML）老式的、有 WSDL 契约的 Web 服务契约明确、老 ERP 常见报文冗长，调试麻烦对接老的 ERP（如旧版 SAP、Oracle EBS 的某些接口）
消息队列（RabbitMQ、Kafka 等）发送方把消息放入队列，接收方自己取解耦、削峰、对方挂了消息不丢多一套基础设施要运维；要处理重复和顺序事件量大、要求解耦的场景；本机没有运行验证
中间表（共享数据库表）双方约定一两张表，一方写，一方读简单、两边都会 SQL、天然持久化耦合在数据库结构上；轮询有延迟；权限和性能要管；难以演进对接老系统，国内工厂里非常常见
文件（CSV/XML 放到共享目录或 FTP）定时导出/导入文件最低门槛，什么系统都能做实时性差；半个文件、重复文件、编码问题批量主数据、对账文件
OPC UA工业标准的设备数据交换协议，见 OPC-UA面向设备、有数据模型、跨厂商设备要支持；学习曲线与支持 OPC UA 的设备、SCADA 对接
MQTT轻量的发布/订阅协议，通过 broker 转发，见 MQTT轻、适合设备数据和不稳定网络要 broker；业务语义要自己约定设备和传感器上报；见下
SECS/GEM半导体行业设备通信标准（SECS-I、SECS-II、HSMS、GEM）设备商支持广，状态机、事件、Recipe 管理标准化学习曲线陡；在 SMT 里并不普遍见 SECS-GEM；SMT 设备常有各自的接口，也有走 IPC-CFX、IPC-Hermes 的

几个补充（来自维基百科）：

  • MQTT 有 3 级服务质量（QoS）：0 最多一次（发出不管）、1 至少一次（会重复）、2 恰好一次（握手更多）。"至少一次"意味着接收方必须能处理重复——也就是后面说的幂等。 broker 还可以为每个主题保留最后一条消息（retained），新订阅者一上线就能拿到当前值，这对设备"当前状态"很合适。
  • SECS/GEM：SECS-II（SEMI E5）是消息标准，GEM（SEMI E30）定义了消息、状态机和场景，HSMS（SEMI E37）是跑在 TCP/IP 上的传输，SECS-I（SEMI E4）是跑在 RS-232 上的老传输。据维基百科，许多表面贴装设备（贴片、锡膏、回流炉、检测）支持 GEM，但它在这个行业并不是首选。具体你们的设备走什么协议，要看设备型号和厂商文档（见 SMT设备接口）。

选型的经验： 新系统之间优先 REST + 本篇后面的幂等/重试设计；对接老 ERP 往往只能用中间表或 WebService；设备端以设备支持的协议为准，由 EAP 这类中间层统一翻译成 MES 的内部格式；不要为了"先进"而选，要为"出问题时能查、能补"而选。

七个必须想清楚的问题 ​

1. 幂等：同一个消息处理一次和处理十次，结果一样 ​

幂等（idempotent）的意思是：重复执行同一个操作，效果和执行一次相同。据 RFC 9110，HTTP 的 PUT、DELETE 和只读方法是幂等的，而 POST 不是；RFC 还说，客户端不应该自动重试非幂等的请求，除非能确认不会造成重复效果。

为什么必须幂等？因为网络上"不知道对方有没有收到"是常态：请求发出去，超时了——可能对方根本没收到，也可能对方收到并处理了，只是回复丢了。发送方无法区分，只能重试；所以接收方必须能承受"同一个消息来两遍"。

实现幂等的标准做法：

  1. 每条业务消息有一个业务键（如 ERP 工单号、报工批次号），同一个业务事件永远是同一个键；
  2. 接收方先在日志表里登记这个键，并且用唯一索引保证同一个键只能登记一次；
  3. 登记失败（键已存在）= 重复消息，不重复处理，直接告诉对方"已经收到并处理过"（不是报错）。

"先查有没有，没有再插入"不是可靠的做法：两个线程同时查，都发现没有，都去插入（竞态）。要靠数据库的唯一索引。

2. 重试：失败了怎么再试 ​

要点做法
区分能重试和不能重试的失败超时、网络错误、对方 5xx：可重试；对方明确拒绝（工单不存在、数据非法）：不可重试，重试一万次结果一样
重试要有间隔，且越来越长退避（backoff）：1 分钟、2 分钟、4 分钟……，避免对方刚恢复就被重试风暴打垮
重试有上限达到上限（实验里是 3 次）就不再自动重试，转人工处理
重试要记录次数和原因RetryCount、LastError
只有幂等的操作才能放心重试对方接口不幂等时，重试要带"同一个业务键"，让对方去重

3. 补偿：做错了或者没做成，怎么撤回 ​

当一个跨系统的操作做了一半，没法"整体回滚"（因为分属不同系统，没有统一事务），就要用补偿：做一个相反的操作来抵消。比如 MES 报了 100 块完工，ERP 入库成功，但后来发现报多了，不是去改 ERP 的旧单，而是发一张"冲销/调整"单据。补偿是业务操作，不是技术回滚，要有对应的业务单据和审批。

4. 对账：定期核对两边是否一致 ​

再好的重试也防不住所有问题，所以要有对账：定期（每天/每班）比较两边的汇总，找出差异。比如：MES 报了 N 条完工回传，ERP 确认了 M 条，差的那几条就是要追查的。本篇实验里的"出站日志按状态统计"就是最简单的对账。更完整的做法是双方各出一份清单按业务键比对：MES 有 ERP 没有（漏传）、ERP 有 MES 没有（异常）、两边数量不同（差异）。

5. 失败队列（死信）和人工处理 ​

自动重试到上限还不行的消息，不能默默丢掉，应该进入"失败"状态，并有：

  • 看得见：看板或报表上显示"有 N 条接口消息失败待处理"；
  • 查得清：保存原始报文和失败原因；
  • 能重发：处理好原因（比如 ERP 恢复、主数据补齐）后，运维可以把它重置为待发，再次进入队列；
  • 有约束：只有失败状态的消息可以重置，已成功的不能重发（否则会重复）。

这类"最终进不去"的消息队列常被叫作死信队列（dead-letter queue）。

6. 消息顺序 ​

同一个业务对象的多条消息，顺序可能很重要。比如 ERP 先发"工单计划数改成 120"，再发"工单关闭"；如果到达顺序反了，MES 先关闭、再改数量，结果就不对。办法：

  • 消息里带版本号或序号，接收方只接受比当前新的，旧的丢弃（并记日志）；
  • 同一个业务键的消息串行处理（不要两个线程同时处理同一个工单的消息）；
  • 全局严格有序代价很大，多数场景只要求"同一个业务键内有序"。

7. 版本兼容 ​

接口一旦上线，两边都会改版本：ERP 加了个字段，MES 还是老版本。要向后兼容：

  • 新增字段不破坏旧接收方（接收方忽略不认识的字段）；
  • 报文里带接口版本号，不兼容的改动用新版本，旧版本保留一段时间；
  • 不要随意改字段含义或删字段；
  • 接口文档要有版本和变更记录，上线前双方联调。

数据一致性：谁是主数据源 ​

同一份数据在两个系统里都有，就一定会不一致。解决办法是为每类数据指定唯一的源头（Single Source of Truth）：源头可写，其他系统只读（或只缓存），要改只能去源头改。

数据通常的主数据源MES 的角色
物料主档（料号、描述）ERP（或 PLM，见 主数据与物料编码）只读副本，同步而来
BOMPLM → ERP；MES 取生效版本只读，并在工单下发时锁定版本
工艺路线PLM 或 MES看公司分工：谁维护谁是源
工单（计划数、交期）ERP（计划下达）接收；MES 只更新执行进度（完成数、状态）
设备台账与状态MES（或设备资产系统 EAM）源头
过站、追溯、产量等生产记录MES源头，ERP 只拿汇总
库存账（账面）ERP / WMS不自己维护账，只传消耗

要点：

  • 工单是"分段拥有"的：计划数、交期归 ERP，完成数、执行状态归 MES，两边各改各的字段，不要互相覆盖；
  • 双向同步的数据一定要定义"冲突时听谁的"；
  • 每个同步接口都应当有"全量校对"能力（定期对比两边，修复漂移）。

超时与降级：ERP 挂了，产线不能停 ​

产线生产不能因为 ERP 维护或网络故障而停下来。 这是 MES 接口设计最重要的原则。几条具体做法：

场景降级做法
ERP 工单还没下发工单提前下发，MES 本地已有工单就能生产，不要每次扫码实时向 ERP 请求
过站时要查物料/BOM/路线读 MES 本地的主数据副本，不实时调 ERP
完工要回传 ERP先写本地出站队列（InterfaceLog，Direction = Out），业务事务照常提交，由后台任务慢慢发送；ERP 恢复后自动补发（这叫 Outbox 模式：消息和业务数据在同一个事务里写入，保证"业务成功则消息一定在队列里"）
同步调用对方设超时（几秒），超时就失败，不要无限等；连续失败时熔断（暂时不再调用，过一会儿再试），避免拖垮自己
设备断网设备端本地缓存，恢复后补传；MES 接收补传的数据要用设备报的发生时间，并且按业务键去重（见 设备管理与设备状态 的"事件时间 vs 入库时间"）
必须同步确认的防错（如物料校验）这类不能"降级放行"，否则等于没有防错；要保证 MES 本地有足够的数据能独立判断，或者明确"断线时停线"的规则并由管理者批准

一个重要的区分：允许最终一致的（报工、消耗、库存）可以排队补传；需要即时判断的（防错）必须依靠本地数据。 哪些接口属于哪一类，要在设计阶段逐个定下来。

业务视角 ​

谁在什么环节做什么：

角色动作
生产计划员在 ERP 下达工单，期待 MES 里立刻能看到；关心工单有没有"丢"或"重复"
产线只想正常扫码生产，不关心接口；接口故障不应影响他们
仓库发料与 WMS、ERP 库存对账
财务/成本会计依赖 MES 回传的完工和物料消耗做成本；关心数量能不能和 ERP 对上
IT/接口工程师监控接口失败、重试、处理失败队列；日常对账
设备工程师设备联网、程序下载、状态上报的配置与排障

流程（工单从 ERP 到回传）：

  1. ERP 计划员下达工单 → ERP 发送"工单下发"消息 → MES 接收、幂等去重、校验（物料是否在主数据、数量是否合法）→ 建工单，状态 Created；
  2. MES 里生产、过站、报工；
  3. 报工产生"完工回传"消息，写入出站队列 → 后台任务发给 ERP → ERP 确认 → 标记 Success；
  4. 失败的消息自动重试；超过上限的进入失败队列，IT 处理；
  5. 每天对账：MES 的回传清单 vs ERP 的入库清单。

KPI： 接口成功率（首次成功率、最终成功率）；失败队列积压数及最老消息的等待时长；平均处理延迟；人工处理量；对账差异数。

技术视角 ​

表设计：InterfaceLog ​

一张表同时服务入站（别人发给 MES，要做幂等去重）和出站（MES 发给别人，是待发队列）：

字段含义
Id自增主键
DirectionIn 入站 / Out 出站
Target对方系统（ERP、WMS、EAP……）
MsgType报文类型（WorkOrderRelease、ProductionReport……）
BusinessKey业务键，幂等的依据
Payload报文原文（nvarchar(max)），排错和重发时需要
StatusPending 待处理 / Success 成功 / Failed 失败转人工 / Retrying 已失败过、等待重试
RetryCount已经失败了几次
LastError最近一次的失败原因（我自己加的一列，排错必备）
CreatedAt创建时间

T-SQL 建表如下。我在本机的临时库里运行过：同一个入站业务键插入第二次，被唯一索引拒绝（错误号 2601）；出站的同一个业务键可以有多行（重发）；Status 写成 Done 被 CHECK 拒绝（错误号 547）。

sql
CREATE TABLE InterfaceLog (
    Id          int IDENTITY(1,1) NOT NULL CONSTRAINT PK_InterfaceLog PRIMARY KEY,
    Direction   nvarchar(10)  NOT NULL,
    Target      nvarchar(20)  NOT NULL,
    MsgType     nvarchar(40)  NOT NULL,
    BusinessKey nvarchar(60)  NOT NULL,
    Payload     nvarchar(max) NOT NULL,
    Status      nvarchar(20)  NOT NULL CONSTRAINT DF_IfLog_Status DEFAULT N'Pending',
    RetryCount  int           NOT NULL CONSTRAINT DF_IfLog_Retry DEFAULT 0,
    LastError   nvarchar(200) NULL,
    CreatedAt   datetime      NOT NULL CONSTRAINT DF_IfLog_Created DEFAULT GETDATE(),
    CONSTRAINT CK_IfLog_Direction CHECK (Direction IN (N'In', N'Out')),
    CONSTRAINT CK_IfLog_Status CHECK (Status IN (N'Pending', N'Success', N'Failed', N'Retrying'))
);
-- 入站幂等：同一个 (对方系统, 报文类型, 业务键) 只能有一行
CREATE UNIQUE INDEX UX_InterfaceLog_In ON InterfaceLog(Target, MsgType, BusinessKey) WHERE Direction = N'In';
-- 出站队列：按状态找待发的
CREATE INDEX IX_InterfaceLog_Queue ON InterfaceLog(Direction, Status, Id);

几个设计点：

  1. 唯一索引只对入站生效（筛选索引，见 MES核心数据模型 和微软文档）：入站要去重；出站同一业务键可能因为"人工重发"产生多行，不能唯一。
  2. Status 是状态机：Pending → Success（一次成功）；Pending → Retrying → … → Success（重试后成功）；… → Failed（到上限或业务拒绝）；Failed → Pending（人工重置，计数清零）。状态变更用条件 UPDATE（WHERE Status IN ('Pending','Retrying')），防止两个后台任务重复处理同一条。
  3. Payload 存原文：排错时不用问对方"你到底发了什么"；但要注意脱敏（含个人信息或商业敏感的字段）和保留期（几个月到一年，之后归档或删除，见 MES核心数据模型 的归档）。
  4. 业务数据和消息要同一个事务：入站时"登记日志 + 建工单 + 更新日志状态"；出站时"业务操作 + 写出站队列"。
  5. 索引：队列扫描 (Direction, Status, Id)；按业务键查对账用 BusinessKey（需要的话另建索引）。

实现要点 ​

要点做法
入站先登记再处理先 INSERT 日志（靠唯一索引去重），再处理业务，最后更新状态。重复的消息在第一步就被拦下
重复消息怎么回复回"已处理"（成功），不要回错误，否则对方会无休止地重试
失败也要登记校验失败（物料不在主数据）也写 Failed 并记原因，方便人工处理；不要直接丢弃
出站先入队，后发送业务事务里只写队列，发送交给后台任务（见 后台服务与Windows服务）
后台任务可以有多个实例取消息时用条件 UPDATE（或把状态先置为"发送中"）占位，避免两个实例同时发同一条
退避时间失败后计算"下次可重试时间"，没到时间的不取。实验里只是打印了建议的间隔，没有真的等待；真实系统需要一个 NextRetryAt 列
超时设置对外调用设置超时（几秒到几十秒）；连续失败熔断
监控失败队列条数、最老的待处理消息等待时长，进看板和告警（见 生产看板与实时报表）
大报文不要把几 MB 的报文塞进 Payload，存文件、表里存路径和摘要
InitTables 的坑实验里发现：SqlSugar 的 CodeFirst.InitTables 再次运行时，如果表上有"依赖某一列的筛选索引"，它会尝试改列而报错，所以实验里先删索引、建表、再建索引。这是迷你实验的写法，真实系统请用有版本的迁移脚本

逐步例子：一张工单的接口之旅 ​

入站（ERP → MES）： ERP 向 MES 下发工单 WO-IF-1001（产品 PCBA-A100，计划 100）。

步骤发生了什么结果
1第一次到达：InterfaceLog 插入一行（In、ERP、WorkOrderRelease、WO-IF-1001、Pending）；校验通过；MES 建工单（状态 Created，计划 100）；日志改 Success处理成功
2ERP 因为没收到回复，又发了一遍同一条日志插入被唯一索引拒绝 → 判定为重复 → 回复"已处理"；工单没有重复创建
3ERP 发来 WO-IF-1002，产品 PCBA-X999（MES 主数据里没有这个料）日志登记后校验失败：日志 Failed，LastError = 物料不在主数据；转人工（先去同步物料主数据）
4ERP 发来 WO-IF-1003，数量 0日志 Failed，原因"数量 0 不合法"
5两个线程同时投递 WO-IF-1004唯一索引保证只有一个成功，另一个收到"重复"

出站（MES → ERP）： MES 要回传 5 条报工 RPT-IF-001 到 005，ERP 对它们的反应不同（实验里用一个按脚本回答的"假 ERP"模拟）：

业务键ERP 的反应状态流转
RPT-IF-001正常Pending → Success
RPT-IF-002前两次超时，第三次成功Pending → Retrying(1) → Retrying(2) → Success
RPT-IF-003一直超时Pending → Retrying(1) → Retrying(2) → Failed（连续 3 次，到上限，转人工）
RPT-IF-004明确拒绝（工单不存在）Pending → Failed（业务拒绝，不重试）
RPT-IF-005正常Pending → Success

之后 ERP 的故障修好了，运维把 RPT-IF-003 重置为 Pending，下一轮发送成功。RPT-IF-004 仍是失败：它不是"ERP 暂时有问题"，而是"数据本身有问题"（工单在 ERP 里不存在），需要人去查原因，而不是重发。

动手实验：入站幂等、出站队列、重试到上限转人工 ​

前提：已经按 MES 建好项目，Seed.Basics 已有物料 PCBA-A100，工单表 WorkOrder 可用（见 工单管理）。本篇的实验不连任何真实的 ERP 或设备，ERP 用一个按脚本回答的假函数代替。练习库是 MiniMES_Lab。

第 1 步：新建 InterfaceLog.cs，只放本篇定义的实体：

csharp
using SqlSugar;

namespace MiniMes;

// 接口收发日志：每条收发的消息一行。Status、RetryCount、LastError 随处理进度更新。入站消息的幂等、出站消息的待发队列都靠它
[SugarTable("InterfaceLog")]
[SugarIndex("IX_InterfaceLog_Queue", nameof(InterfaceLog.Direction), OrderByType.Asc, nameof(InterfaceLog.Status), OrderByType.Asc)]
public class InterfaceLog
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)]
    public int Id { get; set; }
    [SugarColumn(ColumnDataType = "nvarchar(10)")]
    public string Direction { get; set; }      // In 别人发给 MES / Out MES 发给别人
    [SugarColumn(ColumnDataType = "nvarchar(20)")]
    public string Target { get; set; }         // 对方系统：ERP / WMS / EAP ...
    [SugarColumn(ColumnDataType = "nvarchar(40)")]
    public string MsgType { get; set; }        // WorkOrderRelease / ProductionReport ...
    [SugarColumn(ColumnDataType = "nvarchar(60)")]
    public string BusinessKey { get; set; }    // 业务键，幂等的依据：同一个业务事件永远是同一个键
    [SugarColumn(ColumnDataType = "nvarchar(max)")]
    public string Payload { get; set; }        // 报文原文（JSON）
    [SugarColumn(ColumnDataType = "nvarchar(20)")]
    public string Status { get; set; }         // Pending / Success / Failed / Retrying
    public int RetryCount { get; set; }        // 已经失败了几次
    [SugarColumn(ColumnDataType = "nvarchar(200)", IsNullable = true)]
    public string LastError { get; set; }
    public DateTime CreatedAt { get; set; }
}

第 2 步：新建 LabInterface.cs：

csharp
using System.Text.Json;
using SqlSugar;

namespace MiniMes;

// 接口实验：入站幂等去重 + 出站队列的状态流转（重试、到上限转人工、人工重置）。ERP 用一个按脚本回答的假对象代替
public static class LabInterface
{
    const int MaxRetry = 3;
    static bool erpFixed;      // 模拟"ERP 故障已经修好"

    // ---------- 入站：ERP 下发工单 ----------
    static string ReceiveWorkOrder(SqlSugarClient db, string json)
    {
        var doc = JsonDocument.Parse(json).RootElement;
        string key = doc.GetProperty("woNo").GetString(), product = doc.GetProperty("product").GetString();
        int qty = doc.GetProperty("qty").GetInt32();
        var log = new InterfaceLog { Direction = "In", Target = "ERP", MsgType = "WorkOrderRelease", BusinessKey = key, Payload = json, Status = "Pending", CreatedAt = DateTime.Now };
        try { log.Id = db.Insertable(log).ExecuteReturnIdentity(); }
        catch (Exception ex) when (ex.ToString().Contains("duplicate key", StringComparison.OrdinalIgnoreCase))
        {
            // 唯一索引拦下了重复投递：不是错误，告诉对方"收到了"就行
            var old = db.Queryable<InterfaceLog>().First(l => l.Direction == "In" && l.Target == "ERP" && l.MsgType == "WorkOrderRelease" && l.BusinessKey == key);
            return $"重复消息，已有记录状态 {old.Status}，不再处理";
        }
        string err = qty <= 0 ? $"数量 {qty} 不合法"
            : !db.Queryable<Material>().Any(m => m.MaterialCode == product) ? $"物料 {product} 不在主数据" : null;
        if (err != null)
        {
            db.Updateable<InterfaceLog>().SetColumns(l => new InterfaceLog { Status = "Failed", LastError = err }).Where(l => l.Id == log.Id).ExecuteCommand();
            return $"处理失败（{err}），转人工";
        }
        db.Ado.BeginTran();
        try
        {
            db.Insertable(new WorkOrder { WoNo = key, ProductCode = product, PlanQty = qty, Status = "Created", CreatedAt = DateTime.Now }).ExecuteCommand();
            db.Updateable<InterfaceLog>().SetColumns(l => new InterfaceLog { Status = "Success" }).Where(l => l.Id == log.Id && l.Status == "Pending").ExecuteCommand();
            db.Ado.CommitTran();
            return $"处理成功，建工单（计划 {qty}）";
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    // ---------- 出站：MES 报工给 ERP ----------
    static void Enqueue(SqlSugarClient db, string key, int goodQty) =>
        db.Insertable(new InterfaceLog { Direction = "Out", Target = "ERP", MsgType = "ProductionReport", BusinessKey = key, Payload = $"{{\"woNo\":\"WO-IF-1001\",\"goodQty\":{goodQty}}}", Status = "Pending", CreatedAt = DateTime.Now }).ExecuteCommand();

    // 假 ERP：按业务键和"这是第几次尝试"给出固定的回答
    static (string Outcome, string Msg) FakeErp(string key, int attempt) => key switch
    {
        "RPT-IF-002" when attempt <= 2 => ("Timeout", "超时"),
        "RPT-IF-003" when !erpFixed => ("Timeout", "超时"),
        "RPT-IF-004" => ("Reject", "ERP 回复：工单不存在"),
        _ => ("OK", ""),
    };

    // 发一条：成功 -> Success；超时 -> Retrying，到上限 -> Failed；业务拒绝 -> 直接 Failed（重试也没用）
    static string Dispatch(SqlSugarClient db, InterfaceLog m)
    {
        int attempt = m.RetryCount + 1;
        var (outcome, msg) = FakeErp(m.BusinessKey, attempt);
        string status, text, lastError = outcome == "OK" ? null : msg;
        int retry = m.RetryCount;
        if (outcome == "OK") { status = "Success"; text = "Success"; }
        else if (outcome == "Reject") { status = "Failed"; text = $"Failed（{msg}，不重试）"; }
        else
        {
            retry = attempt;
            if (retry >= MaxRetry) { status = "Failed"; text = $"Failed（连续 {retry} 次{msg}，超过上限，转人工）"; }
            else { status = "Retrying"; text = $"Retrying（第 {retry} 次{msg}，{1 << (retry - 1)} 分钟后重试）"; }
        }
        // 条件 UPDATE：只有它还处在待发状态才改，防止两个 worker 重复处理
        int n = db.Updateable<InterfaceLog>().SetColumns(l => new InterfaceLog { Status = status, RetryCount = retry, LastError = lastError })
            .Where(l => l.Id == m.Id && (l.Status == "Pending" || l.Status == "Retrying")).ExecuteCommand();
        return n == 1 ? text : "已被别的 worker 处理";
    }

    static void Rounds(SqlSugarClient db)
    {
        for (int round = 1; ; round++)
        {
            var todo = db.Queryable<InterfaceLog>().Where(l => l.Direction == "Out" && (l.Status == "Pending" || l.Status == "Retrying")).OrderBy(l => l.Id).ToList();
            if (todo.Count == 0) { Console.WriteLine($"   第 {round} 轮：队列里没有待发消息"); return; }
            Console.WriteLine($"   第 {round} 轮：待发 {todo.Count} 条");
            foreach (var m in todo) Console.WriteLine($"      {m.BusinessKey} -> {Dispatch(db, m)}");
        }
    }

    static void Summary(SqlSugarClient db) =>
        Console.WriteLine("   " + string.Join("，", db.Queryable<InterfaceLog>().Where(l => l.Direction == "Out" && l.BusinessKey.StartsWith("RPT-IF-"))
            .GroupBy(l => l.Status).Select(l => new { l.Status, Cnt = SqlFunc.AggregateCount(l.Id) }).ToList().OrderBy(x => x.Status).Select(x => $"{x.Status} {x.Cnt}")));

    public static void Run(SqlSugarClient db)
    {
        Seed.Basics(db);
        // InitTables 遇到"依赖某一列的筛选索引"会尝试改列而报错，所以实验里先删索引、建表、再建索引（真实系统用迁移脚本，不靠 InitTables）
        db.Ado.ExecuteCommand("IF EXISTS (SELECT 1 FROM sys.indexes WHERE name = 'UX_InterfaceLog_In' AND object_id = OBJECT_ID('InterfaceLog')) DROP INDEX UX_InterfaceLog_In ON InterfaceLog");
        db.CodeFirst.InitTables(typeof(InterfaceLog));
        db.Deleteable<InterfaceLog>().Where(l => l.BusinessKey.StartsWith("WO-IF-") || l.BusinessKey.StartsWith("RPT-IF-")).ExecuteCommand();
        db.Deleteable<WorkOrder>().Where(w => w.WoNo.StartsWith("WO-IF-")).ExecuteCommand();
        db.Ado.ExecuteCommand("CREATE UNIQUE INDEX UX_InterfaceLog_In ON InterfaceLog(Target, MsgType, BusinessKey) WHERE Direction = N'In'");
        erpFixed = false;

        Console.WriteLine("1. 入站幂等：ERP 下发工单");
        string Msg(string wo, string product, int qty) => $"{{\"woNo\":\"{wo}\",\"product\":\"{product}\",\"qty\":{qty},\"ver\":1}}";
        Console.WriteLine($"   WO-IF-1001 首次投递 -> {ReceiveWorkOrder(db, Msg("WO-IF-1001", "PCBA-A100", 100))}");
        Console.WriteLine($"   WO-IF-1001 重复投递 -> {ReceiveWorkOrder(db, Msg("WO-IF-1001", "PCBA-A100", 100))}");
        Console.WriteLine($"   WO-IF-1002 物料不在主数据 -> {ReceiveWorkOrder(db, Msg("WO-IF-1002", "PCBA-X999", 50))}");
        Console.WriteLine($"   WO-IF-1003 数量为 0 -> {ReceiveWorkOrder(db, Msg("WO-IF-1003", "PCBA-A100", 0))}");
        var barrier = new Barrier(2);
        var results = new string[2];
        var threads = Enumerable.Range(0, 2).Select(i => new Thread(() =>
        {
            var d = Db.Create();
            barrier.SignalAndWait();
            results[i] = ReceiveWorkOrder(d, Msg("WO-IF-1004", "PCBA-A100", 80));
        })).ToList();
        threads.ForEach(t => t.Start()); threads.ForEach(t => t.Join());
        Console.WriteLine($"   WO-IF-1004 两个线程同时投递 -> 成功 {results.Count(r => r.StartsWith("处理成功"))} 个、重复 {results.Count(r => r.StartsWith("重复"))} 个");
        var inLogs = db.Queryable<InterfaceLog>().Where(l => l.Direction == "In" && l.BusinessKey.StartsWith("WO-IF-")).ToList();
        Console.WriteLine($"   工单表里 WO-IF- 开头的工单 {db.Queryable<WorkOrder>().Count(w => w.WoNo.StartsWith("WO-IF-"))} 张；入站日志 {inLogs.Count} 行：Success {inLogs.Count(l => l.Status == "Success")}，Failed {inLogs.Count(l => l.Status == "Failed")}");

        Console.WriteLine("2. 出站队列：MES 报工给 ERP（最多重试 3 次）");
        for (int i = 1; i <= 5; i++) Enqueue(db, $"RPT-IF-00{i}", 10 * i);
        Rounds(db);

        Console.WriteLine("3. 对账：出站日志按状态统计");
        Summary(db);
        foreach (var f in db.Queryable<InterfaceLog>().Where(l => l.Direction == "Out" && l.Status == "Failed" && l.BusinessKey.StartsWith("RPT-IF-")).OrderBy(l => l.Id).ToList())
            Console.WriteLine($"   待人工：{f.BusinessKey}，失败 {f.RetryCount} 次，原因 {f.LastError}");

        Console.WriteLine("4. 人工处理：ERP 修好后，把 RPT-IF-003 重置为 Pending 再发一轮");
        erpFixed = true;
        int bad = db.Updateable<InterfaceLog>().SetColumns(l => new InterfaceLog { Status = "Pending", RetryCount = 0, LastError = null }).Where(l => l.BusinessKey == "RPT-IF-001" && l.Status == "Failed").ExecuteCommand();
        int fix = db.Updateable<InterfaceLog>().SetColumns(l => new InterfaceLog { Status = "Pending", RetryCount = 0, LastError = null }).Where(l => l.BusinessKey == "RPT-IF-003" && l.Status == "Failed").ExecuteCommand();
        Console.WriteLine($"   重置已成功的 RPT-IF-001：{bad} 行（只允许重置 Failed）；重置 RPT-IF-003：{fix} 行");
        Rounds(db);
        Summary(db);
    }
}

练习题与答案 ​

  1. 什么是幂等？为什么接口必须考虑幂等？ 答：重复执行同一操作，效果与执行一次相同。因为网络上"超时但不知道对方有没有处理"是常态，发送方只能重试，所以接收方必须能承受重复消息。
  2. 怎样可靠地实现入站消息去重？为什么"先查再插"不可靠？ 答：先在日志表登记业务键，用唯一索引保证同一个业务键只能登记一次，登记失败就是重复。"先查再插"在并发时两个线程同时查到"没有"，都去插入。
  3. 收到重复的消息，应该回复成功还是错误？为什么？ 答：回复"已处理"（成功）。回错误会让对方认为失败而继续重试，造成重试风暴。
  4. 超时和"工单不存在"都是失败，处理方式有什么不同？ 答：超时是暂时性的，可以重试；"工单不存在"是业务拒绝，重试结果不会变，应直接转人工。
  5. 重试为什么要有间隔、上限？ 答：间隔（并逐步拉长）避免对方刚恢复就被打垮；上限避免一条坏消息永远占用队列，到上限转人工。
  6. 出站消息为什么要和业务数据在同一个事务里写入队列表？ 答：保证"业务成功则消息一定在队列里"，不会出现业务提交了但消息丢了，或消息发出但业务回滚。这叫 Outbox 模式。
  7. MES 向 ERP 回传了 100 条，ERP 确认了 97 条，应该怎么做？ 答：对账：按业务键找出 3 条差异。看这 3 条在 InterfaceLog 里是什么状态：是 Failed 待人工、Retrying 还在重试，还是 ERP 那边处理失败。分别重发或修正，并查失败原因。
  8. 工单的"计划数"和"完成数"分别该以哪个系统为准？ 答：计划数、交期以 ERP 为准（计划下达）；完成数、执行状态以 MES 为准（生产执行）。两边各改各的字段，不要互相覆盖。
  9. ERP 维护 2 小时，产线能继续生产吗？需要哪些设计保证？ 答：能。工单提前下发，MES 本地有主数据副本，过站不实时调 ERP；报工等回传先写本地出站队列，业务事务照常提交，ERP 恢复后由后台任务自动补发。
  10. 同一个业务键但内容不同的两条消息（版本 1 和版本 2）乱序到达，怎么保证以新版本为准？ 答：消息带版本号，接收方记录已处理的最大版本，只接受更大的；旧版本到达时记日志并丢弃，不覆盖新的。

小结 ​

  • MES 居中：向上对接 ERP（主数据、工单下发、完工回传、物料消耗），向下对接设备（状态、产量、报警、过站、程序下载），横向对接 WMS/QMS/LIMS。
  • 接口方式按场景选：新系统首选 REST；老 ERP 常用中间表或 WebService；设备按设备支持的协议（OPC UA、MQTT、SECS/GEM、厂商接口）经 EAP 统一；消息队列适合解耦和削峰。
  • 接口设计的核心是可靠性：幂等（业务键加唯一索引）、重试（区分暂时性与业务拒绝，退避加上限）、补偿、对账、失败队列转人工、消息顺序（版本号）、版本兼容。
  • 每类数据指定唯一的主数据源；工单"计划归 ERP，执行归 MES"。
  • 产线不能因 ERP 挂而停：主数据本地缓存，工单提前下发，写操作先入本地出站队列（Outbox，同事务），后台任务补发；需要即时判断的防错依赖本地数据。
  • InterfaceLog 同时承担入站幂等和出站队列：入站靠筛选唯一索引去重，出站靠 Status、RetryCount 流转；所有失败都要看得见、查得清、能重发。
