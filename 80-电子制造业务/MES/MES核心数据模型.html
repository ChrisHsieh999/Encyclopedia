MES核心数据模型

AI 生成 · 待核对制造业务MES数据库设计自研专题更新于 2026-10-21

⚠ 待核对：表名、字段、命名规范、审计字段、分区与归档方案是设计建议，不是你们自研系统的现状；真实系统的表结构、命名习惯、数据量、SQL Server 版本和硬件都可能不同，请对照你们的数据库核实，不一致的地方告诉我，我来修正。"规划中"的表及其建议字段，会随后续词条的写作变化。分区的语法和限制已对照微软文档；表清单、类型对比、查询输出是我在本机 SQL Server LocalDB 上实际运行得到的。

本篇是 MES 系列第 8 篇，一篇总览性的词条：把前面和后面所有词条用到的表放在一张图、一张清单里，再讲命名、审计字段、软删除、分区归档、索引这些"每张表都要想一遍"的事。读完你应该能：画出（或看懂）MES 核心表的关系；判断一张新表该归哪一类、该有什么约束；定出一套团队统一的命名规范；说清大表怎么分区和归档；知道从迷你模型走到真实系统还缺什么。本篇没有新的实验类，但有一组在 LocalDB 里就能跑的 T-SQL，用来检查"库里实际有什么表"。

一句话定义 ​

MES 核心数据模型是支撑 MES 全部功能的那一组表，以及它们之间的关系和设计约定。本系列把它们分成三类：主数据（稳定、有版本）、单据（有状态机）、记录（只追加的流水）。

先修知识 ​

  • MES：三类表的划分原则，基础项目里的 7 张表。
  • 工单管理、BOM与物料清单、工艺路线与工序：工单、BOM、路线相关的表。
  • 条码与板码规则、过站与工序流转：拼板、板、过站记录相关的表。
  • 会写基本的 SELECT、JOIN；知道主键、外键、索引是什么。

它解决什么问题 ​

一个 MES 往往是很多个人、很多个月一点点做出来的：今天加一个"上料记录"，下个月加"治具使用"，再下个月加"返修"。如果没有一个"全局视角"，几件事一定会发生：

  • 同一个东西，各表叫法不同：A 表叫 Sn，B 表叫 SerialNo，C 表叫 BarCode。查询时到处要记"这张表里板码叫什么"，连表也容易连错。
  • 同一个东西，类型不同：我在本机的迷你模型里实际查过：WorkOrder.WoNo 是 varchar(30)，而后来的 Unit.WoId 是 nvarchar(30)；Bom.ProductCode 是 varchar(50)，Unit.ProductCode 是 nvarchar(50)。看起来无害，实际会拖慢查询（后面有实测）。
  • 不知道有什么表、哪张是干什么的：新人接手只能一张张点开看，改了一张表不知道会影响哪些功能。
  • 规则各自为政：有的表软删除，有的表物理删除；有的记录表可以改，有的不可以；有的有创建人，有的没有。出了问题无法追查。
  • 没人想过数据量：过站记录一年上千万行，查询越来越慢，才发现没有分区、没有归档方案，改动已经很难。

先画一张全局图、定一套统一的约定，可以把这些问题大部分挡在设计阶段。

核心概念 ​

三类表（回顾与细化） ​

类别特点设计要点典型例子
主数据稳定、被很多地方引用、变得少要有版本；旧版本不删，只"作废"；改动要留痕；生效版本要有唯一约束物料、BOM、工艺路线、设备、站位表、不良代码
单据有生命周期，状态会变，业务按它推进有状态机，状态变化受控；状态条件写进 UPDATE 的 WHERE；不物理删除工单、板（Unit）、返修单、锁定单
记录（流水）只增不改，像流水账，量最大只追加；更正靠"追加一条更正记录"；要考虑分区和归档；索引要克制过站记录、炉温记录、上料记录、不良记录、设备状态日志

判断一张新表属于哪一类，问三个问题：会不会被修改？（会→单据或主数据；不会→记录）改了之后要不要保留旧版本？（要→主数据，加版本）有没有"状态"，业务是不是按状态推进？（有→单据）。

另外还有一类辅助表：自己不是业务，只为别的表服务，例如本系列的号段表 SnSequence（给板码取号用）。

一张图看全局 ​

下图是迷你 MES 的表和后续规划的表。实线框是现在就有的，我在本机用前面各篇的实验实际建出来过；虚线框是规划中的，会由后续词条陆续补充，见后面的"规划中的表"。

读图要点：

  • 左列主数据：Material（物料）是源头；Bom/BomItem、Route/RouteStep 是"头—行"结构（一张头表加一张明细表）；
  • 中列单据：WorkOrder 下发时绑定当时生效的 Bom 和 Route 版本（图里两条线汇入它）；一张工单对应很多块 Unit；Panel/PanelBoard 记录拼板与子板的对应，子板通过 SerialNo 对应到 Unit；
  • 右列记录：TrackRecord 按 SerialNo 关联 Unit，是全系统追溯的主线；ReflowRecord（炉温记录）按板码关联，只是列名叫 Sn，和后来的表不统一；
  • 虚线框里的表，几乎都会通过 SerialNo（板）、WoId（工单）、StepNo（工序）这几个键和 Unit、TrackRecord 关联，所以上一篇里强调这几个字段的名字不要乱改。

表清单：实际有哪些表 ​

先查库里实际有什么 ​

不要靠记忆，直接问数据库。下面是用 INFORMATION_SCHEMA（SQL 标准里定义的元数据视图，各种数据库里大同小异）列表的写法。

前提：按 MES、工单管理、BOM与物料清单、工艺路线与工序、工艺参数与炉温曲线管理、条码与板码规则、过站与工序流转 依次建好项目并运行过实验（init、wo、bom、route、reflow、barcode、track）。练习库是 MiniMES_Lab，不要连别的库。

sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -f 65001 -d MiniMES_Lab -W -Q "SELECT t.TABLE_NAME AS TableName, COUNT(*) AS ColCount FROM INFORMATION_SCHEMA.TABLES t JOIN INFORMATION_SCHEMA.COLUMNS c ON c.TABLE_NAME = t.TABLE_NAME WHERE t.TABLE_TYPE = 'BASE TABLE' GROUP BY t.TABLE_NAME ORDER BY t.TABLE_NAME;"

主键：业务键还是自增 Id ​

方案优点缺点
业务键（如 WoNo）不需要额外的唯一索引，查询直观业务键可能变（ERP 改号规则）；字符串主键占空间，被引用时到处都是字符串
自增 Id短、稳定、聚集索引顺序写入业务键仍要另建唯一索引；跨系统同步时要映射

本系列的迷你模型为了让读者看得清，两种都用了。真实系统里更常见的做法是：用自增 Id（或 bigint）做主键，业务键单独加唯一索引，因为业务键的变化不会波及所有被引用的表。

类型一致性：我实测了一个会拖慢查询的坑 ​

据微软文档，两种数据类型比较时，优先级低的会被转换成优先级高的，nvarchar 的优先级高于 varchar。所以：当一边是 varchar 列，另一边是 nvarchar 常量或参数，转换的是那一整列。（SqlSugar 生成的 SQL 里字符串都带 N 前缀，也就是 nvarchar，可以回头看 工单管理 里抓到的 SQL。）

我在本机的 LocalDB 上做了一个对比实验（数据库的排序规则是 SQL_Latin1_General_CP1_CI_AS）：两张表各 10 万行，一张的 Code 列是 varchar(30)，另一张是 nvarchar(30)，都是主键。按主键等值查一行，用 SET STATISTICS IO ON 看逻辑读：

表的列类型查询条件逻辑读
varchar(30)Code = 'SN050000'（varchar）3
varchar(30)Code = N'SN050000'（nvarchar）1526（整个索引被扫描）
nvarchar(30)Code = N'SN050000'3
nvarchar(30)Code = 'SN050000'3

造数据和测量的脚本如下（用 sqlcmd -I 运行；做完会删掉这两张临时表）：

sql
CREATE TABLE LabVc (Code varchar(30) NOT NULL PRIMARY KEY, Pad char(100) NOT NULL DEFAULT 'x');
CREATE TABLE LabNvc (Code nvarchar(30) NOT NULL PRIMARY KEY, Pad char(100) NOT NULL DEFAULT 'x');
INSERT INTO LabVc(Code)  SELECT TOP 100000 'SN' + RIGHT('000000' + CAST(ROW_NUMBER() OVER (ORDER BY (SELECT 1)) AS varchar(10)), 6) FROM sys.all_objects a CROSS JOIN sys.all_objects b;
INSERT INTO LabNvc(Code) SELECT TOP 100000 N'SN' + RIGHT('000000' + CAST(ROW_NUMBER() OVER (ORDER BY (SELECT 1)) AS varchar(10)), 6) FROM sys.all_objects a CROSS JOIN sys.all_objects b;
SET STATISTICS IO ON;
SELECT Code FROM LabVc WHERE Code = 'SN050000';
SELECT Code FROM LabVc WHERE Code = N'SN050000';
SELECT Code FROM LabNvc WHERE Code = N'SN050000';
SELECT Code FROM LabNvc WHERE Code = 'SN050000';
SET STATISTICS IO OFF;
DROP TABLE LabVc; DROP TABLE LabNvc;

同样的数据、同样的查询意图，类型不匹配的那一种读了 500 多倍的页。10 万行时也许感觉不到，几千万行的过站表上就是灾难。结论：

  1. 同一种东西，所有表用同一种类型（本系列：板码、工单号、料号等编码类列，在新表里统一 nvarchar）。
  2. 如果必须保留 varchar，要确保程序传参的类型也是 varchar（具体怎么指定，取决于你们用的 ORM，请查文档并用执行计划验证），不能想当然。
  3. 本系列早期的表（Material、WorkOrder、Bom 等）的编码列是 varchar，是迷你模型历史原因；用在真实系统时建议统一。

上面的结果我只在 SQL_Latin1_General_CP1_CI_AS 排序规则下测过；换成 Windows 排序规则（如 Chinese_PRC_CI_AS）行为可能不同，请在你们的库上实测。

通用审计字段 ​

每张表至少应该回答："谁、什么时候、创建了这一行"。常见的一组：

列类型含义适用
CreatedAtdatetime / datetime2创建时间所有表
CreatedBynvarchar(30)创建人（工号）所有表
UpdatedAt同上最后修改时间单据、主数据（记录表不改，不需要）
UpdatedBy同上最后修改人同上
RowVersionrowversion数据库自动维护的版本号，用于乐观并发经常被多人编辑的表（主数据、单据）

几点说明：

  • 记录表只需要 CreatedAt/CreatedBy，因为它们不会被修改。TrackRecord 里的 OutAt 和 OperatorCode 其实就承担了这两个角色。
  • 迷你模型的表大多只有 CreatedAt（Bom、WorkOrder、Unit），没有 CreatedBy、UpdatedAt、UpdatedBy。真实系统要补上，并且最好由框架统一填，而不是每处手写。
  • 统一填的办法（SqlSugar）：设置 db.Aop.DataExecuting，在插入时自动给 CreatedAt 赋值。我在本机试过，插入一个没赋 CreatedAt 的 Unit 后，读回来的 CreatedAt 年份是 2026，说明自动填充生效：
csharp
db.Aop.DataExecuting = (oldValue, entityInfo) =>
{
    if (entityInfo.PropertyName == "CreatedAt" && entityInfo.OperationType == DataFilterType.InsertByObject)
        entityInfo.SetValue(DateTime.Now);
};
  • 并发控制二选一：像 Unit 那样把"期望的旧值"写进 UPDATE 的 WHERE（见 过站与工序流转）；或者用 rowversion 列，更新时 WHERE RowVersion = @旧值。前者针对"某几个关键字段"，后者针对"整行有没有被别人改过"。
  • 时间用本地时间还是 UTC：多厂区、跨时区就应该存 UTC（用 datetime2），显示时再转换；单厂可以用本地时间，但要全库统一，并在文档里写明。迷你模型用本地时间的 datetime。

软删除 vs 作废 ​

"删除"在 MES 里要非常小心：被引用的数据一旦物理删除，追溯就断了。三种处理：

做法例子适用
物理删除DELETE纯粹的临时数据、测试数据；业务数据几乎不用
软删除加 IsDeleted bit，查询都带 WHERE IsDeleted = 0"删错了可以恢复"的场景，如不良代码字典里误加的一行
作废/取消（状态）Status = 'Obsolete' / 'Cancelled' / 'Voided'业务上有意义的"不用了"：BOM 作废、路线作废、工单取消、返修单取消

核心区别：作废是一个业务事实，要有原因、有人、有时间，且可以被查询和统计；软删除只是"假装没有了"。MES 的单据和主数据，优先用状态表达作废，而不是 IsDeleted。

软删除有个常见陷阱：唯一约束。如果 ToolCode 要求唯一，软删除一行之后，新建同编码的一行会因为唯一索引冲突而失败。解决办法是用筛选唯一索引，只对"没被删除的行"要求唯一，我在本机验证过：

sql
CREATE TABLE LabSoft (Id int IDENTITY PRIMARY KEY, Code nvarchar(20) NOT NULL, IsDeleted bit NOT NULL DEFAULT 0);
CREATE UNIQUE INDEX UX_LabSoft_Code ON LabSoft(Code) WHERE IsDeleted = 0;

插入 ST-01、把它软删除（IsDeleted = 1）、再插入一条 ST-01，成功；再插入第三条 ST-01（此时已有一条未删除的），被唯一索引拒绝（Cannot insert duplicate key row）。注意：创建筛选索引的会话必须 SET QUOTED_IDENTIFIER ON；用 sqlcmd 时要加 -I 参数，否则会报 1934 号错误（QUOTED_IDENTIFIER 设置不正确），我实际踩到过。

大表分区与归档 ​

记录表到底多大 ​

估算一下 TrackRecord：假设一家工厂每天做 3000 块板，每块板 20 道工序（含返工），每次出站一行：3000 × 20 = 60000 行/天，60000 × 365 ≈ 2190 万 行/年。每行按 200 字节粗估（这是估算），约 4 GB/年，加上索引更多。五年就是一亿行以上。查询没问题（索引够好），但维护会变得痛苦：备份变大、重建索引耗时长、历史数据永远在热表里拖慢一切。

分区 ​

分区（partitioning）是把一张大表按某个列的值水平切成若干块，对应用来说仍是一张表。据微软文档，好处主要是：能快速地把整块数据转移或访问；可以只对某个分区做维护（压缩、重建索引、清空）；可以把整个分区"切换"（switch）到另一张归档表；在查询条件包含分区列时，数据库可以跳过不相关的分区（分区消除）。

关键概念：分区函数（决定哪个值落在哪个分区）、分区方案（把分区映射到文件组）、分区列。对按时间增长的记录表，通常用 OutAt（或 CreatedAt）按月分区。

我在本机试了一个按月分区的最小例子：

sql
CREATE PARTITION FUNCTION pf_Month (datetime) AS RANGE RIGHT FOR VALUES ('2026-09-01', '2026-10-01', '2026-11-01');
CREATE PARTITION SCHEME ps_Month AS PARTITION pf_Month ALL TO ([PRIMARY]);
CREATE TABLE TrackRecordP (
    Id bigint IDENTITY NOT NULL, SerialNo nvarchar(40) NOT NULL, StepNo int NOT NULL, OutAt datetime NOT NULL,
    CONSTRAINT PK_TrackRecordP PRIMARY KEY CLUSTERED (OutAt, Id)) ON ps_Month(OutAt);

三个边界值切出 4 个分区：第 1 区是 9 月 1 日之前，第 2 区是 9 月，第 3 区是 10 月，第 4 区是 11 月 1 日起。RANGE RIGHT 表示边界值属于它右边的分区，即每个月的 1 日属于该月，对按日期分区更直观。插入 5 行（8 月 1 行、9 月 2 行、10 月 2 行），用 $PARTITION.pf_Month(OutAt) 统计，得到分区 1 有 1 行、分区 2 有 2 行、分区 3 有 2 行，和预期一致。

一个必须知道的限制（来自微软文档）：唯一的聚集索引或唯一的非聚集索引，键里必须包含分区列。所以上面的主键写成了 (OutAt, Id) 而不是单独的 Id。这意味着：一旦按时间分区，"板码唯一"这类约束就不能再靠一个跨分区的唯一索引来保证了（SerialNo 唯一索引的键必须带 OutAt）。对 Unit 这样的单据表就不适合按时间分区；而 TrackRecord 本来就允许同一块板有多行，影响不大。所以：只对量大、只追加的记录表分区，单据表和主数据不分。

归档 ​

不管用分区还是不用，历史数据都要有归宿，常见做法：

做法说明注意
分区切换到归档表把最老的分区 SWITCH 到一张结构相同的归档表，几乎是瞬间完成（只改元数据）归档表要结构、索引、文件组都与分区一致，并加与该分区范围吻合的 CHECK 约束
移到历史库定期把超过 N 个月的数据复制到另一个数据库再删除要小心中途失败：先复制、核对、再删除；删除要分批以免长事务
汇总后删除明细保留日/班次汇总（够做报表和 OEE），明细删除追溯能力会减弱：客户要求保存多少年请先问清楚

我在本机把 9 月分区切走：先建一张结构相同、带 CHECK (OutAt >= '2026-09-01' AND OutAt < '2026-10-01') 的归档表，再执行 ALTER TABLE TrackRecordP SWITCH PARTITION 2 TO TrackRecordArchive;，结果主表剩 3 行、归档表有 2 行，这个动作没有复制数据。注意要用的是第 2 个分区（9 月）；我第一次写成了 3，那是 10 月分区——分区编号从 1 开始，且 1 号是"第一个边界之前"，很容易数错。

保留多久不是技术问题：很多电子制造客户（汽车、医疗等）要求追溯数据保存数年到十几年，而且常常写在合同或质量体系里。具体年限请向质量部门和客户确认，我这里没有核对任何标准。

索引设计要点 ​

索引是用空间和写入速度换查询速度。记录表写入多、读取少，索引要克制；单据表查询多，索引可以多一些。

先写下"最常用的查询"，再建索引 ​

查询典型 SQL索引
按板码查一块板（扫码过站、追溯）WHERE SerialNo = @snUnit.SerialNo 唯一索引（已有）；TrackRecord (SerialNo, StepNo)
按工单看各工序进度WHERE WoId = @wo GROUP BY StepNoTrackRecord (WoId, StepNo)；Unit (WoId)
按时间范围统计WHERE OutAt >= @from AND OutAt < @to按时间分区，或 OutAt 上建索引
看哪些板被锁定WHERE Status = N'Hold'Status 区分度低，不要单独建；用筛选索引只收录锁定的行

两条常用查询我在本机实际跑过（使用过站实验留下的数据）：

sql
SELECT StepNo, StepCode, Result FROM TrackRecord WHERE SerialNo = N'TRK-0002' ORDER BY Id;
SELECT CurrentStepNo, COUNT(*) AS Cnt FROM Unit WHERE WoId = N'WO-TRK-001' AND Status = N'InProcess' GROUP BY CurrentStepNo ORDER BY CurrentStepNo;

第一条返回这块板的完整履历 6 行（10 PRINT Pass、20 SPI Fail、20 SPI Pass、30 MOUNT Pass、40 REFLOW Pass、50 AOI Pass）；第二条返回这张工单各工序的在制品数：序号 10 有 1 块、序号 40 有 1 块（"当前工序序号"就是它已完成的最后一道）。这两条正是第 1 行 (SerialNo, StepNo) 和 (WoId, StepNo) 索引存在的理由。

筛选索引：只给"少数重要的行"建 ​

比如锁定的板很少，但要快速找出来：

sql
CREATE INDEX IX_Unit_Hold ON Unit(WoId) WHERE Status = N'Hold';

据微软文档，筛选索引只对满足条件的行建索引，体积小、维护成本低。我在本机建出来后，sys.indexes 里的 filter_definition 是 ([Status]=N'Hold')。（迷你模型里已有的 UX_Bom_Active 也是这类索引。）

其他要点 ​

  • 复合索引的列顺序：把"等值查询的列"放前面，"范围查询/排序的列"放后面。(WoId, StepNo) 能回答"这张工单"和"这张工单的某道工序"，但回答不了"某道工序的全部工单"。
  • 唯一约束先于性能：该唯一的一定要建唯一索引（SerialNo），这是数据正确性，不是优化。
  • 类型一致：见上面"类型一致性"，索引列类型和查询参数类型不一致，索引形同虚设。
  • 索引要定期检查：用不到的索引只会拖慢写入。可以用 sys.dm_db_index_usage_stats 之类的视图观察使用情况（本篇没有实测，请查阅官方文档）。
  • 别给 Status、Result 这种只有几个值的列单独建普通索引：区分度太低，数据库往往不会用。

Panel WoNo nvarchar 30

第 4 步，读结果：ProductCode 在 Bom、Route、WorkOrder 是 varchar(50)，在 Panel、Unit 是 nvarchar(50)；工单号在 WorkOrder.WoNo 是 varchar(30)，在 Unit.WoId、TrackRecord.WoId 是 nvarchar(30)，在 Panel 里又叫 WoNo。同一个概念，三个名字、两种类型。 这是迷你模型先写旧表、后写新表留下的不一致，也正好说明为什么需要本篇的规范和定期体检。真实系统要在设计阶段就统一，而不是等到出了性能问题再去改。

动手实验：给自己的库做一次体检 ​

本篇没有新的实验类，下面是用 T-SQL 完成的练习。前提：前面的实验都跑过，连的是练习库 MiniMES_Lab。

  1. 运行上面"表清单"的两条查询，对照本篇的"表清单（已有）"，确认每张表都在，主键对得上。

  2. 运行"体检"的两条查询，列出你那边不一致的列。

  3. 在 Unit 上建筛选索引（注意 sqlcmd 要加 -I）：

    sql
    CREATE INDEX IX_Unit_Hold ON Unit(WoId) WHERE Status = N'Hold';
SELECT name, filter_definition FROM sys.indexes WHERE name = 'IX_Unit_Hold';

    应该看到 filter_definition 是 ([Status]=N'Hold')。练习完用 DROP INDEX IX_Unit_Hold ON Unit; 删掉。

  4. 在练习库里自己建两张表（一张 varchar 主键、一张 nvarchar 主键，各 10 万行，可以参考上面实测的写法，用 sys.all_objects 交叉连接造数据），用 SET STATISTICS IO ON 复现"逻辑读 3 对 1526"的差别，做完把这两张表删掉。

  5. 画一遍你们自己系统的"板码"相关表：哪些表有板码？列名和类型一致吗？

常见坑与误区 ​

误区 / 坑事实与办法
同一概念在不同表里叫不同的名字写命名规范，上线前用 INFORMATION_SCHEMA 体检
同一概念在不同表里类型不同（varchar/nvarchar）类型不匹配会让索引形同虚设（实测逻辑读差 500 倍）。全库统一
业务数据用物理删除追溯断链。用状态表达"作废/取消"；必要时软删除并用筛选唯一索引
记录表允许 UPDATE历史不可信。只追加；数据库加触发器或权限；更正走"追加"
单据表也按时间分区分区会要求唯一索引的键带分区列，SerialNo 唯一就保证不了。只给大的记录表分区
一开始不想数据量过站表一年千万行级别。提前设计分区、归档、保留年限
归档前没确认保留年限客户或合同可能要求保存多年。先问质量部门
每个人各写各的审计字段统一在框架层（如 SqlSugar 的 DataExecuting）填，别在业务代码里一处处手写
CodeFirst 当作数据库迁移它只建表、补列，不改已有列。真实系统用有版本的迁移脚本
给低区分度的列（Status）建普通索引基本用不上，白白拖慢写入。用筛选索引
索引越多越好每个索引都要在每次写入时维护。记录表尤其要克制
筛选索引建不出来（错误 1934）QUOTED_IDENTIFIER 要为 ON；sqlcmd 加 -I

练习题与答案 ​

  1. 工单、BOM、过站记录、炉温记录、拼板对应表，分别属于主数据、单据、记录中的哪一类？ 答：工单是单据；BOM 是主数据；过站记录、炉温记录是记录；拼板对应表（PanelBoard）是单据（对应关系建立后一般不再变，也有人把它视为主数据/关系表，关键是"有唯一约束、不物理删除"）。
  2. 判断一张新表属于哪一类，要问哪三个问题？ 答：会不会被修改？改了要不要保留旧版本？有没有状态、业务是否按状态推进？
  3. 为什么记录表（如 TrackRecord）通常只需要 CreatedAt，不需要 UpdatedAt？ 答：记录表只追加、不修改，没有"最后修改时间"这回事。更正通过追加一条新记录表达。
  4. 一张表的 Code 列是 varchar(30) 主键，程序用 nvarchar 参数 N'SN050000' 按它查询，为什么慢？ 答：nvarchar 优先级高于 varchar，被比较的整列要转换成 nvarchar，索引不能用于精确查找，退化为扫描。我实测 10 万行时逻辑读是 1526（对比类型一致时的 3）。
  5. 软删除和"作废"的区别？MES 里更推荐哪个？ 答：软删除是"假装没有了"（IsDeleted）；作废是业务事实，用状态表达，带原因、人、时间，可被查询统计。MES 的单据和主数据更推荐用状态。
  6. 软删除一行后，再插入同编码的新行会因为唯一索引失败，怎么解决？ 答：用筛选唯一索引：CREATE UNIQUE INDEX ... ON 表(编码) WHERE IsDeleted = 0，只对未删除的行要求唯一。
  7. 分区表的主键为什么要写成 (OutAt, Id) 而不能只写 Id？这对"板码唯一"有什么影响？ 答：据微软文档，唯一的聚集或非聚集索引的键必须包含分区列。所以主键要带 OutAt；同理，SerialNo 的唯一索引也得带分区列，这样"板码全局唯一"就保证不了。因此单据表（Unit）不适合按时间分区，只给量大的记录表分区。
  8. 日产 3000 块、每块 20 道工序、每次出站一行，一年有多少过站记录？ 答：3000 × 20 × 365 = 2190 万 行。
  9. 为什么说"筛选索引"适合"找出被锁定的板"？ 答：锁定的板很少，只对 Status = N'Hold' 的行建索引，体积小、维护成本低，查询很快；而对 Status 建普通索引，区分度低，数据库往往不用。
  10. CodeFirst.InitTables 为什么不适合真实系统的数据库变更？ 答：它只建不存在的表、补缺失的列，不会改已有列的类型（如 varchar 改 nvarchar），也没有版本、评审和回滚。真实系统应使用有版本的迁移脚本。

小结 ​

  • MES 的表分三类：主数据（稳定有版本）、单据（有状态机）、记录（只追加）；另有辅助表。
  • 表清单要靠数据库自己回答：用 INFORMATION_SCHEMA 列表、列主键、体检同名列的类型。
  • 命名规范写下来并统一：板码叫 SerialNo、nvarchar(40)；工单、料号等编码类列，在所有表里同名同类型。
  • 类型不一致不是小问题：varchar 列遇上 nvarchar 参数，我实测逻辑读从 3 变成 1526。
  • 审计字段、并发控制、软删除与作废、分区与归档、索引，都是"每张表都要想一遍"的事；分区只给大的记录表，单据表保证唯一性更重要。
  • 迷你模型到真实系统，要补组织与权限、审计、变更、接口、容灾、迁移脚本与数据字典；后续词条会补上规划中的表。
