过站与工序流转

AI 生成 · 待核对制造业务MES过站防错更新于 2026-10-21

⚠ 待核对：过站的业务流程（进站检查项、Fail 之后的处理、返修回路、双面板）是电子厂常见的通用做法，没有逐条联网核实；你们自研 MES 的过站是"进站、出站各一次扫描"还是"一次扫描完成"，Fail 之后是自动锁定还是人工判定，状态名叫什么，都可能不同，请对照你们的系统。代码和输出是我在本机 SQL Server LocalDB 上实际运行得到的；"DML 触发器强制只追加"的写法在本机 LocalDB 试过。

本篇是 MES 系列第 7 篇，也是后面很多篇的基础：本篇定义的两个实体 Unit（一块板）和 TrackRecord（过站记录），会被上料防错、首件、报工、追溯、不良拦截、返修、OEE、看板、接口等词条反复使用。读完你应该能：说清进站、出站各做什么；列出进站检查清单；解释漏站、跳站、重复过站、不良品不得进下一站、双面板、返工回路各自怎么处理；画出板子的状态机；写出"并发下只有一个终端能成功"的出站代码，并在末站同时更新工单完成数。

一句话定义 ​

过站是一块板在某道工序"进入"和"离开"时，在系统里登记的动作：进站（Track In）时系统检查"这块板现在能不能做这道工序"，出站（Track Out）时登记"做完了，结果是合格还是不合格"，并让这块板推进到下一道。

先修知识 ​

  • MES：搭好了"迷你 MES"项目；知道三类表（主数据、单据、记录）。
  • 工艺路线与工序：知道工序序号、工序码、"进站判断"（本篇直接复用那里的 CanEnter），以及双面板里工序码会重复。
  • 工单管理：知道工单状态和"把条件写进 UPDATE 的 WHERE"这个防并发技巧，本篇用它防止两个终端同时处理同一块板。
  • 条码与板码规则：知道板码（SN）是什么、怎么保证唯一。

它解决什么问题 ​

先看没有过站控制的车间：

  • 漏站：回流焊之后本来要过 AOI，操作员一忙，板子直接流到了测试站。没有焊好的板子被测试，要么测试失败浪费时间，要么（更糟）刚好测过了，带着焊接缺陷出了货。
  • 跳站：印刷完没过 SPI（锡膏检测）就直接贴片。如果锡膏印刷其实有问题，后面所有元件白贴了。
  • 重复过站：同一块板扫了两次，系统里有两条"回流焊完成"的记录；报工数量因此多算，工单"提前完成"，而实际有板子根本没做。
  • 不良品混进好品：AOI 判了不合格的板子被放回了流水线，因为没有任何东西阻止它进下一站。
  • 没人知道板子在哪：客户问"这批货做到哪一步了"，只能靠人去产线上数。

过站把这些全部变成系统自动判断：进站前检查，不对就当场拦住并告诉操作员原因；出站时记录结果，不合格的板自动锁定，不让往下走。结果是三样东西：防错（做错之前拦住）、记录（每块板每一站的履历）、在制品可见（每块板此刻在哪一站）。

核心概念 ​

进站与出站 ​

动作时机系统做什么
进站 Track In板子到达工站，操作员（或设备）扫码检查：这块板现在允许做这道工序吗？通过则开始计时，不通过则拒绝并提示原因
出站 Track Out这道工序做完登记：结果 Pass 还是 Fail、哪个工站、谁做的、何时进何时出；板子推进到下一道（Pass）或被锁定（Fail）

两个动作之间的时间就是这块板在这道工序上花的时间（节拍/工时）。

很多电子厂的设备（贴片机、回流炉、AOI）可以自动上报，不需要人扫码；而手工工位（如目检、插件）需要人扫码。无论哪种，在 MES 里都是这两个动作。有些设计里进站、出站合成一次（一次扫码，直接写 Pass/Fail），本篇的迷你模型是一次出站写一行记录，进站时只做检查并把进站时间带到出站。

在制品 WIP ​

在制品（WIP，Work In Process）是已经投入生产、还没有完工的板子。MES 的一个基本能力就是随时回答"现在每道工序上有多少块在制品"。这要求每块板有一行"当前状态"，即本篇的 Unit。

本篇要用的两个实体 ​

实体类别含义变不变
Unit单据（有状态）一块板：它是谁（SerialNo）、属于哪张工单、做到哪一步了（CurrentStepNo）、现在什么状态（Status）会变，受状态机控制
TrackRecord记录（流水）每次出站一行：哪块板、哪道工序、结果、何时、哪个工站、谁只追加，不修改不删除

两者分工要记牢：Unit 回答"现在怎么样"，TrackRecord 回答"过去发生了什么"。Unit 可以从 TrackRecord 重新推算出来，但反过来不行，所以 TrackRecord 才是真相的来源，Unit 是为了快。

CurrentStepNo：记序号，不记工序码 ​

CurrentStepNo 是已经出站且合格的最后一道工序的序号，0 表示还没开始。和 工艺路线与工序 里强调的一样：记序号，不记工序码。双面板里 REFLOW 出现两次（序号 40 和 80），只有序号能说清楚板子到底做完了哪一遍。

状态机 ​

Unit.Status 有四个值：

状态含义能进站吗
InProcess 在制正常生产中能（路线允许的下一道）
Hold 锁定某站判了 Fail，等待处理（返修、复判、报废）；也可能被质量人员主动锁定不能
Completed 完工走完了路线的最后一道且合格不能（终态）
Scrapped 报废判定无法修复不能（终态）

状态机的意义：每个状态下允许的动作是固定的，不能随便从任何状态跳到任何状态。例如 Hold 的板只能被"返修放行"（回到 InProcess）或"判报废"（到 Scrapped），不能直接进下一站。"锁定后谁能放行"是质量管理的问题，见 不良品拦截与锁定 和 返修与维修管理。

几种防错，各自怎么拦 ​

错误例子怎么识别怎么拦
漏站/跳站板子只做完印刷，想直接进贴片想进的工序不是路线里"下一道"路线判断（CanEnter）拒绝，提示"应该是 SPI"
重复过站同一块板的印刷已经出站，又扫了一次印刷想进的工序序号 ≤ 已完成序号，且后面没有同名工序同上，提示"重复"
不良品进下一站AOI 判 Fail 的板想进下一道板状态是 Hold状态检查拒绝，提示"必须先返修放行"
工单不对工单已暂停或关闭，板子还在做工单状态不是 Running进站检查拒绝；末站累加完成数时也再查一次
双面板第二次过同一站A 面回流完，板翻面再进印刷同一个工序码第二次出现，但序号更大允许——因为"下一道"正好是 B 面印刷
两个终端同时处理同一块板两台设备（或两个人）同时扫了同一块板出站时 CurrentStepNo 已不是进站时看到的值条件 UPDATE 只让一个成功，另一个得到 0 行
返工回路AOI 缺件，修好后重新过 AOIHold 放行后 CurrentStepNo 没变，下一道仍是出错的那一站放行后重新进站，路线判断自然允许

最后一行很重要：Fail 的那一站不算完成，所以出站 Fail 时 CurrentStepNo 不推进，只把状态改成 Hold。返修放行后，"下一道"仍然是出错的那一站，板子自然回到那一站重做，不需要什么特殊的"回退"逻辑。履历里会留下一条 Fail 和一条后来的 Pass，两条都在，这才是真实的历史。

进站检查清单 ​

进站时要检查的东西，从基本到扩展：

#检查项本篇实验实现说明
1板码存在是扫的码在 Unit 里能找到
2板状态是 InProcess是Hold、Scrapped、Completed 都不能进站
3工单状态是 Running是工单没开工/已暂停/已关闭不能做
4路线允许进这道工序是复用 CanEnter：不漏、不跳、不重复，双面板靠序号
5设备/工站正常否设备停机、保养超期的不能做，见 设备管理与设备状态
6物料已上对否SMT 线上料站位和料盘对得上，见 SMT上料防错与站位表
7首件已通过否换线或换型后首件没过不能批量做，见 首件检验与换线
8治具、钢网在寿命内否见 治具与钢网管理
9工艺参数/程序对否设备程序版本和配方对得上，见 工艺参数与炉温曲线管理
10操作员有资质否例如上岗证、ESD 要求

清单是一串"与"条件，任意一条不满足就拒绝，并明确告诉操作员是哪一条，而不是只说"失败"。实验里只做前 4 项，其余的在对应的后续词条里补上，思路完全一样：多一条检查，多一个拒绝原因。

业务视角 ​

谁在什么环节做什么：

角色动作
产线操作员在工站扫板码进站；做完后扫码（或按键）出站，选择 Pass/Fail；被拦下时按提示处理
设备（自动）贴片机、回流炉、AOI 等通过接口自动进站/出站，见 MES与ERP及设备的接口设计
线长/班组长看在制品分布，处理被拦下的板，决定是否放行
品质对 Hold 的板做判定：返修、特采、报废
维修员处理被锁定的不良板，修好后登记，板子回到流程，见 返修与维修管理
生产计划/管理看每道工序的在制品数量、完成数、瓶颈在哪，见 生产看板与实时报表

流程（单面板，一块板）：

  1. 首站前：板子已有板码，Unit 已建立，状态 InProcess，序号 0（发码和建立见 条码与板码规则）；
  2. 到 PRINT 工站：扫码进站 → 检查通过 → 印刷；
  3. 出站：印刷完，登记 Pass → CurrentStepNo 变成 10，追加一条 TrackRecord；
  4. 依次 SPI、MOUNT、REFLOW、AOI；
  5. 末站出站 Pass → 状态变 Completed，同时工单完成数加 1。

KPI：

  • 直通率（FPY，First Pass Yield）：一次就全部 Pass、没有 Fail 记录的板占比；
  • 各工序在制品数量：看哪里堆板；
  • 节拍/工时：OutAt - InAt 的分布；
  • 拦截次数及原因分布：漏站、跳站、重复各多少，说明操作习惯或配置哪里有问题。

技术视角 ​

表设计 ​

下面是 T-SQL 建表语句（实验里 SqlSugar 会自动建出等价的表，但 T-SQL 版本多了 CHECK 约束和默认值，更适合直接用在真实系统里）。我在本机的临时库里运行过，验证约束和触发器都按预期工作。

sql
CREATE TABLE Unit (
    Id            int IDENTITY(1,1) NOT NULL CONSTRAINT PK_Unit PRIMARY KEY,
    SerialNo      nvarchar(40) NOT NULL,
    WoId          nvarchar(30) NOT NULL,          -- 所属工单（迷你模型里工单主键是 WoNo，所以存工单号）
    ProductCode   nvarchar(50) NOT NULL,
    CurrentStepNo int NOT NULL CONSTRAINT DF_Unit_Step DEFAULT 0,
    Status        nvarchar(20) NOT NULL CONSTRAINT DF_Unit_Status DEFAULT N'InProcess',
    CreatedAt     datetime NOT NULL CONSTRAINT DF_Unit_Created DEFAULT GETDATE(),
    CONSTRAINT UX_Unit_SerialNo UNIQUE (SerialNo),
    CONSTRAINT CK_Unit_Status CHECK (Status IN (N'InProcess', N'Completed', N'Scrapped', N'Hold'))
);

CREATE TABLE TrackRecord (
    Id           int IDENTITY(1,1) NOT NULL CONSTRAINT PK_TrackRecord PRIMARY KEY,
    SerialNo     nvarchar(40) NOT NULL,
    WoId         nvarchar(30) NOT NULL,
    StepNo       int NOT NULL,                    -- 记序号，不是工序码
    StepCode     nvarchar(20) NOT NULL,
    Result       nvarchar(10) NOT NULL,
    StationCode  nvarchar(30) NOT NULL,
    OperatorCode nvarchar(30) NOT NULL,
    InAt         datetime NOT NULL,
    OutAt        datetime NOT NULL,
    CONSTRAINT CK_Track_Result CHECK (Result IN (N'Pass', N'Fail'))
);
CREATE INDEX IX_TrackRecord_Sn ON TrackRecord(SerialNo, StepNo);

几个设计点：

  1. SerialNo 唯一：一个板码对应一行 Unit。这是全系统追溯的锚点。
  2. Status 和 Result 加 CHECK 约束：我实际试过，把状态改成 Foo 会被数据库拒绝（"UPDATE 语句与 CHECK 约束冲突"）。状态是枚举，数据库应该替程序守住。
  3. TrackRecord 只追加：除了不在程序里写 UPDATE/DELETE，还可以在数据库里加一个"拦截"触发器，以防别的程序或手工 SQL 误改。据微软文档，INSTEAD OF 触发器会取代触发它的语句：
sql
CREATE TRIGGER TR_TrackRecord_AppendOnly ON TrackRecord INSTEAD OF UPDATE, DELETE AS
BEGIN
    THROW 50001, N'TrackRecord is append-only', 1;
END;

加上之后，我对 TrackRecord 执行 UPDATE 和 DELETE 都得到了错误 50001 TrackRecord is append-only，表里的数据没有变。（真实系统里还应该通过账号权限，只给应用账号 INSERT 和 SELECT；需要更正时追加一条"更正记录"，而不是改旧的。） 4. 索引：履历查询是"按板码查一块板的全部记录"，用 (SerialNo, StepNo)；工单进度是"按工单、工序汇总"，用 (WoId, StepNo)。详见 MES核心数据模型。 5. 板码列类型一致：Unit.SerialNo 和 TrackRecord.SerialNo 都是 nvarchar(40)，连表比较时不会触发隐式类型转换。

出站的核心：条件 UPDATE ​

把 工单管理 里的技巧用在 Unit 上。出站推进用的是：

sql
UPDATE Unit
SET    CurrentStepNo = @stepNo, Status = @newStatus
WHERE  SerialNo = @sn
  AND  CurrentStepNo = @prev      -- 必须还停在进站时看到的位置
  AND  Status = N'InProcess';     -- 必须仍然是在制

返回受影响行数：1 表示这次出站有效，0 表示被别人抢先了（另一个终端已经处理了这块板，或者它的状态已经变了）。这就是"乐观并发控制"的一种写法：不加人为的锁，让数据库在写入的那一瞬间核对"你看到的世界还是真实的世界吗"。

事务：一次出站要做三件事 ​

一次末站出站要改三个地方，必须同时成功或同时失败：

BEGIN TRAN
  1. UPDATE Unit        -- 推进位置、改状态（条件 UPDATE）
  2. INSERT TrackRecord -- 追加过站记录
  3. UPDATE WorkOrder   -- 仅末站 Pass：完成数 +1（条件：工单是 Running 且不超计划数）
COMMIT

任何一步失败（受影响行数不对、抛出异常），就 ROLLBACK，前面做的全部撤销。如果没有事务，可能出现：板子已经 Completed 了，工单完成数却没加上（因为第 3 步失败）；这种"半成品"状态很难事后查出来。

两个细节：

  • 顺序固定：永远先改 Unit，再写 TrackRecord，最后改 WorkOrder。多个事务按相同顺序拿锁，才不容易互相等待造成死锁。
  • WorkOrder 是"热点行"：一条工单被所有板的末站出站同时更新，会排队。板子数量多、并发高时，有的系统改为"完成数由 TrackRecord 汇总得出，定时刷新"，把热点行拆掉，见 报工与产量统计。迷你模型里直接累加，简单易懂。

其他技术要点 ​

要点做法
重复扫描的幂等扫码枪抖动、设备重发，同一次出站可能来两遍。第二遍条件 UPDATE 得到 0 行。要不要把它当成"成功"返回，取决于业务：设备自动上报通常应当返回"已处理"而不是报错，避免设备重试风暴；人工操作则应当提示"这块板已经出站"
进站后一直没出站本篇的模型只在出站写记录，进站只检查，所以"进站未出站"的板不会留痕。如果要做"工位上现在有哪些板"，需要另外记录进站（例如 TrackIn 表或 Unit 加字段），本篇没有加
拼板的展开SMT 阶段按拼板码扫一次，要在一个事务里对拼板的每块子板各做一遍上面三步（对应关系见 条码与板码规则 的 PanelBoard）
路线从哪来板所属工单下发时已经绑定路线版本（WorkOrder.RouteId）。真实系统出站时要读工单绑定的那一版路线，不能读"现在生效的"，否则改版后在线的板会乱。本篇实验为简化，直接读该产品当前生效的路线
Fail 的处理本实验：Fail 自动锁定（Hold）。真实系统通常先让维修/品质判定（复判、误判可直接放行）再决定修、报废还是放行
更正操作员扫错了怎么办？不是改旧记录，而是品质/主管用"更正"功能，追加一条说明，并按权限把 Unit 位置调整回去，留下审计痕迹

逐步例子：一块板的一生 ​

工单 WO-TRK-001，产品 PCBA-A100，计划 2 块。板码 TRK-0002，路线是 PRINT(10) → SPI(20) → MOUNT(30) → REFLOW(40) → AOI(50)。

步骤操作进站检查结果Unit 之后新增 TrackRecord
1还没印刷就想进 MOUNT下一道是 PRINT，不是 MOUNT拒绝（跳站）序号 0，InProcess无
2进 PRINT，印刷完出站 Pass通过成功序号 10，InProcess10 PRINT Pass
3再进 PRINT序号 10 已完成，后面没有 PRINT拒绝（重复）不变无
4进 SPI，出站 Fail通过成功（但判不良）序号仍 10，Hold20 SPI Fail
5想进 MOUNT状态是 Hold拒绝不变无
6想重做 SPI状态是 Hold拒绝不变无
7返修放行（Hold → InProcess）—成功序号 10，InProcess无
8重新进 SPI，出站 Pass通过（下一道仍是 SPI）成功序号 2020 SPI Pass
9MOUNT、REFLOW 依次 Pass通过成功序号 4030、40 各一条
10AOI 出站 Pass（末站）通过成功，工单完成数 +1序号 50，Completed50 AOI Pass

最终履历（共 6 条，Fail 与后来的 Pass 并存）：10 PRINT Pass / 20 SPI Fail / 20 SPI Pass / 30 MOUNT Pass / 40 REFLOW Pass / 50 AOI Pass。要算这块板的"首次通过率"，数一数有没有 Fail 记录就行。下面的实验会把这张表完整跑一遍。

第 2 步：新建 LabTrack.cs：

csharp
using SqlSugar;

namespace MiniMes;

// 过站实验：进站检查（读）+ 出站登记（一个事务里：条件 UPDATE 板 + 追加过站记录 + 末站时累加工单完成数）
public static class LabTrack
{
    // 这是 LabRoute.CanEnter 的原样搬运（原方法是私有的，不能直接调用）
    static (bool Ok, string Why) CanEnter(List<RouteStep> steps, int lastDone, string target)
    {
        var next = steps.OrderBy(s => s.StepNo).FirstOrDefault(s => s.StepNo > lastDone);
        if (next == null) return (false, "所有工序都已完成");
        if (next.StepCode == target) return (true, "按顺序");
        var same = steps.Where(s => s.StepCode == target).ToList();
        if (same.Count == 0) return (false, "这个工序不在路线里");
        return same.Any(s => s.StepNo > lastDone)
            ? (false, $"跳站，下一道应该是 {next.StepCode}")
            : (false, "重复进已完成的工序");
    }

    static readonly Dictionary<string, string> Stations = new()
    {
        ["PRINT"] = "PRN-01", ["SPI"] = "SPI-01", ["MOUNT"] = "SMT-01", ["REFLOW"] = "RFL-01", ["AOI"] = "AOI-01",
    };

    // 进站检查清单：板存在 -> 板状态是 InProcess -> 工单是 Running -> 路线允许进这道工序
    static (bool Ok, string Why, Unit U, RouteStep Step) Enter(SqlSugarClient db, string sn, string stepCode, List<RouteStep> steps)
    {
        var u = db.Queryable<Unit>().First(x => x.SerialNo == sn);
        if (u == null) return (false, "板码不存在", null, null);
        if (u.Status == "Hold") return (false, "不良品已锁定（Hold），必须先返修放行", u, null);
        if (u.Status == "Scrapped") return (false, "已报废", u, null);
        if (u.Status == "Completed") return (false, "已经完工", u, null);
        var wo = db.Queryable<WorkOrder>().InSingle(u.WoId);
        if (wo == null || wo.Status != "Running") return (false, "工单不是 Running 状态", u, null);
        var (ok, why) = CanEnter(steps, u.CurrentStepNo, stepCode);
        if (!ok) return (false, why, u, null);
        return (true, "按顺序", u, steps.OrderBy(s => s.StepNo).First(s => s.StepNo > u.CurrentStepNo));
    }

    // 出站登记：全部在一个事务里。关键是第一句"条件 UPDATE"：
    // 只有板还停在进站时看到的那个序号、并且仍是 InProcess，才能推进；别的终端抢先了，这里就是 0 行
    static (bool Ok, string Why) Exit(SqlSugarClient db, Unit u, RouteStep step, bool isLast, string result, DateTime inAt)
    {
        string sn = u.SerialNo, wo = u.WoId, before = u.Status;
        int prev = u.CurrentStepNo, stepNo = step.StepNo;
        string newStatus = result == "Fail" ? "Hold" : (isLast ? "Completed" : "InProcess");
        db.Ado.BeginTran();
        try
        {
            var q = db.Updateable<Unit>();
            int n = result == "Pass"
                ? q.SetColumns(x => new Unit { CurrentStepNo = stepNo, Status = newStatus })
                    .Where(x => x.SerialNo == sn && x.CurrentStepNo == prev && x.Status == "InProcess").ExecuteCommand()
                : q.SetColumns(x => new Unit { Status = newStatus })
                    .Where(x => x.SerialNo == sn && x.CurrentStepNo == prev && x.Status == "InProcess").ExecuteCommand();
            if (n != 1) { db.Ado.RollbackTran(); return (false, "别的终端已经处理了这块板"); }

            db.Insertable(new TrackRecord
            {
                SerialNo = sn, WoId = wo, StepNo = stepNo, StepCode = step.StepCode, Result = result,
                StationCode = Stations.GetValueOrDefault(step.StepCode, "ST-00"), OperatorCode = "OP001",
                InAt = inAt, OutAt = DateTime.Now,
            }).ExecuteCommand();

            if (result == "Pass" && isLast)
            {
                int w = db.Updateable<WorkOrder>()
                    .SetColumns(x => x.FinishedQty == x.FinishedQty + 1)
                    .Where(x => x.WoNo == wo && x.Status == "Running" && x.FinishedQty + 1 <= x.PlanQty)
                    .ExecuteCommand();
                if (w != 1) { db.Ado.RollbackTran(); return (false, "工单完成数会超过计划数，整笔回滚"); }
            }
            db.Ado.CommitTran();
            return (true, "");
        }
        catch { db.Ado.RollbackTran(); throw; }
    }

    // 一次完整过站：进站检查 + 出站登记
    static string Pass(SqlSugarClient db, string sn, string code, List<RouteStep> steps, string result = "Pass")
    {
        var (ok, why, u, step) = Enter(db, sn, code, steps);
        if (!ok) return $"拒绝（{why}）";
        var (ok2, why2) = Exit(db, u, step, step.StepNo == steps.Max(s => s.StepNo), result, DateTime.Now.AddSeconds(-30));
        return ok2 ? $"进站通过 -> 出站 {result}" : $"拒绝（{why2}）";
    }

    static void NewUnit(SqlSugarClient db, string sn, string wo, string product, int stepNo = 0) =>
        db.Insertable(new Unit { SerialNo = sn, WoId = wo, ProductCode = product, CurrentStepNo = stepNo, Status = "InProcess", CreatedAt = DateTime.Now }).ExecuteCommand();

    static string History(SqlSugarClient db, string sn) =>
        string.Join(" / ", db.Queryable<TrackRecord>().Where(r => r.SerialNo == sn).OrderBy(r => r.Id).ToList()
            .Select(r => $"{r.StepNo} {r.StepCode} {r.Result}"));

    static string Wo(SqlSugarClient db, string no) { var w = db.Queryable<WorkOrder>().InSingle(no); return $"{w.FinishedQty}/{w.PlanQty}"; }

    public static void Run(SqlSugarClient db)
    {
        Seed.Basics(db);
        db.CodeFirst.InitTables(typeof(Unit), typeof(TrackRecord));
        db.Deleteable<TrackRecord>().Where(r => r.SerialNo.StartsWith("TRK-")).ExecuteCommand();
        db.Deleteable<Unit>().Where(u => u.SerialNo.StartsWith("TRK-")).ExecuteCommand();
        db.Deleteable<WorkOrder>().Where(w => w.WoNo.StartsWith("WO-TRK-")).ExecuteCommand();
        foreach (var (no, product, plan) in new[] { ("WO-TRK-001", "PCBA-A100", 2), ("WO-TRK-002", "PCBA-A200", 1) })
            db.Insertable(new WorkOrder { WoNo = no, ProductCode = product, PlanQty = plan, Status = "Running", CreatedAt = DateTime.Now }).ExecuteCommand();

        var route = db.Queryable<Route>().First(r => r.ProductCode == Seed.Product && r.Status == "Active");
        var steps = db.Queryable<RouteStep>().Where(s => s.RouteId == route.RouteId).OrderBy(s => s.StepNo).ToList();

        // 1. 正常过站
        Console.WriteLine("1. 正常过站：TRK-0001 走完单面板路线（工单 WO-TRK-001，计划 2 块）");
        NewUnit(db, "TRK-0001", "WO-TRK-001", Seed.Product);
        foreach (var s in steps) Console.WriteLine($"   {s.StepNo,3} {s.StepCode,-7} {Pass(db, "TRK-0001", s.StepCode, steps)}");
        var u1 = db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0001");
        Console.WriteLine($"   板状态 {u1.Status}，当前工序 {u1.CurrentStepNo}，工单完成 {Wo(db, "WO-TRK-001")}");

        // 2、3. 漏站、重复
        NewUnit(db, "TRK-0002", "WO-TRK-001", Seed.Product);
        Console.WriteLine($"2. 漏站：TRK-0002 还没印刷就想进 MOUNT -> {Pass(db, "TRK-0002", "MOUNT", steps)}");
        Pass(db, "TRK-0002", "PRINT", steps);
        Console.WriteLine($"3. 重复过站：TRK-0002 印刷已出站，再进 PRINT -> {Pass(db, "TRK-0002", "PRINT", steps)}");

        // 4. 不良不得进下一站，返修放行后回到出错那一站
        Console.WriteLine("4. 不良品不得进下一站：");
        Console.WriteLine($"   TRK-0002 在 SPI 判 Fail -> {Pass(db, "TRK-0002", "SPI", steps, "Fail")}");
        Console.WriteLine($"   状态 {db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0002").Status}；想进 MOUNT -> {Pass(db, "TRK-0002", "MOUNT", steps)}");
        Console.WriteLine($"   想重做 SPI -> {Pass(db, "TRK-0002", "SPI", steps)}");
        int rel = db.Updateable<Unit>().SetColumns(x => new Unit { Status = "InProcess" }).Where(x => x.SerialNo == "TRK-0002" && x.Status == "Hold").ExecuteCommand();
        Console.WriteLine($"   返修放行（Hold -> InProcess，受影响 {rel} 行），板仍停在序号 {db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0002").CurrentStepNo}");
        foreach (var code in new[] { "SPI", "MOUNT", "REFLOW", "AOI" })
            Console.WriteLine($"   {code,-7} {Pass(db, "TRK-0002", code, steps)}");
        Console.WriteLine($"   履历：{History(db, "TRK-0002")}");
        Console.WriteLine($"   工单完成 {Wo(db, "WO-TRK-001")}");

        // 5. 双面板（路线只在内存里构造；产品 PCBA-A200）
        var twoSided = new List<(int No, string Code)> { (10, "PRINT"), (20, "SPI"), (30, "MOUNT"), (40, "REFLOW"), (50, "PRINT"), (60, "SPI"), (70, "MOUNT"), (80, "REFLOW"), (90, "AOI") }
            .Select(x => new RouteStep { StepNo = x.No, StepCode = x.Code, StepName = x.Code }).ToList();
        NewUnit(db, "TRK-0003", "WO-TRK-002", "PCBA-A200");
        Console.WriteLine("5. 双面板：TRK-0003（产品 PCBA-A200，9 道工序，工序码重复出现）");
        foreach (var s in twoSided.Take(3)) Pass(db, "TRK-0003", s.StepCode, twoSided);
        Console.WriteLine($"   A 面只做到贴片(30)，想进 PRINT -> {Pass(db, "TRK-0003", "PRINT", twoSided)}");
        Pass(db, "TRK-0003", "REFLOW", twoSided);
        Console.WriteLine($"   A 面回流(40)后进 PRINT -> {Pass(db, "TRK-0003", "PRINT", twoSided)}");
        foreach (var s in twoSided.Skip(5)) Pass(db, "TRK-0003", s.StepCode, twoSided);
        var recs = db.Queryable<TrackRecord>().Where(r => r.SerialNo == "TRK-0003").OrderBy(r => r.Id).ToList();
        Console.WriteLine($"   履历：{string.Join(" ", recs.Select(r => $"{r.StepCode}({r.StepNo})"))}");
        var u3 = db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0003");
        Console.WriteLine($"   板状态 {u3.Status}，工单 WO-TRK-002 完成 {Wo(db, "WO-TRK-002")}");

        // 6. 并发：两个终端同时对同一块板做 PRINT
        NewUnit(db, "TRK-0004", "WO-TRK-001", Seed.Product);
        var barrier = new Barrier(2);
        var results = new bool[2];
        var threads = Enumerable.Range(0, 2).Select(i => new Thread(() =>
        {
            var d = Db.Create();
            var (ok, _, u, step) = Enter(d, "TRK-0004", "PRINT", steps);      // 两个终端都通过了进站检查
            barrier.SignalAndWait();                                           // 等对方也检查完，再一起出站
            results[i] = ok && Exit(d, u, step, false, "Pass", DateTime.Now).Ok;
        })).ToList();
        threads.ForEach(t => t.Start()); threads.ForEach(t => t.Join());
        var u4 = db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0004");
        Console.WriteLine($"6. 并发：两个终端同时对 TRK-0004 做 PRINT -> 成功 {results.Count(r => r)} 个，被拒绝 {results.Count(r => !r)} 个");
        Console.WriteLine($"   TRK-0004 的过站记录 {db.Queryable<TrackRecord>().Count(r => r.SerialNo == "TRK-0004")} 条，当前工序 {u4.CurrentStepNo}");

        // 7. 事务：工单已完成 2/2，再有一块板走完末站，应该整笔回滚
        NewUnit(db, "TRK-0005", "WO-TRK-001", Seed.Product, 40);
        Console.WriteLine($"7. 事务：TRK-0005 已走到序号 40，工单 WO-TRK-001 已完成 {Wo(db, "WO-TRK-001")}，再过 AOI -> {Pass(db, "TRK-0005", "AOI", steps)}");
        var u5 = db.Queryable<Unit>().First(x => x.SerialNo == "TRK-0005");
        Console.WriteLine($"   回滚后：板状态 {u5.Status}，当前工序 {u5.CurrentStepNo}，AOI 过站记录 {db.Queryable<TrackRecord>().Count(r => r.SerialNo == "TRK-0005")} 条，工单完成 {Wo(db, "WO-TRK-001")}");
    }
}

  • 场景 1：TRK-0001 按路线顺序过完 5 站，每站"进站通过 → 出站 Pass"；末站出站后状态变 Completed，工单完成数从 0 变 1；
  • 场景 2、3：漏站和重复被 CanEnter 拦住，提示和 工艺路线与工序 实验里的完全一致，因为用的是同一套判断；
  • 场景 4：SPI 出站 Fail，板被锁定。此时想进 MOUNT 或重做 SPI 都被拒绝（"不良品已锁定"）。返修放行让状态回到 InProcess，序号仍是 10，所以下一道依然是 SPI；重做 SPI Pass 之后一路走到末站。履历里 SPI 出现了两次（先 Fail 后 Pass），工单完成数变成 2/2；
  • 场景 5（双面板）：A 面只做到贴片（序号 30）想进 PRINT，被拒绝并提示"下一道应该是 REFLOW"；回流（40）之后再进 PRINT，允许，因为下一道正好是 B 面印刷（序号 50）。整个履历里 PRINT、SPI、MOUNT、REFLOW 各出现两次，但序号各不相同。双面板的路线是在内存里构造的，产品 PCBA-A200 和它的工单 WO-TRK-002 也只是实验用的临时数据；
  • 场景 6（并发）：两个独立连接的终端都通过了进站检查（用 Barrier 让它们等对方检查完再一起出站），然后同时出站；条件 UPDATE 让其中一个得到 1 行，另一个得到 0 行，所以成功 1 个、被拒绝 1 个，TrackRecord 里只有 1 条记录，位置只往前走了一步；
  • 场景 7（事务）：工单已完成 2/2，TRK-0005 假设已走到序号 40（实验里直接插入一行来模拟），再过 AOI。条件 UPDATE WorkOrder 因为会超过计划数而得到 0 行，整笔回滚：板状态仍是 InProcess、序号仍是 40、没有 AOI 的过站记录、工单完成数仍是 2/2。三件事要么全做要么全不做。

常见坑与排查 ​

误区 / 坑事实与办法
先查位置再更新位置并发时两个终端都通过检查。把 CurrentStepNo、Status 写进 UPDATE 的 WHERE，看受影响行数
出站不开事务板子推进了但记录或工单完成数没写，数据对不上。三步放同一个事务
TrackRecord 被修改/删除履历不可信。程序不写 UPDATE/DELETE，数据库加触发器或权限，更正走"追加"
用工序码记录进度双面板分不清第几遍。记序号
Fail 之后也推进序号不良板被当成合格继续。Fail 只改状态，不推进序号
返修放行用特殊"回退"逻辑容易出错。让 Fail 的站不算完成，放行后下一道自然就是它
拒绝时只说"失败"操作员不知道怎么处理。每个拒绝都带明确原因（跳站、重复、锁定、工单状态）
进站检查只在前端做设备自动上报、接口调用会绕过。检查和条件 UPDATE 都在服务端/数据库
读"当前生效的路线"而不是工单绑定的版本改版后在线的板规则变了。出站读 WorkOrder.RouteId 对应的那一版
板码列 varchar / nvarchar 混用连表可能隐式转换影响索引。全库统一
以为"人少不会并发"设备自动上报、扫码枪重复触发、多终端，并发比想象的多
工单热点行高并发时完成数累加互相排队，考虑改为汇总计算

练习题与答案 ​

  1. 进站和出站分别做什么？ 答：进站检查"这块板现在能不能做这道工序"；出站登记"做完了，结果是 Pass 还是 Fail"，并让板推进（Pass）或锁定（Fail）。
  2. Unit 和 TrackRecord 的区别？为什么说 TrackRecord 是"真相的来源"？ 答：Unit 是单据，记当前状态，会变；TrackRecord 是流水，只追加，记过去发生的每件事。Unit 可以由 TrackRecord 推算出来，反过来不行，所以 TrackRecord 是源头，Unit 是为了查询快。
  3. 为什么出站 Fail 时 CurrentStepNo 不推进？ 答：出错的那一站没有真正完成。不推进的话，返修放行后"下一道"自然还是它，板子重做这一站，不需要专门的"回退"逻辑；履历里 Fail 和后来的 Pass 都保留。
  4. 板的当前序号是 20，状态 InProcess，路线是 10/20/30/40/50，操作员想进序号 40 的 REFLOW，系统怎么判断？ 答：拒绝，原因是"跳站，下一道应该是 MOUNT（序号 30）"。
  5. 为什么出站要用 WHERE CurrentStepNo = @prev AND Status = N'InProcess' 的条件 UPDATE？ 答：进站检查和出站写入之间有空档，别的终端可能已经处理了这块板。把进站时看到的位置和状态写进 WHERE，数据库在写入的瞬间核对，不一致就得到 0 行，只有一个终端成功。
  6. 一次末站出站要改哪三个地方？为什么必须在一个事务里？ 答：Unit（位置和状态）、TrackRecord（追加记录）、WorkOrder（完成数加 1）。必须同成功同失败，否则会出现板子已完工但工单没计数、或有记录没有位置变化的不一致。
  7. 实验场景 7 中，工单已经 2/2，板 TRK-0005 过末站被拒绝，板的状态为什么没有变成 Completed？ 答：条件 UPDATE WorkOrder 因为会超过计划数得到 0 行，程序据此回滚整个事务，之前对 Unit 的修改和对 TrackRecord 的插入一起撤销。
  8. 双面板 A 面回流（40）做完，板翻面再进 PRINT 为什么允许？ 答：路线里"序号大于 40 的第一道"是序号 50 的 B 面印刷，工序码是 PRINT，匹配，所以允许。靠序号而不是工序码判断。
  9. 设备因为网络抖动把同一次出站发了两遍，第二遍应该怎么处理？ 答：条件 UPDATE 会得到 0 行，数据不会重复。对设备自动上报通常返回"已处理"（幂等），避免设备不停重试；对人工操作则提示"这块板已经出站"。
  10. 为什么 TrackRecord 要用触发器或权限保证"只追加"，光靠程序不写 UPDATE 够吗？ 答：不够。别的程序、脚本、手工 SQL 都能改库。数据库层的约束对所有访问方都生效，是最后一道保险。

小结 ​

  • 过站 = 进站（检查）+ 出站（登记）；Unit 记"现在在哪、什么状态"，TrackRecord 记"过去发生了什么"，只追加。
  • 板的进度记序号，状态机四个值：InProcess、Hold、Completed、Scrapped；Fail 只改状态不推进序号，返修放行后板子自然回到出错那一站。
  • 漏站、跳站、重复靠路线判断（CanEnter）拦；不良品靠 Hold 状态拦；双面板靠序号判断；并发靠条件 UPDATE 的受影响行数。
  • 一次出站的"推进位置 + 追加记录 + 累加工单完成数"放进一个事务，任一步失败整体回滚；顺序固定以免死锁。
  • 把规则放进数据库：CHECK 约束守住状态枚举，触发器或权限守住"只追加"。
  • 进站检查清单可以不断加项（设备、物料、首件、治具、参数、人员），后续词条会逐项补上。
