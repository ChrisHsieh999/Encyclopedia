生产看板与实时报表

AI 生成 · 待核对制造业务MES看板报表前端自研专题更新于 2026-10-21

⚠ 待核对：看板应该放哪些指标、给谁看、多久刷新，是通用做法加我的设计建议，没有逐条联网核实，你们现场的看板有哪些、数据口径（计划数怎么取、直通率怎么定义）、刷新频率、用什么前端技术，请对照你们的系统。SignalR 的传输方式（WebSockets / Server-Sent Events / Long Polling）和索引视图的限制已对照微软文档；SignalR 推送方案和 Element Plus 的用法我没有在本机跑，只在正文里描述思路，未给代码。其余查询、接口、页面代码和输出，是我在本机 SQL Server LocalDB 上实际运行得到的，页面用 headless Edge 实际打开验证过渲染。

本篇是 MES 系列第 19 篇。它不新增业务表，只在 Unit、TrackRecord、WorkOrder、Equipment 这些已有数据上做聚合查询，再通过一个 HTTP 接口给前端。读完你应该能：说出生产看板上有哪些指标、不同的人看什么；比较轮询、推送这些数据更新方式；理解实时查询、汇总表、索引视图各适合什么场景；写出按线体统计"计划/完成/达成率/直通率/在制品"的聚合查询；搭出一个最小的看板页面并验证它能正确显示。

一句话定义 ​

生产看板是把车间正在发生的事（做到哪了、做得对不对、设备在不在跑）实时、醒目地展示给现场和管理者的屏幕或页面；实时报表是同样的数据按需要查询、导出的形式。

先修知识 ​

  • 过站与工序流转：Unit（板的当前位置和状态）和 TrackRecord（过站记录）是看板的主要数据来源。
  • 设备管理与设备状态：Equipment（设备台账与当前状态），用来判断线体是运行还是故障。
  • OEE：设备综合效率，也是看板上常见的一个指标。
  • 工单管理：工单状态和计划数。
  • 会基本的 SQL 聚合（GROUP BY）；知道 HTML、JavaScript 请求接口是怎么回事（见 Vue）。

它解决什么问题 ​

看一个没有看板的车间：

  • 线长拿着一块白板，每小时去数一次产出，写在板上；到了交接班，写错的、漏写的、擦掉的都有。
  • 主管想知道"A 线今天能不能按时完成"，要打电话问线长，线长再去数。
  • 一台贴片机报警停了 20 分钟，只有站在旁边的人知道，隔壁线的线长、办公室的主管都不知道，更没人去催维修。
  • 管理层看的是第二天早上从 Excel 里汇总的"昨日报表"，发现问题时已经晚了一整天。
  • 品质异常（一批板在 AOI 连续判 Fail）要靠人汇报，没人汇报就没人知道。

生产看板要解决的核心只有一个：让对的人，在对的时间，看到对的数字，并且异常能自己"跳出来"，不用靠人去问、去数、去汇报。

核心概念 ​

看板上放什么：指标 ​

下面是电子厂 SMT/PCBA 车间看板上常见的指标。口径要写清楚，否则两个人对同一个数字有两种理解：

指标含义常见口径（本篇实验采用）数据来源
计划数这条线本班/今天要做多少Running 工单的计划数之和WorkOrder.PlanQty
实际/完成数已经做完（末站合格）多少状态 Completed 的板数Unit
达成率完成/计划完成数 ÷ 计划数上两项
直通率 FPY一次就合格的比例有过站记录的板里，一次都没 Fail 过的占比TrackRecord
线体状态运行/待机/故障有设备 Down 就是故障，否则有设备 Run 就是运行，否则待机Equipment.Status
在制品 WIP在线上还没做完的板Unit 状态为 InProcess，按"已完成的工序"分布Unit
锁定数被锁住待处理的板Unit 状态为 HoldUnit
报警需要立刻关注的事故障设备台数（也可以是锁定板数、超时未处理的异常）Equipment、Unit
交期风险是否可能做不完达成率落后"时间进度"10 个百分点以上算风险（实验里的简化规则）达成率与班次进度

另外常见但本篇没做的：OEE（见 OEE）、各工序节拍、不良 Top N、物料短缺预警、各工序在制品停留时间（超过阈值标红）。

几个口径的坑，写代码前必须先问清：

  • 直通率 FPY 有"整线一次通过率"和"每个工序一次通过率的连乘（RTY）"两种常见说法，数字差很多；
  • "完成"以哪里为准：末站出站合格？入库？还是报工？不同口径差一个班次；
  • 在制品是否包含锁定板：本篇把 Hold 单独列，不算进在制品；
  • 计划数：一条线同时跑多张工单怎么加总；一张工单跨线怎么拆；

不同的人看什么 ​

看板不是"一块屏给所有人"。不同角色关心的东西、需要的刷新速度、愿意看的详细程度都不一样：

受众关心什么粒度刷新展示形式
线长/班组长（线边大屏）这条线现在做到哪，哪里堵，设备有没有报警，今天能不能做完单条线、到工序、到设备几秒到十几秒大屏，大数字，红黄绿，远看一眼就懂
主管/车间经理（办公室或会议室）各条线对比，谁落后，异常在哪，锁定多少多条线的汇总十几秒到几分钟多卡片、对比图表，可点开下钻
管理层/厂长整体达成、良率趋势、OEE、交期风险厂级、日/周/月趋势几分钟到小时，可以是定时报表趋势图、少量关键数字，能在手机上看
品质/工艺不良分布、异常批次工序、缺陷类型、批次按需查询报表、可导出
设备/维修哪台设备在停、停多久、什么原因设备级实时列表、告警推送

一条设计原则：越靠近现场，数据越实时、粒度越细、信息越少越大；越往上，越汇总、越看趋势。

数据怎么更新到屏幕上 ​

浏览器上的看板要拿到新数据，常见几种方式：

方式原理优点缺点适合
轮询（Polling）页面每隔 N 秒向服务器发一次请求最简单，什么服务器都能用，出错易排查有延迟（最多 N 秒）；没有变化也要请求，浪费大多数看板，刷新 5–30 秒就够
长轮询（Long Polling）请求挂着，有新数据才返回，返回后立刻再发延迟小，兼容性好服务器要为每个客户端挂住一个连接老浏览器、受限网络的兜底
Server-Sent Events（SSE）服务器通过一个长连接单向持续推送比 WebSocket 简单，自动重连只能服务器到浏览器单向只看不操作的看板
WebSocket浏览器与服务器建立双向长连接延迟最小，双向要处理断线重连、心跳、网关/代理支持对实时性要求高（秒级以内）
SignalR（.NET）微软的封装，自动选择最好的传输方式连接管理、分组推送都帮你做了要引入 ASP.NET Core 的这套东西C# 技术栈里需要推送时的首选

据微软文档，SignalR 按优雅降级的顺序支持 WebSockets、Server-Sent Events、Long Polling 三种传输，自动选择客户端和服务器都支持的最佳方式，WebSockets 是首选（一般性能最好）；它也能向所有或指定分组的客户端发消息；文档把"仪表盘和监控应用"列为典型场景。这对看板很贴切：可以按线体建分组，只给看那条线的屏幕推送那条线的变化。

选择建议：先用轮询。看板数字几秒钟延迟完全不影响决策；轮询出了问题好排查（浏览器开发者工具里一目了然）。只有当出现"几百块屏幕同时轮询压垮服务器"，或者"报警必须秒级推到手机"时，再引入推送。不要一上来就搞 WebSocket，复杂度是真实的。（本篇实验用的就是 5 秒轮询。）

性能：别让每个看板都去扫大表 ​

看板是读多、反复读同一份数据的典型场景：一个车间有 10 块屏幕，每 5 秒各刷一次，每秒就是 2 次查询，一天 17 万次。如果每次都去扫上千万行的 TrackRecord，数据库很快被拖垮。三种办法：

办法做法优点缺点
实时查询每次请求直接聚合明细表数据永远最新，没有额外结构窗口越大越慢；每块屏幕重复算
汇总表（预聚合）定时（或随写入）把明细按"工站 × 小时"之类汇总到一张小表，看板读小表读非常快，与明细量无关要维护汇总逻辑；有延迟；口径要和明细对得上
索引视图（SQL Server 的物化视图）给视图建唯一聚集索引，数据库自动维护自动、一致限制多：要 WITH SCHEMABINDING、有 GROUP BY 必须带 COUNT_BIG(*)、不能有外连接/子查询/MIN/MAX、SUM 可空表达式要用 ISNULL 等；增删改明细时要连带更新视图，写入变慢

据微软文档，索引视图在被引用的表上做增删改时，视图也必须更新，所以写入频繁的表（像 TrackRecord）要谨慎，需要先测试。多数 MES 项目采用的是汇总表加定时任务（比如每分钟把最近一小时刷新一次），简单可控。

我在本机 LocalDB 里做了一个对比实验：造了 100 万行的过站记录（5 个工站，约 46 天），分别用"实时聚合明细表"和"读按工站×小时的汇总表"查同样的结果，用 SET STATISTICS IO ON 看逻辑读：

查询范围实时查明细（逻辑读）读汇总表（逻辑读）
一个班次（8 小时）各工站产出和良品4331
一个月各工站产出365231

两点结论：(1) 窗口小（一个班次）并且 OutAt 上有合适的覆盖索引时，实时查询也足够快，汇总表几乎没有收益；(2) 窗口一大（一个月），实时查询的读量随数据量线性增长，汇总表保持不变，差了 100 多倍。所以"当班实时"可以直接查明细，"本周/本月/趋势"要用汇总表。 脚本在实验后面，你可以自己在 LocalDB 的临时库里跑（完成后会删除自己建的表）。

大屏的展示设计原则 ​

现场大屏不是"网页缩小放大"，它有自己的规则：

原则做法原因
远看一眼就懂关键数字用超大字号（几十像素以上），一块屏只放最重要的 5–8 个指标线长站在 3–5 米外看
颜色只表示状态绿＝正常、黄＝注意、红＝异常，不要用装饰性的红绿；同时配上文字（如"故障"）而不是只靠颜色红绿色盲约占男性的一小部分；背景光线复杂
深色背景车间屏幕常用深色背景加亮色字不刺眼，远处字更醒目，也不容易有"满屏白光"
异常自己跳出来故障、落后、超时用红色加粗，必要时闪烁、提示音；正常的信息保持安静看板的价值是"发现问题"，不是"展示漂亮"
显示数据时间页面上始终显示"数据更新时间"断线、卡死时，人能立刻发现数据不是最新的
断线要提示请求失败时显示明显的"连接中断"提示，不要保持旧数据装作没事比数据延迟更危险的是"以为是实时的其实早就停了"
刷新要克制每 5–30 秒轮询一次；屏幕内容不要整页闪烁重绘，只更新变化的部分减少服务器压力，也避免晃眼
一屏一个主题想看更多就轮播或分屏，不要把所有东西挤在一屏信息过多等于没有信息
不要依赖鼠标大屏通常没有人操作，所有信息要自动展示；需要钻取的放在办公室的版本里现场没人点鼠标
可适应分辨率用相对单位，适配 1080p 和 4K，测试手机/平板（管理层）屏幕五花八门

业务视角 ​

谁在什么环节做什么：

角色动作
线长开班前确认看板上的计划数；班中盯在制品分布，哪里堆板去哪里；红灯立刻处理或叫人
设备/维修看设备故障报警，响应
主管每小时看各线达成率，落后的线增派人手或调整
管理层每天看日报/周报；看交期风险，决定加班或延期
系统管理员（IT）维护看板配置（哪条线、哪块屏、刷新周期）、数据口径、权限

流程： 现场操作和设备数据（过站、状态变化）自动写入 MES → 看板定期取数 → 展示 → 异常触发处理 → 处理结果（返修放行、设备恢复）回到 MES → 看板数字变化。看板本身只读，不改数据。

KPI： 看板本身的 KPI 是"异常响应时间"——从异常出现到有人处理的分钟数。看板的价值在这里。

技术视角 ​

整体结构 ​

 现场（扫码、设备）→ MES 数据库 ──→ 聚合查询（SQL）──→ HTTP 接口（JSON）──→ 浏览器页面（Vue）
                      Unit / TrackRecord        BoardQuery.Build         GET /api/board       每 5 秒轮询
                      WorkOrder / Equipment      (必要时读汇总表)
  • 聚合在数据库里做，不要把明细拉到应用里再算；
  • 接口只返回看板需要的现成数字，页面不做业务计算（口径统一在一处）；
  • 看板用只读账号；数据量大时指向只读副本，避免影响产线写入。

工单属于哪条线？一个设计取舍 ​

迷你模型里的 WorkOrder 没有线体字段，但看板要"按线体"汇总计划数。本篇的做法是：工单所在线体 = 该工单的过站记录经过的工站对应的线体（过站记录里有工站，设备台账里有工站所在线体）：

sql
WITH lw AS (
    SELECT w.WoNo, w.PlanQty, x.LineCode
    FROM WorkOrder w
    JOIN (SELECT DISTINCT r.WoId, e.LineCode FROM TrackRecord r JOIN Equipment e ON e.EquipCode = r.StationCode) x ON x.WoId = w.WoNo
    WHERE w.Status = N'Running')

这个公共表表达式（CTE，见 SQL子查询与CTE）后面被几个查询复用。局限：还没有过站记录的工单（刚下发）不会出现；一张工单跨两条线会被算两次。真实系统应该在工单或排产表上直接记录线体（见 APS），本篇只是在没有该字段的迷你模型里的权宜之计。

聚合查询：每个指标一条 ​

指标查询要点
计划数上面的 CTE，SUM(PlanQty) GROUP BY LineCode
完成数、在制品分布、锁定数Unit 连 CTE，GROUP BY LineCode, Status, CurrentStepNo，一条查询得到三个指标
直通率TrackRecord 连 CTE，COUNT(DISTINCT SerialNo) 与 COUNT(DISTINCT CASE WHEN Result = N'Fail' THEN SerialNo END)
线体状态、故障设备数Equipment 按 LineCode, Status 分组计数（SqlSugar 的 GroupBy 写法）
交期风险达成率与"时间进度"（当前时间在班次中的位置）比较，纯计算

一块看板只显示配置给它的线体（实验里是 LINE-A、LINE-B，函数的 show 参数）：数据库里别的线（比如别的实验造的数据）不会出现在这块屏上，真实系统里就是"这块屏对应哪几条线"的配置。

每个指标一条小查询，在 C# 里拼成一个对象，比写一条巨大的多表 JOIN 更容易验证和维护；每条查询都应该有对应的索引（Unit(WoId)、TrackRecord(WoId, StepNo)，见 MES核心数据模型）。

接口与页面 ​

接口返回的 JSON 形如（实验输出里就是它）：

{"asOf":"2026-10-21 14:00","lines":[{"line":"LINE-A","status":"运行","plan":20,"done":12,"rate":0.6,...}]}

页面用 Vue 3：ref 保存数据，fetch 请求接口，setInterval 每 5 秒刷新（见 Vue响应式、Vue组合式API）。企业里做管理后台版的看板，常用 Element-Plus 的卡片、表格、进度条组件，用法与本篇页面里手写的 div 卡片是同一个思路——数据来自同一个接口，只是外观组件不同。本篇没有运行 Element Plus 版本，实验页面是用 Vue 3 的 CDN 版（vue.global.prod.min.js）写的，不需要 npm，页面里的 是 Vue 的模板插值。

逐步例子：A 线和 B 线的看板数字怎么来的 ​

班次 08:00–18:00，"现在" 14:00，时间进度 = 6 ÷ 10 = 60%。

A 线（工单 WO-BRD-A，计划 20 块）共 20 块板：

状态数量说明
Completed12其中 1 块（A12）线尾 AOI 先判 Fail、返修后重过 Pass
InProcess6序号 10（印刷后）3 块、30（贴片后）2 块、40（回流后）1 块
Hold2在 SPI 判 Fail 被锁定
  • 计划 20，完成 12，达成率 = 12 ÷ 20 = 60%；
  • 直通率：20 块板都有过站记录；出现过 Fail 的有 A12（AOI 先 Fail）和 2 块 Hold，共 3 块；一次没 Fail 的 = 20 − 3 = 17；FPY = 17 ÷ 20 = 85%；
  • 在制品 6：PRINT 之后 3，MOUNT 之后 2，REFLOW 之后 1；锁定 2；
  • 设备：5 台里 4 台 Run、1 台 Idle，没有 Down → 线体状态运行，故障设备 0；
  • 风险：达成率 60% ≥ 时间进度 60% − 10% = 50%，正常。

B 线（工单 WO-BRD-B，计划 10 块；只投了 8 块）：

状态数量说明
Completed4
InProcess3序号 20（SPI 后）2 块、30（贴片后）1 块
Scrapped1在回流焊判 Fail 后报废
  • 计划 10，完成 4，达成率 40%；
  • 直通率：8 块有过站记录，1 块（报废的）有 Fail → 7 ÷ 8 = 87.5%；
  • 在制品 3，锁定 0；
  • 设备：贴片机 Down → 线体状态故障，故障设备 1 台；
  • 风险：40% < 60% − 10% = 50% → 风险。

注意 B 线的直通率（87.5%）比 A 线（85%）高，但它的达成率落后、设备还在故障：单看一个指标会被误导，这就是看板要同时展示多个指标的原因。

动手实验：聚合查询 + 最小看板页面 ​

前提：已经做完 设备管理与设备状态（项目里有 Equipment.cs）和 过站与工序流转（项目里有 Unit.cs）。练习库是 MiniMES_Lab。 实验分两部分：先在命令行里跑聚合查询（board），再启动一个本机小服务，用浏览器看（boardweb）。

第 1 步：新建 LabBoard.cs。它包含：两个只做展示用的 DTO（WipItem、BoardLine，不是数据库表）、聚合查询类 BoardQuery、造数据并打印看板的 LabBoard。造的数据：A 线 20 块板、B 线 8 块板，设备状态按"逐步例子"里设定（B 线贴片机故障）。

csharp
using System.Data;
using System.Globalization;
using System.Text.Encodings.Web;
using System.Text.Json;
using SqlSugar;

namespace MiniMes;

// 看板上一条线的数据（DTO，不是数据库表）
public class WipItem { public string After { get; set; } public int Qty { get; set; } }

public class BoardLine
{
    public string Line { get; set; }
    public string Status { get; set; }         // 运行 / 待机 / 故障
    public int Plan { get; set; }
    public int Done { get; set; }
    public double Rate { get; set; }           // 达成率 = 完成 / 计划
    public int FpyGood { get; set; }
    public int FpyAll { get; set; }
    public double Fpy { get; set; }            // 直通率 = 没出现过 Fail 的板 / 有过站记录的板
    public int Wip { get; set; }               // 在制品（InProcess）
    public int Hold { get; set; }              // 锁定待处理
    public int DownEquip { get; set; }         // 故障设备台数（报警）
    public bool AtRisk { get; set; }           // 达成率明显落后于时间进度
    public List<WipItem> WipDist { get; set; } = new();
}

public static class BoardQuery
{
    // 工单 -> 所在线体：工单的过站记录经过的工站，对应设备台账里的产线。只取 Running 的工单
    const string LineWo = @"
WITH lw AS (
    SELECT w.WoNo, w.PlanQty, x.LineCode
    FROM WorkOrder w
    JOIN (SELECT DISTINCT r.WoId, e.LineCode FROM TrackRecord r JOIN Equipment e ON e.EquipCode = r.StationCode) x ON x.WoId = w.WoNo
    WHERE w.Status = N'Running')
";

    public static List<BoardLine> Build(SqlSugarClient db, string[] show, DateTime now, DateTime shiftStart, DateTime shiftEnd)   // show：这块看板配置要显示哪些线
    {
        var route = db.Queryable<Route>().First(r => r.ProductCode == Seed.Product && r.Status == "Active");
        var steps = db.Queryable<RouteStep>().Where(s => s.RouteId == route.RouteId).ToList().ToDictionary(s => s.StepNo, s => s.StepCode);
        var lines = new Dictionary<string, BoardLine>();
        BoardLine L(string code) { if (!lines.TryGetValue(code, out var b)) lines[code] = b = new BoardLine { Line = code }; return b; }

        // 计划数：按线体汇总 Running 工单的计划数
        foreach (DataRow r in db.Ado.GetDataTable(LineWo + "SELECT LineCode, SUM(PlanQty) AS Plan_ FROM lw GROUP BY LineCode").Rows)
            L((string)r["LineCode"]).Plan = Convert.ToInt32(r["Plan_"]);

        // 板的状态分布：完成数、在制品按工序分布、锁定数
        foreach (DataRow r in db.Ado.GetDataTable(LineWo + @"
SELECT lw.LineCode, u.Status, u.CurrentStepNo, COUNT(*) AS Cnt
FROM Unit u JOIN lw ON lw.WoNo = u.WoId
GROUP BY lw.LineCode, u.Status, u.CurrentStepNo ORDER BY lw.LineCode, u.CurrentStepNo").Rows)
        {
            var b = L((string)r["LineCode"]); int n = Convert.ToInt32(r["Cnt"]), step = Convert.ToInt32(r["CurrentStepNo"]);
            switch ((string)r["Status"])
            {
                case "Completed": b.Done += n; break;
                case "Hold": b.Hold += n; break;
                case "InProcess":
                    b.Wip += n;
                    b.WipDist.Add(new WipItem { After = step == 0 ? "未开始" : steps[step] + " 之后", Qty = n });
                    break;
            }
        }

        // 直通率：有过站记录的板里，一次都没 Fail 过的占比
        foreach (DataRow r in db.Ado.GetDataTable(LineWo + @"
SELECT lw.LineCode, COUNT(DISTINCT r.SerialNo) AS Boards,
       COUNT(DISTINCT CASE WHEN r.Result = N'Fail' THEN r.SerialNo END) AS FailBoards
FROM TrackRecord r JOIN lw ON lw.WoNo = r.WoId GROUP BY lw.LineCode").Rows)
        {
            var b = L((string)r["LineCode"]);
            b.FpyAll = Convert.ToInt32(r["Boards"]); b.FpyGood = b.FpyAll - Convert.ToInt32(r["FailBoards"]);
        }

        // 线体状态与报警：看设备台账里的当前状态（SqlSugar 写法）
        var equip = db.Queryable<Equipment>().GroupBy(e => new { e.LineCode, e.Status })
            .Select(e => new { e.LineCode, e.Status, Cnt = SqlFunc.AggregateCount(e.Id) }).ToList();
        double progress = (now - shiftStart).TotalMinutes / (shiftEnd - shiftStart).TotalMinutes;
        foreach (var b in lines.Values)
        {
            var mine = equip.Where(e => e.LineCode == b.Line).ToList();
            b.DownEquip = mine.Where(e => e.Status == "Down").Sum(e => e.Cnt);
            b.Status = b.DownEquip > 0 ? "故障" : mine.Any(e => e.Status == "Run") ? "运行" : "待机";
            b.Rate = b.Plan == 0 ? 0 : (double)b.Done / b.Plan;
            b.Fpy = b.FpyAll == 0 ? 1 : (double)b.FpyGood / b.FpyAll;
            b.AtRisk = b.Rate < progress - 0.1;          // 落后时间进度 10 个百分点以上算风险
        }
        return lines.Values.Where(b => show.Contains(b.Line)).OrderBy(b => b.Line).ToList();
    }
}

// 看板实验：造两条线的数据，跑聚合查询，打印看板，并输出接口返回的 JSON
public static class LabBoard
{
    public static readonly string[] Lines = { "LINE-A", "LINE-B" };            // 这块看板显示的线体（数据库里别的线不显示）
    public static readonly DateTime Now = new(2026, 10, 21, 14, 0, 0);          // 演示用的"现在"
    public static readonly DateTime ShiftStart = new(2026, 10, 21, 8, 0, 0);
    public static readonly DateTime ShiftEnd = new(2026, 10, 21, 18, 0, 0);
    static readonly Dictionary<int, string> Suffix = new() { [10] = "PRN", [20] = "SPI", [30] = "MNT", [40] = "RFL", [50] = "AOI" };
    static readonly Dictionary<int, string> Code = new() { [10] = "PRINT", [20] = "SPI", [30] = "MOUNT", [40] = "REFLOW", [50] = "AOI" };
    static int minute;

    static void Add(SqlSugarClient db, List<TrackRecord> recs, string letter, string wo, string sn, string status, int step, string extra = null)
    {
        db.Insertable(new Unit { SerialNo = sn, WoId = wo, ProductCode = Seed.Product, CurrentStepNo = step, Status = status, CreatedAt = ShiftStart }).ExecuteCommand();
        void Rec(int s, string result)
        {
            var t = ShiftStart.AddMinutes(minute++);
            recs.Add(new TrackRecord { SerialNo = sn, WoId = wo, StepNo = s, StepCode = Code[s], Result = result, StationCode = $"BRD-{letter}-{Suffix[s]}", OperatorCode = "OP001", InAt = t.AddSeconds(-30), OutAt = t });
        }
        for (int s = 10; s <= step; s += 10)
        {
            if (extra == "RETRY_AOI" && s == 50) Rec(s, "Fail");      // 线尾 AOI 先判了一次 Fail，返修后重过
            Rec(s, "Pass");
        }
        if (extra == "FAIL_NEXT") Rec(step + 10, "Fail");               // 下一站判 Fail：板被锁定或报废
    }

    public static void Run(SqlSugarClient db)
    {
        CultureInfo.DefaultThreadCurrentCulture = CultureInfo.InvariantCulture;
        CultureInfo.CurrentCulture = CultureInfo.InvariantCulture;
        Seed.Basics(db);
        db.CodeFirst.InitTables(typeof(Equipment), typeof(Unit), typeof(TrackRecord));
        db.Deleteable<TrackRecord>().Where(r => r.SerialNo.StartsWith("BRD-")).ExecuteCommand();
        db.Deleteable<Unit>().Where(u => u.SerialNo.StartsWith("BRD-")).ExecuteCommand();
        db.Deleteable<WorkOrder>().Where(w => w.WoNo.StartsWith("WO-BRD-")).ExecuteCommand();
        db.Deleteable<Equipment>().Where(e => e.EquipCode.StartsWith("BRD-")).ExecuteCommand();
        minute = 0;

        // 工单：A 线 20 块，B 线 10 块；C 单只是已下发还没开始，不该出现在看板上
        foreach (var (no, plan, st) in new[] { ("WO-BRD-A", 20, "Running"), ("WO-BRD-B", 10, "Running"), ("WO-BRD-C", 50, "Released") })
            db.Insertable(new WorkOrder { WoNo = no, ProductCode = Seed.Product, PlanQty = plan, Status = st, CreatedAt = ShiftStart }).ExecuteCommand();

        // 设备：每条线 5 台。B 线的贴片机故障
        var status = new Dictionary<string, string> { ["BRD-A-AOI"] = "Idle", ["BRD-B-SPI"] = "Idle", ["BRD-B-MNT"] = "Down" };
        var equips = new List<Equipment>();
        foreach (var letter in new[] { "A", "B" })
            foreach (var suffix in Suffix.Values)
                equips.Add(new Equipment { EquipCode = $"BRD-{letter}-{suffix}", EquipName = $"{letter} 线 {suffix}", LineCode = $"LINE-{letter}", EquipType = suffix, Status = status.GetValueOrDefault($"BRD-{letter}-{suffix}", "Run") });
        db.Insertable(equips).ExecuteCommand();

        // 板：A 线 20 块，B 线 8 块（另外 2 块还没投）
        var recs = new List<TrackRecord>();
        for (int i = 1; i <= 11; i++) Add(db, recs, "A", "WO-BRD-A", $"BRD-A{i:00}", "Completed", 50);
        Add(db, recs, "A", "WO-BRD-A", "BRD-A12", "Completed", 50, "RETRY_AOI");
        for (int i = 13; i <= 15; i++) Add(db, recs, "A", "WO-BRD-A", $"BRD-A{i}", "InProcess", 10);
        for (int i = 16; i <= 17; i++) Add(db, recs, "A", "WO-BRD-A", $"BRD-A{i}", "InProcess", 30);
        Add(db, recs, "A", "WO-BRD-A", "BRD-A18", "InProcess", 40);
        for (int i = 19; i <= 20; i++) Add(db, recs, "A", "WO-BRD-A", $"BRD-A{i}", "Hold", 10, "FAIL_NEXT");
        for (int i = 1; i <= 4; i++) Add(db, recs, "B", "WO-BRD-B", $"BRD-B0{i}", "Completed", 50);
        for (int i = 5; i <= 6; i++) Add(db, recs, "B", "WO-BRD-B", $"BRD-B0{i}", "InProcess", 20);
        Add(db, recs, "B", "WO-BRD-B", "BRD-B07", "InProcess", 30);
        Add(db, recs, "B", "WO-BRD-B", "BRD-B08", "Scrapped", 20, "FAIL_NEXT");
        db.Insertable(recs).ExecuteCommand();

        var board = BoardQuery.Build(db, Lines, Now, ShiftStart, ShiftEnd);
        double progress = (Now - ShiftStart).TotalMinutes / (ShiftEnd - ShiftStart).TotalMinutes;
        Console.WriteLine($"看板时间 {Now:yyyy-MM-dd HH:mm}，班次 {ShiftStart:HH:mm}-{ShiftEnd:HH:mm}，时间进度 {progress * 100:F0}%");
        foreach (var b in board)
        {
            Console.WriteLine($"{b.Line}  状态 {b.Status}  计划 {b.Plan}  完成 {b.Done}  达成率 {b.Rate * 100:F1}%  直通率 {b.Fpy * 100:F1}% ({b.FpyGood}/{b.FpyAll})  故障设备 {b.DownEquip} 台  交期 {(b.AtRisk ? "风险" : "正常")}");
            Console.WriteLine($"   在制品 {b.Wip}（{string.Join("，", b.WipDist.Select(w => $"{w.After} {w.Qty}"))}），锁定 {b.Hold}");
        }
        var json = JsonSerializer.Serialize(board, new JsonSerializerOptions { PropertyNamingPolicy = JsonNamingPolicy.CamelCase, Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping });
        Console.WriteLine("接口返回：" + json);
    }
}

第 8 步（选做）：实时查询 vs 汇总表的对比实验。下面的 T-SQL 在一个临时库里建两张临时表（造 100 万行），比较两种查询的逻辑读，结束时会删除自己建的表。在 LocalDB 里建个临时库（例如 Lab_board），sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -f 65001 -d Lab_board -I -i agg.sql 运行（-I 表示使用带引号的标识符设置，建索引相关语句常需要，加上没有坏处）。不要在 MiniMES_Lab 里跑，更不要碰默认实例。

sql
SET NOCOUNT ON;
CREATE TABLE TrackLab (
    Id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    SerialNo nvarchar(40) NOT NULL,
    StationCode nvarchar(30) NOT NULL,
    Result nvarchar(10) NOT NULL,
    OutAt datetime NOT NULL);
-- 100 万行：5 个工站，每个工站每分钟约 3 块，连续约 66 天
INSERT INTO TrackLab (SerialNo, StationCode, Result, OutAt)
SELECT TOP 1000000
       N'SN' + CAST(n AS nvarchar(12)),
       CHOOSE(n % 5 + 1, N'PRN-01', N'SPI-01', N'SMT-01', N'RFL-01', N'AOI-01'),
       CASE WHEN n % 20 = 0 THEN N'Fail' ELSE N'Pass' END,
       DATEADD(SECOND, (n / 5) * 20, '2026-08-01')
FROM (SELECT ROW_NUMBER() OVER (ORDER BY (SELECT 1)) AS n FROM sys.all_objects a CROSS JOIN sys.all_objects b CROSS JOIN sys.all_objects c) t;
CREATE INDEX IX_TrackLab_OutAt ON TrackLab(OutAt) INCLUDE (StationCode, Result);
SELECT COUNT(*) AS Total, MIN(OutAt) AS MinAt, MAX(OutAt) AS MaxAt FROM TrackLab;
GO
-- 预聚合：按 工站 x 小时 汇总
SELECT StationCode, DATEADD(HOUR, DATEDIFF(HOUR, 0, OutAt), 0) AS HourStart,
       COUNT(*) AS Total, SUM(CASE WHEN Result = N'Pass' THEN 1 ELSE 0 END) AS Good
INTO TrackHour FROM TrackLab GROUP BY StationCode, DATEADD(HOUR, DATEDIFF(HOUR, 0, OutAt), 0);
CREATE UNIQUE CLUSTERED INDEX UX_TrackHour ON TrackHour(StationCode, HourStart);
GO
SET STATISTICS IO ON;
PRINT '--- 实时查询：一个班次（8 小时）各工站产出和良品';
SELECT StationCode, COUNT(*) AS Total, SUM(CASE WHEN Result = N'Pass' THEN 1 ELSE 0 END) AS Good
FROM TrackLab WHERE OutAt >= '2026-09-10 08:00' AND OutAt < '2026-09-10 16:00' GROUP BY StationCode ORDER BY StationCode;
PRINT '--- 汇总表查询：同一个班次';
SELECT StationCode, SUM(Total) AS Total, SUM(Good) AS Good
FROM TrackHour WHERE HourStart >= '2026-09-10 08:00' AND HourStart < '2026-09-10 16:00' GROUP BY StationCode ORDER BY StationCode;
PRINT '--- 实时查询：整个月';
SELECT StationCode, COUNT(*) AS Total FROM TrackLab WHERE OutAt >= '2026-08-01' AND OutAt < '2026-09-01' GROUP BY StationCode ORDER BY StationCode;
PRINT '--- 汇总表查询：整个月';
SELECT StationCode, SUM(Total) AS Total FROM TrackHour WHERE HourStart >= '2026-08-01' AND HourStart < '2026-09-01' GROUP BY StationCode ORDER BY StationCode;
SET STATISTICS IO OFF;
SELECT (SELECT COUNT(*) FROM TrackHour) AS HourRows;
GO
DROP TABLE TrackHour; DROP TABLE TrackLab;

输出里 Table 'TrackLab' 和 Table 'TrackHour' 两行的 logical reads 就是上面表格里的数字（一个班次 43 和 31，一个月 3652 和 31；Worktable、Workfile 两行是排序/分组的中间表，读数为 0，可忽略）。我造数据的方式让"不良"全部落在 PRN-01 一个工站上，所以班次结果里只有 PRN-01 的良品数（1080）小于总数（1440），这只是造数据的副作用，不代表真实情况。

常见坑与排查 ​

误区 / 坑事实与办法
每块屏幕每次刷新都直接扫明细大表屏幕一多就拖垮数据库。小窗口建覆盖索引；大窗口用汇总表
一上来就用 WebSocket/SignalR复杂度高（断线、心跳、代理）。先用 5–30 秒轮询
页面断线仍显示旧数据现场以为是实时的。显示数据时间；请求失败要有明显提示
看板里自己算业务口径同一个"直通率"各屏幕不一样。口径只在服务端一处计算
看板上放太多指标没人看得清。一屏 5–8 个，异常才突出
只靠颜色表示状态色盲或光线差时看不出来。颜色加文字
把汇总表当作明细的"唯一真相"汇总逻辑有 bug 时数字就错。定期用明细对账（同一窗口两种算法比较）
汇总表没有处理迟到数据补录、乱序的记录没有计入。汇总任务要能"重算最近 N 小时"
工单没有线体字段，靠过站记录推断刚下发、没有过站的工单看不到。真实系统要在工单/排产里记录线体
按日期（天）分组算班次夜班跨午夜。班次要有明确的开始/结束时间
看板账号有写权限误操作或被攻击会改数据。用只读账号，或只读副本
大屏分辨率不适配字被截断或太小。用相对单位，在目标屏上实测
开发时用的假数据和生产差距大上线后才发现没有索引、查询很慢。用接近生产量级的数据压测

练习题与答案 ​

  1. 线长、主管、厂长三类人，看板各自应该看什么？刷新频率有什么区别？ 答：线长看单线、到工序和设备的细节，刷新几秒；主管看多线对比、异常，十几秒到几分钟；厂长看厂级汇总和趋势，几分钟到小时即可，可以做成日报。越靠近现场越实时、越细。
  2. 为什么说看板应该"异常自己跳出来"？ 答：看板的价值在于缩短从异常发生到有人响应的时间。正常的信息保持安静，异常用红色、加粗、声音等方式主动吸引注意，人才不会错过。
  3. 轮询和推送各有什么优缺点？什么情况下该从轮询换成推送？ 答：轮询简单、通用、易排查，但有最多一个周期的延迟，空请求有浪费；推送（SSE、WebSocket、SignalR）延迟小，但要处理断线重连等复杂度。当大量客户端轮询压垮服务器，或报警必须秒级送达时再换。
  4. 本篇的"达成率"和"直通率"各怎么定义？A 线数字为什么是 60% 和 85%？ 答：达成率 = 完成数 ÷ 计划数 = 12 ÷ 20 = 60%；直通率 = 没出现过 Fail 的板数 ÷ 有过站记录的板数 = 17 ÷ 20 = 85%（3 块出现过 Fail：A12 线尾先 Fail、2 块 Hold）。
  5. B 线的直通率比 A 线高，为什么它仍然标"风险"？ 答：风险是看达成率和时间进度的关系：B 线 40% 低于 60% − 10% = 50%。直通率只反映质量，不反映产出进度，两个指标回答不同的问题。
  6. 一个班次的查询用实时聚合就够了，一个月的趋势为什么要用汇总表？ 答：实时聚合的读量随窗口内的明细行数增长；一个班次的数据量小，有覆盖索引时很快；一个月的明细多，每次都扫太慢。汇总表按"工站 × 小时"预先汇总，读量与明细量无关。实验里一个月的逻辑读 3652 对 31。
  7. 索引视图（物化视图）的主要限制是什么？为什么对 TrackRecord 这种写入频繁的表要谨慎？ 答：要 WITH SCHEMABINDING；有 GROUP BY 必须带 COUNT_BIG(*)；不能有外连接、子查询、MIN/MAX 等。因为基表每次增删改，视图也要同步更新，写入频繁的表会被明显拖慢。
  8. 为什么接口里返回的是算好的数字，而不是让页面自己用明细计算？ 答：口径只在服务端一处，所有屏幕数字一致；明细不暴露给前端，也减少传输量。
  9. 看板的数据时间为什么要显示在页面上？ 答：让人一眼判断数据是否最新。如果服务挂了或断线，页面上的时间停在过去，人就知道别信这些数字。
  10. 迷你模型里 WorkOrder 没有线体字段，本篇怎么解决？有什么问题？ 答：用工单的过站记录经过的工站，到设备台账里找所在线体。问题是刚下发还没过站的工单看不到；跨线的工单会被重复计算。真实系统应该在工单或排产表里直接记录线体。

小结 ​

  • 看板的目的是让对的人在对的时间看到对的数字，并让异常自己跳出来；不同受众看不同粒度、不同刷新频率的内容。
  • 指标口径必须写清楚：计划数、完成、达成率、直通率、在制品、线体状态、交期风险，各有常见口径，也各有陷阱。
  • 数据更新先用轮询（5–30 秒），需要时再上 SSE/WebSocket/SignalR。
  • 性能上：当班实时可以直接查明细（有覆盖索引时），本周/本月/趋势用汇总表；索引视图有一堆限制，写入频繁的表要慎用。我实测一个月的聚合，实时查询逻辑读 3652，汇总表 31。
  • 技术上就是聚合查询加一个 JSON 接口加一个轮询页面；聚合放数据库里做，口径放服务端一处，看板用只读账号。
  • 大屏设计的要点：大字、深色、颜色加文字、显示数据时间、断线要提示、一屏一个主题。
