EF-Core

AI 生成 · 待核对dotNETORM数据库更新于 2026-10-21

本篇是 dotNET 数据访问部分的第 2 篇。读完你应该能：说清 EF Core 里 DbContext、DbSet、变更跟踪、迁移分别是什么；用它建表、增删改查、做事务和软删除；会用 dotnet ef 命令生成和应用迁移；并能和 SqlSugar、Dapper 比较、决定什么时候选谁。

一句话定义 ​

EF Core（Entity Framework Core）是微软官方的 ORM：你定义 C# 类和一个 DbContext，用 LINQ 查询，它负责生成 SQL、跟踪对象的修改，并用"迁移（Migration）"管理表结构的演进。

先修知识 ​

  • SqlSugar：先读它，理解"类 = 表、对象 = 行"的 ORM 思路；本篇会处处对照。
  • LINQ：EF Core 的查询语言就是 LINQ。
  • CSharp类与对象、CSharp集合与泛型。
  • SQL连接JOIN、事务与ACID。
  • NuGet：装包；依赖注入：Web 项目里 DbContext 是怎么被注入的（本篇用控制台，不涉及）。

它解决什么问题 ​

和所有 ORM 一样，它让你不用手写 SQL。EF Core 特别强的两点：

  1. 变更跟踪：你查出一个对象，改它的属性，调用 SaveChanges()，EF 自己找出哪些属性变了、只生成对应的 UPDATE。你不用手写"更新哪几列"。
  2. 迁移：表结构变更（加列、改长度）用 C# 代码文件记录下来，一条命令应用到数据库，也能生成 SQL 脚本交给 DBA。适合"代码和库结构要一起版本管理"的团队。

核心概念（由浅入深） ​

1. 三件套：实体、DbContext、DbSet ​

csharp
public class Employee { public int Id { get; set; } public string Name { get; set; } = ""; ... }   // 实体类 = 一张表的一行

public class LabContext : DbContext                      // DbContext = 一次"与数据库的会话" + 配置
{
    public DbSet<Employee> Employees => Set<Employee>(); // DbSet = 一张表的入口
    protected override void OnConfiguring(DbContextOptionsBuilder b) => b.UseSqlServer("连接字符串");
}
  • DbContext：相当于 SqlSugar 里的 db，但它轻量、生命周期短：一次业务操作（一个 Web 请求）用一个实例，用完释放。它不是线程安全的，不要在多线程里共享同一个。
  • DbSet<T>：相当于一张表。db.Employees.Where(...) 对应查这张表。

2. 约定优于配置 ​

EF 会按约定推断：属性叫 Id 或 类名Id → 主键；int 主键 → 自增；string → nvarchar(max)（默认就是 Unicode，没有 SqlSugar 里 varchar 把中文变问号的坑）；DeptId + 导航属性 Dept → 外键。约定不合适时，用 Fluent API 覆盖：

csharp
protected override void OnModelCreating(ModelBuilder mb)
{
    mb.Entity<Employee>().Property(e => e.Name).HasMaxLength(50);                 // nvarchar(50)
    mb.Entity<Employee>().Property(e => e.Salary).HasColumnType("decimal(10,2)");
    mb.Entity<Employee>().HasQueryFilter(e => !e.IsDeleted);                      // 软删除全局过滤器
}

也可以用特性（[MaxLength(50)]、[Column(TypeName = "decimal(10,2)")]），效果相同；团队统一一种风格即可。

3. 变更跟踪（Change Tracking） ​

从 DbContext 查出来的实体默认被"跟踪"：EF 记下它们的原始值，SaveChanges() 时对比，发现哪些变了才发 UPDATE。状态有 Unchanged / Added / Modified / Deleted。

  • 只读场景（列表页、报表）用 AsNoTracking()，不跟踪，更快、更省内存。
  • 对一个新建对象 Add 后状态是 Added，SaveChanges() 时生成 INSERT，数据库生成的自增 Id 会自动回填到对象上。

4. 迁移（Migrations） ​

流程：

  1. 改实体/配置（比如给 Employee 加属性 Phone）。
  2. dotnet ef migrations add AddPhone：EF 对比"当前模型"和"上次模型快照"，生成一个迁移类（Up() 是升级，Down() 是回退）。
  3. dotnet ef database update，或程序里 db.Database.Migrate()：把还没应用的迁移依次执行；已应用的记录在数据库的 __EFMigrationsHistory 表里。
  4. 要交给 DBA 审核：dotnet ef migrations script 起点 终点 导出 SQL。

迁移文件要提交到 Git，和代码一起走。

5. EF Core 与 SqlSugar 对比 ​

方面EF CoreSqlSugar
出身微软官方，生态大（文档、教程、问题答案多）国产，国内企业用得多，中文文档
查询风格LINQ（from ... select 或方法链）链式 Queryable/Where/... + SqlFunc
改数据变更跟踪：改属性 → SaveChanges()显式 Updateable，要自己决定更新哪几列
表结构管理迁移（可回退、有历史表、可导出脚本）CodeFirst.InitTables（简单，但没有迁移历史）
string 默认类型nvarchar(max)不指定会建成 varchar（中文会变 ?）
生命周期DbContext 每请求一个（Scoped），非线程安全SqlSugarScope 单例，线程安全
复杂 SQLFromSql… 原生 SQLSqlQueryable / Ado.SqlQuery
批量ExecuteUpdate/ExecuteDelete（EF 7+）；大批量插入需第三方库或 SqlBulkCopy内置 Fastest().BulkCopy

没有绝对的好坏。你们公司主力是 SqlSugar，维护老系统就沿用它；新项目要不要换 EF Core，取决于是否需要迁移管理和团队熟悉度。 想用最少的魔法、最多的 SQL 控制权，看 Dapper。

逐步例子 ​

输出全部来自本机真实运行（LocalDB 临时库 Lab_EfCore，最后用 EnsureDeleted 删除）。完整代码在"动手实验"。

例 1：生成并应用迁移 ​

模型 v1（无 Phone）：执行

dotnet ef migrations add InitialCreate

会生成 Migrations 目录下三个文件（时间戳前缀因你运行时刻而不同）：

20261021121407_InitialCreate.cs            迁移本体：Up() / Down()
20261021121407_InitialCreate.Designer.cs   迁移元数据
LabContextModelSnapshot.cs                 当前模型的快照（下次 add 对比用）

迁移本体的内容（EF 生成的，不用手写）：

csharp
using Microsoft.EntityFrameworkCore.Migrations;

#nullable disable

namespace EfLab.Migrations
{
    /// <inheritdoc />
    public partial class InitialCreate : Migration
    {
        /// <inheritdoc />
        protected override void Up(MigrationBuilder migrationBuilder)
        {
            migrationBuilder.CreateTable(
                name: "Depts",
                columns: table => new
                {
                    Id = table.Column<int>(type: "int", nullable: false)
                        .Annotation("SqlServer:Identity", "1, 1"),
                    Name = table.Column<string>(type: "nvarchar(50)", maxLength: 50, nullable: false)
                },
                constraints: table =>
                {
                    table.PrimaryKey("PK_Depts", x => x.Id);
                });

            migrationBuilder.CreateTable(
                name: "Employees",
                columns: table => new
                {
                    Id = table.Column<int>(type: "int", nullable: false)
                        .Annotation("SqlServer:Identity", "1, 1"),
                    Name = table.Column<string>(type: "nvarchar(50)", maxLength: 50, nullable: false),
                    DeptId = table.Column<int>(type: "int", nullable: false),
                    Salary = table.Column<decimal>(type: "decimal(10,2)", nullable: false),
                    IsDeleted = table.Column<bool>(type: "bit", nullable: false)
                },
                constraints: table =>
                {
                    table.PrimaryKey("PK_Employees", x => x.Id);
                    table.ForeignKey(
                        name: "FK_Employees_Depts_DeptId",
                        column: x => x.DeptId,
                        principalTable: "Depts",
                        principalColumn: "Id",
                        onDelete: ReferentialAction.Cascade);
                });

            migrationBuilder.CreateIndex(
                name: "IX_Employees_DeptId",
                table: "Employees",
                column: "DeptId");
        }

        /// <inheritdoc />
        protected override void Down(MigrationBuilder migrationBuilder)
        {
            migrationBuilder.DropTable(
                name: "Employees");

            migrationBuilder.DropTable(
                name: "Depts");
        }
    }
}

可以看出：Name 是 nvarchar(50)（我们配置了 HasMaxLength(50)）、Salary 是 decimal(10,2)、Dept 到 Employee 的外键和索引自动建好了。程序里调用 db.Database.Migrate() 后：

=== 1 应用迁移(Migrate) ===
已应用的迁移: 20261021121407_InitialCreate
Employees 列: Id int, Name nvarchar(50), DeptId int, Salary decimal, IsDeleted bit

Employees 表里各列类型是 Name nvarchar(50)，不是 varchar。

例 2：增删改查（程序见"动手实验"） ​

插入（含关联）：

csharp
var smt = new Dept { Name = "SMT车间" };
db.Employees.Add(new Employee { Name = "张三", Dept = smt, Salary = 5000m });   // 通过导航属性关联
db.SaveChanges();     // 一次保存：先插 Dept，拿到自增 Id，再插 Employee 并填上 DeptId
=== 2 插入(Add + SaveChanges) ===
SaveChanges 写入行数 = 7
部门 Id 由数据库回填: 1, 2

7 行 = 2 个部门 + 5 个员工，一次 SaveChanges() 在一个事务里完成（EF 默认把一次 SaveChanges 包成事务）。注意看 EF 自己决定了插入顺序：先 Dept 后 Employee，部门自增 Id（1、2）也回填到了对象上。

查询（LINQ）：

csharp
var rich = db.Employees.AsNoTracking().Where(e => e.Salary >= 7000m).OrderByDescending(e => e.Salary).ToList();
Console.WriteLine(db.Employees.Where(e => e.Name.Contains("三")).ToQueryString());   // 不执行，只看生成的 SQL
var page2 = db.Employees.OrderBy(e => e.Id).Skip(2).Take(2).Select(e => e.Name).ToList();   // 分页 = Skip + Take
=== 3 查询(LINQ) ===
  [SQL] SELECT [e].[Id], [e].[DeptId], [e].[IsDeleted], [e].[Name], [e].[Salary] FROM [Employees] AS [e] WHERE [e].[IsDeleted] = CAST(0 AS bit) AND [e].[Salary] >= 7000.0 ORDER BY [e].[Salary] DESC
工资>=7000: 孙七:9000.00, 赵六:8000.00, 王五:7000.00
ToQueryString:
SELECT [e].[Id], [e].[DeptId], [e].[IsDeleted], [e].[Name], [e].[Salary]
FROM [Employees] AS [e]
WHERE [e].[IsDeleted] = CAST(0 AS bit) AND [e].[Name] LIKE N'%三%'
第2页(每页2条): 王五, 赵六  总数=5
  • 日志里的 SQL 比你写的 LINQ 多了 [e].[IsDeleted] = CAST(0 AS bit)：这是全局过滤器自动加的。
  • ToQueryString() 是调试利器：不访问数据库，直接给出生成的 SQL。Contains("三") 翻译成 LIKE N'%三%'，带了 N 前缀，中文没问题。
  • 分页与 SqlSugar 不同：EF 用 Skip/Take（页码计算自己做：Skip((页码-1)*每页条数).Take(每页条数)），总数另外 Count()。

连表与分组：

csharp
var withDept = db.Employees.Include(e => e.Dept).OrderBy(e => e.Id)
                 .Select(e => new { e.Name, Dept = e.Dept.Name, e.Salary }).ToList();
var grp = db.Employees.GroupBy(e => e.DeptId)
            .Select(g => new { g.Key, Cnt = g.Count(), Avg = g.Average(x => x.Salary) }).ToList();
=== 4 连表(Include)与分组 ===
  张三 | SMT车间 | 5000.00
  李四 | SMT车间 | 6000.00
  王五 | 质量部 | 7000.00
  赵六 | 质量部 | 8000.00
  孙七 | 质量部 | 9000.00
  部门1: 2 人, 平均 5500.00
  部门2: 3 人, 平均 8000.00

Include 表示"把关联的 Dept 一起加载"；这里用了 Select 投影，其实 EF 能直接用 e.Dept.Name 生成 JOIN，Include 在只投影部分字段时可以省略（这里为了展示写法保留）。

例 3：更新——变更跟踪 vs ExecuteUpdate ​

csharp
var z = db.Employees.First(e => e.Name == "张三");
z.Salary = 5500m;                           // 只改了对象，还没写库
Console.WriteLine(db.Entry(z).State);      // Modified
db.SaveChanges();                           // 此时才发 UPDATE，并且只 SET Salary

db.Employees.Where(e => e.DeptId == 2)
  .ExecuteUpdate(s => s.SetProperty(e => e.Salary, e => e.Salary + 100m));   // 不加载对象，直接一条 UPDATE
=== 5 更新:变更跟踪 vs ExecuteUpdate ===
变更跟踪状态: Modified
  [SQL] SET IMPLICIT_TRANSACTIONS OFF; SET NOCOUNT ON; UPDATE [Employees] SET [Salary] = @p0 OUTPUT 1 WHERE [Id] = @p1;
SaveChanges 影响行数 = 1
  [SQL] UPDATE [e] SET [e].[Salary] = [e].[Salary] + 100.0 FROM [Employees] AS [e] WHERE [e].[IsDeleted] = CAST(0 AS bit) AND [e].[DeptId] = 2
ExecuteUpdate 全员加薪100, 影响 3 行

注意两条 SQL：第一条只有 SET [Salary] = @p0 ... WHERE [Id] = @p1——EF 发现只有 Salary 变了，所以只更新这一列，不会像 SqlSugar 整行更新那样覆盖其它列。第二条 ExecuteUpdate 是批量更新，一条 SQL 影响 3 行，且 SQL 里仍带着软删除过滤条件。

捕获: 故意失败  (未 Commit, 离开 using 自动回滚)
人数 5 -> 5

单次 SaveChanges 自带事务；要把"几次 SaveChanges + 原生 SQL"放在一个事务里，才用 BeginTransaction()，成功时显式 tx.Commit()。回滚后注意 db.ChangeTracker.Clear()：被回滚的对象还留在跟踪列表里，不清掉会影响后续操作。

例 5：软删除与原生 SQL ​

=== 7 软删除(HasQueryFilter) ===
软删除后 Count = 4;  IgnoreQueryFilters Count = 5
恢复后 Count = 5
=== 8 原生 SQL ===
FromSqlInterpolated: 王五, 赵六, 孙七
ExecuteSqlInterpolated 影响行数 = 2
  • IgnoreQueryFilters() 对应 SqlSugar 的 ClearFilter。
  • FromSqlInterpolated($"... {min}") 看起来像字符串拼接，其实 min 被当作参数传递（插值字符串被特殊处理成了 FormattableString）；换成普通 string 拼接才会有注入风险，所以 EF 还提供 FromSqlRaw，用它时必须自己写参数占位符。

  • list 显示 AddPhone 是 (Pending)，即还没应用到数据库。
  • script 导出的 SQL 是增量脚本：只有 ALTER TABLE ... ADD [Phone] nvarchar(max) NULL，外加往 __EFMigrationsHistory 登记一行，整体包在事务里。这个脚本可以交给 DBA 审核后在生产库执行。

Model.cs：实体 + DbContext（点击展开）
csharp
using Microsoft.EntityFrameworkCore;

namespace EfLab;

public class Dept
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Employee> Employees { get; set; } = new();
}

public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int DeptId { get; set; }
    public Dept Dept { get; set; } = null!;
    public decimal Salary { get; set; }
    public bool IsDeleted { get; set; }
}

public class LabContext : DbContext
{
    public DbSet<Dept> Depts => Set<Dept>();
    public DbSet<Employee> Employees => Set<Employee>();

    public static bool LogSql;

    protected override void OnConfiguring(DbContextOptionsBuilder b) =>
        b.UseSqlServer(@"Server=(localdb)\MSSQLLocalDB;Database=Lab_EfCore;Trusted_Connection=True;TrustServerCertificate=True;")
         .LogTo(s => { if (LogSql) Console.WriteLine("  [SQL] " + System.Text.RegularExpressions.Regex.Replace(s[(s.IndexOf("']", StringComparison.Ordinal) + 2)..], @"\s+", " ").Trim()); },
                new[] { Microsoft.EntityFrameworkCore.Diagnostics.RelationalEventId.CommandExecuted });

    protected override void OnModelCreating(ModelBuilder mb)
    {
        mb.Entity<Employee>().Property(e => e.Name).HasMaxLength(50);
        mb.Entity<Employee>().Property(e => e.Salary).HasColumnType("decimal(10,2)");
        mb.Entity<Employee>().HasQueryFilter(e => !e.IsDeleted);   // 软删除过滤器
        mb.Entity<Dept>().Property(d => d.Name).HasMaxLength(50);
    }
}

常见坑与排查 ​

现象原因处理
dotnet ef 报 ef.dll 版本不匹配你的项目名/程序集名就叫 ef改项目名
dotnet ef 提示找不到 Microsoft.EntityFrameworkCore.Design没装 Design 包dotnet add package Microsoft.EntityFrameworkCore.Design
Invalid object name 'Depts'没应用迁移（库是空的）先 Migrate() 或 dotnet ef database update
运行时 Migrate() 抛 InvalidOperationException ... PendingModelChangesWarning: The model for context 'LabContext' has pending changes. Add a new migration before updating the database（实测）改了模型但没 migrations add先 dotnet ef migrations add 名字
查询慢，N+1循环里访问导航属性触发一次次查询用 Include 或 Select 投影一次取够；开 LogTo 数一数 SQL 条数
改了对象但没保存忘了 SaveChanges()；或对象是 AsNoTracking 查出来的检查有无跟踪 db.Entry(x).State
多线程报"第二个操作在此上下文上开始"多个线程共享一个 DbContext每个线程/请求一个实例；Web 里注册为 Scoped
字符串列都是 nvarchar(max)没配置长度HasMaxLength 或 [MaxLength]；max 列不能建普通索引
生产环境自动 Migrate() 出事故迁移含删列/改类型，在启动时自动执行生产用 migrations script 导出让 DBA 审核再执行

业务视角与技术视角 ​

  • 业务视角：MES 的表结构会随业务演进（新增追溯字段、扩大料号长度）。迁移相当于"数据库的版本记录"：任何时候都能回答"这个库现在是哪一版结构、从上一版改了什么"，对追求可追溯的制造业系统是个好习惯。
  • 技术视角：EF Core 适合"领域模型清晰、CRUD 多"的后台；对"设备数据高频批量落库、复杂报表"的场景，往往要配合 SqlBulkCopy、原生 SQL 或 Dapper。和 SqlSugar 混用时注意：各自有各自的连接与事务，一个事务里不要混用两个 ORM 的连接，除非共享同一个 DbTransaction。

练习题与答案 ​

练习 1：db.Employees.Where(e => e.Salary > 7000m) 这一句执行后有没有访问数据库？

答案：没有。这是延迟执行，只构建了查询；直到 ToList()、First()、Count() 或 foreach 才真正发 SQL。（可以用 ToQueryString() 查看 SQL 而不执行。）

练习 2：下面两种改工资方式，哪个会把整个对象加载进内存？各适用什么场景？

csharp
// A
var e = db.Employees.First(x => x.Id == 1); e.Salary += 100; db.SaveChanges();
// B
db.Employees.Where(x => x.Id == 1).ExecuteUpdate(s => s.SetProperty(x => x.Salary, x => x.Salary + 100m));

答案：A 会加载对象并跟踪；适合要先读后判断业务规则的场景。B 不加载，一条 UPDATE，适合简单批量修改；但它绕过变更跟踪和 SaveChanges 里的拦截逻辑。

练习 3：为什么要把迁移文件提交到 Git？

答案：迁移文件和快照是表结构历史的一部分；团队成员拉代码后运行 Migrate()，就能得到一致的库结构。不提交的话，每个人的库结构各不相同。

练习 4：FromSqlInterpolated($"... {name}") 和 FromSqlRaw("... " + name) 哪个有注入风险？

答案：后者。前者把插值变量转成参数；后者是纯字符串拼接，用户输入会直接进入 SQL。

练习 5（动手）：运行实验后，把 Employee 的 Name 去掉 HasMaxLength(50)，新建迁移 dotnet ef migrations add NameMax，用 dotnet ef migrations script 看看生成的 SQL 把 Name 改成了什么类型。

答案（实测）：脚本里先有一段查询并删除该列默认约束的 SQL（DECLARE @var ... default_constraints ...），然后是 ALTER TABLE [Employees] ALTER COLUMN [Name] nvarchar(max) NOT NULL;，再往 __EFMigrationsHistory 登记。做完用 dotnet ef migrations remove 撤销这个迁移（它删除的是尚未应用的最后一个迁移）。

小结 ​

  • EF Core = 实体 + DbContext + DbSet + 变更跟踪 + 迁移。
  • string 默认 nvarchar(max)，中文安全；但要用 HasMaxLength 控制长度。
  • 改对象再 SaveChanges() 只更新变化的列；批量更新用 ExecuteUpdate。
  • 迁移文件进 Git；生产环境用脚本、让 DBA 审核。
  • 项目别叫 ef；DbContext 短生命周期、非线程安全。
