CSharp-TCP通信

AI 生成 · 待核对.NET生态通信工厂上位机更新于 2026-10-21

一句话定义 ​

在 C# 里做 TCP 通信，服务端用 TcpListener 监听端口、接受连接，客户端用 TcpClient 发起连接，双方通过 NetworkStream 读写字节流；而 TCP 只保证字节有序到达，不保证"一次发送对应一次接收"，所以必须自己约定怎么切分消息（粘包与拆包问题）。

先修知识 ​

  • TCP-IP 与 TCP与UDP：知道 IP 地址、端口，以及 TCP 是"面向连接、可靠、字节流"的。
  • Socket编程：套接字（Socket）的基本概念，本篇的 TcpClient/TcpListener 是对 Socket 的封装。
  • CSharp异步编程：本篇所有读写都用 async/await。
  • 十六进制：看报文要会读十六进制。

它解决什么问题 ​

工厂里设备大量走以太网：PLC、扫码枪的网口版、测试机、AOI/SPI，以及自己写的采集程序之间。这些设备大多提供"连上某个 IP 和端口，发一串字节，收一串字节"的接口（Modbus-TCP 就是这样）。你需要在 C# 里：

  1. 当客户端：主动连设备，发请求，收回应（最常见）；
  2. 当服务端：监听端口，等设备主动上报（扫码结果、测试数据）；
  3. 正确地把收到的字节切成一条条完整消息——这是本篇的重点，也是新手最容易出错的地方。

核心概念（由浅入深） ​

端点（IP + 端口）。127.0.0.1（回环地址）表示"本机自己"，只在本机内部通信，不经过网线，适合做实验。端口是 0–65535 的数字，用来区分一台机器上的不同程序。

服务端流程：TcpListener.Start() 开始监听 → AcceptTcpClientAsync() 等一个客户端连进来（得到一个 TcpClient）→ GetStream() 拿到 NetworkStream → 读写 → 关闭。

客户端流程：new TcpClient() → ConnectAsync(ip, 端口) → GetStream() → 读写 → 关闭（using 结束即关闭）。

字节流（Stream）与"没有消息边界"。把 TCP 想成一根水管：你往一头倒水（Write），另一头接水（Read），水是连续的，没有"这一杯、那一杯"的分界。具体来说：

  • 粘包：发送方分 3 次各写了一条消息，接收方一次 Read 却拿到了 3 条连在一起；
  • 拆包（半包）：发送方一次写了一条消息，接收方第一次 Read 只拿到前半条，后半条还在路上。

这不是 Bug，是 TCP 的设计：它只负责字节不丢、不乱序、不重复。Read 返回的字节数是"当前缓冲区里有多少就给多少"，不等于对方一次 Write 的大小。

三种常见的"切分消息"约定：

方法做法例子
定长每条消息固定 N 字节老设备的固定 16 字节状态包
分隔符用特殊字节结尾，读到它就是一条文本协议以 \r\n 结尾；扫码枪网口版常以回车结尾
长度头消息前面带一个"后面还有多少字节"的字段Modbus TCP 的 MBAP 头有长度字段；自定义二进制协议最常用

本篇重点演示长度头，因为最通用，而且 Modbus TCP 本身就是这种设计。

按长度读取：ReadExactlyAsync。.NET 提供 stream.ReadExactlyAsync(buffer)：一直读，直到把 buffer 填满才返回；如果对方在填满前关闭连接，抛 EndOfStreamException。有了它，"读 4 字节长度头，再读 N 字节正文"就变成两行代码，不用自己写循环拼。

逐步例子 ​

例 1：亲眼看到粘包 ​

回环地址上做实验。服务端接受连接后先等 300 毫秒（让数据都到缓冲区），再只调一次 Read；客户端分 3 次各写一条消息。

建项目：

dotnet new console -n TcpLab -o tcp

Program.cs（整个文件分几段给出，合起来就是完整的程序；顶部是入口和用到的命名空间）：

csharp
using System.Net;
using System.Net.Sockets;
using System.Text;

Console.OutputEncoding = Encoding.UTF8;
string mode = args.Length > 0 ? args[0] : "framed";
switch (mode)
{
    case "sticky": await StickyDemo(); break;
    case "partial": await PartialDemo(); break;
    case "framed": await FramedDemo(); break;
    case "modbus": await ModbusRaw(); break;
}

// ---------- 1. 粘包演示：发 3 条小消息，对方一次 Read 可能全读到 ----------
static async Task StickyDemo()
{
    var listener = new TcpListener(IPAddress.Loopback, 5301);
    listener.Start();
    var serverTask = Task.Run(async () =>
    {
        using var conn = await listener.AcceptTcpClientAsync();
        var stream = conn.GetStream();
        await Task.Delay(300);                       // 让三条消息都先到达接收缓冲区
        var buf = new byte[1024];
        int n = await stream.ReadAsync(buf);         // 只调用一次 Read
        Console.WriteLine($"服务端一次 Read 收到 {n} 字节: {Encoding.UTF8.GetString(buf, 0, n)}");
    });
    using var client = new TcpClient();
    await client.ConnectAsync(IPAddress.Loopback, 5301);
    var cs = client.GetStream();
    foreach (var s in new[] { "AAA", "BBB", "CCC" })
        await cs.WriteAsync(Encoding.UTF8.GetBytes(s));   // 分三次 Write
    Console.WriteLine("客户端分 3 次 Write 了 AAA、BBB、CCC");
    await serverTask;
    listener.Stop();
}

运行 dotnet run -- sticky，我跑了 3 次，每次输出都是：

客户端分 3 次 Write 了 AAA、BBB、CCC
服务端一次 Read 收到 9 字节: AAABBBCCC

3 条消息粘成了 9 字节。注意：这个结果是回环上的典型表现，不是绝对保证——网络状况不同可能拆开。重点是：你不能假设一次 Read 对应一条消息。

例 2：亲眼看到半包 ​

客户端把消息 HELLO-WORLD 分成两次发，中间隔 300 毫秒，服务端连续 Read 两次：

csharp
// ---------- 1b. 半包演示：一条消息分两次到达，一次 Read 只拿到前半 ----------
static async Task PartialDemo()
{
    var listener = new TcpListener(IPAddress.Loopback, 5301);
    listener.Start();
    var serverTask = Task.Run(async () =>
    {
        using var conn = await listener.AcceptTcpClientAsync();
        var stream = conn.GetStream();
        var buf = new byte[1024];
        int n1 = await stream.ReadAsync(buf);        // 第一次 Read
        Console.WriteLine($"第 1 次 Read: {n1} 字节: {Encoding.UTF8.GetString(buf, 0, n1)}");
        int n2 = await stream.ReadAsync(buf);        // 第二次 Read
        Console.WriteLine($"第 2 次 Read: {n2} 字节: {Encoding.UTF8.GetString(buf, 0, n2)}");
    });
    using var client = new TcpClient();
    await client.ConnectAsync(IPAddress.Loopback, 5301);
    var cs = client.GetStream();
    await cs.WriteAsync(Encoding.UTF8.GetBytes("HELLO-"));   // 一条完整消息 "HELLO-WORLD"，分两次发
    await cs.FlushAsync();
    await Task.Delay(300);
    await cs.WriteAsync(Encoding.UTF8.GetBytes("WORLD"));
    await serverTask;
    listener.Stop();
}

dotnet run -- partial 实际输出：

第 1 次 Read: 6 字节: HELLO-
第 2 次 Read: 5 字节: WORLD

如果你的代码是"一次 Read 就当一条完整消息处理"，这里会把 HELLO- 当成整条，后半条 WORLD 变成"下一条消息"，数据彻底错位。

例 3：用长度头解决——"4 字节长度 + 正文" ​

约定：每条消息 = 4 字节大端长度（后面正文有多少字节）+ UTF-8 正文。发送时先写长度再写正文；接收时先 ReadExactly 读 4 字节，解出长度 N，再 ReadExactly 读 N 字节。

csharp
// ---------- 2. 定长头(4 字节长度)+ 正文：按长度读取 ----------
static async Task SendFrame(NetworkStream s, string text)
{
    var body = Encoding.UTF8.GetBytes(text);
    var head = new byte[4];
    System.Buffers.Binary.BinaryPrimitives.WriteInt32BigEndian(head, body.Length);
    await s.WriteAsync(head);
    await s.WriteAsync(body);
}

static async Task<string?> ReadFrame(NetworkStream s)
{
    var head = new byte[4];
    try { await s.ReadExactlyAsync(head); }          // 读满 4 个字节才返回
    catch (EndOfStreamException) { return null; }     // 对方已关闭
    int len = System.Buffers.Binary.BinaryPrimitives.ReadInt32BigEndian(head);
    if (len < 0 || len > 1_000_000) throw new InvalidDataException($"长度异常: {len}");
    var body = new byte[len];
    await s.ReadExactlyAsync(body);
    return Encoding.UTF8.GetString(body);
}

static async Task FramedDemo()
{
    var listener = new TcpListener(IPAddress.Loopback, 5301);
    listener.Start();
    var serverTask = Task.Run(async () =>
    {
        using var conn = await listener.AcceptTcpClientAsync();
        var s = conn.GetStream();
        while (await ReadFrame(s) is { } msg)
        {
            Console.WriteLine($"服务端收到一帧(长度 {msg.Length}): {(msg.Length > 20 ? msg[..20] + "…" : msg)}");
            await SendFrame(s, "ACK:" + msg);
        }
        Console.WriteLine("服务端: 客户端已断开");
    });
    using (var client = new TcpClient())
    {
        await client.ConnectAsync(IPAddress.Loopback, 5301);
        var s = client.GetStream();
        foreach (var m in new[] { "AAA", "扫码:SN001", new string('x', 5000) })
            await SendFrame(s, m);                    // 连着发，不等回应
        for (int i = 0; i < 3; i++)
        {
            var r = await ReadFrame(s);
            Console.WriteLine($"客户端收到回应(长度 {r!.Length}): {(r.Length > 20 ? r[..20] + "…" : r)}");
        }
    }                                                 // using 结束 = 关闭连接
    await serverTask;
    listener.Stop();
}

客户端故意"连着发三条且不等回应"，其中一条 5000 个字符（会被 TCP 拆成多个报文段），dotnet run -- framed 实际输出：

服务端收到一帧(长度 3): AAA
服务端收到一帧(长度 8): 扫码:SN001
服务端收到一帧(长度 5000): xxxxxxxxxxxxxxxxxxxx…
客户端收到回应(长度 7): ACK:AAA
客户端收到回应(长度 12): ACK:扫码:SN001
客户端收到回应(长度 5004): ACK:xxxxxxxxxxxxxxxx…
服务端: 客户端已断开

关键观察：

  • 不管数据在网络上怎么被切分、合并，三条消息都被完整、按序地还原；
  • "扫码:SN001" 的字符数是 8，但它的 UTF-8 字节数是 扫码:SN001 = 2 个汉字×3 字节 + :SN001 6 字节 = 12 字节，所以回应 ACK: + 它是 12 个字符——长度头里写的是字节数，不是字符数，这是常见错误（见下面的坑）；
  • 最后一行说明：客户端 using 结束关闭连接后，服务端的 ReadExactlyAsync 抛 EndOfStreamException，被我们转成 null 退出循环。

实际代码里还应处理：服务端循环 AcceptTcpClientAsync 接多个客户端、每个连接开一个任务；读写加超时。这里为了聚焦"切分消息"省略了。

例 4：让 C# 客户端连 Python 模拟从站，读 Modbus 寄存器 ​

Modbus 一篇的实验里有一个 Python 写的模拟从站（modbus_server.py，监听 127.0.0.1:5020）。我们用裸 TcpClient 手拼一帧 Modbus TCP 请求，读地址 1 起的 3 个保持寄存器，并按报文头里的长度字段读取响应——这正是"长度头"思想的真实案例。

先在一个终端启动从站（脚本见 Modbus 的动手实验）：python modbus_server.py。然后：

csharp
// ---------- 3. 用裸 TcpClient 手拼 Modbus TCP，访问 Modbus.md 的 Python 模拟从站 ----------
static async Task ModbusRaw()
{
    using var client = new TcpClient();
    using var cts = new CancellationTokenSource(3000);
    await client.ConnectAsync("127.0.0.1", 5020, cts.Token);
    var s = client.GetStream();
    // MBAP: 事务号0001 协议号0000 长度0006 单元号01 | PDU: 03 起始0001 数量0003
    byte[] req = [0x00, 0x01, 0x00, 0x00, 0x00, 0x06, 0x01, 0x03, 0x00, 0x01, 0x00, 0x03];
    await s.WriteAsync(req, cts.Token);
    Console.WriteLine("发送: " + Convert.ToHexString(req));
    var head = new byte[7];
    await s.ReadExactlyAsync(head, cts.Token);
    int length = (head[4] << 8) | head[5];            // 单元号之后还有 length-1 字节
    var pdu = new byte[length - 1];
    await s.ReadExactlyAsync(pdu, cts.Token);
    Console.WriteLine("收到: " + Convert.ToHexString(head) + Convert.ToHexString(pdu));
    int count = pdu[1] / 2;
    for (int i = 0; i < count; i++)
        Console.WriteLine($"寄存器[{1 + i}] = {(pdu[2 + 2 * i] << 8) | pdu[3 + 2 * i]}");
}

dotnet run -- modbus 实际输出（从站是刚启动的、寄存器是初始值）：

发送: 000100000006010300010003
收到: 000100000009010306000A0014001E
寄存器[1] = 10
寄存器[2] = 20
寄存器[3] = 30

对照 Modbus-TCP 一篇：响应头 00 01 00 00 00 09 01，长度字段 00 09 = 9，表示单元号之后还有 8 字节（03 06 + 6 字节数据，再加 1 个单元号共 9）；我们的代码先读 7 字节头，从 head[4..5] 取出长度 9，再读 9 - 1 = 8 字节，就得到完整 PDU。数据 000A 0014 001E 就是 10、20、30，与 Python 客户端的结果一致。

动手实验 ​

  1. 把 StickyDemo 里的 Task.Delay(300) 去掉再运行几次，观察一次 Read 收到的字节数是否有时会变化。（我没有专门测过，请你亲自试，并思考为什么不稳定。）
  2. 把 ReadFrame 里读正文的 ReadExactlyAsync(body) 改成普通的 ReadAsync(body)，发送那条 5000 字节的消息，看看会发生什么，并解释原因。（提示：ReadAsync 返回的可能小于 5000。）
  3. 启动 modbus_server.py 后，把例 4 请求里最后两个字节（数量）改成 0x00, 0x00（读 0 个）。我实际运行的结果：先打印"收到: 000100000003018303"（功能码 83 = 03 + 80，异常码 03 = 非法数据值，见 Modbus功能码），随后程序因 IndexOutOfRangeException 崩溃——因为示例代码没有判断响应是不是异常响应，却把它当成正常数据去解析。请你给 ModbusRaw 加上"功能码最高位为 1 就报错"的判断。
  4. 在 modbus 模式下不启动从站，直接运行，观察异常信息（我实际看到 SocketException (10061)：目标计算机积极拒绝），再思考正式程序应该如何处理（重连、日志、超时）。

常见坑与排查 ​

现象原因 / 办法
偶尔收到半条/多条合并的消息把一次 Read 当成一条消息。必须用长度头/分隔符/定长，并且循环读满
长度头写的是字符数，包含中文时错位长度必须是字节数（Encoding.GetBytes(text).Length），不是 text.Length
大端/小端搞反，长度变成几亿网络协议通常是大端（高字节在前）；用 BinaryPrimitives.ReadInt32BigEndian。对长度做合理性检查（上限），防止对方发乱码时一次性分配巨大内存
SocketException: 由于目标计算机积极拒绝，无法连接（10061）对方没在监听该端口，或 IP/端口写错，或被防火墙拦住。我在没启动从站时就会看到它
SocketException: 地址已在使用（10048）端口已被别的程序占用，或上次的监听没关干净。换端口或结束占用进程
程序卡死不报错没设超时。对 Connect/Read 传 CancellationToken（如 3 秒），或设置 ReceiveTimeout
对方断线了我这边没发现对方正常关闭时 Read 返回 0（或 ReadExactly 抛 EndOfStreamException）；对方掉电/拔网线则没有任何通知，要靠应用层心跳或超时判断
设备主动上报时只接收到一个连接服务端要循环 AcceptTcpClientAsync，并为每个连接开独立任务处理
发送后立刻 Close，对方没收全关闭前应先 Flush 并等对方确认，或用 Shutdown(SocketShutdown.Send) 优雅关闭
一直开着窗口程序时界面卡网络读写放在 async 或后台线程，不要阻塞 UI 线程（见 WinForms）

业务视角与技术视角 ​

  • 业务视角：设备联网是 MES/数据采集的基础，网络通信出问题时，现场表现是"数据断了""状态灯不亮""偶尔丢数据"。通信模块必须有可观测性：每次收发的原始报文（十六进制）要能记日志，出问题才能判断是设备、网络还是自己的程序（见 日志）。
  • 技术视角：不要在业务代码里到处直接读写 NetworkStream。把"成帧"（切分消息）封装成一个小类，业务只面对完整的消息；把"连接管理"（断线重连、超时、心跳）单独封装。如果协议是标准的（Modbus 等），优先用成熟库，见 NModbus；真正需要自己写的是厂家私有协议。
  • 通信的收发循环常常放进 后台服务与Windows服务，保证无人值守时也能持续运行。

练习题与答案 ​

  1. 为什么 TCP 通信里不能假设"一次 Write 对应一次 Read"？ 答：TCP 是字节流，没有消息边界；系统可能把多次发送合并，或把一次发送拆成多段，Read 返回的是缓冲区当前可读的字节，大小与对方 Write 的大小无关。
  2. 长度头为什么要对数值做上限检查？ 答：如果对方发的是乱码或恶意数据，长度可能解析成几亿，程序会按它分配内存而崩溃；设置合理上限（如本例 1,000,000）并在超出时报错断开。
  3. 一条消息 "温度=25"，用 UTF8 编码，长度头应写几？ 答：字节数：温、度 各 3 字节，=25 3 字节，共 9。写 text.Length（5）是错的。
  4. 在 Modbus TCP 的响应 00 05 00 00 00 07 01 03 04 00 01 00 02 里，读完 7 字节头后还要再读多少字节？ 答：长度字段 00 07 = 7，等于"单元号 1 字节 + PDU 6 字节"；7 字节头里已经读到了单元号，所以还要读 7 - 1 = 6 字节（03 04 00 01 00 02）。
  5. 动手：把 FramedDemo 的服务端改成可以同时服务多个客户端。 答：在服务端用 while (true) { var conn = await listener.AcceptTcpClientAsync(); _ = Task.Run(() => Handle(conn)); }，Handle 里放现在的读帧循环并 using conn。

小结 ​

  • TcpListener 监听、TcpClient 连接、NetworkStream 读写字节；
  • TCP 是字节流，会粘包、会半包，必须自己约定如何切分消息；
  • 长度头 + ReadExactlyAsync 是最通用的做法，长度写字节数，并做上限检查；
  • 联调时先用回环地址验证自己的代码，再接真实设备；永远带超时，永远记录原始报文。
