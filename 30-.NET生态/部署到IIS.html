部署到IIS

AI 生成 · 待核对dotNET部署IIS更新于 2026-10-21

本篇是 dotNET Web 主线的最后一篇：把写好的 ASP.NET Core 程序放到 Windows 服务器的 IIS 上让别人访问。读完你应该能：说清"发布 → 装 Hosting Bundle → 建应用程序池和站点 → 配权限和密钥 → 验证"的完整流程；知道 IIS 和 Kestrel 是什么关系；看到 500.19、502.5、500.30 这些错误页时知道往哪里查。

⚠ 本篇验证范围：我的电脑上 IIS 服务在运行、ASP.NET Core Module 也已安装，但当前会话没有管理员权限，无法创建站点和应用程序池，所以"在 IIS 里建站并访问"的部分未在本机运行验证，步骤以微软官方文档为准。已在本机实际验证的部分是：dotnet publish 的产物、生成的 web.config、已发布程序以 Production 环境运行时的行为（含缺少密钥时的报错）。每一节都会标明是哪一种。

一句话定义 ​

IIS（Internet Information Services）是 Windows 自带的 Web 服务器；"部署到 IIS"就是把 ASP.NET Core 程序发布成一个文件夹，让 IIS 通过 ASP.NET Core Module（ANCM） 启动并代理请求给它。

先修知识 ​

  • ASP.NET-Core：知道它自带的 Web 服务器叫 Kestrel。
  • dotNET运行时与SDK：SDK、运行时（Runtime）、框架依赖 vs 自包含的区别。
  • 配置与日志：appsettings.json、环境变量、ASPNETCORE_ENVIRONMENT。
  • HTTP：状态码 403/404/500/502 的大致含义。
  • 身份认证与JWT 与 HttpClient 里的 MesApi 小服务，可作为本篇的发布对象。

它解决什么问题 ​

开发时我们用 dotnet run，程序自己带一个 Kestrel 服务器监听端口。放到生产环境后，你需要的是：开机自动启动、崩溃自动拉起、多个站点共用 80/443 端口、HTTPS 证书管理、日志、权限隔离……这些 IIS 都有现成的。很多工厂的服务器本来就是 Windows Server，运维人员熟悉 IIS，所以 MES 的 Web 部分常部署在 IIS 上。

核心概念（由浅入深） ​

1. IIS 和 Kestrel 的关系 ​

ASP.NET Core 程序一定有 Kestrel。部署到 IIS 有两种托管模型：

托管模型做法特点
进程内（InProcess）你的程序被加载进 IIS 的工作进程（w3wp.exe）里运行，不使用 Kestrel 监听端口默认值，性能更好
进程外（OutOfProcess）IIS 作为反向代理，把请求转发给独立运行的 Kestrel 进程程序和 IIS 分开进程，可与其他反向代理共用同一套配置

官方文档中 hostingModel 的默认值是 InProcess（我们 dotnet publish 生成的 web.config 里也写着 hostingModel="inprocess"）。连接 IIS 和你的程序的桥梁就是 ASP.NET Core Module（ANCM），一个装在 IIS 里的原生模块；web.config 里的 <handlers> 告诉 IIS"所有请求交给 AspNetCoreModuleV2"。

2. 发布产物：两种方式 ​

dotnet run 是开发用的；部署要用 dotnet publish 生成"可以直接拷走的文件夹"。

方式命令服务器要求本机实测大小
框架依赖（Framework-dependent）dotnet publish -c Release -o publish服务器必须装有对应版本的 .NET 运行时（Hosting Bundle 里包含）21 个文件，2.8 MB
自包含（Self-contained）dotnet publish -c Release -r win-x64 --self-contained true -o publish_sc不需要装运行时，把运行时一起打包351 个文件，109 MB

（两项数字都来自本机对 MesApi 项目的实测。）多数企业环境用框架依赖：包小，运行时由运维统一打补丁；自包含适合"服务器不能装东西"的场景，但每次安全补丁都要重新发布整个程序。

3. Hosting Bundle ​

服务器上要装 .NET Hosting Bundle：它包含 .NET 运行时 + ASP.NET Core 共享框架 + ANCM 模块。官方文档强调两点：

  • 先装 IIS，再装 Hosting Bundle。如果顺序反了，要把 Hosting Bundle 再运行一遍（Repair）。
  • 装完可能需要重启 IIS（以管理员身份）：
net stop was /y
net start w3svc

官方文档还指出：ASP.NET Core 不对共享框架的补丁版本做自动前滚，升级 Hosting Bundle 之后要这样重启 IIS 或重启系统。

4. 应用程序池（Application Pool） ​

应用程序池是 IIS 里"一组网站共用的工作进程 + 它的运行身份"。要点：

  • .NET CLR 版本设为"无托管代码（No Managed Code）"：ASP.NET Core 自己启动运行时，不依赖老的 .NET Framework CLR（官方：可选但推荐）。
  • 一个站点用一个独立的应用程序池：官方列出的错误码里（500.34、500.35）说明了把进程内和进程外、或多个进程内应用放在同一个池里会出错。
  • 池的**标识（Identity）**默认是 ApplicationPoolIdentity，对应一个虚拟账号 IIS AppPool\池名，文件夹权限要授给它。

=== 2 web.config ===
﻿<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <location path="." inheritInChildApplications="false">
    <system.webServer>
      <handlers>
        <add name="aspNetCore" path="*" verb="*" modules="AspNetCoreModuleV2" resourceType="Unspecified" />
      </handlers>
      <aspNetCore processPath="dotnet" arguments=".\MesApi.dll" stdoutLogEnabled="false" stdoutLogFile=".\logs\stdout" hostingModel="inprocess" />
    </system.webServer>
  </location>
</configuration>
  • 产物是一个文件夹：你的程序集 MesApi.dll、依赖的第三方 DLL、appsettings*.json、以及 web.config。
  • web.config 是 dotnet publish 自动生成的，作用是让 IIS 知道怎么启动：processPath="dotnet" arguments=".\MesApi.dll"（框架依赖时用 dotnet 启动 DLL）。自包含发布时，我实测这一行变为 processPath=".\MesApi.exe"。
  • stdoutLogEnabled="false"：默认不记录标准输出日志。排查启动故障时可临时改成 true（见后面"排查"）。
  • 注意 appsettings.Development.json 也被发布出来了——里面如果有开发用密钥，就一起带到了服务器。这个文件只在 Development 环境才被读取，生产环境不读，但仍应在发布前确认不含敏感信息，或不把它拷到服务器。

例 2（本机已验证）：在命令行以生产环境试跑已发布程序 ​

在把文件夹拷到 IIS 之前，先在命令行直接跑一遍。这是官方排错文档推荐的方法：能暴露绝大多数启动问题，而且错误信息比 IIS 的错误页清楚得多。

PowerShell：

powershell
cd publish
$env:ASPNETCORE_ENVIRONMENT = "Production"
dotnet MesApi.dll --urls http://localhost:5202

结果：

=== 1 Production 且没配密钥（dotnet MesApi.dll --urls http://localhost:5202）===
Unhandled exception. System.InvalidOperationException: 缺少 Jwt:Key 配置
   at Program.<Main>$(String[] args) in ...\api\Program.cs:line 33
=== 2 Production + 环境变量 Jwt__Key ===
GET /api/ping -> 200
GET /openapi/v1.json -> 404
GET /swagger/index.html -> 404

三点发现：

  1. 没配密钥时程序启动就抛异常退出——这正是 身份认证与JWT 里"缺少配置立即失败"的设计。如果这是在 IIS 里，用户看到的会是 HTTP 500.30（进程内启动失败） 一类的错误页（官方文档把"应用启动失败"归在 500.30），具体要去事件查看器或 stdout 日志里才能看到真正原因 ——"缺少 Jwt:Key 配置"。这一条在 IIS 里的表现我未实测，仅根据官方错误码说明推断。
  2. 设置环境变量 Jwt__Key 后，服务正常启动：/api/ping 返回 200。
  3. 生产环境下 /openapi/v1.json 和 /swagger 都是 404，因为 MapOpenApi 和 Swagger UI 只在 Development 环境启用（见 Swagger与OpenAPI）。

这里 --urls 在 IIS 进程内模式下不起作用（IIS 的绑定决定了地址），仅用于命令行试跑。

例 3（⚠ 未在本机运行验证）：在 IIS 里建站 ​

以下步骤来自微软官方文档和通行的 appcmd 用法。我的会话没有管理员权限，没有实际执行过；命令的细节（尤其路径、端口）请在你们的测试服务器上先试。不要直接在生产服务器上第一次尝试。

准备（服务器上，管理员）：

  1. 确认 IIS 已启用（"启用或关闭 Windows 功能"里的 Internet Information Services，或服务器管理器里的 Web 服务器角色）。
  2. 安装 .NET Hosting Bundle（版本不低于你的程序目标版本，下载入口见官方文档）。装完执行 net stop was /y 与 net start w3svc。
  3. 验证模块已安装：文件 C:\Program Files\IIS\Asp.Net Core Module\V2\aspnetcorev2.dll 存在（我的电脑上存在，文件版本是 20.0.26177.10），右键属性→详细信息可看版本。
  4. 把本机 publish 文件夹整个拷到服务器，例如 C:\sites\MesApi。部署更新时，官方建议先放一个 app_offline.htm 让 ANCM 优雅关闭程序、释放被占用的 DLL，拷完再删掉它。

图形界面（IIS 管理器）：

  1. 展开服务器节点 → 应用程序池 → 添加：名称 MesApi，".NET CLR 版本"选"无托管代码"。
  2. 网站 → 添加网站：站点名称 MesApi，应用程序池选刚建的 MesApi，物理路径 C:\sites\MesApi，绑定填一个明确的主机名或具体 IP+端口（官方警告：不要使用顶级通配绑定如 http://*:80/，可能带来安全风险）。
  3. 给应用程序池身份授予文件夹权限：IIS AppPool\MesApi 需要对 C:\sites\MesApi 有"读取和执行"，对需要写入的目录（日志目录 logs、上传目录等）要有"修改"权限。命令行写法（官方文档以 DefaultAppPool 举例用 ICACLS，权限级别请按最小权限原则取舍）：
icacls "C:\sites\MesApi" /grant "IIS AppPool\MesApi:(OI)(CI)RX"
mkdir "C:\sites\MesApi\logs"
icacls "C:\sites\MesApi\logs" /grant "IIS AppPool\MesApi:(OI)(CI)M"

命令行（appcmd，管理员）：

%windir%\system32\inetsrv\appcmd.exe add apppool /name:MesApi /managedRuntimeVersion:
%windir%\system32\inetsrv\appcmd.exe add site /name:MesApi /physicalPath:C:\sites\MesApi /bindings:http/127.0.0.1:8081:
%windir%\system32\inetsrv\appcmd.exe set app "MesApi/" /applicationPool:MesApi

（/managedRuntimeVersion: 后面留空表示"无托管代码"。上面绑定到本机 8081 端口，仅用于测试。）

配置环境变量与密钥：

  • 环境变量 ASPNETCORE_ENVIRONMENT=Production，以及 Jwt__Key。官方文档的两种方式：

    • 在 web.config 的 aspNetCore 元素下加 <environmentVariables>（官方示例）：

      xml
      <aspNetCore processPath="dotnet" arguments=".\MesApi.dll" hostingModel="inprocess">
  <environmentVariables>
    <environmentVariable name="ASPNETCORE_ENVIRONMENT" value="Production" />
  </environmentVariables>
</aspNetCore>

      官方说明：web.config 里设置的环境变量优先于系统环境变量。但这等于把密钥写进了站点文件夹，不适合放 Jwt__Key。

    • 为单个应用程序池设置环境变量（IIS 10 及以上），用 appcmd 的对应命令，见官方 IIS 参考文档里的 environmentVariables 条目；密钥更适合放这里或放专用密钥库，并限制只有管理员可读。

验证：

浏览器或 curl 访问 http://127.0.0.1:8081/api/ping，应返回 pong。

⚠ 以上"例 3"没有实际执行。上线前请至少在一台测试服务器上完整走一遍并把过程记在你们自己的运维手册里。

动手实验 ​

可以在你电脑上做的（不需要 IIS）：

  1. 在 MesApi 项目目录运行 dotnet publish -c Release -o publish，打开 publish 文件夹，找到 web.config、MesApi.dll、appsettings.json，对照本篇内容读懂 web.config 每个属性。
  2. 在 publish 目录用 PowerShell 按"例 2"试跑，分别验证：没设密钥时启动失败；设了 Jwt__Key 后 /api/ping 返回 200；/swagger 返回 404。
  3. 试一次自包含发布，对比文件数量和大小：dotnet publish -c Release -r win-x64 --self-contained true -o publish_sc（本机实测 351 个文件、109 MB），再看生成的 web.config 里 processPath 变成了什么。
  4. 做完删掉 publish 和 publish_sc 目录，并确认没有遗留的 dotnet 进程占着 5202 端口（netstat -ano | findstr :5202）。

需要你在测试服务器上做的（⚠ 本篇未验证）： 照"例 3"完整建一次站，并故意制造问题观察错误页：把应用程序池的 .NET 运行时卸载/改版本（模拟 500.31/500.30）、撤销 IIS AppPool\MesApi 对文件夹的权限（观察 500.19 或 403 类现象）、去掉 Jwt__Key（观察 500.30）。每次都在"事件查看器 → Windows 日志 → 应用程序"里找来源为 IIS AspNetCore Module 的事件。

常见坑与排查 ​

排查三板斧（来自官方文档）：

  1. 在服务器上用命令行直接运行已发布的程序（dotnet MesApi.dll，环境变量与线上一致），看控制台报什么。
  2. 看 事件查看器 → Windows 日志 → 应用程序，筛选来源 IIS AspNetCore Module。
  3. 临时打开 stdout 日志：新建 logs 目录，web.config 里改 stdoutLogEnabled="true" stdoutLogFile=".\logs\stdout"，并给应用程序池身份写入权限；复现问题后看最新的 stdout_*.log；排查完立刻改回 false（官方警告：该日志没有大小上限，长期开启可能拖垮应用或服务器）。

错误码速查（依据微软官方排错文档与错误参考文档）：

错误页常见原因处理
500.19配置数据无效。官方"错误参考"里把它归于：IIS 角色/功能没装全、ASP.NET Core Module 没安装、或权限不对；另一种情形是子应用的 web.config 里又写了 <handlers>，与父应用冲突确认已安装 Hosting Bundle（aspnetcorev2.dll 存在）并重启过 IIS；确认 IIS 功能已启用；检查应用程序池身份对站点文件夹（含 web.config）可读；子应用不要重复写 <handlers>

业务视角与技术视角 ​

  • 业务视角：MES 的 Web 端一旦上线，就是产线 24 小时在用的系统。"发布"不是把文件拷过去就完，而是一次需要变更审批、回滚预案和停机窗口的操作（见 变更管理ECN-ECR 的思想：任何影响生产的变更都要可追溯）。部署手册、回滚步骤、联系人写清楚，比技术本身更重要。
  • 技术视角：区分好三个环境（开发、测试、生产）的配置：连接串、密钥、日志级别、是否开放接口文档，都通过环境变量或密钥库注入，而不是改代码重新发布。数据库连接（见 SqlSugar）用 Windows 集成认证时，要注意此时连数据库的身份是应用程序池身份，而不是你开发时登录的账号——数据库侧要给它授权，这是"本机能跑、上线连不上库"的头号原因。Windows 服务和 IIS 是两种不同的托管方式，需要后台常驻任务时见 后台服务与Windows服务。

练习题与答案 ​

练习 1：dotnet run 和 dotnet publish 的区别？生产环境为什么不用 dotnet run？

答案：dotnet run 在开发时编译并运行，使用 Debug 配置和开发环境设置，依赖源码和 SDK；dotnet publish 生成 Release 配置的、可直接部署的文件夹（含 web.config），服务器上只需运行时，不需要 SDK 和源码。

练习 2：为什么应用程序池的 .NET CLR 版本要设成"无托管代码"？

答案：ASP.NET Core 在自己的进程/运行时里运行，由 ANCM 启动，不依赖 IIS 加载老的 .NET Framework CLR。官方文档称这一设置是可选但推荐的。

练习 3：网站打开显示 502.5，你的第一步排查是什么？

答案：在服务器上用命令行进入发布目录，直接运行 dotnet 程序名.dll（环境变量与线上一致），看控制台的真实错误；同时看事件查看器中来源为 IIS AspNetCore Module 的事件。502.5 表示工作进程没能起来，原因常是缺运行时、位数不匹配或程序启动即崩溃。

练习 4：本篇例 2 里，没设置 Jwt__Key 就启动，程序抛 缺少 Jwt:Key 配置 并退出。放到 IIS 上你会看到什么？怎么找到真正原因？

答案：浏览器看到的是进程内启动失败的错误页（500.30 一类，未在 IIS 上实测）。真正原因要在事件查看器的 IIS AspNetCore Module 事件或临时打开的 stdout 日志里看到那条异常信息；或者在服务器命令行直接运行同样的程序复现。

练习 5（动手）：运行 dotnet publish -c Release -o publish，然后在 publish 目录里找出 web.config，回答：processPath 和 arguments 分别是什么？

答案（本机实测）：processPath="dotnet"，arguments=".\MesApi.dll"；hostingModel="inprocess"；stdoutLogEnabled="false"；stdoutLogFile=".\logs\stdout"。

小结 ​

  • 流程：dotnet publish → 服务器装 Hosting Bundle（先 IIS 后 Bundle，装完重启 IIS）→ 应用程序池（无托管代码）+ 站点 → 授权 IIS AppPool\池名 → 环境变量/密钥 → 验证。
  • 进程内（默认）和进程外两种托管模型；web.config 由 dotnet publish 生成。
  • 排错三板斧：命令行直接跑、事件查看器、临时 stdout 日志（用完关掉）。
  • 密钥别写进站点文件夹，用环境变量或密钥库；文档/Swagger 默认只在开发环境开放。
  • 本篇未验证的部分：实际在 IIS 里建站、授权、访问、各类错误页的真实出现条件。
