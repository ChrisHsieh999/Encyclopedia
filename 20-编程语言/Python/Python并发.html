Python并发

AI 生成 · 待核对编程语言Python更新于 2026-10-21

本篇是 Python 入门路径的第 13 篇。读完你应该能：说清"并发"和"并行"、"IO 密集"和"CPU 密集"的区别；解释 GIL 是什么、为什么线程对计算没用；用线程池、进程池、asyncio 各自完成一个"同时读多台设备"或"同时算多份数据"的任务；知道什么时候该加锁。

一句话定义 ​

并发是"同时处理多件事"的程序结构。Python 有三条路：线程（threading，适合等待型任务）、进程（multiprocessing，适合计算型任务）、协程（asyncio，用单线程在等待时切换去做别的事，适合大量网络 IO）。

先修知识 ​

  • Python函数、Python面向对象：线程要传函数；
  • Python文件与异常：异常在线程里怎么传出来；
  • 概念基础：进程与线程（进程是资源隔离的"工厂"，线程是工厂里的"工人"）和 并发与锁（多个工人抢同一份资源会出问题）。

它解决什么问题 ​

先看一个场景：车间有 5 台设备，通过网络读各自的状态，每台一次要等约 0.2 秒（网络往返）。顺序读：0.2 × 5 = 1 秒。程序大部分时间是在等，CPU 其实闲着。如果让 5 个请求同时发出去，总耗时约 0.2 秒。这是并发的第一类收益：隐藏等待。

第二类：要对 8 份大数据做 CPU 密集的统计，只用了 1 个核，另外 15 个核在睡觉。让多个核同时算，才能真正缩短时间。

这两类任务要用不同的工具，选错了反而更慢，下面的 GIL 一节解释原因。

核心概念 ​

并发 vs 并行；IO 密集 vs CPU 密集 ​

  • 并发（concurrency）：多个任务"在同一段时间里都在推进"，可以是轮流执行（单核也行）。
  • 并行（parallelism）：多个任务"在同一时刻真的同时执行"，需要多个 CPU 核。
  • IO 密集：时间花在等网络、等磁盘、等串口、等数据库。
  • CPU 密集：时间花在计算（解压、图像处理、大量数值运算）。

GIL：为什么 Python 线程算不快 ​

GIL（Global Interpreter Lock，全局解释器锁）是 CPython（官方实现）里的一把大锁：同一时刻，只有持有这把锁的一个线程能执行 Python 字节码。线程做 IO（等网络、等文件、time.sleep）时会释放锁，让别的线程跑；线程做纯 Python 计算时一直占着锁。

结论：

任务多线程多进程asyncio
IO 密集（等设备、网络、文件）有效有效，但笨重有效，开销最小
CPU 密集（纯 Python 计算）无效（甚至更慢）有效（每个进程有自己的 GIL）无效

GIL 的现状（截至 3.14）：Python 3.13 起提供一个可选的"自由线程"构建版本（free-threaded build），可以关掉 GIL；3.14 起它成为"官方支持但仍是可选"的构建（PEP 779），默认安装的 Python 仍然带 GIL。很多第三方库还在适配，所以当前写代码仍应按"有 GIL"来选择方案。（来源见本篇 sources；如果你的 Python 版本较新，运行前请查官方文档确认现状。）

NumPy 等库在做大块计算时会在 C 代码内部释放 GIL，所以"用线程 + NumPy"有时也能并行，这是特例。

线程：threading ​

pycon
>>> import threading, time
>>> results = []
>>> def worker(name, delay):
...     time.sleep(delay)
...     results.append(name)
>>> ts = [threading.Thread(target=worker, args=(n, d)) for n, d in [("A", 0.3), ("B", 0.1), ("C", 0.2)]]
>>> for t in ts: t.start()
>>> for t in ts: t.join()
>>> results
['B', 'C', 'A']

Thread(target=函数, args=(参数,)) 创建，start() 启动，join() 等它结束。注意结果顺序是完成顺序（B、C、A），不是启动顺序。线程之间共享内存，所以 results.append 能被主线程看见。

竞态条件与锁 ​

多个线程同时读写同一个变量，结果可能出错——竞态条件（race condition）。经典例子是计数器：n += 1 其实是"读出 n → 加 1 → 写回"三步，两个线程交错执行，就会丢失更新。为了让问题稳定复现，下面的代码在"读"和"写"之间让出一次 CPU（time.sleep(0)）：

python
import threading
import time

unsafe_total = 0
safe_total = 0
lock = threading.Lock()


def unsafe(n):
    global unsafe_total
    for _ in range(n):
        tmp = unsafe_total        # 读
        time.sleep(0)             # 让出 CPU，别的线程可能插进来
        unsafe_total = tmp + 1    # 写（可能覆盖别人刚写的）


def safe(n):
    global safe_total
    for _ in range(n):
        with lock:                # 同一时刻只允许一个线程进入
            tmp = safe_total
            time.sleep(0)
            safe_total = tmp + 1


for fn in (unsafe, safe):
    ts = [threading.Thread(target=fn, args=(1000,)) for _ in range(4)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()

print("不加锁:", "丢失了更新" if unsafe_total < 4000 else "凑巧正确", "| 加锁:", safe_total)
text
不加锁: 丢失了更新 | 加锁: 4000

4 个线程各加 1000 次，理论上应该是 4000。不加锁的结果通常小于 4000（每次运行的具体数字不同，所以不打印），加锁的恒为 4000。锁（Lock）保证一段代码同一时刻只有一个线程在执行，用 with lock: 写，离开自动释放。代价是被锁住的部分变成串行，所以锁住的范围要尽量小。

三条经验：

  1. 能不共享就不共享：每个线程处理自己的数据，最后汇总。
  2. 必须共享时，用 Lock，或者用线程安全的 queue.Queue 传递数据。
  3. 多个锁要按固定顺序加，否则可能死锁（互相等待对方释放，永远卡住，见 死锁）。

线程池：concurrent.futures ​

手工管理线程很烦。ThreadPoolExecutor 提供"线程池"：你提交任务，它用固定数量的工人线程去做，并把结果交还给你。

python
import time
from concurrent.futures import ThreadPoolExecutor, as_completed


def read_device(dev_id):
    """模拟一次网络读取：等 0.2 秒，返回状态。"""
    time.sleep(0.2)
    return f"设备{dev_id}:OK"


ids = [1, 2, 3, 4, 5]

t0 = time.perf_counter()
serial = [read_device(i) for i in ids]
t_serial = time.perf_counter() - t0

t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    parallel = list(pool.map(read_device, ids))     # 结果顺序与 ids 一致
t_pool = time.perf_counter() - t0

print(serial == parallel, parallel)
print("线程池明显更快:", t_pool < t_serial * 0.5)

# submit + as_completed: 谁先完成先拿谁
def slow(n, delay):
    time.sleep(delay)
    return n

with ThreadPoolExecutor() as pool:
    futs = [pool.submit(slow, n, d) for n, d in [(1, 0.3), (2, 0.1), (3, 0.2)]]
    print([f.result() for f in as_completed(futs)])
text
True ['设备1:OK', '设备2:OK', '设备3:OK', '设备4:OK', '设备5:OK']
线程池明显更快: True
[2, 3, 1]

要点：

  • pool.map(f, 序列)：像内置 map，但并发执行，按输入顺序返回结果。
  • pool.submit(f, 参数) 返回一个 Future（"未来的结果"）；future.result() 取结果（没完成就等待；任务里抛的异常会在这里重新抛出）；as_completed 按完成顺序产出 Future。
  • 用 with 创建线程池，离开时自动等待所有任务完成并关闭。
  • 本机实测：串行约 1.0 秒，线程池约 0.2 秒（取决于机器，所以程序里只打印比较结果）。

线程池是 IO 密集任务最省事的方案：把"串行 for 循环"改成 pool.map，几乎不用改其它代码。

进程池：真正的并行 ​

进程之间内存互相隔离，每个进程有自己的解释器和 GIL，所以能用上多个核。Python 提供 multiprocessing，但多数时候用 concurrent.futures.ProcessPoolExecutor，接口和线程池一模一样。

Windows 上必须注意：新进程是"重新启动 Python 并导入你的脚本"，所以启动进程池的代码必须放在 if __name__ == "__main__": 里面（见 Python模块与包），否则会无限递归地创建进程并报错。另外，传给进程池的函数必须是模块顶层定义的函数（要能被 pickle 序列化，lambda 不行）。

python
import threading
import time
from concurrent.futures import ProcessPoolExecutor


def count_primes(limit):
    """纯 Python 的 CPU 密集计算：数一数 limit 以内的素数。"""
    n = 0
    for x in range(2, limit):
        if all(x % d for d in range(2, int(x ** 0.5) + 1)):
            n += 1
    return n


def timeit(fn):
    t0 = time.perf_counter()
    r = fn()
    return r, time.perf_counter() - t0


if __name__ == "__main__":
    jobs = [200000] * 4

    serial, t_serial = timeit(lambda: [count_primes(n) for n in jobs])

    def with_threads():
        out = [None] * len(jobs)

        def run(i):
            out[i] = count_primes(jobs[i])

        ts = [threading.Thread(target=run, args=(i,)) for i in range(len(jobs))]
        for t in ts:
            t.start()
        for t in ts:
            t.join()
        return out

    threaded, t_threads = timeit(with_threads)

    def with_procs():
        with ProcessPoolExecutor(max_workers=4) as pool:
            return list(pool.map(count_primes, jobs))

    procs, t_procs = timeit(with_procs)

    print("结果一致:", serial == threaded == procs, serial)
    print("线程没有明显加速:", t_threads > t_serial * 0.7)
    print("进程明显加速:", t_procs < t_serial * 0.7)
text
结果一致: True [17984, 17984, 17984, 17984]
线程没有明显加速: True
进程明显加速: True

20 万以内有 17984 个素数，三种方式结果一致；线程耗时和串行差不多（GIL 的体现），进程则明显更快。进程加速的前提是机器至少有 2 个以上空闲核，且任务足够大（启动进程有固定开销，任务太小反而更慢）。进程之间不共享内存，数据要通过参数和返回值（会被序列化）传递，传大对象成本很高。

协程：asyncio ​

协程是可以"暂停和恢复"的函数。asyncio 在单个线程里运行一个事件循环，各个协程在 await（"我要等了，你们先去做别的"）处主动让出控制权。因为没有线程切换的开销，也没有多线程的数据竞争，可以轻松管理成千上万个等待中的连接。

基本规则：

  • async def 定义协程函数；调用它只得到协程对象，不会执行。
  • 在协程里用 await 等待另一个协程（或 asyncio.sleep 等异步操作）。
  • asyncio.run(main()) 启动事件循环，是程序入口。
  • asyncio.gather(*协程) 并发运行多个协程并收集结果（顺序与传入顺序一致）。
  • 不能在协程里调用会阻塞的函数（如 time.sleep、同步的 requests.get），否则整个事件循环被卡住；要用异步版本（asyncio.sleep、aiohttp 等），或用 await asyncio.to_thread(阻塞函数) 扔到线程里。
python
import asyncio
import time


async def read_device(dev_id):
    await asyncio.sleep(0.2)               # 模拟异步网络等待
    return f"设备{dev_id}:OK"


async def read_with_timeout(dev_id, delay):
    async def slow():
        await asyncio.sleep(delay)
        return f"设备{dev_id}:OK"
    try:
        return await asyncio.wait_for(slow(), timeout=0.3)
    except asyncio.TimeoutError:
        return f"设备{dev_id}:超时"


async def main():
    t0 = time.perf_counter()
    results = await asyncio.gather(*(read_device(i) for i in range(1, 6)))
    elapsed = time.perf_counter() - t0
    print(results)
    print("asyncio 明显更快:", elapsed < 0.5)

    # 单个任务超时，不影响其它
    print(await asyncio.gather(read_with_timeout(1, 0.1), read_with_timeout(2, 1.0)))

    # 限制并发数：同时最多 2 个
    sem = asyncio.Semaphore(2)
    running, peak = 0, 0

    async def limited(i):
        nonlocal running, peak
        async with sem:
            running += 1
            peak = max(peak, running)
            await asyncio.sleep(0.05)
            running -= 1
        return i

    await asyncio.gather(*(limited(i) for i in range(6)))
    print("同时运行的峰值:", peak)


asyncio.run(main())
text
['设备1:OK', '设备2:OK', '设备3:OK', '设备4:OK', '设备5:OK']
asyncio 明显更快: True
['设备1:OK', '设备2:超时']
同时运行的峰值: 2

wait_for 给单个等待加超时；Semaphore（信号量）限制同时进入的数量，常用于"别一下子打爆设备 / 服务器"。

怎么选 ​

你的任务首选
一批互不相关的 IO 请求（读多台设备、下载文件）ThreadPoolExecutor.map（最简单）
成千上万个网络连接，或整个程序都是异步库asyncio
大量纯 Python 计算ProcessPoolExecutor
一个后台持续采集 / 轮询的任务一个 threading.Thread + Event 控制停止
真要极致性能的计算换 NumPy 等 C 实现的库，或把热点用 C# / C 写

后台线程：用 Event 优雅停止 ​

"每隔一会儿采集一次数据"是上位机常见需求。后台线程里 while not stop.is_set() 循环，主线程需要停止时调用 stop.set()；用 stop.wait(间隔) 代替 time.sleep(间隔)，这样收到停止信号能立刻醒来，不用等满一个间隔。

python
import threading
import time

stop = threading.Event()
samples = []


def poll(interval):
    while not stop.is_set():
        samples.append(len(samples) + 1)     # 模拟采集一次
        stop.wait(interval)                  # 等待间隔；被 set() 时立刻返回


t = threading.Thread(target=poll, args=(0.05,), daemon=True)
t.start()
time.sleep(0.3)
stop.set()
t.join()
print("采集次数合理:", 3 <= len(samples) <= 10, "| 线程已结束:", not t.is_alive())
text
采集次数合理: True | 线程已结束: True

daemon=True 表示守护线程：主程序退出时它不会阻止退出。

逐步例子：并发读取多台设备并汇总 ​

需求：读 6 台设备的温度（模拟，每次约 0.1 秒，其中设备 4 会失败），用线程池并发读取；失败的设备记录下来而不是让整个程序崩溃；最后输出成功台数、平均温度与失败列表。

手算：设备 n 的温度设为 20 + n（21..26），其中设备 4 失败。成功的是 1、2、3、5、6，温度 21、22、23、25、26，和 = 117，平均 117 / 5 = 23.4。

python
import time
from concurrent.futures import ThreadPoolExecutor


def read_temp(dev):
    time.sleep(0.1)
    if dev == 4:
        raise TimeoutError(f"设备{dev}无响应")
    return 20 + dev


devs = [1, 2, 3, 4, 5, 6]
ok, failed = {}, {}

with ThreadPoolExecutor(max_workers=6) as pool:
    futures = {dev: pool.submit(read_temp, dev) for dev in devs}
    for dev, fut in futures.items():
        try:
            ok[dev] = fut.result()                 # 任务里的异常在这里重新抛出
        except TimeoutError as e:
            failed[dev] = str(e)

print("成功", len(ok), "台，平均", round(sum(ok.values()) / len(ok), 1))
print("失败:", failed)
text
成功 5 台，平均 23.4
失败: {4: '设备4无响应'}

和手算一致。关键点：线程里的异常不会自动出现在主线程，只有调用 future.result() 时才会重新抛出，所以每个 Future 都要取一次结果并处理异常。

动手实验 ​

实验：亲眼看看线程池大小的影响。把 pool_io.py 里 5 个任务（每个 0.2 秒）的 max_workers 依次设成 1、2、5，预测并测量总耗时。

python
import time
from concurrent.futures import ThreadPoolExecutor


def task(_):
    time.sleep(0.2)


for workers in (1, 2, 5):
    t0 = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as pool:
        list(pool.map(task, range(5)))
    elapsed = time.perf_counter() - t0
    print(f"workers={workers}: 约 {round(elapsed * 5) / 5:.1f} 秒")
text
workers=1: 约 1.0 秒
workers=2: 约 0.6 秒
workers=5: 约 0.2 秒

预测：1 个工人要 5 × 0.2 = 1.0 秒；2 个工人分 3 批 = 0.6 秒；5 个工人 1 批 = 0.2 秒。输出里为了稳定，把耗时取整到 0.2 秒的倍数。线程不是越多越好：线程太多，切换开销和对方服务器的压力会抵消收益。

常见坑与排查 ​

现象原因办法
多线程跑纯计算反而更慢GIL，线程切换还有开销换进程池或专用库
Windows 上进程池无限报错 / 窗口狂弹启动进程的代码没放在 if __name__ == "__main__":加上保护
PicklingError / Can't pickle传给进程池的是 lambda、局部函数或不可序列化对象用模块顶层函数，参数用简单类型
线程里报错了，主程序却没反应线程异常默认只打印，不会终止主线程用线程池并检查 future.result()
计数 / 累加结果偏小竞态条件加 Lock，或让每个线程算自己的再汇总
程序卡死不退出死锁；或非守护线程在无限循环固定加锁顺序；用 Event 通知停止；必要时 daemon=True
RuntimeWarning: coroutine ... was never awaited调用了协程函数却没 await加 await，或 asyncio.run / create_task
asyncio 里整体变慢 / 卡住在协程里调用了阻塞函数（time.sleep、同步网络）换异步版本，或 await asyncio.to_thread(...)
RuntimeError: asyncio.run() cannot be called from a running event loop在 Jupyter 等已有事件循环的环境中调用直接 await main()
线程数开太大，设备 / 服务器被打挂没有并发上限控制 max_workers，asyncio 用 Semaphore
多进程之间想共享变量没生效进程内存隔离用返回值、multiprocessing.Queue，或写文件 / 数据库

练习题与答案 ​

练习 1：把下面的串行代码改成线程池版本，并保持结果顺序不变。

python
import time
from concurrent.futures import ThreadPoolExecutor


def fetch(x):
    time.sleep(0.1)
    return x * x


# 原来: results = [fetch(x) for x in range(6)]
with ThreadPoolExecutor() as pool:
    results = list(pool.map(fetch, range(6)))
print(results)
text
[0, 1, 4, 9, 16, 25]

练习 2：下面这个 asyncio 程序总共耗时大约多少秒？为什么？

python
import asyncio
import time


async def job(n):
    await asyncio.sleep(n)


async def main():
    t0 = time.perf_counter()
    await asyncio.gather(job(0.2), job(0.3), job(0.1))
    print(round(time.perf_counter() - t0, 1))


asyncio.run(main())
text
0.3

答案：约 0.3 秒。三个协程并发运行，总时间取决于最慢的那个。如果改成 await job(0.2); await job(0.3); await job(0.1)，是顺序执行，约 0.6 秒。

练习 3：为什么"用 4 个线程同时压缩 4 个大文件"在纯 Python 里不一定变快，而"用 4 个线程同时下载 4 个大文件"会变快？

答案：下载主要在等网络（IO），等待时线程释放 GIL，别的线程可以继续工作；压缩如果用纯 Python 实现，全程占用 CPU 并持有 GIL，线程只能轮流跑。（实际 zlib 等 C 扩展在压缩时会释放 GIL，所以具体要看用的库。）

练习 4：什么时候需要加锁？写出判断标准。

答案：当多个线程会同时修改同一份数据，并且修改包含"读 → 计算 → 写"多个步骤，中间被打断会导致结果错误时。只读共享数据不需要锁；每个线程只改自己的数据不需要锁。

小结 ​

  • IO 密集用线程池 / asyncio，CPU 密集用进程池。
  • GIL：同一时刻只有一个线程执行 Python 字节码；等 IO 时释放，所以线程对 IO 有效、对纯计算无效。官方已提供可选的无 GIL 构建，但默认安装仍有 GIL。
  • 共享可变数据 -> 竞态条件 -> Lock 或 Queue；多把锁要注意顺序，防死锁。
  • concurrent.futures 是最省事的统一接口：map、submit、as_completed。
  • Windows 上用进程池必须有 if __name__ == "__main__":。
  • 线程里的异常要通过 future.result() 取回。
