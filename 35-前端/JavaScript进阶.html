JavaScript进阶

AI 生成 · 待核对前端JavaScript更新于 2026-10-21

本篇是 前端 入门路径的第 5 篇。读完你应该能：解释变量在哪里能被访问（作用域）、写出和看懂闭包；判断一个函数里的 this 指谁；用 Promise 和 async/await 写异步代码，会并行请求；用 import/export 拆分文件；预测一段代码里同步、微任务、宏任务的输出顺序。

一句话定义 ​

进阶部分讲 JS 里最容易让人"看不懂"的五件事：作用域与闭包（变量的可见范围）、this（函数里的"我"指谁）、Promise 与 async/await（处理要等一会儿才有结果的事）、模块（把代码拆成多个文件）、事件循环（JS 只有一个线程，怎么同时"等"很多事）。

先修知识 ​

  • JavaScript基础：变量、函数、对象、数组方法。
  • 知道 HTTP 请求需要等待服务器响应（几十到几百毫秒），期间页面不能卡住。
  • 本篇的代码用 Node 运行。含 await 在最外层的文件，扩展名用 .mjs（ES 模块），否则会报错。

它解决什么问题 ​

  • 点击"刷新"按钮后，从服务器取工单数据要等 200 毫秒，等待期间页面不能冻住，用户还能点别的 → 异步。
  • 一个数据取回来后，要依次取详情、再取库存，每一步都依赖上一步 → Promise / async-await，避免层层嵌套。
  • 工单号生成器每次调用要记住"上次到几号" → 闭包。
  • 代码写了 3000 行挤在一个文件，没法维护 → 模块。
  • 同样一段代码，用 var 和 let 结果不同，回调里 this 变成了 undefined → 需要理解作用域和 this 的规则。

核心概念 ​

1. 作用域与提升 ​

作用域（scope）：变量能被访问的范围。

声明方式作用域提升行为
var函数作用域（if/for 的花括号拦不住它）声明被提升，值为 undefined
let / const块（{}）作用域提升但有"暂时性死区"，声明前访问报错
函数声明 function f(){}函数作用域整个函数被提升，声明前就能调用

实测：

js
function f() {
  if (true) { var a = 1; let b = 2; }
  console.log(a, typeof b);
}
f();
// 1 undefined
try { console.log(hoist); let hoist = 1; } catch (e) { console.log(e.name + ": " + e.message); }
// ReferenceError: Cannot access 'hoist' before initialization
console.log(hv); var hv = 5;
// undefined
  • var a 在 if 外面仍可见（输出 1）；let b 出了花括号就消失，typeof b 得 "undefined"。
  • let 在声明前访问报 ReferenceError；var 在声明前访问不报错，只得到 undefined，这就是 var 容易出隐蔽 bug 的原因。结论：只用 let / const。

作用域链：内层作用域找不到变量，就逐层向外找，直到全局。内层能读外层的变量，外层不能读内层的。

2. 闭包 ​

闭包（closure）：一个函数"带着"它诞生时周围的变量一起走。即使外层函数已经执行完毕，内层函数仍能访问那些变量。

类比：员工（内层函数）从公司（外层函数）出发去出差，出发前带上了公司的内部通讯录（外层变量）。公司本部执行完日常工作结束了，通讯录仍在他包里，而且每个员工有各自的一份。

实测：工单号生成器

js
function makeCounter(prefix) {
  let n = 0;                      // 外层的私有变量，外部无法直接访问
  return () => `${prefix}-${String(++n).padStart(4, "0")}`;
}
const c1 = makeCounter("WO"), c2 = makeCounter("PO");
console.log(c1(), c1(), c2(), c1());
// WO-0001 WO-0002 PO-0001 WO-0003
  • c1 和 c2 各有自己的 n，互不影响（WO 已到 3 号时 PO 才到 1 号）。
  • padStart(4, "0") 左边补零到 4 位；++n 先加 1 再取值。

经典陷阱：循环里的回调

js
const fs1 = []; for (var i = 0; i < 3; i++) fs1.push(() => i);
console.log(fs1.map(f => f()));
// [ 3, 3, 3 ]
const fs2 = []; for (let j = 0; j < 3; j++) fs2.push(() => j);
console.log(fs2.map(f => f()));
// [ 0, 1, 2 ]

var i 全循环只有一个变量，等到回调执行时循环早就结束了，i 已是 3；let j 每轮循环都创建一个新的 j，各个回调捕获各自的那一份。这个现象在给多个按钮绑点击事件时最常遇到。

3. this：函数里的"我" ​

this 的值取决于函数怎么被调用，不是在哪里定义的（箭头函数除外）：

调用方式this 是谁
obj.method()obj（点前面的那个对象）
单独调用 fn()严格模式/ES 模块里是 undefined；浏览器普通脚本里是 window
fn.call(x) / fn.apply(x) / fn.bind(x)()你指定的 x
new Fn()新创建的对象
箭头函数没有自己的 this，用定义处外层的 this
事件处理函数（addEventListener 里的普通函数）触发事件的元素

实测（在 ES 模块里运行，即 .mjs 文件）：

js
const board = {
  name: "看板",
  hello() { return "hello " + this.name; },
  later() { return [1].map(() => this.name); },
};
console.log(board.hello(), board.later());
// hello 看板 [ '看板' ]
const h = board.hello;               // 把方法"拿出来"
try { console.log(h()); } catch (e) { console.log(e.name + ": " + e.message); }
// TypeError: Cannot read properties of undefined (reading 'name')
console.log(h.call({ name: "别人" }), h.bind({ name: "绑定" })());
// hello 别人 hello 绑定
  • board.hello() 点前面是 board，this 就是 board。
  • h = board.hello; h() 前面没有点，this 丢了，在模块里是 undefined，访问 .name 报错。这是"把方法当回调传出去后 this 丢了"的经典 bug。
  • later 里的 map(() => ...) 是箭头函数，没有自己的 this，沿用外层 later 的 this，所以拿到 board.name。如果这里写成普通函数 function () { return this.name }，this 就会丢。
  • call/bind 手动指定 this；bind 返回一个新函数，下次调用 this 固定。

经验规则：对象里的方法用 obj.method() 形式调用；回调函数优先用箭头函数；需要稳定的 this 时用 bind 或箭头函数。

class（类）是创建同类对象的模板，写法与 C# 类似（见 CSharp类与对象）：

js
class WorkOrder {
  constructor(id, qty) { this.id = id; this.qty = qty; }
  describe() { return `${this.id} x${this.qty}`; }
  static create(id) { return new WorkOrder(id, 0); }
}
console.log(new WorkOrder("WO-1", 5).describe(), WorkOrder.create("WO-2").describe());
// WO-1 x5 WO-2 x0

constructor 在 new 时执行，this 指新对象；static 方法属于类本身而不是实例。

4. 异步：回调 → Promise → async/await ​

JS 引擎只有一个主线程，一次只能做一件事。如果取数据时"原地死等"，整个页面就卡死。所以凡是需要等待的操作（网络请求、定时器、文件读取）都是异步的：发出请求后马上继续往下执行，结果回来后再通知你。

Promise（承诺）是"将来会有结果"的对象，有三种状态：

状态含义
pending进行中
fulfilled成功，带一个结果值
rejected失败，带一个错误

状态只会从 pending 变成另外两种之一，且不可逆。

实测：用 setTimeout 模拟 50 毫秒的取数据请求。

js
const sleep = (ms) => new Promise(r => setTimeout(r, ms));
const fetchWO = (id) => new Promise((resolve, reject) => {
  setTimeout(() => id.startsWith("WO") ? resolve({ id, qty: 100 }) : reject(new Error("无此工单 " + id)), 50);
});

写法一：.then 链

js
fetchWO("WO-1").then(w => { console.log("then:", w); return w.qty * 2; })
  .then(n => console.log("翻倍", n))
  .catch(e => console.log("never"))
  .finally(() => console.log("finally 1"));
await sleep(100);
// then: { id: 'WO-1', qty: 100 }
// 翻倍 200
// finally 1

.then 返回新的 Promise，所以能一路链下去；任何一步出错，直接跳到最近的 .catch；.finally 无论成败都执行。

写法二：async/await（推荐）

js
async function run() {
  try {
    const a = await fetchWO("WO-2");
    console.log("await:", a);
    await fetchWO("XX-3");
    console.log("不会到这里");
  } catch (e) { console.log("捕获:", e.message); }
  finally { console.log("finally 2"); }
}
await run();
// await: { id: 'WO-2', qty: 100 }
// 捕获: 无此工单 XX-3
// finally 2
  • async 函数永远返回 Promise；
  • await 只能写在 async 函数里（或 ES 模块的最外层），它暂停当前函数等 Promise 完成，拿到结果值，但不会阻塞页面；
  • 失败时 await 会抛出异常，用普通的 try/catch 捕获，写起来像同步代码。

串行与并行：

js
let t0 = Date.now();
await fetchWO("WO-1"); await fetchWO("WO-2"); await fetchWO("WO-3");   // 串行：50+50+50
const serial = Date.now() - t0;                                        // 约 150ms
t0 = Date.now();
const rs = await Promise.all(["WO-1", "WO-2", "WO-3"].map(fetchWO));   // 并行：同时发出
const par = Date.now() - t0;                                           // 约 50ms
console.log(rs.length, "串行>=150:", serial >= 140, "并行<120:", par < 120);
// 3 串行>=150: true 并行<120: true

三个互不依赖的请求，应该用 Promise.all 并行，耗时是最慢那个，而不是三个之和。

Promise 组合工具：

方法含义
Promise.all([...])全部成功才成功（返回结果数组）；有一个失败就整体失败
Promise.allSettled([...])等全部结束，不管成败，返回每个的状态
Promise.race([...])谁先结束就用谁的结果（可实现超时）
Promise.any([...])第一个成功的
js
const st = await Promise.allSettled([fetchWO("WO-1"), fetchWO("BAD")]);
console.log(st.map(s => s.status), st[1].reason.message);
// [ 'fulfilled', 'rejected' ] 无此工单 BAD
const timeout = (ms) => new Promise((_, rej) => setTimeout(() => rej(new Error("超时")), ms));
try { await Promise.race([sleep(200), timeout(50)]); } catch (e) { console.log(e.message); }
// 超时

两个必踩的坑：

js
const p = fetchWO("WO-9"); console.log(p instanceof Promise, p);
// true Promise { <pending> }      ← 忘了 await，拿到的是 Promise 本身，不是数据
const out = [];
[1, 2, 3].forEach(async n => { await sleep(10); out.push(n); });
console.log("forEach 之后", out.length);
// forEach 之后 0                  ← forEach 不会等回调里的 await
await sleep(50); console.log("稍后", out);
// 稍后 [ 1, 2, 3 ]
for (const n of [4, 5]) { await sleep(10); out.push(n); }
console.log(out);
// [ 1, 2, 3, 4, 5 ]               ← for...of 里的 await 才会真正按顺序等

要"按顺序等"就用 for...of + await；要"同时发出再等全部"就用 Promise.all(arr.map(...))；不要在 forEach 里用 await。

5. 模块：把代码拆成文件 ​

ES 模块（ESM）用 export 导出、import 导入，是浏览器和 Node 的标准写法。

yield.js：

js
export const PASS_LINE = 0.95;                        // 命名导出
export function yieldRate(good, qty) {
  return qty === 0 ? 0 : good / qty;
}
export default function judge(good, qty) {            // 默认导出：每个文件最多一个
  return yieldRate(good, qty) >= PASS_LINE ? "合格" : "预警";
}
console.log("yield.js 被加载了");

main.js：

js
import judge, { yieldRate, PASS_LINE as line } from "./yield.js";   // 默认导入 + 命名导入（可改名）
import * as y from "./yield.js";                                     // 全部导入成一个对象
import "./yield.js";                                                 // 再次导入不会重复执行
console.log(judge(480, 500), judge(261, 300), yieldRate(1, 4), line, Object.keys(y));
const m = await import("./yield.js");                                // 动态导入：运行时按需加载，返回 Promise
console.log(m.default === judge);

两个文件放在同一目录，再放一个 package.json，内容是 {"type":"module"}（让 Node 把 .js 当 ES 模块），然后运行 node main.js，实测输出：

yield.js 被加载了
合格 预警 0.25 0.95 [ 'PASS_LINE', 'default', 'yieldRate' ]
true

要点：

  • yield.js 只被执行了一次（"被加载了"只出现一次）：模块有缓存，多次导入共享同一个实例。
  • 480/500 = 0.96 ≥ 0.95，合格；261/300 = 0.87，预警。
  • 导入路径要写相对路径 ./，浏览器里还必须带 .js 扩展名。
  • 在浏览器里使用：script type="module" src="main.js"。
  • 老的 CommonJS 写法：module.exports = {...} 与 require("./x")，Node 早期的标准，很多老项目和老教程还在用，遇到时认得即可。新代码用 ESM。

6. 事件循环：单线程如何同时"等"很多事 ​

JS 引擎的运行方式：

  1. 调用栈：执行当前同步代码，一行一行跑完。
  2. 任务队列：异步操作完成后，把它的回调放入队列排队。分两种：
    • 微任务队列（microtask）：Promise.then、await 之后的代码、queueMicrotask；
    • 宏任务队列（macrotask）：setTimeout、setInterval、DOM 事件、网络回调。
  3. 事件循环：不断检查：调用栈空了吗？空了就先把微任务队列清空，再取一个宏任务执行，如此往复（浏览器还会在其间做页面渲染）。

实测：预测输出顺序（先自己想一遍再看答案）。

js
console.log("1 同步开始");
setTimeout(() => console.log("5 setTimeout 0"), 0);
Promise.resolve().then(() => console.log("3 微任务 then"));
queueMicrotask(() => console.log("4 queueMicrotask"));
console.log("2 同步结束");

实际输出（和编号完全一致）：

1 同步开始
2 同步结束
3 微任务 then
4 queueMicrotask
5 setTimeout 0

解释：同步代码先跑完（1、2）；调用栈空了，先清微任务（3、4），再取宏任务（5）。setTimeout(…, 0) 并不是"立刻"，而是"至少在同步代码和微任务之后"。

再来一个含 await 的：

js
setTimeout(() => console.log("timeout"), 0);
(async () => { console.log("a1"); await null; console.log("a2"); })();
Promise.resolve().then(() => console.log("p1"));
console.log("sync");

输出：a1、sync、a2、p1、timeout。async 函数里 await 之前的部分是同步执行的（a1）；await 之后相当于放进微任务，排在 p1 之前，因为它先入队。

这解释了一个关键现象：while(true){} 这样的死循环会让整个页面卡死，因为调用栈永远不空，队列里的点击事件永远轮不到执行。长时间的计算会让页面失去响应。

逐步例子：并发取多张工单并统计 ​

目标：给定一组工单号，并发取回详情；有失败的要单独汇总；最后输出成功条数与失败列表。

第 1 步：用 map 把每个工单号变成一个 Promise（同时发出）。 第 2 步：Promise.allSettled 等全部结束。 第 3 步：用 filter 分别取出成功和失败的。

js
const sleep = (ms) => new Promise(r => setTimeout(r, ms));
const fetchWO = (id) => new Promise((resolve, reject) => {
  setTimeout(() => id.startsWith("WO") ? resolve({ id, qty: 100 }) : reject(new Error("无此工单 " + id)), 50);
});
const ids = ["WO-1", "BAD-2", "WO-3"];
const results = await Promise.allSettled(ids.map(fetchWO));
const ok = results.filter(r => r.status === "fulfilled").map(r => r.value.id);
const failed = results.filter(r => r.status === "rejected").map(r => r.reason.message);
console.log("成功:", ok, "失败:", failed);

保存为 batch.mjs，运行 node batch.mjs，输出：

成功: [ 'WO-1', 'WO-3' ] 失败: [ '无此工单 BAD-2' ]

这个模式就是网页里"并发请求多个接口，部分失败不影响其余"的标准做法（真实请求换成 Axios与跨域 里的 axios.get）。

常见坑与排查 ​

  • await 用在普通函数里：SyntaxError: await is only valid in async functions and the top level bodies of modules。给外层函数加 async；最外层用 await 需要 ES 模块（.mjs 或 "type": "module"）。
  • 忘了写 await：拿到 Promise { <pending> }，后续 .id、.length 都是 undefined。
  • forEach 里 await 不生效：改用 for...of 或 Promise.all(arr.map(...))。
  • 未处理的 Promise 拒绝：失败的 Promise 没有 catch 会报 UnhandledPromiseRejection，Node 里甚至使进程退出。异步函数要用 try/catch 包好。
  • 回调里 this 丢了：用箭头函数，或 bind。
  • var 在循环里的闭包陷阱：改用 let。
  • 串行 await 拖慢速度：互不依赖的请求要并行。
  • 循环依赖：a.js 导入 b.js，b.js 又导入 a.js，可能拿到 undefined，要重新拆分模块。
  • import 路径漏了 ./ 或浏览器里漏了 .js：会被当成"包名"去找，报找不到模块。
  • 以为 setTimeout(fn, 0) 立刻执行：它在所有同步代码和微任务之后。

业务视角与技术视角 ​

  • 业务视角：生产看板常常要"每 5 秒刷新一次"几个接口（工单、设备状态、不良统计）。如果串行等待，刷新慢；如果并行，部分接口失败也不应该让整个看板白屏，要像本篇 allSettled 例子那样局部失败、局部提示。产线的网络不稳定，超时与重试（Promise.race 做超时）是必需的。
  • 技术视角：C# 里的 async/await + Task（见 CSharp异步编程）与 JS 概念非常接近：Task.WhenAll 对应 Promise.all。不同的是 JS 单线程、靠事件循环，C# 靠线程池；所以 JS 里不存在需要加锁的"数据竞争"（见 并发与锁），但长时间同步计算会卡死界面。模块的 export/import 类似 C# 的命名空间和 using，真正使用时由 Vite 打包。

练习题与答案 ​

题 1：下面输出什么？

js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);

答案：3 3 3。var i 只有一个，三个回调在循环结束后才执行。改成 let i 得 0 1 2。

题 2：const f = obj.method; f(); 里的 this 是什么？怎么修好？

答案：丢失，模块/严格模式下是 undefined。修法：obj.method.bind(obj)，或传 () => obj.method()。

题 3：三个互不依赖的请求，写出并行版本。

答案：const [a, b, c] = await Promise.all([getA(), getB(), getC()]);

题 4：预测输出：

js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);

答案：1 4 3 2。

题 5：什么时候用 Promise.allSettled 代替 Promise.all？

答案：希望"部分失败不影响其他结果"时，比如看板并发取多个接口，某个失败只在对应位置显示错误。

小结 ​

  • 只用 let/const；作用域是块级；闭包让函数记住诞生时的外层变量。
  • this 看调用方式；箭头函数没有自己的 this；call/bind 可手动指定。
  • 异步用 Promise，写法首选 async/await + try/catch；并行用 Promise.all/allSettled；forEach 里别 await。
  • 模块用 export/import，只执行一次，路径要写 ./。
  • 事件循环顺序：同步 → 微任务 → 宏任务；死循环会卡死页面。
